# 변경 검토와 윤문

기준은 저장소의 [AGENTS.md](../../../AGENTS.md)와 [변경 판단·작성 규칙](../../../CONTRIBUTING.md)이다. 규칙 본문을 이 스킬에 복제하지 않는다.

1. 요청한 대상과 변경 권한을 확인한다. 리뷰 요청이면 먼저 읽고 판단하며, 수정 요청이 포함되면 해당 범위의 문제를 고친다.
2. 실제 diff·새 파일과 연결된 계약을 읽는다. 구조·파일 배치는 [서비스 내부 분류](../../../docs/architecture.md#서비스-내부-분류), DB 변경은 [DB 정책](../../../docs/migrations.md), 테스트는 [테스트 작성](../../../CONTRIBUTING.md#테스트-작성)을 적용한다.
3. 기존 구성 유지·재사용·더 단순한 안을 비교한다. 중요한 선택에는 필요 여부와 이유·실제 근거를 연결하고, 검토하지 않은 대안을 만들어 적지 않는다.
4. [간결화·윤문 기준](../../../CONTRIBUTING.md#간결화윤문-검토)으로 중복·모호한 표현을 줄인다. 금액·상태·예외·버전·검증 범위를 원문과 대조해 보존한다.
5. 변경에 필요한 [검증](../../../docs/development.md#개발검증)을 수행하거나 같은 최종 후보의 기존 결과를 확인한다. 수정했다면 영향받는 계약과 diff를 다시 검토한다.

결과는 발견 사항을 먼저 쓰고 위치·위반한 계약·영향·근거를 연결한다. 취향에 따른 제안은 결함과 구분한다. 발견 사항이 없으면 확인한 핵심 경계와 실제 검증·남은 한계를 짧게 보고한다.

중요한 선택과 검증은 해당 PR·기준 문서에 필요한 만큼 남긴다. 매번 별도 리뷰 보고서·구현 일지·학습 노트를 만들거나 README에 진행 상황을 추가하지 않는다. 이 절차가 커밋·외부 게시·설정 변경의 권한을 부여하지는 않는다.
