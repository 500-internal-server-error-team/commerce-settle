# 서비스 간 업무 흐름의 조율과 완료 책임

- 상태: 핵심 업무 책임·조율 방식 결정, 업무 구현·실행 검증 예정
- 결정일: 2026-10-29
- 범위: 전체 업무의 진행·완료·실패 복구 책임과 서비스 간 조율 방식. 실제 적용할 API·이벤트·금액·상태 계약은 유지. 대안은 필요한 계약 변경까지 명시하여 비교

## 결정

**같은 서비스의 원자 처리는 로컬 트랜잭션으로, 여러 서비스의 실행 순서·보상이 필요한 흐름은 업무 소유자의 영속 진행 상태로, 확정 사실의 후속 반영은 소비 서비스의 이벤트 처리로 관리합니다.** 모든 흐름을 맡는 새 조율 서비스는 추가하지 않습니다.

주문·예약은 Commerce, 금융 결제·환불은 Payment, 원장·정산·지급은 Settlement, 알림은 Commerce의 알림 영역이 책임집니다. 환불의 단계 실행·보상·전체 완료는 Payment가 조율합니다. 결제 결과와 구매확정의 후속 반영은 각 소비자가 재개합니다. 취소는 Commerce가 요청하고 Payment가 이후 승인 차단을 확정한 결과로 예약을 해제합니다.

이를 아래의 **C안: 업무별 진행 책임과 이벤트 반영**으로 채택합니다. 완료 범위, 환불 조율자의 위치, 후속 반영 방식을 각각 비교한 뒤 내린 현재의 설계 판단입니다. 과거에 세 대안을 비교해 채택했다는 기록이나 실행·성능 검증 결과로 소급하지 않습니다.

**선택 이유는 패턴 통일이나 기존 구현 보존이 아닙니다.** 금융 판정과 다음 금융 작업은 Payment 안에서 원자적으로 연결하고, 환불 단계 사이의 실행 판단은 한 업무 책임자가 맡으며, 이미 확정된 결제 사실은 각 소유자가 반영하게 합니다. 이 경계를 위해 아래 전면 사건 연결 예보다 성공 경로 발행이 두 건 늘어나는 비용을 받아들입니다. 아래 비교는 이 우선순위에 따른 선택이며 보편적인 최소 메시지 수·최저 지연의 증명은 아닙니다.

## 문제와 판단 기준

결제의 결과 전파와 환불의 전체 진행만 비교하면 비교 단위가 다릅니다. 같은 프로젝트 안에서도 주문의 완료, 금융 결제의 확정, 원장 반영, 금융 환불의 전체 완료, 지급 성공, 알림 발송 확인은 서로 다른 결과입니다. 먼저 무엇을 완료로 약속할지 선택하고, 같은 완료 약속 아래에서 누가 다음 단계·보상·재개를 결정하는지 비교해야 합니다. 완료 범위와 조율 방식은 서로 독립된 결정입니다.

| 구분 | 이 문서에서의 의미 |
| --- | --- |
| 오케스트레이션 | 진행 책임자가 단계와 결과를 영속 추적하고 참여자에게 다음 실행·보상을 지시 |
| 코레오그래피 | 참여자가 받은 사건과 자기 상태로 후속 처리·사건 발행을 결정. 전체 결과 조회에는 사건을 모아 판정하는 수단이 필요 |
| 로컬 응용 서비스·Batch Step | 같은 소유 DB 안의 작업 조정. 여러 서비스를 묶는 Saga 조율과 구분 |
| Kafka·OutboxRelay·Inbox | 저장과 전달·중복 방지·재개를 위한 기술 경계. 업무의 다음 단계나 완료 정책은 응용 서비스가 결정 |
| 명령·사실·확인 | 실행 요청, 이미 확정된 사실, 선행 요청의 처리 결과라는 의미 구분. 모두 Kafka로 전달할 수 있으며 이름·전송 수단만으로 조율 방식을 판정하지 않음 |

판단 순서는 다음과 같습니다. 수치로 측정한 가중치가 아니라 이 ADR에서 채택하는 설계 우선순위입니다.

1. **필수 조건:** 원거래 금액·예약 보존, 미확정의 안전한 취급, 선택한 완료 약속과 장애 후 재개를 모두 만족해야 합니다. 어느 안도 패턴 이름만으로 통과하지 않습니다.
2. **금융 판단의 위치:** 원기관 결과의 확정과 다음 금융 실행·보상 결정을 같은 소유 DB의 진행 상태·작업·Outbox에 연결할 수 있는지를 우선합니다. 이는 주로 Payment 대 Commerce 조율자 배치의 기준이며, Payment를 유지하는 B와 C의 차이로 중복 계산하지 않습니다.
3. **개발·디버깅:** 전체 진행의 다음 실행·보상 규칙을 한 상태기계에서 읽고 검사하며, 현재 단계에서 기대한 요청·확인을 기준으로 장애를 추적하는 편의를 우선합니다. 진행 조회를 모으는 것과 실행 규칙을 모으는 것은 구분합니다. 아래 비용 비교와 구체 조사 경로로 이 선택을 설명합니다.
4. **업무 프로토콜 의존성:** 참여자가 자기 자원을 처리하는 계약과 다른 참여자의 단계 의미를 알아야 하는 계약을 구분합니다. 환불 단계의 연결·재개 책임은 Payment에 모으고 Commerce가 Settlement의 환불 원장 단계를 직접 해석하지 않도록 하는 쪽을 우선합니다.
5. **감수할 비용:** 전달 수·대기 단계·진행 조회·구현 상태 수를 비교합니다. C는 아래 환불 경로에서 후반 직접 연결 변형보다 한 건, 전면 사건 연결 예보다 두 건 더 발행합니다. 그 비용보다 3번의 개발 편의와 4번의 책임 경계를 우선한다는 선택을 명시하며 처리량·지연 우열은 측정 전 단정하지 않습니다.

기존 계약과의 호환성은 실제 전환 계획의 비용으로만 기록합니다. 새로 설계해도 같은 기준으로 선택할 수 있어야 하며, “이미 이렇게 되어 있음”은 채택 근거로 사용하지 않습니다.

### 완료 범위의 선택 이유

[현재 정책](../policies.md#대상과-발송-시점)과 [측정 기준](0002-performance-and-integrity-metrics.md)은 결제 금융 확정과 환불 전체 완료를 다르게 정의합니다. 그 정의가 존재한다는 사실만으로 비대칭이 옳다고 결론내리지 않습니다. 이 ADR은 다음 제품 판단으로 그 범위를 채택합니다.

| 구분 | 사용자·운영자에게 답할 질문 | 선택한 의미와 이유 |
| --- | --- | --- |
| 결제 금융 확정 | 돈의 승인이 확정되었는가? | `PaymentConfirmed`는 외부 승인·마일리지 차감의 확정 사실입니다. 승인 뒤에도 주문 이행은 계속되므로 금융 확정과 주문 반영·발송 자격을 구분합니다. Commerce가 해당 회차를 반영하기 전에는 주문 처리 중으로 보이고 발송·구매확정을 허용하지 않습니다. 결제 완료 알림도 주문 반영을 기다립니다. |
| 환불 금융 확정 | 돈이 반환되었는가? | `RefundFinancialCompleted`는 외부 환불·마일리지 복원 사실입니다. 내부 복구가 늦어도 이미 반환된 금액은 그대로 보여야 하며 외부 환불을 다시 실행하지 않습니다. |
| 환불 처리 종결 | 이 환불에서 플랫폼이 할 복구까지 끝났는가? | 원장 상쇄와 해당 주문·쿠폰·재고 처리가 남아 있는데 환불 **처리가 모두 끝났다**고 안내하지 않는 약속을 선택합니다. Payment의 FinancialRefund `COMPLETED`와 환불 완료 TPS는 이 범위입니다. 발송 상품의 실제 입고는 별도 절차이며 이 종결에 포함하지 않습니다. |

결제는 승인 사실, 환불 전체 완료는 복구 업무의 종결이라는 **서로 다른 질문**에 답합니다. 이 제품 선택이 비대칭의 이유이며 환불이라는 거래 종류나 오케스트레이션 자체가 그 비대칭을 강제하지 않습니다. 내부 복구 대기 중에는 “금융 환불 확정·내부 반영 대기”를 구분할 수 있어야 합니다. 이름만 `RefundCompleted`인 기존 v1 메시지도 주문 복구 의뢰이지 이 종결 사실이 아닙니다.

대칭인 계약도 안전하게 설계할 수 있습니다.

| 완료 범위 대안 | 얻는 것 | 필요한 선택·변경과 이번 판단 |
| --- | --- | --- |
| 결제·환불 모두 금융 완료만 Payment 결과로 제공 | 금융 서비스의 경계와 상태 이름이 대칭이고 돈의 결과가 내부 반영 지연에 가려지지 않음 | 전체 환불 처리 종결은 Commerce의 요청 상태나 별도 조회 모델에서 제공할 수 있습니다. 기존 `order_refund_requests`를 활용할 수 있어 새 테이블·중앙 서비스가 필수는 아닙니다. FinancialRefund API의 완료 의미, 알림 조건, TPS·전체 진행 조회를 함께 조정해야 합니다. 충분히 유효한 대안이지만, 이번에는 하나의 환불 실행 결과에 내부 복구까지 포함하는 약속을 택합니다. |
| 결제·환불 모두 주문·원장까지 전체 완료 제공 | 두 업무의 플랫폼 반영 완료를 같은 범위로 조회·측정 가능 | 결제의 주문·원장 적용 확인과 영속 진행 판정이 필요합니다. 금융 확정 사실은 즉시 보존·발행하고, 별도의 전체 완료를 추가해야 합니다. 현재 제품 판단은 결제 금융 확정 이후 주문 이행을 별도로 다루므로 그 전체 완료를 필수 결제 상태로 추가하지 않습니다. |
| 이번 선택: 금융 사실은 각각 즉시, 환불 처리 종결은 복구 확인 뒤 | 돈의 진실과 플랫폼 복구 종결을 함께 표현 | 금융 확정·주문 반영·환불 전체 완료의 범위가 다르다는 설명·조회 비용을 감수합니다. API·알림·측정에서 같은 단어로 섞지 않습니다. |

따라서 대칭 대안을 불가능하거나 반드시 더 비싼 안으로 배제하지 않습니다. 완료 범위를 바꾸면 조율자 위치도 다시 비교하며, 단지 기존 API 이름을 지키려고 Payment 조율을 선택하지 않습니다.

### 세 대안에 고정하는 조건

**아래 A/B/C의 조율 방식 비교에는 위에서 선택한 동일한 완료 조건을 적용합니다.** 완료 범위의 대안 비교와 구분합니다. A를 택해 금융 확정 사실을 늦추거나 B를 택해 환불 주문 복구 확인을 생략하지 않습니다. 대안의 실행 요청·구독·확인 메시지는 변경 가능하며, 제안하는 변경은 현재 v1과 구분합니다. 실제 적용 계약은 이 문서 변경으로 바꾸지 않습니다.

- **로컬 원자성 유지:** 주문·재고·쿠폰 예약, Payment의 결제·마일리지, Settlement의 항목·예약·지급 작업, 가입·웰컴 발급을 불필요한 서비스 간 단계로 쪼개지 않습니다.
- 서비스별 DB·권한·도메인 불변식, 중복·역순 처리, 원거래 금액·정책 사본과 업무 키를 유지합니다. 조율자도 다른 서비스 DB를 직접 고치지 않습니다.
- 외부 PG·지급의 실행·조회 HTTP와 서비스 컨텍스트 조회는 기존 계약을 유지합니다. 전면 코레오그래피도 외부 기관의 프로토콜을 이벤트로 바꾼다는 뜻은 아닙니다.
- 타임아웃·전달 지연은 금융 실패가 아닙니다. 미확정 상태·예약을 유지하고 원키 조회·재개·대조로 확정합니다. 조율 방식 자체가 분산 ACID나 정확히 한 번의 외부 실행을 제공하지 않습니다.
- API 접수, Kafka ACK, Inbox의 영속 인계, 금융 확정, 업무 전체 완료를 구분합니다. [완료·측정 기준](0002-performance-and-integrity-metrics.md)과 [전달 계약](0005-kafka-event-delivery-and-capacity.md)을 유지합니다.

| ID·도메인 | 소유자 | 직접 판단·저장할 것 | 다른 영역과의 경계·완료 책임 |

## 업무별 시작·저장·완료·복구

진행 책임은 업무 상태를 관리하는 주체입니다. API·Consumer·Scheduler·Worker는 그 응용 서비스를 호출하는 진입점이며, 실행 프로세스 수와 논리 책임자 수는 다릅니다.

아래 원자 저장은 각 단계의 로컬 커밋 단위입니다. 외부 HTTP·Kafka 응답 대기 동안 DB 트랜잭션·연결·잠금을 유지하지 않습니다. 요청 전 저장과 외부 결과 확인 뒤 저장은 각각 짧게 커밋하고, 중간 중단은 영속 작업·원업무 키·임대로 재개합니다.

금융 환불의 주문 복구 확인은 정책상 해당 상태·쿠폰·재고 처리를 확인합니다. 발송 상품의 실물 입고·재고 복원은 판매자 입고 확인을 따르므로 금융 환불 완료를 실물 입고 완료로 표시하지 않습니다. 월간 혜택의 등급은 선정자의 쿠폰 조건이며 Payment 마일리지나 모든 회원의 상시 등급이 아닙니다.

| --- | --- | --- |
| W04→W05 | `OrderPaymentRequested`; `PaymentAccepted`, `PaymentConfirmed`, `PaymentDeclined` | Commerce의 결제 의뢰, Payment의 접수/확정/거절 사실. Commerce가 자기 회차에 반영하고 Settlement가 확정 원장 반영 |
| W06 | `PaymentCancellationRequested`; `PaymentCancellationRejected`, `PaymentCancelled` | Commerce의 승인 차단 요청과 Payment의 결과. 요청 발행이나 Consumer ACK만으로 예약을 해제하지 않음 |
| W07→W08 | `RefundApproved`, `RefundAccepted` | Commerce의 취소/반품 승인과 Payment의 환불 접수. 두 사실 모두 환불 전체 성공이 아님 |
| W08 예약·보상 | `RefundReservationRequested`, `RefundReservationResult`; `RefundReleaseRequested`, `RefundReservationReleased`; `RefundFailed` | Payment가 예약/해제 요청과 결과로 다음 단계·보상을 결정. Settlement는 자기 자원의 경합을 판정. Commerce는 확정 실패를 반영 |
| W08 금융·원장·주문 복구 | `RefundFinancialCompleted`, `RefundLedgerReversed`, `RefundCompleted`, `RefundOrderRestored` | 금융 성공→원장 상쇄 확인→주문 복구 의뢰→복구 확인. 기존 `RefundCompleted` 발행 시 상태는 INTERNAL_PENDING이며 전체 완료는 마지막 확인 뒤 |
| W07→W09 | `PurchaseConfirmed` | Commerce의 구매확정 사실. Settlement는 결제 원장과 함께 지급 조건 판정 |
| W12 | `PaymentNoticeRequested`, `SettlementNoticeRequested` | 금융/정산 소유자가 알림을 의뢰. 알림 그룹은 금융 그룹과 독립적으로 필요한 선행 반영을 기다리고 발송 |

## 대안별 예상 구조

아래 예상은 설계 비교이며 실행 실험 결과가 아닙니다. 비교 단위는 **서비스 간 업무 진행의 결정 위치**입니다. 같은 DB 안의 작업을 Kafka로 쪼개거나 새 중앙 서버를 강제하지 않습니다. 진행 조회를 위해 사실을 모으는 것만으로 오케스트레이션이 되는 것도 아닙니다. 다음 실행·보상을 지시하는 주체가 있는지로 구분합니다.

| 안 | 구성 | 기대 이점 | 추가 책임·비용 |
| --- | --- | --- | --- |
| A 전면 오케스트레이션 | 서비스 간 흐름마다 진행 관리자가 실행 요청·응답·기한·보상을 영속 추적. 각 기존 서비스 안에 배치 가능 | 단계·재개와 처리 기한의 실행 책임을 한 흐름에서 찾기 쉬움 | 독립 결과 반영까지 지시할 때 추가 진행·확인 계약 필요. 중앙 서버·엔진은 필수가 아니며 기존 상태를 재사용할 수 있음 |
| B 전면 코레오그래피 | 후속 실행·보상을 참여자가 사건과 자기 상태로 결정. 전체 결과는 사건 관측으로 판정 가능 | 직접 사실 연결로 중간 전달을 줄일 수 있고 참여자가 자기 후속 처리를 독립적으로 재개 | 참여자가 선행 사건의 업무 의미를 알아야 함. 영속 대기·상관관계·재개 담당과 전체 관측 책임을 따로 명시 |
| C 업무별 진행 책임과 이벤트 반영 | 단계·보상은 해당 업무 소유자가 관리하고, 확정 사실은 각 소비자가 반영 | 금융 환불 단계의 다음 실행 책임을 모으고 결제 원장·주문 반영은 자기 소유자에 둠 | 환불에서 확인을 Payment로 돌려 다음 요청을 보내는 전달 비용, 진행 상태·임대·Outbox 연결, 흐름별 책임 설명 필요 |

W01~W04·W07·W11·W15의 같은 서비스 내부 처리는 세 안 모두 로컬 트랜잭션·소유 앱의 Job/Worker로 유지합니다. W04의 결제 의뢰 이후는 W05, W07의 환불 승인 이후는 W08로 연결합니다. 모든 흐름에서 서로 다른 구조를 만들어 내지 않습니다. **Payment 조율의 A 환불과 C 환불, B 결제 결과 반영과 C 결제 결과 반영은 각각 같은 구조입니다.**

### 환불 조율자 위치

조율 방식과 별도로 Payment·Commerce 배치를 비교합니다. Commerce는 `order_refund_requests`와 자격·승인·주문 복구를, Payment는 `refunds`·`refund_sagas`·금융 작업과 외부 결과를, Settlement는 예약·원장을 소유합니다. [저장 모델](../data-model.md#refund_sagas)의 소유권만으로 전체 진행 책임자가 자동 결정되는 것은 아닙니다.

| 판단 지점 | Payment에 전체 진행 배치 | Commerce에 전체 진행 배치 |
| --- | --- | --- |
| Settlement 예약 성공 후 외부 실행 | Payment가 예약 확인·환불 단계·금융 실행 작업을 같은 로컬 커밋으로 연결 | Commerce가 예약 결과를 받아 **금융 실행 의뢰**를 영속 발행하고 Payment가 단계·예약 근거·업무 키를 검증하여 작업 생성. 의뢰는 대안의 개념적 계약이며 현재 v1에 있다고 가정하지 않음 |
| PG 응답 유실·확정 거절·성공 | 원키 조회의 권위 있는 결과와 다음 조회/보상/내부 복원 결정을 Payment에서 연결 | 금융 결과·UNKNOWN 조회 권한은 여전히 Payment. Commerce가 해제 등 후속 단계를 결정하려면 권위 있는 **금융 단계 결과**를 받아야 함. 전체 보상 뒤의 `RefundFailed`를 보상 전 PG 실패 사실로 재해석할 수 없음 |
| 원장 상쇄 뒤 주문 복구·최종 종결 | 상쇄 확인→복구 의뢰→Commerce 복구 확인이 필요. Payment는 Commerce 확인에 결합 | Commerce가 상쇄 확인과 로컬 주문 복구·요청 종결을 가까이 연결할 수 있음. 현재처럼 Payment FinancialRefund에도 전체 완료를 남기면 최종 확인을 Payment에 전달 |
| 진행 상태·요청 조회 | 금융 실행·진행·다음 작업을 Payment에 모음. Commerce 요청 상태는 확인 사실로 갱신 | 진행 레코드를 Commerce로 옮기거나 기존 요청 상태에 통합 가능. Payment에 금융 실행·미확정 기록은 남지만 전체 진행 테이블이 반드시 중복되는 것은 아님 |
| 업무 의존성·변경 범위 | Payment가 금융 판정과 단계 연결을 소유하고 Commerce는 자격/복구 계약 제공 | Commerce가 금융 실행 단계와 보상 전 결과까지 알아야 함. 반대로 사용자 요청·이행 중심의 전체 흐름을 Commerce에서 찾기 쉬움. 예약 요청 생산자·결과 라우팅 등 v1 변경도 명시해야 함 |

**Payment를 선택하는 기준은 원기관의 금융 판정과 그에 따른 다음 금융 작업의 원자적 연결을 우선한다는 것입니다.** 미확정이면 예약 유지·조회, 확정 실패면 해제 보상, 성공이면 내부 복원으로 전진하는 결정을 권위 있는 금융 상태와 함께 저장합니다. Commerce 배치도 이 보존 조건을 만족시킬 수 있지만 금융 실행 의뢰와 보상 전 결과라는 제어 경계를 건너야 합니다. 이 경계를 줄이는 쪽을 주문 요청 종결의 로컬 처리 이점보다 우선합니다. 발행 총수가 반드시 줄어든다는 주장은 아닙니다.

이는 Payment가 Commerce의 주문 자격이나 Settlement의 예약 가능 여부를 대신 판단한다는 뜻이 아닙니다. 참여자는 자기 불변식을 검사하고 결과만 돌려줍니다. 반대로 금융 환불 API를 금융 완료만으로 좁히고 사용자 요청의 종결·이행 조정을 최우선으로 삼는다면 Commerce 조율이 더 자연스러운 후보가 됩니다. 그때는 전체 진행을 옮기는 대안을 다시 선택할 수 있습니다.

### 대표 흐름의 상태·메시지·복구 비교

Payment가 다음 실행·보상을 결정하는 **오케스트레이션**, 그 결정을 영속 상태·전이로 표현하는 **상태기계**, 아래의 **발행 건수**는 서로 다른 구분입니다. 현재 환불은 Payment 오케스트레이션을 상태기계로 구현하는 선택이며, 발행 8건이 상태 8개나 상태 전이 8개를 뜻하지 않습니다.

다음은 문서상의 대표 실행 추적입니다. **건수는 성공 경로의 Kafka 업무 envelope 발행 수**이며 구독자별 전달 수·처리 시간·성능 측정이 아닙니다. 공통 알림, 재전달·중복, 기술 ACK, 외부 PG HTTP, 임대·조회는 제외합니다. 표의 번호는 메시지 식별 순서이며 독립 발행 사이의 전역 순서를 약속하지 않습니다.

#### 환불 성공: C 8건과 후반 직접 연결 변형 7건

외부 결제와 마일리지가 있는 전액 환불, Settlement 예약 가능, 모든 참여자 정상인 한 건을 비교합니다. 먼저 금융 예약 프로토콜은 유지하고 원장 상쇄 이후만 직접 사건으로 연결하는 변형을 봅니다. 이는 금융 구간의 조율이 남은 절충안이며 전면 B 자체로 부르지 않습니다.

| 번호 | C: Payment 단계 조율 | 후반 직접 연결 변형 | 상태·다음 결정 |
| --- | --- | --- | --- |
| 1 | Commerce→Payment `RefundApproved` | 동일 | Commerce 승인·Outbox. Payment가 원결제/중복 검증 후 접수 |
| 2 | Payment→Commerce `RefundAccepted` | 동일 | Payment 환불·진행·접수 Outbox. Commerce가 requestId/orderId/refundId 연결 저장 |
| 3 | Payment→Settlement `RefundReservationRequested` | 동일 | Payment 예약 대기. Settlement가 지급과의 배타 예약 판단 |
| 4 | Settlement→Payment `RefundReservationResult` | 동일 | Settlement 예약·결과 Outbox. Payment가 성공 결과와 금융 실행 작업을 원자 저장 |
| 5 | Payment→Settlement `RefundFinancialCompleted` | 동일 | 외부 성공 확인 뒤 Payment 마일리지 복원·금융 결과·Outbox 저장. Settlement가 원거래 상쇄 |
| 6 | Settlement→Payment `RefundLedgerReversed` | Settlement→Payment·**Commerce** `RefundLedgerReversed` | C: Payment가 상쇄 확인을 진행 상태에 기록하고 7번 의뢰 저장. 직접 변형: Commerce가 상쇄 사실과 환불 매핑을 확인해 복구 결정; Payment는 관측 |
| 7 | Payment→Commerce `RefundCompleted` | Commerce→Payment `RefundOrderRestored` | C: Payment는 INTERNAL_PENDING, Commerce가 주문 복구·확인 Outbox 저장. 직접 변형: 같은 로컬 복구·확인 저장 |
| 8 | Commerce→Payment `RefundOrderRestored` | 추가 발행 없음 | Payment가 금융 성공·상쇄·주문 확인을 모두 반영한 뒤 전체 COMPLETED |

C의 진행 정보는 Payment의 `refund_sagas.step/reservation_ref/ledger_reversed_at/order_restored_at`와 금융 상태·작업에 있습니다. 직접 변형도 이 완료 관측 필드를 활용할 수 있으며 전체 완료를 포기하지 않습니다. 다만 6번 이후 Commerce 실행을 **누가 결정하는지**가 다릅니다. C는 Payment의 상쇄 확인 커밋과 복구 의뢰 Outbox를 연결하고, 직접 변형은 Commerce가 Settlement의 상쇄 사실을 해석하여 복구합니다. Payment가 직접 변형에서 최종 확인을 관측하는 것만으로 그 구간의 조율자가 되는 것은 아닙니다.

이 직접 연결은 현재 v1의 구독·진행 계약 변경을 전제로 합니다. `RefundLedgerReversedPayload`에는 orderId가 없지만 refundId/paymentId/reservationId가 있고 `RefundAcceptedPayload`의 refundId/paymentId/orderId/requestId와 연결할 수 있습니다. 매핑이 늦으면 원본·업무 키를 영속 보존해 기다려야 합니다. payload 확장이 필수이거나 직접 연결이 구현 불가능하다고 보지 않습니다. 호환 전환 중 구 v1 발행까지 병행한다면 실제 발행 수는 이 7건과 달라집니다.

**이 후반 직접 연결 변형은 C보다 한 발행 적습니다.** C는 Commerce가 환불 원장 상쇄의 의미·선행 관계를 직접 알아야 하는 업무 계약을 피하고, 단계 사이의 다음 요청·재개 책임을 Payment에 모으기 위해 한 전달을 더 사용합니다. Commerce와 Settlement 사이에는 이미 `PurchaseConfirmed` 연결이 있으므로 새 네트워크 연결을 피한다는 주장이 아닙니다. **환불 복구가 의존하는 업무 프로토콜의 범위**를 좁히는 선택입니다. 이 우선순위를 뒤집어 직접 사실 연결과 전달 수 감소를 더 중시하면 이 변형이 유리합니다.

전면 A도 환불 조율자를 Payment에 두면 위 C의 8건과 같습니다. A라는 이름 때문에 다른 명령이나 왕복을 임의로 더하지 않습니다. 예약 거절·실패·보상 경로의 발행 수는 이 성공 건수로 설명하지 않습니다.

#### 전면 B: 예약 시작과 해제도 사실에 따라 실행

위 7건에서 멈추면 전면 코레오그래피와의 비교가 아닙니다. 전면 B의 한 대표안은 다음과 같습니다. **현재 v1에 적용된 계약이 아니라, 사실의 payload·구독·실행 의미를 변경하는 설계 대안**입니다.

| 번호 | 전면 B의 성공 경로 | 다음 결정을 내리는 참여자 |
| --- | --- | --- |
| 1 | Commerce→Payment `RefundApproved` | Payment가 금융 환불 접수 검증 |
| 2 | Payment→Commerce·Settlement **예약에 필요한 원금액/근거를 포함하도록 확장한 접수 사실** | Commerce는 요청 연결, Settlement는 해당 환불의 예약 필요를 판단·선점. 현재 `RefundAccepted`에는 그 금액이 없으므로 그대로 쓸 수 없으며 새 사실 계약이나 버전 확장 필요 |
| 3 | Settlement→Payment `RefundReservationResult`에 해당하는 예약 사실 | Payment가 자기 금융 상태·예약 결과로 외부 실행 작업 생성 |
| 4 | Payment→Settlement `RefundFinancialCompleted` | Settlement가 금융 성공 사실로 자기 원장 상쇄 |
| 5 | Settlement→Payment·Commerce `RefundLedgerReversed` | Commerce가 접수 사실의 매핑과 상쇄 사실로 자기 주문 복구. Payment는 상쇄 관측 |
| 6 | Commerce→Payment `RefundOrderRestored` | Payment는 금융·상쇄·주문 사실을 모아 전체 완료 관측 |

이 예는 `RefundReservationRequested` 제어 발행을 접수 사실에 합쳐 **성공 경로 6건**입니다. 이 역시 전면 B의 보편적 최소값이 아닙니다. Settlement가 금액을 조회하는 대안이나 다른 사실 분해도 가능하며, 여기서는 금액을 포함한 접수 사실을 선택했다고 명시합니다. 기존 원거래 검증·배타 예약은 Settlement에 남습니다.

실패 경로도 바꿔야 전면 사건 연결입니다. Payment는 **확정 금융 단계 실패 사실**을 자기 금융 상태와 원자 저장하고, Settlement가 그 사실과 자기 예약 상태로 해제를 결정·해제 사실을 발행하며, Payment가 이를 관측해 보상 종결을 판정합니다. UNKNOWN은 이 실패 사실이 아니므로 예약을 유지합니다. 현재 `RefundFailed`는 전체 실패 결과이므로 보상 전 실패 신호로 재사용하지 않습니다. 그 단계 사실·역순 처리·예약과의 상관관계 계약을 새로 정해야 합니다. 성공 표에 적은 6건은 이 실패 경로 비용까지 센 값이 아닙니다.

전면 B의 이점은 두 중간 제어 발행을 줄이고 각 자원 소유자가 사실로 다음 처리를 선택한다는 점입니다. 비용은 Settlement가 접수·금융 실패 사실에서 예약/해제할 조건을, Commerce가 원장 상쇄 사실에서 복구할 조건을 직접 소유·유지한다는 점입니다. C는 이 참여자 간 연결 규칙을 Payment의 단계 진행에 모으는 대신 대표 성공 경로에서 두 건을 더 발행합니다. 이 **책임 규칙의 위치와 전달 비용**을 비교한 뒤 C를 선택하며, 7건 변형만을 B로 제시해서 결론을 유도하지 않습니다.

#### 발행 수와 수신 서비스의 업무 처리 수

| 대표 성공 경로 | 업무 envelope 발행 | 수신 서비스별 업무 처리 | 처리 주체별 수 |
| --- | --- | --- | --- |
| Payment 조율의 A·현재 C | 8건 | 8회 | Payment 4·Commerce 2·Settlement 2 |
| 금융 제어 유지·후반 직접 연결 | 7건 | 8회 | Payment 4·Commerce 2·Settlement 2 |
| 위 전면 B의 사실 연결 예 | 6건 | 8회 | Payment 4·Commerce 2·Settlement 2 |

B는 접수 사실을 Commerce·Settlement가, 상쇄 사실을 Payment·Commerce가 각각 받습니다. 따라서 발행 두 건을 줄여도 이 예의 수신 업무 처리가 두 번 사라지지는 않습니다. 이 수는 표에 명시한 수신자의 정상 업무 처리 횟수이며 실제 Kafka 토픽/그룹별 전달, DB 트랜잭션·쿼리, 재전달 횟수의 측정값은 아닙니다. 직접 연결은 상쇄 확인 뒤 Commerce 복구가 Payment의 다음 발행을 기다리지 않는 이점이 있습니다. 현재 C는 그 순차 의존성과 발행·Outbox 기록을 더 사용하는 비용을 감수합니다.

#### 결제 결과 반영: B와 C는 동일, A는 추가 실행 관리의 선택

B/C에서는 Payment가 금융 CONFIRMED·결과 Outbox를 저장하고 `PaymentConfirmed`를 발행합니다. Commerce는 현재 회차의 주문·예약·쿠폰을, Settlement는 최초 원장·항목을 각각 Inbox와 같은 트랜잭션으로 반영합니다. 공통 접수 이벤트를 제외한 **이 후속 구간의 사실 발행은 한 건**이며 Payment에 적용 확인을 보내 전체 결제를 종결하는 단계는 두지 않습니다.

대표 A를 “금융 확정 후 Payment 안의 결제 진행 관리자가 두 적용을 지시하고 완료까지 책임진다”로 잡으면, 관리자는 orderApplied/ledgerApplied에 해당하는 영속 진행 정보를 두고 **주문 적용 의뢰·원장 적용 의뢰 두 건과 적용 확인 두 건**을 연결할 수 있습니다. 이는 개념적 대안이며 해당 4개 계약·진행 필드가 현재 존재한다는 뜻은 아닙니다. 참여자는 자기 반영·확인 Outbox를 원자 저장하고 관리자는 미확인 작업을 재개합니다. `PaymentConfirmed`라는 금융 사실의 저장·발행 시점은 늦추지 않습니다.

이 네 건은 선언한 A 예제의 비용일 뿐 모든 오케스트레이션의 최소 메시지 수가 아닙니다. 조율자 위치를 달리하거나 사실/확인을 재사용할 수 있습니다. 반대로 전체 적용 상태를 보여주기만 한다면 C에서도 읽기 전용 진행 집계를 추가할 수 있습니다. **진행 가시성 요구만으로 실행 지시까지 중앙화할 필요는 없습니다.** 이번에는 금융 확정 뒤 Commerce·Settlement 사이에 추가 실행 순서나 금융 보상 결정을 두지 않는 계약을 택하므로 B/C의 독립 반영을 선택합니다.

#### 중단 지점과 재개 책임

아래에서도 A 환불은 Payment에 조율자를 둔 C와 같습니다. B는 위 전면 사건 연결 예이며 후반 직접 연결 변형도 금융 성공 이후에는 같은 처리를 합니다. 모든 안에서 소유 서비스가 원금액·원키·중복 방지와 영속 상태를 유지해야 합니다.

| 중단·실패 입력 | A의 대표안 | B의 대표안 | C의 선택 |
| --- | --- | --- | --- |
| 금융 결제 확정 뒤 Settlement 중단 | 결제 진행 관리자의 ledgerApplied 미확인 상태·적용 의뢰로 재개. Settlement 자체 원장 멱등성도 필요 | Settlement Inbox·선행 대기·재전달/대조로 반영 재개 | B와 동일. 금융 CONFIRMED는 유지하고 새 승인·임의 취소하지 않음 |
| PG 환불 성공 뒤 Payment 결과 커밋 전 중단 | C 환불과 동일 | Payment 외부 작업·원키를 조회하여 성공 확정 뒤 로컬 복원/Outbox 커밋 | B와 동일. 조율자 위치와 무관하게 Payment가 금융 원천. 응답 유실로 새 키의 외부 환불 금지 |
| 금융 환불 확정 뒤 Settlement 중단 | C 환불과 동일 | Payment 금융 사실 Outbox와 Settlement Inbox/대기로 상쇄 재개. 이후 Commerce가 상쇄 사실을 받아 복구 | Payment 진행에 상쇄 확인 대기. 공통 전달 복구 뒤 확인 수신 커밋에서 다음 복구 의뢰 생성. 내부 대기를 외부 실패로 바꾸지 않음 |
| 상쇄 성공 뒤 Commerce의 환불 매핑 지연 | C 환불과 동일 | Settlement 상쇄·Outbox는 보존. Commerce가 상쇄 원문과 refundId를 Inbox/업무 대기에 보존하고 Accepted 연결 후 복구 재개 | Payment 상쇄 확인·복구 의뢰 Outbox 보존. RefundCompleted에는 orderId가 있어 B의 Accepted join이 필수는 아님. Commerce가 주문/원환불·원키를 검증하고 실제 선행 조건이 미충족일 때 영속 대기 |
| Commerce 복구 커밋 뒤 Payment 최종 확인 유실 | C 환불과 동일 | Commerce 복구·`RefundOrderRestored` Outbox 재전달. Payment 관측 필드가 모이면 전체 완료 | 같은 원키의 복구 확인 재전달로 진행 완료. Payment의 대기 기록만으로 Commerce 복구를 다시 증식시키지 않음 |
| PG 확정 실패 뒤 예약 해제 실패·응답 유실 | C 환불과 동일 | Payment 금융 단계 실패 사실을 Settlement가 받아 자기 예약 해제·확인 발행. Payment가 확인을 관측해야 보상 종결. 원문·선행 대기를 보존해 같은 사실로 재개 | Payment COMPENSATING·해제 요청 Outbox로 재개. Settlement 확인 전 보상 완료 금지. UNKNOWN은 확정 실패 경로에 넣지 않음 |

실행 책임자는 Relay 메모리나 한 JVM이 아닙니다. C는 Payment의 단계·다음 작업·Outbox, B는 각 단계 소유자의 사건·대기·다음 로컬 작업, A는 관리자의 단계별 확인을 재시작 가능한 저장으로 이어야 합니다. 실제 재전달·기한·운영 재개는 그 저장을 기준으로 하며 패턴 이름만으로 복구되지 않습니다.

### 독립 결제 반영이 성립하는 조건과 반례

W05의 선택은 [주문 설계](../design.md#주문쿠폰배송지)에 따라 Commerce가 자원을 선예약하고 금융 미확정 동안 임의 만료·해제하지 않으며, 현재 결제 회차·주문 버전을 검사한다는 조건에 기대고 있습니다. 이 조건 아래 일시적 DB 장애·선행 사건 지연은 같은 금융 사실과 고정 사본으로 재개합니다. Settlement도 고정 원금액과 선행 원장을 기준으로 반영합니다.

스키마·본문·금액 충돌이나 잘못된 회차는 반복 재전달만으로 수렴하지 않습니다. 원금융 사실을 보존하고 격리·경보·대조로 분류하여 소유 서비스의 승인된 수정/재개 경로로 해결해야 합니다. 유효 주문 반영 전 발송·구매확정, 지급 조건 충족 전 지급을 막습니다. “독립 반영이니 언제나 재시도하면 된다”는 가정으로 안전성을 대신하지 않습니다.

재고·쿠폰이 별도 원격 서비스로 분리되거나 승인 후 독립 만료·거절할 수 있다면 이 전제가 깨집니다. 그때는 자원 예약 확약과 실패 시 금융 보상을 포함하는 주문/결제 Saga를 먼저 결정해야 합니다. 기존 C의 독립 반영을 그대로 확대하지 않습니다.

### 개발 관점의 환불 조율과 Commerce 주문 진행

현재 선택은 **Payment에 명시적인 환불 상태기계를 두어 전체 단계의 다음 실행·보상 규칙을 한곳에서 읽고 고칠 수 있게 하는 것**입니다. 세 안 모두 진행 사실을 모아 조회할 수 있지만, 다음 실행을 지시하는 규칙의 위치는 다릅니다. 메시지 두 건 절감보다 이 개발 편의를 우선합니다.

| 개발 작업 | Payment 조율의 A·현재 C | 위 전면 B |
| --- | --- | --- |
| 흐름 이해·변경 | Payment의 단계 전이와 다음 요청으로 환불 진행 정의를 읽고 수정. 참여자의 자원 규칙은 각 서비스에 유지 | 접수→예약, 금융 실패→해제, 상쇄→주문 복구를 참여자별 사건 처리기에서 연결하여 읽고 영향 범위 수정 |
| 장애 조사 | 현재 단계에서 기대한 요청·확인과 Outbox를 기준으로 조사를 시작 | 전체 관측 상태와 함께 각 참여자의 구독·사건 처리 조건·후속 작업을 확인 |
| 진행 판단 테스트 | 정상·거절·UNKNOWN·보상·늦은 확인에 대한 다음 행동 선택을 Payment 상태기계에서 검사 | 참여자별 후속 판단과 그 사건 계약의 조합으로 전체 진행을 검사 |
| 재개 판단 | Payment의 진행 단계·원키·다음 작업이 어느 요청/확인을 이어야 하는지 정하는 기준 | 해당 사건을 처리할 참여자가 자기 Inbox·작업·원키로 재개. 전체 관측자가 실행 권한을 자동으로 얻는 것은 아님 |

설명용 장애 사례로, 외부 환불·원장 상쇄가 끝났는데 주문 복구가 멈췄다고 가정합니다. C에서는 **Payment의 상쇄 확인 반영→같은 커밋의 복구 의뢰 Outbox→Commerce 수신/복구→복구 확인의 반환**을 조사 순서로 삼습니다. 복구 의뢰가 없으면 Payment의 전이/커밋, 미발행이면 전달 작업, Commerce에 도착했으면 그 Inbox·자원 검증·복구 작업, 복구가 끝났으면 확인 Outbox와 Payment 수신을 확인합니다. 한 단계에서 무엇이 있어야 하는지 명시한 이점이며, 모든 원인을 Payment DB만으로 알아낼 수 있다는 주장은 아닙니다.

직접 연결에서는 상쇄 사실과 환불 매핑이 Commerce에 준비되어 있다면 Payment 중단 중에도 주문 복구가 진행될 수 있습니다. C는 Payment 재개·복구 의뢰 전달까지 기다리는 비용이 있습니다. 7건 변형도 Payment에 전체 진행 조회를 유지할 수 있어 디버깅이 불가능하지 않습니다. 차이는 후반 복구의 실행 규칙을 Commerce에 두는 대신 중계 한 번을 줄이는 것입니다. 이번에는 그 규칙까지 Payment의 명시적 단계에 두는 편을 우선하며, 이 선택을 보편적인 성능·총비용 우위로 주장하지 않습니다.

이 이점은 구현 시 단계·다음 작업·Outbox를 원자적으로 연결하고, refundId·eventId로 상태 전이와 참여자 처리 기록을 추적할 수 있어야 실현됩니다. 기존 `refund_sagas`·금융 작업·Outbox를 활용하며 새 중앙 서비스나 범용 엔진은 요구하지 않습니다. Payment의 단계/오류만으로 참여자의 실제 실패 원인을 알 수는 없습니다. 진행 판단의 국소 테스트와 별개로 참여자 DB·멱등성·메시지 계약·전체 장애 복구 시험도 필요합니다. 아직 실제 개발 시간·디버깅 시간의 개선을 측정한 결과는 아닙니다.

Commerce도 주문·취소/반품·배송의 진행 상태를 소유합니다. 주문·재고·쿠폰·행사 예약과 결제 의뢰는 같은 DB의 응용 서비스가 로컬 트랜잭션으로 묶어 한 조건 실패 시 함께 롤백합니다. 이를 내부 Kafka 단계로 분리하지 않아 예약의 원자성과 조사 위치를 유지합니다. 미결제 취소는 Commerce가 요청을 시작하고 **Payment의 이후 승인 차단 확인 뒤** 로컬 예약을 해제합니다. 금융 미확정 동안 기한만으로 예약을 풀지 않습니다.

Commerce의 주문 진행과 Payment의 금융 진행을 연결하되, 주문 금액·반품 자격·배송·복구 규칙은 Commerce, PG 결과·미확정 조회·금융 보상은 Payment, 배타 예약·원장은 Settlement가 판단합니다. Commerce를 통째로 코레오그래피로 부르지 않습니다. 같은 서비스의 응용 서비스 조정, 취소 요청/확인 추적, 확정 결제·구매확정의 독립 반영을 흐름별로 구분합니다.

## C안을 선택하는 근거와 감수하는 비용

결정을 세 부분으로 나눕니다. **제품 완료 범위는 돈의 사실과 환불 복구 종결을 구분하고, 환불 조율자 배치는 금융 판정·다음 작업을 가까이 두는 Payment를, 흐름 연결은 환불의 단계 조율과 결제의 독립 반영을 선택합니다.** 앞의 결정이 뒤의 결정을 논리적으로 강제한다고 주장하지 않습니다.

- A는 필요한 진행·보상·기한을 맡길 수 있는 유효한 안입니다. 환불에서는 C와 같고, 결제에서는 위 대표안처럼 별도 실행 지시/확인 책임을 추가할 수 있습니다. 현재의 선예약·금융 확정 후 독립 반영 조건에서는 추가 순서 지시보다 각 소비자의 재개가 책임에 맞습니다. 전체 관측이 필요하면 읽기 집계를 먼저 비교하며 “현재 안 쓰므로 배제”하지 않습니다.
- B도 순서·보상과 전체 완료를 지킬 수 있습니다. Payment 금융 실행의 원자성은 B에서도 같습니다. 위 전면 사건 연결 환불 예는 성공 발행이 6건으로 C의 8건보다 적고, 후반만 연결해도 7건입니다. 그럼에도 C를 택하는 결정적인 차이는 단계 사이 다음 실행·보상·재개를 Payment의 한 상태기계에서 읽고 검사하고, Commerce가 Settlement의 환불 단계에 직접 의존하지 않게 하는 것입니다. 이 개발 편의와 책임 경계를 대표 성공 경로의 메시지 두 건 절감보다 우선합니다. 단순히 전면 B가 상태·사건이 더 많다는 이유로 배제하지 않습니다.
- C는 Payment가 Commerce·Settlement 확인 계약에 결합되고, 확인→다음 의뢰 전달과 한 단계 지연이 추가됩니다. 단계·다음 작업·Outbox를 원자 저장하고 여러 Worker의 임대·버전으로 재개해야 합니다. 지연이나 경합이 더 작다는 실측 근거는 없습니다.
- 독립 결과 반영도 소비자별 멱등·영속 대기·경보·대조가 필요합니다. 사용자 조회는 금융 확정과 주문/원장 반영 지연을 구분해야 합니다. 전달 기반 시험만으로 이 업무 검증이 끝나지 않습니다.

따라서 **현재 완료 약속과 위 판단 우선순위에서 C를 채택**합니다. 패턴 수가 적어서 단순한 것이 아니라, 로컬 원자 처리·금융 단계 실행·확정 사실 반영마다 다음 행동을 누가 결정하는지 찾을 수 있도록 하는 구조입니다. 더 적은 메시지, Commerce 중심 요청 종결, 더 강한 단계별 실행 기한 중 무엇을 우선하느냐가 달라지면 다른 안이 더 나을 수 있습니다.

## 결정한 책임의 구현·검증과 별도 미정 범위

**현재 지원하는 주문·결제·환불·정산의 핵심 책임과 조율 방식은 이 ADR로 결정합니다. 다음 단계는 이 책임대로 업무 코드·상태 전이·트랜잭션·이벤트·복구를 연결하고 검증하는 것입니다.** 구현 중이라는 이유로 책임 선택을 미정으로 되돌리지 않습니다. 구체적인 계약 모순이나 완료 조건을 충족할 수 없는 문제가 발견되면, 해당 문제·영향·대안을 근거로 관련 결정을 재검토하고 ADR을 갱신합니다.

문서의 비교·검사나 Kafka 전달 기반의 국소 시험을 주문·환불·지급·인증·알림 전체의 실행 검증으로 사용하지 않습니다. 현재 제공 동작은 [개발 환경](../development.md)과 코드·설정·해당 변경의 검증 결과로 확인합니다. 아래 구독 제안·Worker 실행 프로세스 분리 등 별도 미정 항목은 위 핵심 책임 결정과 구분합니다.

## 재검토 조건

- 결제 승인 뒤 자원이 독립 만료·거절할 수 있게 되면 예약 확약·금융 보상을 포함한 주문/결제 Saga를 재설계합니다. 단순 결과 재전달의 전제가 유지되는지 먼저 확인합니다.
- 여러 서비스의 실행 순서·보상·기한을 한 업무가 책임져야 하거나 같은 진행 코드가 반복되면 A의 진행 관리자 확대를 비교합니다. 전체 조회만 부족하면 C의 읽기 집계와도 비교하고, 새 중앙 서비스는 별도 배포·소유 근거가 있을 때 판단합니다.
- 환불의 추가 제어 전달·대기 비용이 단계 연결을 Payment에 모으는 이점보다 크거나 Commerce가 원장 상쇄 계약을 직접 소유·유지하는 편이 명료해지면 B의 직접 연결을 비교합니다. Payment 전체 완료 관측, 역순 매핑 대기와 v1 전환을 함께 검증합니다.
- 환불을 금융 완료와 Commerce 요청 종결로 나누거나 사용자 요청·이행 조정을 더 우선한다면 Commerce 조율자와 진행 상태 이동을 재평가합니다. 결제에도 전체 적용 완료를 제공할지는 별도 제품 결정으로 다룹니다.
- 실제 부하·장애 시험에서 진행 상태 경합·대기 장기화·관측 누락이 확인되면 같은 입력·완료 기준으로 대안을 측정합니다. 문서상의 발행 건수를 처리량·지연의 증거로 바꾸지 않습니다.
