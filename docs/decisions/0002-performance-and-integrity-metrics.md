# 성능·정합성 측정 지표와 응답 목표

- 상태: 제안·팀 검토 중
- 제안일: 2026-10-27
- 범위: 결제 확정 처리량·구간별 응답 시간·오류 분류·장애 복구 시간·금액 대조의 측정 정의, 배포 환경 API 응답 목표

## 결정

[성능 목표](../../README.md#성능-목표와-검증)의 TPS·p95/p99 응답 시간·오류율·거래 복구 시간·정산 금액 불일치 건수를 아래 세부 지표로 측정합니다. 배포 환경에서 사용자 요청 API의 기본 목표는 **p99 3초 이하**이며 1초를 넘는 응답은 주의 구간으로 보고 원인을 분석합니다. 메트릭 이름·저장 컬럼은 구현 때 정하며, 아직 업무 지표·부하 스크립트·대조 쿼리를 구현하거나 측정한 상태는 아닙니다.

### 처리량

요청 수가 아니라 완료 시점으로 구분합니다.

| 지표 | 정의 |
| --- | --- |
| 요청 접수량 | Gateway가 결제 요청에 정상 응답한 초당 건수. 결제 확정 TPS와 구분합니다. |
| 결제 확정 TPS | README의 정의. PG A/B/C·간편결제·마일리지 전액 결제별로 함께 표시합니다. |
| 환불 완료 TPS | 외부 환불·마일리지 복원·원장 상쇄·주문 복구까지 완료한 초당 건수. 결제와 섞는 시험에서 사용합니다. |
| 지속 가능 TPS | 아래 응답 시간·오류율 기준을 지키며 15분 유지한 최대 결제 확정 TPS |

k6 arrival-rate 방식으로 단계적으로 올리고 단계마다 요청 접수량과 확정 TPS의 차이, 즉 적체 증가를 기록합니다. 적체가 계속 늘어나는 단계는 지속 가능 TPS로 인정하지 않습니다.

### 응답 시간

구간별 p50/p95/p99를 따로 계산합니다.

| 구간 | 측정 범위 |
| --- | --- |
| API 응답 | Gateway 수신부터 응답까지. 경로 템플릿·상태 코드별 |
| 결제 확정 지연 | 결제 접수부터 Payment DB 확정 반영까지 |
| 외부 호출 | Payment·Settlement에서 `finance-mock` 대역별 호출. 주입한 지연과 내부 처리 시간을 구분 |
| Outbox·Kafka | Outbox 저장부터 발행까지, 이벤트 발생부터 소비 반영까지. Kafka lag 건수 |
| 정산 반영 지연 | 결제 확정부터 Settlement 원장 반영까지 |
| 정산 배치 | 배치 시작부터 종료까지. 대상 항목 건수와 함께 기록 |

p99는 구간별 1만 건 이상에서 계산하고 기동 직후 warm-up 구간을 제외합니다. 부하 발생기 위치·커넥션 풀 크기·데이터 건수를 함께 기록합니다. 3초 목표는 API 응답 구간에만 적용하며 비동기 결제 확정 지연과 정산 배치는 포함하지 않습니다.

### 오류율

의도한 거절을 결함과 섞지 않습니다.

| 분류 | 예 | 집계 |
| --- | --- | --- |
| 시스템 오류 | 5xx·타임아웃·연결 실패 | 오류율에 포함 |
| 의도한 거절 | 400/401/403/404/409/429, 잔액 부족, PG 확정 거절, 매진 | 별도 집계. 결함률에 합치지 않음 |
| 미확정 | `UNKNOWN` 건수와 최장 나이 | 복구 지표로 추적 |
| 메시지·작업 실패 | 재시도 횟수 분포, DLT 이동, `REVIEW_REQUIRED` | 0건이거나 전부 원인 확인 |

재시도 후 성공한 비율을 따로 기록해 일시 장애와 영구 실패를 구분합니다. 초기 기준으로 시스템 오류율 0.1% 미만을 제안하며 첫 시험 결과로 조정합니다. 운영 경보 기준은 [운영 알람](../policies.md#운영-알람)을 따릅니다.

### 복구 시간

장애 주입 시각부터 세 시점을 측정합니다.

- 탐지 시간: 해당 알람이 발생할 때까지
- 서비스 복구 시간: 시스템 오류율이 기준 이하로 돌아올 때까지
- 정합 복구 시간: 장애로 생긴 미확정·미발행 Outbox·미처리 Inbox·Kafka lag가 0이 되고 아래 금액 대조에 불일치가 없을 때까지. 핵심 지표입니다.

| 시나리오 | 주입 | 복구 완료 조건 |
| --- | --- | --- |
| PG 응답 유실·조회 장애 | [PG 3종과 장애 시나리오](../design.md#pg-3종과-장애-시나리오)의 설정 | 같은 PG·업무 키 조회로 확정, 중복 승인·차감 0건 |
| Worker 강제 종료 | 승인 처리 중 `payment-worker` 컨테이너 종료 | 재기동 후 처리 중 작업 재개·완료 |
| Kafka 중단 | broker를 일정 시간 중지 후 재시작 | 미발행 Outbox 0건, consumer lag 0 |
| DB 재시작 | PostgreSQL 컨테이너 재시작 | 연결 회복, 실패 작업 재처리 완료 |
| 정산 배치 중단 | 대상 고정 커밋 뒤 프로세스 종료 | 재실행 시 원래 대상·합계·업무 키로 완료 |
| 지급 응답 유실 | 지급 대역의 성공 후 응답 유실 | 원거래 조회로 확정, 중복 지급 0건 |

### 금액 불일치

대조할 쌍과 식을 고정합니다. 기호는 [금액·데이터 불변식](../design.md#7-금액데이터-불변식)을 따릅니다.

| 대조 | 조건 |
| --- | --- |
| 결제 구성 | 확정 결제마다 `T=E+M` |
| Payment ↔ `finance-mock` | 결제·환불 건별 외부 금액·상태 일치. 원결제별 승인·환불 각 1회 |
| 마일리지 | 계정별 `현재 잔액=사전 지급−차감+복원`, `잔액−예약 합계≥0` |
| Settlement 원장 | 항목별 `E+M+P=B=N+F`. 전액 환불 시 각각 상쇄 |
| 정산 ↔ 지급 | 지급액=선점 항목 합계, 항목별 지급 배정 1회, 지급 성공액=대역 차감액 |
| 재원·PG 입금 | `기초잔액+PG입금−입금후환불−성공지급=현재잔액`. 원승인별 입금은 E 한 번이며 입금 전 전액 환불은 0원 종결 |

대조 쌍별로 불일치 건수와 차액 합계를 함께 기록하고, 금액이 맞아도 중복 승인·환불·지급·원장 반영 건수를 따로 셉니다. 부하 시험 종료 후, 장애 시나리오의 정합 복구 후에 실행합니다. 완료 조건은 모든 대조에서 0건·0원입니다. 반영 대기로 생긴 차이는 정합 복구 완료 뒤 다시 대조하고 그때도 남으면 결함으로 분류합니다.

## 선택 이유와 대안

기존 기준은 측정 항목 이름만 있어 무엇을 언제부터 언제까지 재는지, 어떤 결과를 결함으로 볼지가 정해지지 않았습니다. 비동기 결제 구조에서는 API 응답과 결제 확정 시점이 다르고, 의도한 거절과 시스템 오류가 섞이면 오류율이 결함을 나타내지 못합니다. 그래서 완료 시점·구간·분류·대조 식을 먼저 고정합니다.

응답 목표 3초는 1초를 넘으면 사용자의 사고 흐름이 끊기기 시작하고([Nielsen Norman Group](https://www.nngroup.com/articles/response-times-3-important-limits/)), 모바일 페이지 로딩이 1초에서 3초로 늘면 이탈 확률이 32% 증가한다는 조사([Think with Google](https://www.thinkwithgoogle.com/marketing-strategies/app-and-mobile/page-load-time-statistics/))를 근거로 합니다. 이 조사는 페이지 로딩 기준이며 API 목표로 옮긴 것은 팀의 판단입니다.

| 검토한 안 | 판단 |
| --- | --- |
| 로컬 시험 결과로 응답 목표 판정 | 발생기와 서버가 자원을 공유해 배포 환경을 대표하지 않으므로 보류. 로컬은 변경 전후 비교에 사용 |
| 평균 응답 시간 목표 | 일부 느린 요청이 가려지므로 보류 |
| 배포 환경 API p99 3초 이하, 1초 초과 주의 | 사용자 이탈 근거와 연결되고 꼬리 지연을 드러내므로 제안 |
| 모든 HTTP 오류 0 요구 | 의도한 거절까지 결함으로 세므로 보류. 시스템 오류와 분리 |
| 순간 최대 TPS 보고 | 적체가 쌓여도 높게 나오므로 보류. 15분 지속 가능 TPS 사용 |

## 감수하는 비용과 검증

구간별 지연·대조 쿼리·장애 주입 시나리오를 각 소유 서비스가 구현해야 하므로 지표 수집과 시험 준비 비용이 늘어납니다. 배포 환경이 없는 동안에는 3초 목표의 달성 여부를 판정할 수 없습니다. 0.1% 오류율 기준과 3초 목표는 실제 측정 결과가 아니며 첫 시험 후 조정합니다.

- 처리량: 단계별 요청 접수량과 확정 TPS 차이, 15분 유지 여부, `dropped_iterations`.
- 응답 시간: 구간별 표본 1만 건 이상, warm-up 제외, 발생기 위치·풀 크기 기록.
- 복구: 시나리오별 탐지·서비스 복구·정합 복구 시간, 중복 승인·지급 0건.
- 금액: 대조 쌍별 0건·0원, 반영 대기 차이의 재대조.

이 문서는 측정 정의이며 문서 검사나 리뷰가 성능·정합성 검증을 대신하지 않습니다.
