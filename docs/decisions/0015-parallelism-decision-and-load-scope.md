# 배포 인스턴스 기준 병렬도 결정 절차와 부하 시험 범위

- 제안일: 2026-11-12
- 상태: 채택. 병목 판정 결과와 병렬도 값은 측정 전이라 미정
- 범위: AWS 배포 2대 구성(앱 EC2, 인프라 EC2)에서 이벤트 처리 구간의 병렬도를 올리기 전 판단 순서, 시험 대상, 측정·판정 기준
- 연결 문서: [EC2 2대 배포·부하 시험 제안](0013-ec2-deployment-and-load-test.md), [Kafka 전달과 처리 용량](0005-kafka-event-delivery-and-capacity.md), [정산 일배치 범위](0007-settlement-batch-scope-and-schedule.md)

## 배경

- 배포 구성은 [ADR 0013](0013-ec2-deployment-and-load-test.md)을 따릅니다. 앱 EC2에는 Gateway·Commerce·Payment API/Worker·Settlement·Finance Mock이, 인프라 EC2에는 PostgreSQL·Kafka·Redis와 관측 도구가 올라갑니다. 부하 발생기는 로컬 PC에서 공개 도메인으로 요청합니다.
- 코드 기본값은 결제 요청 처리 3, 결제 승인 6, Payment Kafka 리스너 3(파티션 3), Outbox 발행 in-flight는 Commerce·Settlement 8과 Payment 32, 지급 워커 8입니다. 실제 배포값은 시험 전에 따로 기록합니다. 정산 일배치는 단일 스레드 chunk(1)이며 [ADR 0007](0007-settlement-batch-scope-and-schedule.md)의 파티셔닝은 부하 시험 뒤에 검토합니다.
- 두 호스트의 CPU와 메모리는 여러 서비스, 저장소, 관측 도구가 나눠 씁니다. 병렬도를 올리면 앱 CPU, DB 잠금과 디스크, Kafka, 관측 중 먼저 막히는 자원이 달라질 수 있습니다. 병목 위치를 측정하지 않고 병렬도를 올리면 원인을 나눌 수 없습니다.
- 병렬도 설정 변경과 호스트 사양 변경은 같은 결과로 보일 수 있으므로 따로 기록합니다.

## 결정

### 1. 판정 순서

1. 시험 전 배포 설정을 기록합니다. 배포 커밋, 컨테이너 CPU·메모리 상한, JVM 프로세서 수, 커넥션 풀 크기, Kafka 파티션 수, 트레이스 샘플링률, 호스트 사양을 포함합니다.
2. 현재 설정으로 기준선 실험을 수행하고 호스트별 자원 시계열을 수집합니다.
3. 기준선에서 포화나 대기가 확인된 처리 구간만 병렬도 실험 대상으로 삼습니다. 확인되지 않은 구간은 시험하지 않고 확인 근거를 남깁니다.
4. 호스트 사양 변경 효과는 병렬도 실험과 별도 실험으로 기록합니다. 병렬도 비교는 같은 사양 안에서만 합니다.

### 2. 병렬도 실험 대상 후보

- 후보는 결제 요청 처리, 결제 승인(PG 호출), Kafka 리스너, Outbox 발행입니다. 기준선 판정 결과로 고릅니다.
- 다음 구간은 이 시험의 대상이 아닙니다.
  - 정산 일배치: [ADR 0007](0007-settlement-batch-scope-and-schedule.md)의 별도 시험에서 다룹니다.
  - 파티션 수 증설: key 재배치와 순서 검증이 따로 필요하므로 후속 ADR에서 다룹니다.

### 3. 변수 변경 방식

- 한 번에 한 변수만 바꿉니다.
- 실험 전에 값을 고정하고, 결과를 본 뒤 값이나 판정 기준을 바꾸지 않습니다.
- 도착률·기간·예열·구매자/상품 수·결제 구성을 전후에 같게 유지합니다. [주문 부하 실행기](../../tests/load/README.md#mac에서-공개-https-주문-부하-시험)의 기본 200건/초·60초는 단기 비교이며, 15분 지속 가능 TPS 판정과 구분합니다.

### 4. 관측

- 시험 중에도 관측 도구를 끄지 않습니다. 접수 gate가 Prometheus 조회에 의존하므로 관측을 끄면 주문 접수 자체가 막힐 수 있습니다.
- 호스트별 CPU, 컨테이너 메모리와 GC, DB 풀 대기, 잠금 대기, 디스크 지연, Kafka lag, Outbox 적체, 접수 gate 상태, 발생기 CPU, `dropped_iterations`를 기록합니다.
- 관측 컨테이너가 쓰는 CPU는 따로 기록합니다.

### 5. 실험 간 데이터 격리

- 실험마다 새 상품과 실행 번호를 사용합니다. 기본 실행기는 한 구매자·한 상품에 집중하며, 구매자·상품을 분산하는 시험은 별도 시나리오로 고정합니다. 구매자를 재사용하면 잔액·예약 등 해당 시험의 초기 조건을 함께 확인합니다.
- 데이터는 삭제하지 않습니다.
- 실험 시작 전에 Outbox 미발행 0, Kafka lag 0, 이전 실행의 잔여 처리 0을 확인합니다.

### 6. 판정 기준

- [측정 지표](0002-performance-and-integrity-metrics.md)에 따라 결제 확정 TPS와 주문 접수→정산 최초 반영 지연을 비교하고, API 응답·Outbox 발행·Kafka 전달 지연과 적체를 구간별로 확인합니다. 같은 조건의 기준선 대비 개선할 지표와 허용할 회귀 폭을 시험 전에 고정합니다.
- [ADR 0005](0005-kafka-event-delivery-and-capacity.md)의 p99 1.10배·PUBLISHED/초 0.95배는 국소 SQL 비교의 회귀 허용폭입니다. 이 수치만으로 주문·결제 전체의 개선이나 AWS 성능 목표 달성을 판정하지 않습니다.
- 거절(재고, 접수 gate, PG, 오류)은 성공과 분리해 따로 집계합니다.
- 목표 TPS를 채우지 못했을 때 입력량을 줄여 달성으로 보고하지 않습니다.
- 발생기 한계와 서버 한계는 `dropped_iterations`와 발생기 자원 기록으로 구분합니다.

### 7. 정합성 검증

성능 수치보다 우선하며, 실험마다 다음 다섯 항목을 모두 확인합니다.

1. 재고 초과 배정이 없고 수량이 보존됩니다. 일반 상품 시험에서는 준비한 초기 수량이 종료 시 가용·예약·판매 수량의 합과 일치합니다.
2. 같은 거래 안의 이벤트 순서를 지킵니다. 선행 이벤트를 추월하지 않습니다([ADR 0005](0005-kafka-event-delivery-and-capacity.md)).
3. PG 거절 주문의 보상이 누락되거나 중복 반영되지 않습니다.
4. 같은 결제의 중복 승인과 중복 원장이 없습니다. 멱등 키로 막습니다.
5. 종료 후 정산 대조(기준 시점)의 불일치가 0입니다.

### 8. 결정 범위

- 이 ADR은 판단 절차와 측정·판정 기준만 정합니다.
- 병목 판정 결과와 병렬도 값은 측정 뒤 별도 ADR이나 이 ADR의 갱신으로 확정합니다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
| --- | --- |
| 병목 판정 없이 승인·Outbox·Kafka를 바로 올림 | 원인을 나눌 수 없고, 병목이 아닌 구간에서 CPU 경합만 늘 수 있습니다 |
| 후보 구간의 값을 격자로 조합 | 실행 횟수와 누적 데이터가 커서 원인 구분에 불리합니다 |
| 사양 변경과 병렬도 변경을 함께 적용 | 두 효과를 분리할 수 없습니다 |
| 시험 중 관측 도구를 끔 | 병목 판정 근거를 잃고, 접수 gate가 Prometheus에 의존해 주문이 막힐 수 있습니다 |
| 실험 사이에 데이터 초기화 | 데이터 보존 요구와 충돌합니다 |

## 결과와 한계

- 호스트 사양은 [ADR 0013](0013-ec2-deployment-and-load-test.md)의 시험 후보입니다. 실제 Task 상한과 JVM 설정은 배포 설정에서 확인해야 합니다.
- 이 ADR은 측정 전에 고정할 조건만 정합니다. 병렬도 값은 기준선과 단일 변수 실험 결과가 있어야 확정할 수 있습니다.
- 2대 구성은 고가용성이 아닙니다. 호스트 장애 격리는 이 ADR의 목적이 아닙니다.

## 검증 계획

1. 기준선 실험 후 호스트별 자원 시계열로 병목 위치를 판정합니다.
2. 판정된 구간별로 한 변수씩 바꾸고, 실험마다 정합성 다섯 항목을 확인합니다.
3. 사전에 고정한 업무 완료·지연·적체·정합성 기준으로 결과를 비교하고 병렬도 결정을 기록합니다.
