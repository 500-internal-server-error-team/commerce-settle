# 내부 호출 자격으로 대상별 정적 Bearer 사용

- 상태: 채택·구현 예정
- 결정일: 2026-10-28
- 범위: Gateway→커머스·Payment·Settlement 전달, 서비스 간 `/internal`·`/mock` 호출, 운영자 호출의 자격 형식과 백엔드 판정. 사용자 세션은 [Redis 세션 결정](0003-redis-sessions.md)이 소유

Gateway·서비스·운영자가 백엔드를 호출할 때 **발신자·대상 서비스 쌍마다 발급한 256비트 이상 임의값을 `Authorization: Bearer`로 보냅니다.** 백엔드는 이 자격으로 발신자를 확정하고, 빌드에 포함한 OpenAPI의 `x-actor`·`x-owner-service`로 호출할 수 있는 작업인지 판정한 뒤에만 사용자 신원 헤더를 읽습니다. 형식은 [OpenAPI](../openapi.json)의 `serviceCredential` 스킴과 같고 Gateway 자격도 이 형식을 따릅니다. 자격 생성·검증 코드와 설정은 아직 없습니다.

## 결정

### 자격과 발급 단위

- 자격은 CSPRNG로 만든 256비트 이상의 URL-safe 문자열입니다. 사용자 세션 토큰·Redis·DB 비밀번호와 별개이며 다른 용도로 쓰지 않습니다.
- **발신자·대상 서비스 쌍마다 다른 값을 씁니다.** 한 대상에 보낸 자격을 다른 대상에서 쓸 수 없습니다. 현재 명세 기준 쌍은 다음과 같습니다.

| 발신자 ID | 대상 서비스 | 근거 `x-actor` |
| --- | --- | --- |
| `gateway` | 커머스, Payment, Settlement | `/api/`의 PUBLIC·BUYER·SELLER 작업 |
| `service:payment` | 커머스, Finance Mock | `SERVICE:payment` |
| `service:settlement` | 커머스, Payment, Finance Mock | `SERVICE:settlement` |
| `operator:<운영자 식별자>` | 커머스, Payment, Settlement, Finance Mock | `OPERATOR` |

- Payment API·Worker는 같은 `service:payment` 자격을 씁니다. 운영자 식별자는 감사의 [`actor_ref`](../data-model.md#audit_logs)에 남는 값이며 이메일을 쓰지 않습니다.
- 대상 서비스는 허용할 발신자별 자격을 설정으로 받습니다. 교체 중에는 발신자당 현재·이전 두 값까지 허용합니다. 필수 자격 설정이 없거나 256비트 미만이면 앱을 기동하지 않습니다.
- 대상 서비스는 자격 원문을 설정으로 받고 별도의 해시 설정을 두지 않습니다. 자격이 그 대상에만 유효하므로 대상의 설정이 노출돼도 다른 서비스에 쓸 수 없고, 해시 설정을 따로 생성·배포하는 비용이 더 큽니다. 비교는 양쪽 SHA-256 결과를 `MessageDigest.isEqual`로 상수 시간 비교합니다.

### 백엔드 판정 순서

각 백엔드는 컨트롤러 전에 한 곳에서 아래 순서로 판정하고, 결과를 **검증된 발신자**(발신자 ID·종류, Gateway 경유면 계정 종류·ID) 하나로 응용 계층에 전달합니다.

1. `Authorization`이 없거나 Bearer가 아니거나 일치하는 자격이 없으면 `401 COMMON_AUTHENTICATION_REQUIRED`입니다.
2. 요청의 HTTP 메서드·정규화한 경로를 빌드에 포함한 OpenAPI 작업과 대조합니다. 명세에 없는 작업은 `404 COMMON_RESOURCE_NOT_FOUND`입니다. 작업의 `x-owner-service`가 자기 서비스가 아니거나 발신자 종류가 위 표의 `x-actor`와 맞지 않으면 `403 COMMON_ROLE_FORBIDDEN`입니다. 예를 들어 Gateway 자격으로 `/internal`을, Settlement 자격으로 `SERVICE:payment` 작업을, 운영자 자격으로 `/api/` 작업을 호출할 수 없습니다.
3. `X-Authenticated-Actor-Kind`·`X-Authenticated-Actor-Id`·`X-Authenticated-Session-Hash`는 발신자가 `gateway`일 때만 읽습니다. 다른 발신자의 요청에 하나라도 있으면 `403 COMMON_ROLE_FORBIDDEN`입니다. 이 판정은 위 한 곳에서만 합니다.
4. Gateway 경유 보호 작업은 [신원 전달 계약](../architecture.md#사용자-인증과-내부-신원-전달)을 따릅니다. 계정 종류·ID가 없거나 로그아웃에 세션 해시가 없으면 `401`, 계정 종류가 작업의 `x-actor`와 다르면 `403`입니다. PUBLIC 작업은 신원 헤더를 사용하지 않습니다.

자격 원문과 해시는 로그·추적·응답에 넣지 않고 발신자 ID만 기록합니다. 판정 실패는 발신자 ID(확정 전이면 `unknown`)와 결과로 집계해 설정 불일치를 탐지합니다.

### 교체

대상 서비스에 새 값을 추가해 두 값을 허용 → 발신자를 새 값으로 전환 → 대상에서 이전 값을 제거하는 순서입니다. 환경 변수 설정이므로 각 단계에서 해당 앱을 재기동합니다. 설정 변수 이름과 생성은 구현 PR에서 [환경 생성기](../../scripts/init_env.py)·`.env.example`과 함께 정합니다.

## 대안과 선택 이유

| 대안 | 판단 |
| --- | --- |
| **대상별 정적 Bearer 자격** | 채택. 서비스·운영자·Gateway를 한 형식과 한 판정 경로로 처리하고 운영자가 `curl`로 호출할 수 있음 |
| HMAC 요청 서명 | 보류. 아래 비교처럼 현재 구성에서 추가로 막는 경우가 좁고 서명 정규화·시각·운영자 도구 비용이 큼 |
| Gateway 서명 단기 JWT | 검토에서 제외. 키 관리와 JWT 검증을 백엔드마다 추가하는 비용이 [사용자 JWT를 택하지 않은 이유](0003-redis-sessions.md#jwt-대신-불투명-세션을-선택한-이유)와 같음 |
| mTLS | 보류. 전송 보호와 발신자 인증을 함께 얻지만 로컬·CI에 인증서 발급·교체 체계가 필요함. 배포 환경의 내부 TLS와 함께 재검토 |
| 같은 네트워크 신뢰 | 제외. [인증 경계](../architecture.md#사용자-인증과-내부-신원-전달)가 네트워크·계정 ID만으로 신뢰하지 않도록 정함 |
| Gateway만 HMAC, 서비스·운영자는 정적 자격 | 보류. 운영 API가 더 약한 형식으로 남아 근거가 어긋나고 검증기·교체 절차·시험이 두 벌이 됨 |

### HMAC 요청 서명과의 비교

HMAC은 메서드·경로·쿼리·신원 헤더·시각을 대상별 키로 서명하는 방식입니다. 모든 컨테이너가 같은 `backend` 네트워크에 있다는 전제에서 비교했습니다.

| 위협 | 정적 자격 | HMAC 서명 |
| --- | --- | --- |
| 자격 없는 컨테이너의 직접 호출 | 차단 | 차단 |
| 다른 서비스의 사용자 사칭 | 발신자 ID로 차단 | Gateway 키가 없어 차단 |
| 자격·키 자체의 유출 | 교체 전까지 임의 사용자 사칭 | 같음 |
| 요청 하나의 헤더 노출 | 무기한 재사용, 경로·신원 변경 가능 | 허용 시간 안의 같은 메서드·경로·신원으로 제한 |
| 허용 시간 안 재전송·본문 변조 | 막지 못함 | nonce·본문 서명 없이는 막지 못함 |

HMAC이 더 막는 경우는 요청 하나의 헤더가 노출될 때뿐입니다. 로그 노출은 [로그 계약](../../CONTRIBUTING.md#로그)이 자격 기록을 금지하고 actuator는 `health`·`info`·`prometheus`만 공개합니다. 내부망 캡처가 가능한 위치라면 Redis·PostgreSQL 비밀번호와 응답의 개인정보도 평문으로 보이고, 커머스의 Redis 자격으로 세션을 직접 만들 수 있습니다. 내부 전송이 평문인 동안 서명만으로 줄어드는 위험은 작습니다.

반면 HMAC은 WebFlux Gateway와 MVC 백엔드가 같은 경로·쿼리 정규화를 구현해야 하며 불일치는 정상 요청의 `401`로 나타납니다. 시각 허용 범위와 동기화, 모든 호출 클라이언트의 서명 인터셉터, 운영자·smoke용 서명 도구가 필요하고, 본문을 보호하려면 Gateway가 본문을 버퍼링해야 합니다.

### 형식을 하나로 두는 이유

형식이 둘이어도 검증기를 요청 내용이 아닌 스킴으로 고르고, 신원 헤더 판정을 한 곳에 두고, 모든 자격을 대상에 묶으면 결함은 피할 수 있습니다. 다만 사람이 서명할 수 없는 운영자 자격은 정적 형식이 필요하므로, 분리하면 더 민감한 운영 API가 약한 형식으로 남습니다. 하나의 형식으로 검증기·교체 절차·시험을 한 벌로 유지합니다.

## 감수하는 비용

- 노출된 자격은 교체 전까지 재사용할 수 있고 경로·신원을 바꿀 수 있습니다. **Gateway 자격을 가진 쪽은 해당 대상의 임의 사용자를 사칭할 수 있으므로** Gateway 설정의 접근을 제한합니다.
- 내부 HTTP는 평문이며 이 결정은 전송 구간을 보호하지 않습니다.
- 백엔드의 자격 거절 `401`은 Gateway가 그대로 전달하므로 클라이언트에는 세션 만료와 같게 보입니다. 설정 불일치는 위 판정 실패 집계와 smoke로 탐지합니다.
- 각 백엔드가 OpenAPI를 빌드 리소스로 포함해야 하며, 명세의 작업·권한을 바꾸면 Gateway와 해당 백엔드를 함께 다시 빌드합니다.
- 교체에 앱 재기동이 필요합니다.

## 검증과 재검토

구현 PR에서 다음을 HTTP 경계와 Compose smoke로 확인합니다.

- 자격 없음·틀린 값·다른 대상의 자격은 `401`, 교체 중에는 두 값 모두 허용하고 제거 뒤에는 이전 값을 거절
- 발신자와 맞지 않는 작업(Gateway의 `/internal`, Settlement의 `SERVICE:payment` 작업, 운영자의 `/api/`)과 같은 경로의 다른 메서드는 `403`
- Gateway가 아닌 자격에 신원 헤더가 있으면 `403`, 클라이언트가 보낸 신원 헤더는 Gateway에서 제거
- 필수 자격 설정 누락·짧은 값에서 기동 실패, 로그·추적·응답에 자격 미포함

배포 환경에서 내부 TLS·mTLS를 도입할 때, 요청 헤더를 기록·중계하는 구성요소가 생길 때, 자격 유출 사례가 생길 때, 운영자 개인별 인증이 필요해질 때 다시 검토합니다.
