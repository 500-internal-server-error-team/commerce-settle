# 거래 데이터의 주 저장소로 PostgreSQL 선택

- 상태: 설계 기준
- 작성일: 2026-10-27
- 범위: 주문·결제·환불·정산의 원천 데이터 저장

## 결정

주문·결제·환불·정산의 원천 데이터는 PostgreSQL에 저장합니다. 서비스마다 자기 데이터를 소유하고, 함께 확정해야 하는 변경은 같은 서비스의 DB 트랜잭션으로 처리합니다. 서비스 간에는 이벤트와 Outbox·Inbox로 상태를 전달합니다.

## 배경과 선택 이유

마일리지를 사용한 결제에서 잔액 차감·사용 원장·결제 확정·Outbox가 따로 저장되면, 잔액만 줄거나 확정한 결제의 후속 처리가 누락될 수 있습니다. 이 변경들을 함께 커밋하거나 롤백할 수 있어야 합니다. 같은 결제 요청과 이벤트가 다시 들어와도 원장에는 한 번만 반영돼야 하며, 환불과 지급이 같은 정산 금액을 동시에 선점해서도 안 됩니다.

주문·결제·환불·원장은 각각의 상태와 이력을 가지면서 원거래로 연결됩니다. 명확한 컬럼과 관계로 저장하고, 서비스 DB 안에서 판매자별 금액 집계와 원거래·상쇄 내역을 SQL로 대조하는 관계형 모델을 선택합니다.

PostgreSQL은 이 모델에 필요한 [트랜잭션](https://www.postgresql.org/docs/18/tutorial-transactions.html)과 제약 조건을 함께 제공합니다. 특히 [부분 유니크 인덱스](https://www.postgresql.org/docs/18/indexes-partial.html)는 조건에 해당하는 행에만 유일성을 적용할 수 있습니다. 예를 들어 같은 정산 항목의 활성 예약을 하나로 제한하면, 환불·지급 예약을 동시에 만들려는 요청 중 하나를 DB에서 거절할 수 있습니다. 애플리케이션의 사전 조회에만 의존하지 않고 경합 시점에도 규칙을 보호하기 위해 PostgreSQL을 선택합니다.

## 검토한 대안

| 안 | 판단과 이유 |
| --- | --- |
| PostgreSQL의 관계형 모델 | 거래별 상태·이력과 원거래 관계를 분리해 저장하고, 로컬 트랜잭션·제약·SQL 대조로 일관성을 관리할 수 있어 채택 |
| MongoDB의 문서 모델 | 여러 문서에 걸친 [트랜잭션도 지원](https://www.mongodb.com/docs/manual/core/transactions/)하지만, 현재 요구는 거래 관계·중복 방지·원장 대조가 중심입니다. 가변적인 문서 구조를 주 저장소 선택의 우선 조건으로 삼을 요구가 없어 보류 |

## 감수하는 비용과 재검토 조건

동시 갱신은 행 잠금·조건부 갱신·트랜잭션 경계를 설계해야 하며, 인덱스 유지와 스키마 변경도 관리해야 합니다. 참조 유효성과 여러 행의 합계는 애플리케이션과 트랜잭션에서 검증합니다. 물리 FK를 두지 않는 기준과 변경 이력은 [DB 정책](../migrations.md)을 따릅니다.

DB 트랜잭션은 외부 PG 호출이나 다른 서비스의 DB까지 묶지 않습니다. 미확정 결과 조회·재시도·보상은 [서비스 경계와 정합성 설계](../architecture.md)에서 다루며, DB 선택만으로 금융 처리의 정확성이 완성되지는 않습니다.

문서별로 크게 다른 구조가 핵심 저장 요구가 되거나, 인덱스·쿼리·잠금 조정으로 요구 처리량을 충족하기 어려워지면 저장 모델과 DB를 재검토합니다. 이때 데이터 이전·운영·장애 복구 비용도 함께 비교합니다.

## 구현 시 확인

동일 요청·이벤트의 동시 재처리에서 중복 원장이 생기지 않는지, 환불·지급 경합에서 활성 예약이 하나만 남는지 확인합니다. 중간 실패 시 상태·원장·Outbox가 함께 롤백되는지 검증합니다. 구체적인 테이블·제약·원자 처리 범위는 [데이터 모델](../data-model.md#트랜잭션과-관계)이 소유합니다.
