# 공통 API 계약과 공유 코드의 경계

- 상태: 제안
- 작성일: 2026-10-28
- 범위: Gateway와 MVC 서비스의 HTTP 계약 및 표현 계층 기술 코드 공유

## 배경

[공통 규약](../../CONTRIBUTING.md#구현-규약)과 [OpenAPI](../openapi.json)가 요청·응답 형식과 오류 계약을 정합니다. [Gateway 라우팅과 오류 처리](https://github.com/500-internal-server-error-team/commerce-settle/pull/42)는 WebFlux 경계에 구현됐지만, MVC 서비스의 공통 오류 처리는 아직 구현 전입니다.

같은 응답 클래스를 사용해도 실행 경계의 처리가 빠지면 계약은 달라집니다. 설명용으로 `traceId: "test"`는 현재 Problem 스키마의 문자열 조건을 만족하지만 실제 요청의 추적 ID라는 보장은 없습니다. 응답 형식의 공유와 실제 동작 검증을 함께 다뤄야 합니다.

## 결정안

1. **계약은 기존 명세를 유지합니다.** 필드·타입은 OpenAPI, HTTP 상태·오류·검증 규칙은 공통 규약과 [API 명세](../api.md)가 소유합니다. 이 ADR에 규격을 다시 정의하지 않습니다. 성공 응답은 기능별 DTO, 오류 응답은 Spring `ProblemDetail`을 사용합니다.
2. **안정된 표현 계층 코드만 공유합니다.** 공통 오류 코드와 오류 응답 생성 규칙을 후보로 삼습니다. 업무 DTO·도메인 예외·업무별 HTTP 매핑은 각 서비스가 소유하며, 도메인이 공통 HTTP 코드에 의존하지 않습니다.
3. **처리기는 실행 경계에 둡니다.** MVC 예외 처리와 Gateway의 WebFlux 오류 처리를 구분합니다. 필터·인증 경로도 해당 경계에서 검사하고, Gateway는 백엔드의 상태·오류 본문을 보존합니다. 실제 추적 문맥은 각 경계에서 얻습니다.
4. **공유 모듈은 실사용과 함께 도입합니다.** Gateway와 첫 MVC 서비스에서 같은 생성 규칙을 사용할 때 중복과 의존성을 확인하고 추출합니다. 필요한 HTTP 타입만 의존하는 라이브러리로 두며, MVC·WebFlux starter나 DB·Redis 자동 설정을 소비 앱에 전파하지 않습니다.
5. **목록 응답도 계약별로 판단합니다.** `PageResponse<T>`는 표준 목록 API의 실제 재사용에 맞춰 도입합니다. 정산 대조 피드의 `snapshotAt`·`nextCursor` 같은 별도 계약을 공통 클래스에 맞추기 위해 바꾸지 않습니다.
6. **일관성은 실제 HTTP 응답으로 검증합니다.** 공유 클래스 사용 여부와 별개로 각 서비스의 응답을 같은 OpenAPI 계약과 동작 기준에 대조합니다.

## 비교한 대안

모든 안에 같은 실제 HTTP 계약 시험을 적용하고, 코드 공유의 이익과 의존성·변경 비용을 비교합니다.

| 안 | 판단과 이유 |
| --- | --- |
| 서비스별 구현 유지 | 현재 출발점으로 사용합니다. 공유 모듈 의존성이 없지만 같은 생성 규칙이 반복되면 여러 곳을 수정하는 비용이 남습니다. |
| 작은 API 기술 모듈 즉시 도입 | 생성 규칙을 한곳에 둘 수 있습니다. 다만 MVC 실사용이 없는 상태에서 공통 인터페이스를 먼저 정하고 빌드도 분리해야 하므로 보류합니다. |
| 실제 중복 확인 후 좁게 추출 | 서비스별 구현에서 출발해 Gateway와 MVC가 함께 사용하는 책임만 공유하도록 제안합니다. 도입이 늦어지는 동안의 코드 중복과 추출 비용은 감수합니다. |
| 요청·응답·업무 예외·처리기를 큰 common 모듈로 통합 | 코드가 한곳에 모이지만 업무 타입과 실행 프레임워크의 의존 범위도 넓어집니다. 공유 필요성이 확인되지 않은 업무 책임까지 묶으므로 제외합니다. |

## 감수하는 비용과 재검토 조건

MVC와 WebFlux의 예외 연결 코드는 각각 유지해야 하며, 공통 생성 코드가 바뀌면 소비 서비스의 계약 시험도 확인해야 합니다. 계약 시험은 HTTP 형식·오류 동작을 확인하며 금융 정합성·권한·DB 경합 시험을 대신하지 않습니다.

현재 [루트 빌드](../../build.gradle)는 모든 하위 모듈에 Boot 플러그인과 앱 의존성을 적용합니다. 공유 라이브러리를 도입할 때는 실행 앱과 라이브러리의 플러그인·의존성·패키징 설정을 분리하는 비용이 있습니다. 이 ADR에서는 빌드 설정이나 실행 코드를 변경하지 않습니다.

서로 다른 실행 경계의 요구 때문에 공유 코드에 서비스별 분기가 늘거나, 한 서비스의 변경이 무관한 서비스의 계약까지 바꾸면 공유 범위를 다시 줄입니다. 새 공유 코드도 [기존 변경 판단](../../CONTRIBUTING.md#변경-판단)에 따라 필요성과 전체 유지 비용을 비교합니다.

## 구현 시 확인

- 각 서비스의 대표 성공·실패 응답을 OpenAPI 스키마에 대조합니다. 입력 검증 실패는 필드 오류를 포함하고, HTTP 상태와 오류 코드의 대응도 확인합니다.
- 오류의 추적 ID가 실제 요청의 추적 문맥과 연결되는지, 응답·로그에 토큰·거절된 원문 값·예외 원문·내부 주소가 노출되지 않는지 검사합니다. 스키마 검사만으로 통과시키지 않습니다.
- MVC와 Gateway의 필터·인증 오류가 해당 처리 경계에 도달하는지, Gateway가 백엔드 오류를 바꾸지 않는지 확인합니다.
- 공유 라이브러리 도입 시 Gateway와 MVC 소비 앱을 각각 빌드·기동해 의존성 경계를 확인하고, 계약 시험을 기본 CI 경로에 연결합니다.

공유 모듈 추출·MVC 오류 처리·서비스별 계약 시험은 후속 구현 범위입니다. 이 문서는 해당 구현이나 실행 검증의 완료를 뜻하지 않습니다.
