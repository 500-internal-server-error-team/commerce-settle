# 같은 서비스 내부에서도 FK constraint 미사용 유지

- 상태: 채택
- 제안일: 2026-10-27
- 채택일: 2026-10-28
- 범위: 같은 서비스 DB 안의 테이블 간 FK constraint, JPA 연관관계 매핑, 내부 참조 정합성 대조. Settlement를 기준으로 검토하고 다른 서비스에도 같은 기준을 적용

## 결정

서비스 간뿐 아니라 **같은 서비스 내부에서도 FK constraint를 두지 않는** [기존 정책](../migrations.md#데이터-보존과-제약-조건)을 유지합니다. 대신 FK가 막았을 고아 참조를 [금액 대조](0002-performance-and-integrity-metrics.md#금액-불일치)와 같은 시점에 실행하는 **서비스 내부 참조 대조**로 탐지합니다. 엔티티 간 참조는 JPA 연관관계가 아닌 식별자 값으로 둡니다. 저장 구조는 [데이터 모델](../data-model.md), 대조 시점과 완료 조건은 [측정 지표 결정](0002-performance-and-integrity-metrics.md)이 소유합니다. 추가 업무 테이블의 제약과 대조 쿼리는 해당 구현에서 검증합니다.

Settlement의 내부 대조 대상은 다음과 같습니다. 완료 조건은 모든 항목 0건입니다.

| 대조 | 고아·불일치 조건 |
| --- | --- |
| `payouts.batch_id` | 대응하는 `settlement_batches`가 없거나 seller_id가 다름 |
| `settlement_items.payout_id` | 대응하는 `payouts`가 없거나 seller_id가 다름 |
| `settlement_entries.item_id` | 대응하는 `settlement_items`가 없거나 payment_id가 다름 |
| `settlement_entries.reversal_of` | 원원장 항목이 없거나 다른 item의 항목을 가리킴 |
| `settlement_reservations.item_id`, `payout_id` | 대응하는 항목·지급이 없음 |
| `payout_jobs.payout_id` | 대응하는 `payouts`가 없음 |

## 선택 이유와 대안

같은 DB 안에서는 FK의 일반적인 단점이 작습니다. 금융 이력을 삭제하지 않으므로 cascade나 삭제 순서 문제도 거의 없습니다. 그래도 이 설계에서는 FK의 비용이 가장 민감한 구간에 몰리고, FK가 지키는 참조 존재를 정상 경로는 쓰기 흐름과 삭제 금지 정책이 보장하며 우회 경로는 대조로 사후 탐지할 수 있어 FK를 두지 않습니다.

- 잠금 충돌: 다중 행 전이를 행 잠금과 조건부 갱신으로 보호합니다([트랜잭션과 관계](../data-model.md#트랜잭션과-관계)). PostgreSQL FK 검사가 거는 부모 행의 `FOR KEY SHARE`는 `FOR UPDATE`와 충돌합니다. 따라서 항목·지급을 잠근 동안 다른 트랜잭션의 원장·예약 INSERT가 대기하고, 잠금 순서가 엇갈리면 데드락이 생길 수 있습니다. 둘 이상의 트랜잭션이 같은 지급을 동시에 참조하면 그 부모 행에 공유 잠금이 겹쳐 MultiXact 부하가 생길 수 있습니다. 한 트랜잭션이 많은 항목의 `payout_id`를 같은 지급으로 채우는 것만으로는 생기지 않습니다. 이 구간은 환불/지급 경합과 부하 시험의 핵심 측정 대상입니다.
- 작은 추가 보장: FK는 자식 행이 존재하는 부모 행을 가리킨다는 것만 보장하며, 없는 부모를 가리키는 쓰기와 자식이 남은 부모의 삭제를 막습니다. 이 설계에서 두 경우는 다음 수단이 맡으므로 FK가 추가로 막는 것은 쓰기 흐름을 우회한 잘못된 쓰기를 커밋 시점에 거부하는 것뿐입니다.

| FK가 막는 경우 | 대신 맡는 수단 |
| --- | --- |
| 환불·지급 예약의 `item_id` | 같은 트랜잭션에서 항목 상태를 조건부 갱신(예: `PAYABLE`→`REFUND_RESERVED`)한 뒤 예약을 저장합니다. 항목이 없으면 갱신이 0건이라 예약 전에 중단됩니다. |
| 원장의 `item_id` | E·M·P·B를 항목에서 읽어야 원장 금액을 만들 수 있어 항목 없이 쓸 수 없습니다. |
| 원장의 `reversal_of` | 원원장 항목을 읽어 반대 부호 금액을 만듭니다. `UNIQUE(reversal_of)`가 중복 상쇄를 막습니다. |
| 지급의 `batch_id`, 지급 작업의 `payout_id`, 항목의 `payout_id` | 배치·지급·지급 작업·항목 선점을 한 트랜잭션에 원자 저장해 함께 커밋되거나 함께 롤백됩니다. |
| 자식이 남은 부모의 삭제 | 정산 이력은 삭제하지 않고 상태 전이와 정정·상쇄 기록으로 보존하므로 부모가 사라지지 않습니다. |
| 위 흐름을 우회한 수동 정정·배치 보정·잘못된 ID 전달 | 쓰기 시점에는 막지 못하고 결정의 내부 참조 대조로 사후 탐지합니다. |
- 대조가 더 넓게 검사: 단일 ID FK는 참조 대상의 존재만 보장합니다. seller_id·payment_id 일치는 부모에 `UNIQUE(id, seller_id)` 같은 제약을 두고 복합 FK를 걸면 표현할 수 있지만, 부모마다 추가 UNIQUE 인덱스가 필요하고 FK 검사의 잠금 비용은 그대로 남습니다. 대조 쿼리는 스키마를 바꾸지 않고 존재와 일치를 함께 검사합니다.
- 규칙 일관성: 서비스 간과 내부를 같은 규칙으로 두면 리뷰마다 FK 허용 여부를 판단하지 않아도 되고, 서비스마다 기준이 갈라지지 않습니다.

| 검토한 안 | 판단 |
| --- | --- |
| 같은 서비스 내부 FK 전면 허용 | 고아 참조를 즉시 막지만 행 잠금 경합·배치 갱신 부하와 정책 변경 비용이 있어 보류 |
| 추가 전용 금융 테이블만 FK 허용 | 범위는 좁지만 원장·예약 INSERT가 잠금 경합 구간과 겹치고 규칙이 둘로 나뉘어 보류 |
| 애플리케이션 검증만 사용 | 우회 경로의 버그를 탐지할 수 없어 보류 |
| FK 미사용 + 내부 참조 대조 | 경합 구간에 비용을 더하지 않고, 이미 계획된 대조에 항목만 추가하면 되므로 채택 |

JPA 연관관계를 쓰면 지연 로딩·N+1·의도하지 않은 cascade와 dirty checking이 행 잠금 범위와 쓰기 대상을 흐리므로 식별자 참조를 유지합니다. 같은 애그리거트로 볼 수 있는 `settlement_items`와 `settlement_reservations`의 묶음 여부는 구현 때 별도로 검토합니다. 조회 화면의 결합은 조회 전용 쿼리로 처리합니다.

## 감수하는 비용과 검증

고아 참조를 쓰기 시점에 막지 못하고 대조를 실행할 때 발견합니다. 그 사이 잘못된 참조가 다른 처리에 쓰일 수 있습니다. 서비스마다 내부 대조 쿼리를 구현하고 관리해야 합니다. FK의 비용은 핵심 흐름을 단순화한 PostgreSQL 18.3 SQL 실험으로만 확인했습니다. 배치 배정 시간 중앙값은 항목 1,000개에서 FK 없음 14.6ms·FK 있음 26.4ms, 10,000개에서 204.1ms·327.8ms였고, 잠금 통제 사례에서 FK 검사로 인한 대기·타임아웃·데드락이 재현됐습니다. 같은 실험에서 부모 검증을 우회한 쓰기는 FK만 차단했습니다. 실제 앱의 운영 성능을 보장하는 결과는 아닙니다.

- 대조: 부하 시험 종료 후와 장애 시나리오의 정합 복구 후 위 대조를 실행하고 0건을 확인합니다. Settlement는 매일 10:30 KST에도 자기 DB의 위 참조를 검사합니다. 일일 검사 범위와 전달 대기·결함 구분은 [정산 대조 결정](0007-settlement-batch-scope-and-schedule.md#d6-정산-대조)을 따르며, 다른 서비스 DB를 직접 조회하지 않습니다. 통합 테스트에서도 같은 쿼리로 검사합니다.
- 쓰기 흐름: 예약·원장·지급 작업 생성 전에 부모 행을 같은 트랜잭션에서 잠그고 읽는지 리뷰와 테스트로 확인합니다.
- 재검토 조건: 구현 결과 `FOR UPDATE`를 거의 쓰지 않고 낙관적 잠금·조건부 갱신으로 정리될 때, 부모 조회를 우회하는 수동 정정·배치 보정 경로가 생길 때, 대조에서 내부 고아 참조가 실제로 발견될 때 FK 도입을 다시 검토합니다.

이 문서는 설계 판단이며 문서 검사나 리뷰가 실제 DB 경합·정합성 검증을 대신하지 않습니다.
