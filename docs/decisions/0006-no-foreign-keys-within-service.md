# 같은 서비스 내부에서도 FK constraint 미사용 유지

- 상태: 제안·팀 검토 중
- 제안일: 2026-10-27
- 범위: 같은 서비스 DB 안의 테이블 간 FK constraint, JPA 연관관계 매핑, 내부 참조 정합성 대조. Settlement를 기준으로 검토하고 다른 서비스에도 같은 기준을 적용

## 결정

서비스 간뿐 아니라 **같은 서비스 내부에서도 FK constraint를 두지 않는** [기존 정책](../migrations.md#데이터-보존과-제약-조건)을 유지합니다. 대신 FK가 막았을 고아 참조를 [금액 대조](0002-performance-and-integrity-metrics.md#금액-불일치)와 같은 시점에 실행하는 **서비스 내부 참조 대조**로 탐지합니다. 엔티티 간 참조는 JPA 연관관계가 아닌 식별자 값으로 둡니다. 저장 구조는 [데이터 모델](../data-model.md), 대조 시점과 완료 조건은 [측정 지표 결정](0002-performance-and-integrity-metrics.md)이 소유합니다. migration과 대조 쿼리는 아직 구현 전입니다.

Settlement의 내부 대조 대상은 다음과 같습니다. 완료 조건은 모든 항목 0건입니다.

| 대조 | 고아·불일치 조건 |
| --- | --- |
| `payouts.batch_id` | 대응하는 `settlement_batches`가 없거나 seller_id가 다름 |
| `settlement_items.payout_id` | 대응하는 `payouts`가 없거나 seller_id가 다름 |
| `settlement_entries.item_id` | 대응하는 `settlement_items`가 없거나 payment_id가 다름 |
| `settlement_entries.reversal_of` | 원원장 항목이 없거나 다른 item의 항목을 가리킴 |
| `settlement_reservations.item_id`, `payout_id` | 대응하는 항목·지급이 없음 |
| `payout_jobs.payout_id` | 대응하는 `payouts`가 없음 |

## 선택 이유와 대안

같은 DB 안에서는 FK의 일반적인 단점이 작습니다. 금융 이력을 삭제하지 않으므로 cascade나 삭제 순서 문제도 거의 없습니다. 그래도 이 설계에서는 FK의 비용이 가장 민감한 구간에 몰리고, 얻는 보장은 다른 수단으로 대체할 수 있어 FK를 두지 않습니다.

- 잠금 충돌: 다중 행 전이를 행 잠금과 조건부 갱신으로 보호합니다([트랜잭션과 관계](../data-model.md#트랜잭션과-관계)). PostgreSQL FK 검사가 거는 부모 행의 `FOR KEY SHARE`는 `FOR UPDATE`와 충돌합니다. 따라서 항목·지급을 잠근 동안 다른 트랜잭션의 원장·예약 INSERT가 대기하고, 잠금 순서가 엇갈리면 데드락이 생길 수 있습니다. 배치가 많은 항목의 `payout_id`를 같은 지급으로 채우면 한 부모 행에 공유 잠금이 몰려 MultiXact 부하가 생길 수 있습니다. 이 구간은 환불/지급 경합과 부하 시험의 핵심 측정 대상입니다.
- 작은 추가 보장: 예약·원장·지급 작업은 업무상 부모 행의 상태와 금액을 잠그고 읽은 뒤 생성합니다. 이 흐름을 지키면 고아 참조가 생기지 않으므로 FK가 추가로 막는 것은 이 흐름을 우회한 버그뿐입니다.
- 대조가 더 넓게 검사: FK는 참조 대상의 존재만 보장합니다. 대조 쿼리는 seller_id·payment_id 일치처럼 FK로 표현할 수 없는 관계까지 검사합니다.
- 규칙 일관성: 서비스 간과 내부를 같은 규칙으로 두면 리뷰마다 FK 허용 여부를 판단하지 않아도 되고, 서비스마다 기준이 갈라지지 않습니다.

| 검토한 안 | 판단 |
| --- | --- |
| 같은 서비스 내부 FK 전면 허용 | 고아 참조를 즉시 막지만 행 잠금 경합·배치 갱신 부하와 정책 변경 비용이 있어 보류 |
| 추가 전용 금융 테이블만 FK 허용 | 범위는 좁지만 원장·예약 INSERT가 잠금 경합 구간과 겹치고 규칙이 둘로 나뉘어 보류 |
| 애플리케이션 검증만 사용 | 우회 경로의 버그를 탐지할 수 없어 보류 |
| FK 미사용 + 내부 참조 대조 | 경합 구간에 비용을 더하지 않고, 이미 계획된 대조에 항목만 추가하면 되므로 채택 제안 |

JPA 연관관계를 쓰면 지연 로딩·N+1·의도하지 않은 cascade와 dirty checking이 행 잠금 범위와 쓰기 대상을 흐리므로 식별자 참조를 유지합니다. 같은 애그리거트로 볼 수 있는 `settlement_items`와 `settlement_reservations`의 묶음 여부는 구현 때 별도로 검토합니다. 조회 화면의 결합은 조회 전용 쿼리로 처리합니다.

## 감수하는 비용과 검증

고아 참조를 쓰기 시점에 막지 못하고 대조를 실행할 때 발견합니다. 그 사이 잘못된 참조가 다른 처리에 쓰일 수 있습니다. 서비스마다 내부 대조 쿼리를 구현하고 관리해야 합니다. FK의 잠금 비용은 문서상 추론이며 실제 측정 결과가 아닙니다.

- 대조: 부하 시험 종료 후와 장애 시나리오의 정합 복구 후 위 대조를 실행하고 0건을 확인합니다. 통합 테스트에서도 같은 쿼리로 검사합니다.
- 쓰기 흐름: 예약·원장·지급 작업 생성 전에 부모 행을 같은 트랜잭션에서 잠그고 읽는지 리뷰와 테스트로 확인합니다.
- 재검토 조건: 구현 결과 `FOR UPDATE`를 거의 쓰지 않고 낙관적 잠금·조건부 갱신으로 정리될 때, 부모 조회를 우회하는 수동 정정·배치 보정 경로가 생길 때, 대조에서 내부 고아 참조가 실제로 발견될 때 FK 도입을 다시 검토합니다.

이 문서는 설계 판단이며 문서 검사나 리뷰가 실제 DB 경합·정합성 검증을 대신하지 않습니다.
