# 로그인·비밀번호 복구 요청 제한 정책 제안

- 상태: 제안·미확정
- 범위: 구매자·판매자 로그인 및 비밀번호 복구 요청의 계정별 요청 한도

## 요약 제안

| 작업 | 계정별 한도 | 고정 시간창 | 초과 시 동작 |
| --- | ---: | ---: | --- |
| 로그인 | 5회 | 15분 | `429`와 남은 시간의 `Retry-After` 반환 |
| 비밀번호 복구 요청 | 3회 | 1시간 | `429`와 남은 시간의 `Retry-After` 반환 |

이 수치는 프로젝트에 적용할 초기 기본값 제안입니다. 보안 표준값이나 실제 사용자 트래픽으로 검증된 최적값을 뜻하지 않습니다. 제한 방식·저장 위치·오류 형식은 기존 [인증·공통 API 정책](../policies.md#로그인복구-요청-제한)을 그대로 따르고, 이 문서에서는 한도와 시간창을 구체화합니다.

## 적용 대상과 카운터 분리

요청 제한 대상은 다음 세 경로입니다.

- `POST /api/buyer-sessions`
- `POST /api/seller-sessions`
- `POST /api/password-reset-requests`

로그인 한도는 계정 종류와 정규화한 이메일별로 적용합니다. 구매자 로그인과 판매자 로그인은 별도 카운터를 사용합니다. 복구 요청도 계정 종류별로 구분하고, 로그인과 복구 요청의 카운터는 서로 공유하지 않습니다. 따라서 한 작업의 요청이 다른 작업의 허용량을 소진시키지 않습니다.

정규화·키 구성·Redis 원자 갱신은 [인증·공통 API 정책](../policies.md#로그인복구-요청-제한)의 기존 규칙을 따릅니다. 카운터 키와 로그에는 이메일 원문을 남기지 않으며, 계정 존재 여부도 카운터 선택 기준으로 사용하지 않습니다.

## 요청 집계와 시간창

- 요청 본문의 형식 검증을 먼저 수행합니다. 해당 작업에 필요한 필드가 형식·범위 검증을 통과한 요청만 카운트합니다. 잘못된 JSON이나 형식이 유효하지 않은 입력은 한도를 소진하지 않습니다.
- 유효한 로그인 요청은 비밀번호가 맞는지와 관계없이 카운트합니다. 성공한 로그인도 포함하며, 로그인 성공으로 카운터를 초기화하지 않습니다. 이는 실패한 비밀번호 시도만 세는 계정 잠금과 구분되는 요청량 제한입니다.
- 계정이 존재하는지와 관계없이 같은 식별자·작업·계정 종류에는 같은 카운터 규칙을 적용합니다. 자격 검증 또는 계정 조회 결과를 제한 응답에 반영하지 않습니다.
- 첫 허용 요청 시 고정 시간창을 시작합니다. 로그인은 첫 요청부터 15분, 복구 요청은 첫 요청부터 1시간입니다. 창 안의 후속 요청은 만료 시각을 연장하지 않습니다.
- 한도 내 요청은 1회씩 차감합니다. 제안값 기준으로 로그인은 첫 다섯 요청까지, 복구 요청은 첫 세 요청까지 허용하며, 그 다음 요청부터 창이 만료될 때까지 제한합니다. 동시 요청도 전체 인스턴스에서 이 한도를 넘지 않도록 기존 정책의 원자적 카운터를 사용합니다.
- 창이 만료되면 제한이 자동 해제됩니다. 별도의 계정 잠금 상태, 인증 버전 변경, 세션 폐기 또는 운영자 해제 절차를 추가하지 않습니다.

## 응답과 복구 요청의 부작용

한도를 초과한 요청에는 공통 오류 형식의 `429 COMMON_RATE_LIMITED`와 양의 정수 초 단위 `Retry-After`를 반환합니다. 남은 시간이 초의 일부이면 올림합니다. 응답 본문과 상태는 계정 존재 여부에 따라 달라지지 않으며, 안내 문구는 “잠시 후 다시 시도해 주세요”를 사용합니다.

제한된 복구 요청은 새 토큰을 만들거나 이메일·문자 안내를 보내지 않습니다. 기존 복구 토큰을 폐기하거나 만료 시각을 바꾸지도 않습니다. 제한 검사를 Redis에서 확정할 수 없는 경우에는 기존 정책대로 인증 처리를 진행하지 않고 `503`을 반환합니다. 제한 저장소가 복구된 뒤에도 이전 요청을 자동 재생하지 않습니다.

## 수치 선정 이유와 감수하는 점

### 로그인: 5회/15분

다섯 번의 요청은 사용자가 비밀번호를 몇 차례 잘못 입력하거나 자격 증명 관리자를 다시 시도할 여지를 주면서, 같은 계정에 대한 짧은 시간의 반복 요청을 제한하는 출발값입니다. 15분 고정 창은 재시도 폭주가 계속되는 상황을 잠시 늦추고 해제 시점을 예측 가능하게 합니다.

요청 수를 성공·실패로 나누지 않는 것은 프로젝트의 기존 요청 제한 계약을 유지하기 위해서입니다. 이 방식은 짧은 시간에 정상 로그인을 여러 번 하는 사용자도 한도를 사용할 수 있다는 비용이 있습니다. 한도는 장기 계정 잠금이 아니며 시간창이 끝나면 자동으로 다시 시도할 수 있습니다.

### 비밀번호 복구: 3회/1시간

복구 요청은 알림 발송을 유발할 수 있으므로 로그인보다 적은 횟수로 제한하는 안을 제안합니다. 한 시간에 세 번은 메시지 지연이나 주소 입력 실수에 대응할 재시도 여지를 두면서 반복 발송을 억제하기 위한 시작값입니다. 실제 메시지 발송 비용이나 정상 요청 분포를 측정한 수치로 해석하지 않습니다.

### 계정별 집계의 범위

계정별 카운터는 출발 IP가 달라져도 같은 계정으로 향하는 요청을 함께 제한합니다. 반면 한 IP가 여러 계정을 대상으로 보내는 요청이나 공격자가 계정 식별자를 바꾸는 요청은 이 정책만으로 제한하지 않습니다. IP별 한도는 기존 정책에 정해져 있지 않으므로 이번 제안에 추가하지 않습니다. 다계정 자동화가 실제로 관측되면 공유 IP의 정상 사용자 오탐과 프록시 신뢰 경계를 확인한 뒤 별도 변경으로 검토합니다.

## 적용 전 확인과 재검토

이 제안값을 채택하기 전에는 로그인과 복구 각각의 기본 설정값에 반영하고, API 명세와 운영 설정이 같은 값인지 확인합니다. 구현 검증에서는 허용 한도 직전·마지막 허용 요청·첫 초과 요청, 시간창 만료, 동시 요청, 다중 인스턴스 공유, 계정 존재·미존재의 응답 동일성, Redis 오류 시 부작용 차단을 확인합니다.

초기 적용 뒤에는 제한 응답 수와 비율, 복구 안내 요청량, 정상 사용자의 제한 문의, Redis 지연·오류를 함께 관찰합니다. 정상 사용자의 반복 제한이나 안내 발송 남용이 확인되면 해당 자료를 근거로 횟수 또는 시간창을 조정하고, 결정 문서·[인증 정책](../policies.md#로그인복구-요청-제한)·API 명세의 값을 함께 갱신합니다. 측정 전에는 제한이 공격을 막는다고 단정하거나 수치를 최적값으로 표시하지 않습니다.
