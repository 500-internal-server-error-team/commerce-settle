# Redis 기반 사용자 세션 선택

- 상태: 채택·구현 예정
- 결정일: 2026-10-27
- 범위: 구매자·판매자 로그인 세션과 Gateway 인증 경계

사용자 로그인 세션의 원본 저장소를 PostgreSQL에서 Redis로 바꿉니다. 고정 30분 만료와 중앙 폐기를 유지하면서 Gateway의 반복 인증 경로를 계정 DB에서 분리하기 위한 선택입니다. 계정·비밀번호·복구 토큰·인증 버전은 PostgreSQL에 둡니다. 인증 코드·ACL·장애 복구는 구현 전이며 성능 개선 수치는 아직 없습니다.

## 문제와 결정 과정

기존 문서는 PostgreSQL에 세션 해시를 저장하는 안이었습니다. 기준 커밋은 `09547e81275ed15120858267951b7ec45f48f661`의 `docs/policies.md`이며, 해당 문서에는 DB 세션을 고른 성능 실험이나 결정 과정이 기록돼 있지 않습니다.

이번 선택은 다음 요구를 함께 검토한 결과입니다.

1. 구매자·판매자 신원을 구분하고 로그아웃·계정 정지·비밀번호 변경 뒤 이전 세션을 차단해야 합니다.
2. Gateway가 매 보호 요청을 인증하되 커머스의 인증 HTTP API를 반복 호출하거나 커머스 DB를 직접 읽지 않아야 합니다. 이미 인증한 내부 요청에서는 백엔드가 발신자·역할·소유권을 확인합니다.
3. 프로젝트에는 Redis 실행 기반이 있고, [결제 확정 1,000 TPS·15분](../../README.md#성능-목표와-검증)을 시험할 계획입니다. 인증 부하도 함께 측정해야 합니다.

초기 DB 세션 안과 아래 대안을 비교해 Redis를 채택했습니다.

## 대안과 선택 이유

| 대안 | 이 프로젝트에서 얻는 점 | 감수할 비용과 판단 |
| --- | --- | --- |
| PostgreSQL 세션 | 계정·비밀번호 변경과 세션 폐기를 한 DB 트랜잭션으로 처리하기 쉽고 운영 저장소를 추가하지 않음 | 만료 판정·만료 행 정리와 반복 세션 조회 경로가 필요함. 충분히 유효한 대안이며 성능이 부족하다고 확인된 것은 아님 |
| Redis 세션 | TTL로 세션을 정리하고 여러 Gateway 인스턴스가 같은 발급·폐기 상태를 확인함. 인증 조회를 계정 DB 경로에서 분리 | Redis 가용성·메모리·ACL·DB와의 폐기 일관성·복구를 책임져야 함. 이 비용을 감수하고 채택 |
| 서명 JWT만 검증 | 저장소 조회 없이 서명과 만료를 확인할 수 있음 | 만료 전 즉시 폐기 요구에는 [별도 상태 확인](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)이 필요함. 현재 요구에는 Redis 세션을 우선 |
| JWT와 서버 상태 확인 | 토큰별 폐기 목록과 계정 인증 버전을 조회하면 현재 세션·계정 전체 폐기를 적용할 수 있음 | 매 요청 저장소 조회와 JWT 서명·클레임 검증을 함께 관리해야 함. 현재 Gateway 경계에서는 불투명 세션을 우선 |

Redis가 편한 부분은 **짧은 수명의 인증 상태를 공유하고 만료·삭제하는 경로**입니다. TTL은 [Redis의 키 만료 기능](https://redis.io/docs/latest/commands/expire/)을 사용하되 서버의 expiresAt 검사도 유지합니다. DB 역시 expiresAt으로 정확히 만료를 판정할 수 있으며, 정리 전 행이 남는다고 유효한 세션이 되는 것은 아닙니다.

Gateway는 공유 인증 상태를 Redis에서 직접 조회하도록 설계했습니다. 이로써 커머스 인증 HTTP 호출과 계정 DB의 세션 조회를 줄일 수 있지만 매 보호 요청의 Redis 조회는 필요합니다. 속도 개선 폭은 구현 후 같은 조건에서 측정합니다.

### JWT 대신 불투명 세션을 선택한 이유

**이 프로젝트는 저장소 조회 없는 인증보다 만료 전 폐기를 우선합니다.** JWT는 사용자 ID·만료 시각 같은 정보를 담는 토큰 형식이고, Bearer는 토큰을 가진 사람이 그 토큰으로 인증받는 방식입니다. JWT와 임의의 세션 토큰 모두 `Authorization: Bearer <token>`으로 보낼 수 있습니다. 여기서는 토큰 자체에 사용자 정보를 담지 않고, 토큰의 해시로 Redis의 로그인 상태를 찾습니다. [Bearer 표준](https://www.rfc-editor.org/rfc/rfc6750#section-1.2)과 [JWT 표준](https://www.rfc-editor.org/rfc/rfc7519#section-3)을 참고합니다.

설명용으로 30분짜리 토큰을 발급하고 5분 뒤 로그아웃한 경우를 비교합니다. 서버 상태를 확인하지 않는 JWT는 서명·만료 등 토큰 검증을 통과하므로, 유출된 토큰도 남은 25분 동안 사용될 수 있습니다. 클라이언트에서 토큰을 지우거나 갱신 토큰(refresh token)만 폐기해도 이미 발급한 접근 토큰(access token)은 무효화되지 않습니다. 현재 세션 설계는 Redis에서 해당 세션을 삭제하고, 이후 Gateway가 검증하는 요청을 거절합니다. 이미 인증을 마친 진행 중 요청까지 취소한다는 뜻은 아닙니다.

선택 기준은 다음과 같습니다.

1. **현재 세션과 계정 전체의 폐기를 구분합니다.** 로그아웃은 해당 세션만 삭제하고, 비밀번호 재설정·계정 정지/삭제는 계정별 인증 가드와 버전으로 이전 세션 전체를 차단합니다. 세부 순서와 실패 처리는 [폐기 정책](../policies.md#폐기와-저장소-복구)을 따릅니다.
2. **JWT에 서버 상태 확인을 더하는 비용을 피합니다.** JWT도 폐기 목록과 계정 인증 버전 조회를 붙이면 같은 요구를 충족할 수 있습니다. 다만 현재 요구대로 매 요청 폐기 여부를 확인하면 저장소 조회를 없애는 이점이 사라집니다. 이 프로젝트는 서버 상태를 확인하는 경로에 JWT 발급·서명·클레임 검증을 더하지 않고 불투명 토큰을 사용합니다.
3. **현재 서비스 경계에 맞춥니다.** 사용자 토큰은 Gateway에서만 검증하고, 백엔드는 Gateway 호출 자격·검증된 신원과 역할·소유권을 검사합니다. 각 서비스가 사용자 JWT를 독립 검증할 필요가 없는 구조이므로, 서비스가 여러 개라는 이유만으로 JWT를 도입하지 않습니다.

이 선택은 JWT보다 빠르거나 항상 안전하다는 측정 결과가 아닙니다. 저장소 없이 검증하는 JWT의 이점 대신 매 요청 Redis 조회와 인증 저장소 장애 시 차단을 감수합니다. JWT와 서버 상태 확인도 유효한 대안이며, 아래 검증 결과와 요구가 달라지면 함께 재검토합니다.

## 구현 계약과 감수하는 비용

- 커머스는 DB에서 자격을 검증하고 Redis에 불투명 토큰의 해시·계정 종류/ID·인증 버전·고정 만료를 저장합니다. Gateway는 세션과 계정별 가드를 확인합니다. 상세 계약은 [정책](../policies.md#인증공통-api-기준)과 [데이터 모델](../data-model.md#redis-인증-데이터)이 소유합니다.
- Gateway는 외부 신원 헤더를 제거하고 대상 서비스 전용 자격과 검증한 신원을 전달합니다. 백엔드는 발신자·역할·소유권을 확인합니다. 내부 서비스·운영자 자격과 Worker 실행은 사용자 세션과 구분합니다. [신원 전달과 4계층 배치](../architecture.md#사용자-인증과-내부-신원-전달)를 따릅니다.
- DB 계정 변경과 Redis 폐기는 분산된 변경입니다. 가드 선차단·DB 인증 버전·감사 기록·재조정으로 실패를 처리합니다. Redis 장애 때 보호 요청은 503이며 DB 세션으로 자동 전환하지 않습니다. 이 복구 복잡성은 DB 세션보다 늘어난 비용입니다.
- Redis 복구 후 이전 폐기 상태가 사라질 가능성을 고려합니다. [AOF 영속화](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)만으로 폐기 보존을 보장하지 않고 [인증 세대 교체·재로그인 절차](../development.md#redis-세션-검증과-복구)를 적용합니다. 일시 단절에도 사용자 인증을 차단하고 운영 복구를 거치는 가용성 비용이 있습니다.
- 현재 단일 Redis·공용 캐시 구성에서는 메모리와 장애 영향이 공유됩니다. ACL 구현, 사용량 관측과 인증 영역 접근 제한이 필요합니다. 별도 인증 서버·새 업무 서비스·DB 세션 사본은 추가하지 않습니다.

## 구현 후 검증과 재검토

고정 만료, 동시 로그인·폐기, 두 저장소의 변경 실패와 복구, Gateway 우회·신원 위조는 [Redis 세션 검증과 복구](../development.md#redis-세션-검증과-복구)의 시나리오로 확인합니다. 계정 정지·삭제·재활성화 API는 현재 범위에 없으며, 시험용 응용 유즈케이스도 같은 폐기 절차를 따라야 합니다.

구현 후에는 같은 장비·인스턴스 수·데이터·부하에서 인증 평균/p95/p99·오류율, Redis 지연·메모리, 계정 DB 쿼리/커넥션, 업무 완료 처리량을 기록합니다. 계정 DB의 반복 세션 조회가 제거됐는지 확인하고, 가능하면 DB 세션 기준 구현과 비교합니다. 비교 구현이 없으면 DB 대비 몇 배 개선이라는 수치를 쓰지 않습니다. API 접수 응답과 결제 확정 TPS는 따로 측정합니다.

운영 복구 시간이 목표를 벗어나거나 인증 조회가 병목이 되면 DB 세션을 포함해 재검토합니다. Redis Cluster·자동 failover를 도입할 때도 현재 단일 노드의 키·원자 연산·인증 세대 복구 가정을 다시 검토합니다.
