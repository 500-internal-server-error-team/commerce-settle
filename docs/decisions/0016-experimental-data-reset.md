# 실험 환경의 데이터 초기화와 스키마 적용

- 결정일: 2026-11-12
- 상태: 채택
- 범위: 로컬·공유 AWS의 개발·시연·부하 시험 데이터와 스키마 변경
- 연결 문서: [DB 정책](../migrations.md), [개발 환경](../development.md#종료재실행초기화)

## 배경

이 프로젝트의 배포 목적은 기능·정합성을 검증하고 병목 개선 전후를 반복 측정하는 것입니다. 현재 다루는 거래는 모의 금융과 시험 데이터이며, 이전 버전의 업무 데이터를 유지하며 서비스하는 것은 목표가 아닙니다.

기존 DB를 계속 유지하면 컬럼·인덱스 변경마다 업그레이드 SQL, 적용 순서, 구버전 호환성과 데이터 보존 검증이 필요합니다. 예를 들어 PR #320·#321·#322는 SQL 부하 개선에 기존 DB용 업그레이드 파일 세 개를 추가합니다. 시험 데이터를 다시 만들 수 있는 현재 단계에서는 이 유지 비용을 감수할 필요가 없습니다.

## 결정

스키마가 바뀌거나 새 독립 실험을 시작할 때는 해당 실험 환경의 데이터를 초기화하고, 서비스별 초기 SQL과 같은 시험 데이터 준비 절차로 다시 구성합니다. 버전별 증분 마이그레이션과 이전 스키마 호환 경로는 추가하지 않습니다.

초기화 대상·순서와 시험 중 데이터 보존의 경계는 [DB 정책](../migrations.md#최초-배포와-기존-데이터-변경)이 소유합니다. 결과 비교에 필요한 입력 조건·코드/설정 버전·지표·정합성 대조 결과는 초기화 대상 밖에 남깁니다.

이 결정은 [ADR 0013의 시험 데이터 초기화 제안](0013-ec2-deployment-and-load-test.md#시험-데이터-초기화-제안)과 [ADR 0015의 실험 간 데이터 격리](0015-parallelism-decision-and-load-scope.md#5-실험-간-데이터-격리)를 대체합니다.

## 검토한 대안

| 대안 | 판단 |
| --- | --- |
| 기존 DB를 유지하며 변경마다 업그레이드 SQL 추가 | 이전 버전 데이터 보존이 목표가 아니어서 적용·호환성·검증 부담을 채택하지 않습니다 |
| 초기 SQL로 환경을 재생성 | 채택. 같은 초기 조건을 준비할 수 있고 스키마 적용 경로를 하나로 유지합니다 |
| DB만 초기화 | 이전 Kafka 메시지·소비 위치와 Redis 상태가 남아 새 DB와 섞이므로 채택하지 않습니다 |

## 결과와 한계

- 금융 원장·멱등 처리·장애 복구의 정합성은 한 시험 안에서 계속 검증합니다. 초기화로 실패를 성공 처리하지 않습니다.
- 장애 복구·재시작·누적 데이터 시험은 검증이 끝날 때까지 같은 데이터를 사용합니다. 이 보존은 버전별 데이터 업그레이드 지원을 요구하지 않습니다.
- 초기화는 실행자가 선택한 실험 환경에 적용합니다. 앱 기동·재시작마다 자동 삭제하는 기능은 추가하지 않습니다.
- 실제 이용자 데이터를 받거나 이전 버전 데이터의 연속성이 요구되면, 그때 별도 ADR로 데이터 보존과 마이그레이션 도입을 결정합니다.
