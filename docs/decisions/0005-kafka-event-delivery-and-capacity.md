## 결정

Kafka는 주문·결제·정산·알림의 후속 작업을 전달하고 장애 뒤 재개하기 위해 사용합니다. [결제 확정 TPS 목표](../../README.md#성능-목표와-검증)를 토픽별 이벤트 유입량과 소비자별 처리량으로 환산하고, 정상 지연·적체 증가·장애 후 배출·금액 정합성을 함께 검증합니다. Kafka 사용이나 접수 응답만으로 처리량 향상·금융 완료를 주장하지 않습니다.

기존 생산자별 토픽과 책임별 Consumer 그룹, 주문의 `orderId`·금융 거래의 `paymentId` 중심 key를 유지합니다. 이벤트 종류·payload·key·그룹은 [API 이벤트 계약](../api.md#이벤트-연동), 금액·상태·재시도 상한은 [업무 정책](../policies.md#정산재처리), 저장 제약은 [메시지 데이터 모델](../data-model.md#메시지멱등성감사)이 소유합니다. 앱·DB·이벤트 이름과 금액·환불·지급 정책은 유지하며, 아래에 전달·실행의 초기 운영값과 신규 접수 제한을 정합니다.

현재는 단일 브로커와 연결 smoke만 있는 실행 기반입니다. 아래 업무 전달·복구·성능 시험은 아직 구현·검증 전입니다.

## 이벤트 구분과 토픽 경계

출처를 식별하는 것, 소비자가 처리할 업무를 고르는 것, 메시지를 분산하는 것은 각각 다른 결정입니다. 예를 들어 `PaymentConfirmed`와 `RefundAccepted`는 모두 Payment가 발행하지만 Settlement가 처리할 이벤트는 같지 않습니다. 서비스 이름만으로 처리기를 선택하면 이 차이를 표현할 수 없습니다.

| 판단 | 현재 기준 | 이유 |
| --- | --- | --- |
| 어느 업무 소유자가 발행했는가 | API에 고정한 생산자별 원본 토픽 | 현재 Kafka 내부 연동에서 발신 업무를 구분할 수 있음 |
| 무엇을 어떻게 처리하는가 | 구독 토픽에서 `eventType`·`eventVersion`과 payload 계약을 함께 확인 | 같은 발행자의 서로 다른 사건·명령을 구분하고 잘못된 토픽의 이벤트도 거절 |
| 어느 거래의 순서를 다루는가 | 이벤트별 `orderId`·`paymentId` 등 기존 key | 서비스 전체를 한 key에 묶지 않고 거래 단위로 분산 |
| 어느 처리 책임이 독립적으로 받는가 | 책임별 Consumer 그룹 | 결제 확정을 커머스와 정산이 모두 받아야 하므로 같은 그룹에서 나눠 받지 않음 |

토픽 이름은 발행 업무의 공개 계약으로 취급합니다. 실행 인스턴스 이름·배포 버전에서 자동 생성하거나 서비스 내부 리팩터링만으로 바꾸지 않습니다. 구체적인 토픽·이벤트·key·그룹의 대응은 API 명세 한 곳에서 관리합니다.

### 토픽 구성의 대안

| 구성 | 장점 | 비용과 판단 |
| --- | --- | --- |
| 공용 토픽 하나 + `serviceId` 필터 | 토픽 수가 적고 발행 경로가 단순함 | 모든 그룹이 무관한 레코드를 읽고 걸러야 하며 보존·권한·부하를 함께 관리. 현재는 제외 |
| 생산자별 토픽 + 이벤트 종류로 처리 | 기존 세 업무 소유권·API 계약을 유지하며 서비스별 운영 경계를 둘 수 있음 | 같은 생산자의 무관한 이벤트를 읽는 비용은 남음. 현재 채택하고 그룹별 비용을 측정 |
| 결제·환불·마일리지 등 업무 스트림별 토픽 | 필요한 스트림만 구독하고 보존·권한·부하를 따로 관리할 수 있음 | 토픽과 구독 조합이 늘고 같은 거래도 여러 토픽의 순서 차이를 처리해야 함. 독립 운영 요구나 측정된 소비 병목이 생기면 비교 |
| 이벤트 종류마다 토픽 | 특정 이벤트만 구독하고 개별 정책을 적용하기 쉬움 | 이벤트 증가에 따라 토픽·배포·호환성 관리가 늘어남. 종류가 다르다는 이유만으로는 채택하지 않음 |

일반 Kafka Consumer는 토픽을 구독합니다. `serviceId`나 이벤트 종류를 헤더에 넣는 것만으로 브로커가 필요한 레코드만 골라 보내지는 않습니다. 별도 라우터를 추가할 근거도 현재 없으므로 소비자 필터 비용을 측정에 포함합니다. [Kafka 구독 API](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#subscribe(java.util.Collection))

### 출처 정보와 메시지 형식의 대안

토픽 구성을 바꾸는 것과 이벤트 형식을 표준화하는 것은 별개입니다. CloudEvents도 생산자별 또는 업무 스트림별 토픽에 담을 수 있으며 그 자체로 토픽 분리·순서·금융 멱등성을 해결하지 않습니다.

| 형식 | 장점 | 비용과 판단 |
| --- | --- | --- |
| 기존 Envelope + 원본 토픽 문맥 | 현재 `eventId`·종류·버전·집계·payload 계약을 유지. 출처를 중복 저장하지 않음 | Kafka 밖으로 본문만 옮기면 출처 문맥이 빠짐. 현재 내부 연동에서는 채택하고 격리·재처리 시 원본 위치를 보존 |
| 자체 출처 필드·헤더 추가 | 토픽과 분리된 논리 출처를 이벤트와 함께 전달 가능 | 발행 소유자·토픽과의 일치, 재전달 시 불변성, 누락·충돌·호환성 규칙이 추가됨. 현재 필요성이 없어 보류 |
| CloudEvents 채택 | `source`·`type`·`id` 등 표준 문맥과 Kafka 바인딩을 외부 도구·다른 전송 방식과 공유 가능 | 기존 Envelope와의 매핑·전환·소비자 호환성 검증이 필요함. 외부 소비자나 여러 전송 방식에서 표준 문맥이 필요해지면 자체 필드 추가와 함께 재검토 |

현재 OpenAPI의 Envelope 21종은 미정의 필드를 허용하지 않습니다. `sourceService` 하나를 본문에 추가하는 것도 소비자와 공유하는 계약 변경입니다. 지금은 필드·헤더를 추가하지 않고, DLT·격리·재처리 기록에 원본 topic·partition·offset과 원래 이벤트 ID를 보존합니다. 출처 필드가 생기더라도 문자열 자체를 발행 권한의 증거로 사용하지 않습니다.

CloudEvents를 채택한다면 `source`는 논리 출처, `type`은 사건 종류, `source+id`는 이벤트 유일성으로 구분합니다. Kafka 바인딩은 속성을 헤더에 두는 방식과 메타데이터·데이터를 본문에 함께 두는 방식을 제공하므로, `sourceService`를 붙인 자체 형식을 CloudEvents 준수라고 부르지 않습니다. [CloudEvents 명세](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)·[Kafka 바인딩](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/bindings/kafka-protocol-binding.md)

업무별 보존·권한·지연 목표가 달라지거나 무관한 이벤트의 읽기 비용이 소비 병목으로 확인되면 토픽 분리를 재검토합니다. 원본 토픽 문맥을 유지할 수 없는 외부 전달·통합이 필요하면 출처와 형식 표준화를 재검토합니다. 그때 ADR에는 선택·대안·전환 이유를, 필드명·필수 여부·헤더/본문 배치·예시는 API 이벤트 명세에 기록하고 관련 소비자와 검토합니다. Java 클래스·직렬화·발행 메서드는 해당 구현에서 정합니다.

## 안전한 전달과 실행

### Outbox와 Producer

첫 구현은 기존 PostgreSQL의 Outbox를 폴링하는 발행기로 시작합니다. 업무 상태와 Outbox를 함께 저장하고, 제한된 묶음과 동시 발행 수로 처리합니다. Kafka의 발행 성공 응답을 확인한 뒤에만 발행 완료와 `topic`·`partition`·`offset`·발행 시각을 같은 DB 트랜잭션으로 저장합니다. 발행 성공 직후 중단되면 원래 `eventId`로 재발행하므로 중복 전달을 허용하고 수신 측에서 막습니다. 위치가 없는 미발행·ack 후 저장 전 중단은 [대조 조회](../api.md#정산-대조-조회)에서 발행 대기로 포함하며, null 위치를 0으로 대체하지 않습니다. 재발행 위치가 달라져도 이미 저장한 원래 Inbox의 업무 처리 결과는 유지합니다.

Producer는 `acks=all`, `enable.idempotence=true`를 명시합니다. `retries>0`, `max.in.flight.requests.per.connection<=5`를 함께 지키고 `delivery.timeout.ms`로 클라이언트 재시도 시간을 제한합니다. Kafka 클라이언트 재시도와 Outbox·업무 재시도의 횟수·시간은 구분합니다. Producer 멱등성은 발행기 재시작 후 애플리케이션이 다시 보내는 이벤트나 외부 PG 실행의 중복까지 막지 않습니다. [Producer 설정](https://kafka.apache.org/42/configuration/producer-configs/)

같은 거래의 순서가 필요한 이벤트는 발행기 간 선점·동시 발행·임대 인계에서도 선행 이벤트를 추월하지 않도록 구현합니다. 같은 key만 사용하거나 UUID·생성 시각으로 정렬하는 것으로 순서를 보장했다고 보지 않습니다. 서로 다른 토픽·서비스·집계 사이의 순서는 가정하지 않고 선행 상태 대기와 업무 상태 전이로 보호합니다.

### Inbox와 Worker

Consumer는 자동 offset 커밋을 끄고, 처리에 필요한 Inbox·실행 작업 또는 로컬 업무 반영을 같은 DB 트랜잭션으로 저장한 뒤 offset을 커밋합니다. 병렬 처리에서도 아직 영속 저장하지 못한 앞 offset을 건너뛰어 커밋하지 않습니다. 저장 뒤 커밋 전에 중단되면 `consumer+eventId`와 업무 유일성으로 재전달을 수용합니다. 같은 ID에 다른 본문이 오면 충돌로 보존하고 자동 적용하지 않습니다.

PG·환불·지급 호출과 장시간 대기는 Worker가 맡습니다. 외부 호출 동안 DB 잠금을 유지하지 않고, 동시 실행 수·호출 시간·임대·상태 조건으로 보호합니다. Consumer 동시 실행 수와 Worker 동시 실행 수는 각각 측정하며 DB 연결 풀·잠금·외부 대역 처리 한도도 함께 확인합니다. Kafka offset 커밋은 금융 업무 완료를 뜻하지 않습니다. Kafka 트랜잭션도 외부 DB·PG와의 원자 처리를 대신하지 않습니다. [전달 보장의 범위](https://kafka.apache.org/42/design/design/)

| 실패 유형 | 처리 방향 |
| --- | --- |
| DB·통신의 일시 장애 | 제한된 재시도·소비 일시 정지. 영속 인계 전에는 offset 커밋 금지 |
| 선행 결제·원장 미도착 | 원본과 다음 재판정 시각을 Inbox `WAITING`으로 보존하고 로컬 재개 |
| 스키마 오류·본문 충돌·금액 불일치 | 소비자별 DLT 또는 수동 확인 상태에 원본 위치·실패 이유를 보존. 무한 재시도·자동 금융 보상 금지 |
| 외부 금융 결과 미확정 | 원래 PG·업무 키로 조회·재개. 시간 경과만으로 실패 확정·예약 해제 금지 |

DLT 발행이 확인되거나 같은 DB의 격리 기록이 커밋되기 전에는 원본 offset을 커밋하지 않습니다. DLT 발행 뒤 offset 커밋 전 중단으로 생긴 중복은 원본 topic·partition·offset으로 식별합니다. 자동 재시도 소진 뒤에도 원래 Inbox·Job·업무 키를 보존하고 운영 재처리는 해당 상태를 재개합니다. offset 되감기나 새 이벤트 ID 발급만으로 재처리를 대신하지 않습니다. 새 조회 모델의 전체 재구축은 별도 소비자·저장 대상으로 구분하고 기존 금융 작업을 다시 실행하지 않습니다.

## TPS를 이벤트 부하로 환산

로컬의 결제 확정 1,000 TPS·15분 목표는 실측 수요나 달성 결과가 아닙니다. 기존 [측정 지표 결정](0002-performance-and-integrity-metrics.md)의 처리량·구간별 지연·오류 분류·금액 대조를 재사용합니다. 배포 환경 API p99 3초 목표를 비동기 결제·원장 반영 목표로 확대하지 않습니다.

설명용으로 모든 신규 결제가 성공하고 각 이벤트를 한 번 발행하는 정상 흐름을 가정합니다.

| 구간 | 초기 발행 이벤트 | 결제 확정 1,000 TPS의 발행량 |
| --- | --- | --- |
| 커머스 생산자 토픽 | `OrderPaymentRequested` | 약 1,000건/초 |
| Payment 생산자 토픽 | `PaymentAccepted`, `PaymentConfirmed`, `PaymentNoticeRequested` | 약 3,000건/초 |
| 합계 | 성공 결제 초기 흐름 | 약 4,000건/초 |

지연된 구매확정·정산/지급 알림과 환불·거절·취소·재발행은 별도로 더합니다. 과거 거래의 구매확정 작업이나 재처리가 한꺼번에 실행되는 순간 부하도 포함합니다. 결제 성공 비율이 낮으면 같은 확정 TPS를 만들기 위한 주문 접수량은 더 커집니다.

`토픽 유입량 = 흐름별 초당 발생량 × 해당 토픽의 이벤트 수`를 합산합니다. 한 이벤트를 여러 그룹이 읽어도 발행량은 늘지 않지만 소비·전송·DB 처리 비용은 늘어납니다. 생산자별 토픽의 관심 없는 이벤트를 읽고 거르는 비용도 그룹별로 측정합니다.

메시지 평균·상위 크기, 토픽별 유입량, 그룹별 읽기/반영량, 재전달량, 압축률을 기록합니다. 평균 1kB를 가정한 4,000건/초는 약 4MB/초, 15분에 360만 메시지·3.6GB이며 복제·인덱스 등은 별도입니다. 이는 용량 계산 예시이고 실제 메시지 크기·상시 유입량을 측정한 값이 아닙니다.

## 파티션·복구·보존

### 파티션과 동시 실행

첫 구현은 원본 토픽당 파티션 3개·그룹별 인스턴스당 Consumer 1개로 시작합니다. 작은 부하에서 정합성을 먼저 확인한 뒤 파티션 3·6·12개와 Consumer 동시 실행 수를 비교합니다. 1,000 TPS에 고정 파티션 수를 대응시키지 않습니다. 토픽마다 가장 느린 필수 그룹의 실제 처리량을 기준으로 다음 식과 메시지 크기·키 편향을 함께 봅니다.

```text
필요 파티션 수 ≈ ceil(토픽 유입량 / (파티션당 측정 처리량 × 목표 사용률))
```

목표 사용률과 시험 조건은 결과를 보기 전에 정합니다. 일반 Consumer 그룹에서 한 파티션은 동시에 한 Consumer에 배정되므로 파티션 수가 소비 병렬도의 상한이지만, DB 작업과 Worker의 실행 능력은 별도입니다. 판매자 2만 곳의 균등 분산과 상위 1%에 결제 70%가 몰리는 기존 시나리오를 비교합니다. 금융 key를 `sellerId`로 바꿔 인기 판매자의 모든 거래를 한 파티션에 묶지 않습니다.

파티션 증설은 key 배정을 바꿀 수 있으므로 기존 메시지와 신규 메시지가 서로 다른 파티션에서 처리될 때도 상태 전이가 안전한지 검증합니다. 병목이 DB 잠금·연결 대기·외부 호출이면 해당 경로를 먼저 조정하며 파티션 증설을 해결책으로 단정하지 않습니다. [파티션과 증설](https://kafka.apache.org/42/operations/basic-kafka-operations/)

### 장애 후 배출

정상 유입률과 같은 처리 능력만 확보하면 장애 때 쌓인 작업을 따라잡을 수 없습니다. 같은 업무 단계의 건수 단위로 다음을 계산합니다.

```text
적체 B = 초당 유입량 λ × 중단 시간 D
복구에 필요한 초당 처리량 μ >= λ + B / 허용 배출 시간 T
```

예를 들어 원장 반영이 초당 1,000건 유입되는 동안 5분 멈추면 30만 건이 쌓입니다. 유입을 유지하며 재개 후 5분 안에 배출하려면 최소 약 2,000건/초의 반영 능력이 필요합니다. 실제 토픽 읽기량·재시도·편향과 여유 용량은 별도로 반영합니다.

정상 원장 반영 p99 5초 이내, 5분 중단 후 재개부터 5분 이내 배출을 초기 시험 후보로 둡니다. 원장 반영 구간은 결제 확정부터 Settlement DB 반영까지이며, 탐지·서비스 복구·정합 복구 시간의 정의는 기존 측정 ADR을 따릅니다. 이 수치는 운영 보장이나 측정 결과가 아니며 환경·메시지 구성과 함께 시험 전에 확정합니다. 변경하면 적용 시점과 이전 기준을 남기고 실패한 시험을 소급 통과시키지 않습니다.

Kafka lag와 함께 미발행 Outbox·대기 Inbox·실행 Job의 건수와 최장 나이, 원장 반영 지연을 봅니다. Kafka lag가 0이어도 DB 작업이 남아 있으면 정합 복구 완료가 아닙니다. 저장 공간·작업 한도에 접근하면 신규 접수를 제한하되 이미 접수한 금융 작업을 버리지 않습니다. 초기 제한값·재개 조건과 거절 응답은 아래 [신규 접수 제한과 재개](#신규-접수-제한과-재개)를 따릅니다.

### 브로커와 보존

로컬은 단일 브로커를 유지하고 재시작·적체 복구를 시험합니다. 브로커 장애 내성이 필요한 별도 환경에서는 서로 다른 장애 영역의 브로커, 복제 계수 3·`min.insync.replicas=2`·`acks=all`을 후보로 검증합니다. 단일 브로커의 `acks=all`이나 같은 호스트의 컨테이너 증설을 호스트 장애 내성으로 보고하지 않습니다. 복제 수는 TPS만으로 정하지 않습니다. [복제와 최소 ISR](https://kafka.apache.org/42/configuration/topic-configs/)

Kafka 보존은 금융 원장의 보존과 구분합니다. 첫 구현의 보존·동시 실행·접수 제한은 다음 기준으로 고정합니다. 구현 코드·Compose에 적용된 설정이나 성능 측정 결과가 아니며, 금융 Worker의 기존 임대·재시도·미확정 예약 정책을 대체하지 않습니다.

### 보존과 삭제 초기값

| 대상 | 첫 구현 기준 | 이유·만료 뒤 처리 |
| --- | --- | --- |
| 생산자별 원본 토픽 | `cleanup.policy=delete`, `retention.ms=86400000`(24시간), `retention.bytes=-1` | 5분 중단 시험과 당일 재개에 여유를 둔 출발점. 용량 상한에 의한 조기 삭제는 사용하지 않고 저장 공간 경보·신규 접수 제한으로 대응 |
| 소비자별 DLT | `cleanup.policy=delete`, `retention.ms=604800000`(7일), `retention.bytes=-1` | 원인 확인의 시간을 원본 토픽보다 길게 확보. DLT만 유일한 원본으로 쓰지 않음 |
| Outbox·Inbox·금융 Job·격리 기록 | 초기 자동 삭제 비활성. 완료·미완료 모두 DB에 보관 | Kafka·DLT 만료 뒤에도 원래 ID·본문·업무 상태와 대조 가능. 저장 증가 비용은 감수하고 별도 정리기를 먼저 만들지 않음 |
| 금융·주문 멱등 기록 | `expires_at=null`, 자동 삭제 금지 | 오래된 요청도 원업무에 연결하고 같은 키 다른 본문을 거절. 일반 관리·구매자 가입의 기존 24시간 정책은 유지 |
| 결제·환불·정산 원장·대역 원거래 | 기존 추가 전용·비삭제 정책 유지 | 전달 기록의 TTL을 금융 이력에 적용하지 않음 |

DLT로 옮기는 모든 오류는 해당 소비자 DB의 Inbox 또는 격리 기록에 원본 bytes·topic·partition·offset·eventId(해석 가능한 경우)·실패 사유를 먼저 영속 저장합니다. 스키마를 해석할 수 없는 bytes도 보관할 수 있어야 합니다. 그 뒤 DLT를 발행하며, DB 저장이 실패하면 offset을 커밋하지 않습니다. 기존의 “DLT 발행 확인 또는 DB 격리 커밋 후 ack” 중 첫 구현은 DB 격리를 필수 경로로 선택합니다. DLT 발행 실패는 기록된 원본으로 재개합니다.

24시간·7일은 조회 가능 기간의 운영 기준이며 세그먼트 정리가 정확히 그 시각에 끝난다는 뜻은 아닙니다. 필요한 시간 이전에 용량 제한으로 삭제되지 않는지 토픽 실제 설정을 검사합니다. `retention.bytes`는 파티션별 제한이므로 나중에 유한값을 사용하면 key 편향을 포함한 파티션별 유입량·보존 시간으로 산정하고 재검증합니다. [Kafka 보존 설정](https://kafka.apache.org/42/configuration/topic-configs/)

시험 전 실제 메시지 크기·시험 총 유입량·재발행·복제·인덱스·DB/WAL 증가량과 기존 점유를 합산하고 저장 공간에 30% 이상 여유를 둡니다. 약 3.6GB는 앞의 15분 원본 payload 예시일 뿐 전체 디스크 요구량이 아닙니다. 보존 기간 변경·DB 정리기 도입은 미완료/격리 건 보존, 모든 재전달 경로와 중복 방지 기록의 수명, 원업무 유일성·복구 검증을 함께 검토한 별도 변경으로 합니다. Kafka offset이 보존 범위를 벗어나면 `auto.offset.reset=none`으로 중단·경보하고, 기존 그룹을 임의 earliest/latest로 열지 않습니다. 원천 DB·Outbox와 대조해 원래 ID로 누락을 복구한 뒤 같은 업무를 재개합니다. 신규 그룹의 최초 offset은 빈 토픽 생성 뒤 생산자를 열기 전에 명시적으로 초기화하며, 기존 그룹의 offset 이탈 복구와 구분합니다.

### 동시 실행과 자원 초기값

첫 로컬 흐름은 각 실행 역할 1개 인스턴스로 시작합니다. 아래 값은 처리량 목표를 달성한 값이 아니라 제한 없는 실행을 피하기 위한 시작값입니다.

| 설정 | 초기값·범위 |
| --- | --- |
| 원본 토픽 파티션 | 토픽당 3개 |
| Consumer 동시 실행 | 그룹별·인스턴스당 1개, `max.poll.records=100`. 같은 그룹 전체의 활성 Consumer는 파티션 수 이내 |
| Outbox 발행기 | 인스턴스당 조회 간격 100ms·묶음 100건·미완료 발행 최대 8건. 묶음을 한 번에 전부 임대하지 않고 빈 슬롯만 선점 |
| Payment 금융 Worker | 인스턴스당 승인·환불·결과 조회를 합쳐 최대 8건. 그중 2개 슬롯은 도래한 미확정 조회·중단 복구 전용이며 새 승인에 빌려주지 않음 |
| Settlement 지급 Worker | 인스턴스당 지급·결과 조회를 합쳐 최대 8건. 같은 방식으로 복구 전용 2개 슬롯 확보 |
| JDBC 연결 풀 | JDBC를 사용하는 JVM당 `maximumPoolSize=10`. HTTP 호출 중에는 연결·트랜잭션을 점유하지 않음 |

금융 Worker는 빈 슬롯만큼만 선점하며 실행 대기열을 무제한으로 만들지 않습니다. 복구 외 작업은 나머지 6개 슬롯을 공유하고, 복구 전용 슬롯만 기다리는 도래 작업은 우선 실행합니다. [금융 Worker 정책](../policies.md#금융-worker-임대와-결과-반영)의 조회 1초·임대 30초·HTTP 총 5초와 함께 적용합니다. Outbox의 8개 동시 발행도 같은 집계의 선행 이벤트 추월 금지를 완화하지 않습니다.

서버 설정으로 역할별 값을 명시하고 누락·0·음수·`복구 전용 슬롯>=전체 슬롯`·`HTTP 제한 시간>=임대 시간` 등 잘못된 조합은 시작 때 거절합니다. 인스턴스를 늘리면 Worker·발행 동시성·풀은 합산하고 외부 대역·DB의 한도와 비교합니다. 파티션만 늘려 외부 호출·DB 처리량이 같이 늘었다고 보지 않습니다.

### 신규 접수 제한과 재개

제한 대상은 새 금융 부하를 만드는 `POST /api/orders`와 확정 거절 뒤 새 결제 회차를 만드는 `POST /api/orders/{orderId}/payment-retries`입니다. 동일 멱등키·본문의 이미 접수된 요청은 기존 결과로 연결하고, 다른 본문은 기존 `409`를 유지합니다. 취소·환불·기존 지급·원업무 재처리·상태 조회에는 이 신규 접수 gate를 적용하지 않습니다. 각 작업의 권한·상태·저장소 가용성 검사는 계속 필요합니다.

| 관측 항목 | 신규 접수 중단 | 재개 기준 |
| --- | --- | --- |
| 필수 그룹 `commerce.v1`·`payment.v1`·`settlement.v1`의 Kafka lag | 그룹별 구독 파티션 lag 합계가 하나라도 100,000건 이상 | 각 그룹 50,000건 미만 |
| 소유 서비스별 미완료 Outbox·금융 Inbox·금융 Job | 논리 대기열별 100,000건 이상 또는 실행이 도래한 미처리 건의 최장 지연 60초 이상 | 모든 대상 대기열 50,000건 미만·도래 지연 30초 미만 |
| Kafka·PostgreSQL 데이터 저장소 | 파일시스템 사용률 하나라도 80% 이상 | 모든 대상 70% 미만 |
| 필수 관측·운영 중단 | 필수 관측 누락·수집 실패·관측 시각이 45초보다 오래됨 또는 운영자가 접수 중단 | 모든 관측 유효·최신, 운영 중단 해제 |

하나라도 중단 조건이면 새 접수를 닫고, **모든 재개 조건이 연속 60초** 유지된 뒤 다시 엽니다. 기동 때는 닫힌 상태로 같은 검사를 시작합니다. 알림 전용 그룹·Job의 적체는 금융 gate의 건수·지연 조건에서 제외하고 별도 경보로 다룹니다. 공유 디스크 압박은 전체 저장 능력에 영향을 주므로 제외하지 않습니다.

건수는 아직 종결되지 않은 로컬 행을 각각 세며 같은 업무가 서로 다른 단계에 있다는 이유로 합산한 총량과 비교하지 않습니다. 미발행 Outbox와 RECEIVED/WAITING/REVIEW_REQUIRED Inbox, 실행·재시도·수동 확인이 남은 금융 Job을 포함합니다. 예약된 미래 지급·재시도의 도래 전 시간은 지연으로 세지 않고, REVIEW_REQUIRED는 자동 실행 지연에서 제외하되 미완료 건수와 별도 알람에는 포함합니다. 이로써 정상적인 다음 실행 시각 대기나 5분 조회 주기를 적체로 오인하지 않습니다.

Commerce의 각 인스턴스가 기존 내부 Prometheus에서 필요한 관측을 15초마다 묶어서 읽어 접수 상태를 판정합니다. 요청마다 원격 지표·다른 서비스 DB를 조회하지 않습니다. 각 소유 앱은 자기 DB의 논리 대기열·수집 시각을 내보내며 같은 대기열을 여러 인스턴스가 관측해도 중복 합산하지 않습니다. Kafka lag와 실제 데이터 파일시스템 사용률도 담당 수집기의 원본 관측 시각을 확인합니다. 누락된 지표를 0으로 대체하거나 Prometheus 조회 성공만으로 오래된 표본을 최신으로 취급하지 않습니다. 업무 지표·lag·저장소 수집과 gate 구현은 아직 없습니다.

거절은 `503 COMMON_CAPACITY_EXCEEDED`, `Retry-After: 30`으로 응답합니다. 일시적 서비스 용량 부족을 계정별 `429`와 구분합니다. gate 확인은 기존 멱등 결과/본문 충돌 판정 뒤, 새 주문·결제 회차와 재고·쿠폰·마일리지 예약·Outbox 저장 전에 하며, 거절을 완료된 멱등 결과로 캐시하지 않습니다. 클라이언트는 같은 키·본문으로 재시도합니다. 이미 접수한 작업의 상태·예약·원키는 바꾸지 않고 Consumer·Worker·Outbox 배출을 계속합니다. 저장소 오류로 트랜잭션을 완료할 수 없다면 접수 성공을 반환하지 않습니다.

이는 표본 간격·진행 중 요청만큼 초과할 수 있는 조기 제한이며 정확한 최대 행 수나 저장 공간 확보의 보장은 아닙니다. 관측 시스템 장애에도 신규 접수가 닫히는 가용성 비용을 감수합니다. 디스크 80% 이전 경보와 남은 20%를 기존 작업의 배출·복구에 사용하며, 새 접수를 닫아도 공간이 부족하면 저장소 확보와 장애 복구가 필요합니다. 기록 삭제·보존 기간 단축·이미 접수한 금융 작업 폐기로 공간을 만들지 않습니다.

### 초기값의 검증과 조정

기능 구현 PR에서 아래 입력과 실제 상태·응답·설정을 검사합니다. 이 문서의 수치 검토나 기존 smoke 통과를 아래 검증의 수행으로 보고하지 않습니다.

- 보존 24시간 직전/이후·DLT 7일 만료·Consumer offset 이탈을 작은 전용 토픽의 단축 TTL 시험으로 재현합니다. 원본 DB 보존, 무단 offset 초기화 없음, 원키 복구·중복 금융 효과 0건을 확인하고 실제 토픽 설정도 검사합니다.
- Consumer·발행기·Worker·HTTP 동시 호출과 DB 연결을 관측해 한도를 넘지 않는지, 일반 슬롯을 채운 동안 복구 전용 2개 슬롯이 진행하는지 확인합니다. 다른 key의 병렬 처리와 같은 key의 순서도 검사합니다.
- 건수 99,999/100,000·도래 지연 59/60초·디스크 79/80%·표본 나이 45초 초과·수집 실패를 각각 입력해 중단을 확인합니다. 재개 조건을 59/60초 유지하고 중간에 다시 나빠지는 경우도 검사합니다.
- 닫힌 동안 신규 503·Retry-After·예약/업무 부작용 없음, 기존 동일 키 결과 반환·본문 충돌409, 환불·취소·지급·조회·원키 복구 진행을 확인합니다. 두 인스턴스에서도 논리 대기열 중복 합산 없이 각 gate가 닫히는지 검사합니다.
- 작은 부하→목표 부하→5분 중단/복구 순서로 실제 메시지 크기·DB/WAL 증가·적체·호출 지연을 관측합니다. 8개 Worker 슬롯이 1,000 TPS를 처리한다는 가정은 하지 않습니다. 실패한 병목의 동시성·풀·파티션·접수 한도를 한 번에 하나씩 바꾸고 설정·이유·시험 조건·이전 결과를 남깁니다. 목표 부하에서 gate가 닫혀 거절된 요청도 별도 집계하며, 입력을 줄여 목표 TPS 달성으로 보고하지 않습니다. 수치를 바꾸면 다음 시험 전에 고정하고 이전 실패 기준을 소급 변경하지 않습니다. 성능·정합성 목표는 앞 절과 기존 측정 ADR을 유지합니다.

## 선택 이유와 대안

| 검토한 안 | 판단·이유 |
| --- | --- |
| 서비스 간 동기 호출만 사용 | 후속 처리·다중 소비의 장애와 지연이 호출 경로에 결합되므로 현재 연동에는 채택하지 않음 |
| 서비스 간 DB 작업 테이블 공유 | 다른 서비스 DB 직접 접근 금지와 소유권에 어긋남. 각 서비스 내부 Job은 유지 |
| Kafka + 폴링 Outbox·Inbox·Worker | 현재 DB·실행 구성을 재사용하고 안전한 인계와 금융 복구를 나눠 검증할 수 있어 채택 |
| 처음부터 Debezium CDC 사용 | 커넥터·복제 슬롯·WAL 보존·장애 복구 운영이 추가되므로 보류. 폴링의 DB 비용·발행 지연이 병목이면 비교 |
| 판매자별 금융 파티셔닝 | 인기 판매자의 거래가 한 파티션에 집중되므로 제외. 토픽·메시지 형식 대안은 위 비교를 따름 |
| Kafka 트랜잭션으로 금융 전체를 정확히 한 번 처리 | 외부 DB·PG 협력이 별도로 필요하므로 중복 방지·조회 계약의 대체안에서 제외 |

다중 소비와 원래 업무 재개가 필요해 Kafka를 선택하며 1,000 TPS 자체를 도입 근거로 삼지 않습니다. 폴링에서 CDC로 바꾸더라도 이벤트 ID·key·payload·중복 처리 계약을 보존해야 합니다. [Debezium Outbox](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)

## 감수하는 비용과 구현 검증

Outbox·Inbox·Job 저장과 중복 검사가 DB 쓰기를 늘리고, 비동기 상태 조회·메시지 호환성·격리·재처리·보존 운영이 필요합니다. 알림의 독립 그룹도 같은 앱·DB의 자원을 사용할 수 있으므로 금융 작업과의 경합을 확인합니다. 기능 분리만으로 처리량이나 장애 격리 개선을 달성했다고 보지 않습니다.

1. 주문 한 건부터 결제 확정·원장 반영을 연결하고 발행 직후 중단, DB 저장 후 offset 커밋 전 중단, 임대 인계·중복·역순·본문 충돌을 검증합니다.
2. 잘못된 메시지·DB 장애·선행 원장 대기·PG 응답 유실·DLT 발행 실패를 구분해 검증합니다. Kafka·Job 재개 뒤 원래 업무 키와 금액이 유지되어야 합니다.
3. 실제 업무 시나리오로 warm-up을 제외한 결제 확정 1,000 TPS·15분을 시험합니다. 기존 측정 ADR의 표본·응답·오류 기준과 함께 Outbox·Inbox·Kafka·Job 적체가 계속 증가하지 않는지 확인합니다.
4. Consumer·Worker·브로커를 각각 중단·재개하고 유입이 계속되는 동안 배출 시간을 측정합니다. 단일 브로커 재시작과 복제 환경의 브로커 장애 시험은 구분합니다.
5. 대기열 배출 후 기존 대조 쌍별 누락·중복·고아 항목 0건과 금액 차이 0원을 확인합니다. 별도 자원을 확보한 뒤 3천·5천·1만 TPS 확장 시험을 진행합니다.

시나리오·seed·데이터 건수·메시지 크기·파티션/그룹/동시 실행 수·압축·풀 크기·자원 한도·발생기 위치·목표·버전을 시험 전에 기록합니다. 기능이나 설정을 구현한 뒤의 실제 검증이며, 이 ADR이나 기존 smoke 통과가 금융 정합성·성능 달성을 뜻하지 않습니다.
