# Kafka 이벤트 전달과 용량 산정

- 상태: 설계 기준·일부 구현 및 국소 검증. 금융 전체의 성능·복구 목표는 검증 전이며, 초기 운영값은 부하 시험 전에 변경값·목표를 고정
- 결정일: 2026-10-27
- 범위: 서비스 간 이벤트 전달·Outbox/Inbox 인계·소비와 금융 실행 분리·용량 및 복구 시험

## 결정

Kafka는 주문·결제·정산·알림의 후속 작업을 전달하고 장애 뒤 재개하기 위해 사용합니다. [결제 확정 TPS 목표](../../README.md#성능-목표와-검증)를 토픽별 이벤트 유입량과 소비자별 처리량으로 환산하고, 정상 지연·적체 증가·장애 후 배출·금액 정합성을 함께 검증합니다. Kafka 사용이나 접수 응답만으로 처리량 향상·금융 완료를 주장하지 않습니다.

기존 생산자별 토픽과 책임별 Consumer 그룹, 주문의 `orderId`·금융 거래의 `paymentId` 중심 key를 유지합니다. 이벤트 종류·payload·key·그룹은 [API 이벤트 계약](../api.md#이벤트-연동), 금액·상태·재시도 상한은 [업무 정책](../policies.md#정산재처리), 저장 제약은 [메시지 데이터 모델](../data-model.md#메시지멱등성감사)이 소유합니다. 앱·DB·이벤트 이름과 금액·환불·지급 정책은 유지하며, 아래에 전달·실행의 초기 운영값과 신규 접수 제한을 정합니다.

현재는 단일 브로커의 로컬 실행 기반과 일부 Outbox·Inbox 구현이 있습니다. 아래 금융 업무 전체의 전달·복구·성능 목표는 아직 검증 전이며, 국소 검증은 해당 절의 조건과 결과로 구분합니다.

## 이벤트 구분과 토픽 경계

출처를 식별하는 것, 소비자가 처리할 업무를 고르는 것, 메시지를 분산하는 것은 각각 다른 결정입니다. 예를 들어 `PaymentConfirmed`와 `RefundAccepted`는 모두 Payment가 발행하지만 Settlement가 처리할 이벤트는 같지 않습니다. 서비스 이름만으로 처리기를 선택하면 이 차이를 표현할 수 없습니다.

| 판단 | 현재 기준 | 이유 |
| --- | --- | --- |
| 어느 업무 소유자가 발행했는가 | API에 고정한 생산자별 원본 토픽 | 현재 Kafka 내부 연동에서 발신 업무를 구분할 수 있음 |
| 무엇을 어떻게 처리하는가 | 구독 토픽에서 `eventType`·`eventVersion`과 payload 계약을 함께 확인 | 같은 발행자의 서로 다른 사건·명령을 구분하고 잘못된 토픽의 이벤트도 거절 |
| 어느 거래의 순서를 다루는가 | 이벤트별 `orderId`·`paymentId` 등 기존 key | 서비스 전체를 한 key에 묶지 않고 거래 단위로 분산 |
| 어느 처리 책임이 독립적으로 받는가 | 책임별 Consumer 그룹 | 결제 확정을 커머스와 정산이 모두 받아야 하므로 같은 그룹에서 나눠 받지 않음 |

토픽 이름은 발행 업무의 공개 계약으로 취급합니다. 실행 인스턴스 이름·배포 버전에서 자동 생성하거나 서비스 내부 리팩터링만으로 바꾸지 않습니다. 구체적인 토픽·이벤트·key·그룹의 대응은 API 명세 한 곳에서 관리합니다.

### 토픽 구성의 대안

| 구성 | 장점 | 비용과 판단 |
| --- | --- | --- |
| 공용 토픽 하나 + `serviceId` 필터 | 토픽 수가 적고 발행 경로가 단순함 | 모든 그룹이 무관한 레코드를 읽고 걸러야 하며 보존·권한·부하를 함께 관리. 현재는 제외 |
| 생산자별 토픽 + 이벤트 종류로 처리 | 기존 세 업무 소유권·API 계약을 유지하며 서비스별 운영 경계를 둘 수 있음 | 같은 생산자의 무관한 이벤트를 읽는 비용은 남음. 현재 채택하고 그룹별 비용을 측정 |
| 결제·환불·마일리지 등 업무 스트림별 토픽 | 필요한 스트림만 구독하고 보존·권한·부하를 따로 관리할 수 있음 | 토픽과 구독 조합이 늘고 같은 거래도 여러 토픽의 순서 차이를 처리해야 함. 독립 운영 요구나 측정된 소비 병목이 생기면 비교 |
| 이벤트 종류마다 토픽 | 특정 이벤트만 구독하고 개별 정책을 적용하기 쉬움 | 이벤트 증가에 따라 토픽·배포·호환성 관리가 늘어남. 종류가 다르다는 이유만으로는 채택하지 않음 |

일반 Kafka Consumer는 토픽을 구독합니다. `serviceId`나 이벤트 종류를 헤더에 넣는 것만으로 브로커가 필요한 레코드만 골라 보내지는 않습니다. 별도 라우터를 추가할 근거도 현재 없으므로 소비자 필터 비용을 측정에 포함합니다. [Kafka 구독 API](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html#subscribe(java.util.Collection))

### 출처 정보와 메시지 형식의 대안

토픽 구성을 바꾸는 것과 이벤트 형식을 표준화하는 것은 별개입니다. CloudEvents도 생산자별 또는 업무 스트림별 토픽에 담을 수 있으며 그 자체로 토픽 분리·순서·금융 멱등성을 해결하지 않습니다.

| 형식 | 장점 | 비용과 판단 |
| --- | --- | --- |
| 기존 Envelope + 원본 토픽 문맥 | 현재 `eventId`·종류·버전·집계·payload 계약을 유지. 출처를 중복 저장하지 않음 | Kafka 밖으로 본문만 옮기면 출처 문맥이 빠짐. 현재 내부 연동에서는 채택하고 격리·재처리 시 원본 위치를 보존 |
| 자체 출처 필드·헤더 추가 | 토픽과 분리된 논리 출처를 이벤트와 함께 전달 가능 | 발행 소유자·토픽과의 일치, 재전달 시 불변성, 누락·충돌·호환성 규칙이 추가됨. 현재 필요성이 없어 보류 |
| CloudEvents 채택 | `source`·`type`·`id` 등 표준 문맥과 Kafka 바인딩을 외부 도구·다른 전송 방식과 공유 가능 | 기존 Envelope와의 매핑·전환·소비자 호환성 검증이 필요함. 외부 소비자나 여러 전송 방식에서 표준 문맥이 필요해지면 자체 필드 추가와 함께 재검토 |

현재 OpenAPI의 Envelope 21종은 미정의 필드를 허용하지 않습니다. `sourceService` 하나를 본문에 추가하는 것도 소비자와 공유하는 계약 변경입니다. 지금은 필드·헤더를 추가하지 않고, DLT·격리·재처리 기록에 원본 topic·partition·offset과 원래 이벤트 ID를 보존합니다. 출처 필드가 생기더라도 문자열 자체를 발행 권한의 증거로 사용하지 않습니다.

CloudEvents를 채택한다면 `source`는 논리 출처, `type`은 사건 종류, `source+id`는 이벤트 유일성으로 구분합니다. Kafka 바인딩은 속성을 헤더에 두는 방식과 메타데이터·데이터를 본문에 함께 두는 방식을 제공하므로, `sourceService`를 붙인 자체 형식을 CloudEvents 준수라고 부르지 않습니다. [CloudEvents 명세](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/spec.md)·[Kafka 바인딩](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/bindings/kafka-protocol-binding.md)

업무별 보존·권한·지연 목표가 달라지거나 무관한 이벤트의 읽기 비용이 소비 병목으로 확인되면 토픽 분리를 재검토합니다. 원본 토픽 문맥을 유지할 수 없는 외부 전달·통합이 필요하면 출처와 형식 표준화를 재검토합니다. 그때 ADR에는 선택·대안·전환 이유를, 필드명·필수 여부·헤더/본문 배치·예시는 API 이벤트 명세에 기록하고 관련 소비자와 검토합니다. Java 클래스·직렬화·발행 메서드는 해당 구현에서 정합니다.

## 안전한 전달과 실행

### Outbox와 Producer

첫 구현은 기존 PostgreSQL의 Outbox와 커밋 후 깨우는 Relay로 시작하며, 신호 누락·재시도·만료 임대는 복구 조회로 처리합니다. 업무 상태와 Outbox를 함께 저장하고, 제한된 묶음과 동시 발행 수로 처리합니다. Kafka의 발행 성공 응답을 확인한 뒤에만 발행 완료와 `topic`·`partition`·`offset`·발행 시각을 같은 DB 트랜잭션으로 저장합니다. 발행 성공 직후 중단되면 원래 `eventId`로 재발행하므로 중복 전달을 허용하고 수신 측에서 막습니다. 위치가 없는 미발행·ack 후 저장 전 중단은 [대조 조회](../api.md#정산-대조-조회)에서 발행 대기로 포함하며, null 위치를 0으로 대체하지 않습니다. 재발행 위치가 달라져도 이미 저장한 원래 Inbox의 업무 처리 결과는 유지합니다.

Producer는 `acks=all`, `enable.idempotence=true`를 명시합니다. `retries>0`, `max.in.flight.requests.per.connection<=5`를 함께 지키고 `delivery.timeout.ms`로 클라이언트 재시도 시간을 제한합니다. Kafka 클라이언트 재시도와 Outbox·업무 재시도의 횟수·시간은 구분합니다. Producer 멱등성은 발행기 재시작 후 애플리케이션이 다시 보내는 이벤트나 외부 PG 실행의 중복까지 막지 않습니다. [Producer 설정](https://kafka.apache.org/42/configuration/producer-configs/)

같은 거래의 순서가 필요한 이벤트는 발행기 간 선점·동시 발행·임대 인계에서도 선행 이벤트를 추월하지 않도록 구현합니다. 같은 key만 사용하거나 UUID·생성 시각으로 정렬하는 것으로 순서를 보장했다고 보지 않습니다. 서로 다른 토픽·서비스·집계 사이의 순서는 가정하지 않고 선행 상태 대기와 업무 상태 전이로 보호합니다.

### 발행 경로 통일

2026-10-29에는 Commerce의 발행 경로를 Outbox로 통일합니다. 업무 응용 서비스는 자기 상태와 `OrderEventOutbox`를 함께 저장하고, `OutboxRelay`만 저장된 topic·key·원문 bytes를 `KafkaTemplate`으로 전송합니다. 선점과 결과 저장은 `OutboxDeliveryService`의 각각 짧은 트랜잭션으로 처리하며, Kafka 응답 대기 중에는 DB 연결·잠금을 유지하지 않습니다.

직접 발행하던 `KafkaOrderEventPublisher`는 이벤트 객체를 다시 직렬화하는 별도 전송 경로였고 호출자는 테스트뿐이었습니다. 이를 제거하고 실제 Outbox 경로에서 원문·발행 위치·실패 복구를 검증합니다. 새 전송 인터페이스나 공통 모듈은 추가하지 않습니다. 발행 경로 하나는 인스턴스 하나를 뜻하지 않으며 기존 선점·임대·집계별 순서 보장을 유지합니다.

| 비교한 안 | 판단·이유 |
| --- | --- |
| Relay가 기존 KafkaTemplate으로 전송 | 저장된 원문을 그대로 보내고 기존 복구 경로를 유지할 수 있어 채택 |
| 원문 전송 전용 Publisher를 Relay 뒤에 유지 | 전송별 변환이나 별도 전송 수단이 필요할 때 재검토. 현재는 중계 계층을 유지할 이득이 작아 제외 |
| 커밋 후 콜백만으로 직접 발행 | DB 커밋 뒤 전송 전에 중단되면 영속 재개 수단이 없으므로 Outbox 대체로 제외 |
| DB·Kafka 트랜잭션 동기화 | 첫 커밋 뒤 두 번째 커밋 실패에는 별도 복구가 필요하므로 현재 영속 인계를 대체하지 않음 |
| Spring Modulith 발행 기록으로 교체 | 영속 기록·재시도를 제공하지만 저장·직렬화·재처리 모델 전환과 현재 원문·순서·위치 계약 재검증이 필요해 보류 |

CDC(Change Data Capture)는 DB에 커밋된 변경 기록을 읽어 전달하는 방식입니다. Debezium을 사용하면 Outbox 삽입을 PostgreSQL WAL에서 읽어 Kafka로 보내므로 앱의 폴링 발행기를 대체할 수 있습니다. Outbox와 업무 상태의 원자 저장·이벤트 중복 처리는 계속 필요합니다. 커넥터·복제 슬롯·WAL 보존과 원문·발행 위치 기록의 전환 비용을 감수할 근거가 아직 없어 아래 CDC 보류 결정을 유지합니다. 이번 경로 정리는 처리량 개선이나 CDC 대비 성능 우위를 입증한 변경이 아닙니다.

근거: [Transactional Outbox](https://microservices.io/patterns/data/transactional-outbox.html), [Spring Kafka 트랜잭션 동기화](https://docs.spring.io/spring-kafka/reference/3.3/kafka/transactions.html#transaction-synchronization), [Spring Modulith 발행 기록](https://docs.spring.io/spring-modulith/reference/1.4/events.html), [Debezium PostgreSQL](https://debezium.io/documentation/reference/stable/connectors/postgresql.html).

### 커밋 후 깨움과 복구 조회

같은 프로세스의 Outbox INSERT가 성공하면 저장 어댑터가 내부 `OutboxAppended` 신호를 등록합니다. `AFTER_COMMIT` 수신기는 단일 스레드·대기열 1개의 조정 실행기에 깨움만 제출합니다. 업무 커밋 스레드와 Kafka 콜백에서는 선점·DB 결과 저장·Kafka 전송을 실행하지 않습니다. 롤백 시에는 깨우지 않습니다. 신호는 전송할 이벤트가 아니라 DB에 저장된 작업을 찾으라는 힌트이며 영속성은 Outbox가 담당합니다.

동시에 온 신호는 합치고, 실행 종료와 겹친 신호도 다시 확인합니다. 빈 슬롯만 선점하며 전송 결과의 DB 반영이 끝나 슬롯을 반환하면 즉시 다음 조회를 요청합니다. `ApplicationReadyEvent`에서도 한 번 깨웁니다. 기본 1초 복구 조회는 알림 누락·재시도 예정 시각·만료 임대를 처리합니다. 정상 커밋과 연속 발행은 이 주기를 기다리지 않으며, 실패 후 재시도에는 예정 시각에 더해 다음 복구 조회까지의 지연이 생길 수 있습니다. 실행기 제출 거절 시 커밋 스레드에서 대신 실행하지 않고 저장된 원본을 복구 대상으로 남깁니다.

이 역할은 Transactional Outbox 패턴의 message relay에 해당하므로 이름을 `OutboxRelay`로 정합니다. 응용 서비스는 업무 상태와 Outbox 저장을 책임지고, 저장 어댑터는 삽입 사실만 알리며, Relay는 전송·결과 반영의 흐름을 조정합니다. `OutboxDeliveryService`와 저장소가 짧은 트랜잭션·선점·임대 검사를 담당합니다.

| 깨우는 방식 | 현재 판단 |
| --- | --- |
| 커밋 후 내부 신호 + 복구 조회 | 추가 인프라 없이 같은 프로세스에서 바로 작업을 시작할 수 있어 채택 |
| 고정 주기 조회만 사용 | 단순하지만 정상 경로와 슬롯 재충전에도 주기 지연이 생겨 대체 |
| PostgreSQL LISTEN/NOTIFY + 복구 조회 | 다른 프로세스·인스턴스까지 즉시 깨워야 할 때 재검토. 연결·재구독·초기 조회가 필요하고 알림 자체는 영속 큐가 아님 |
| CDC | 별도 커넥터 운영과 기존 원문·발행 위치 계약 전환이 타당해질 때 재검토 |

현재의 동일 프로세스 구조에서 복잡성과 응답 지연을 줄이기 위한 선택입니다. 범용 최적 방식이나 실측 처리량·지연 개선을 입증한 결정은 아닙니다. 다른 인스턴스에서만 저장한 이벤트는 복구 조회로 발견합니다. 아래 SQL 비교의 100ms 폴링 조건과 결과는 당시 고정 사본의 기록이며 새 Relay의 성능 자료로 사용하지 않습니다.

검증: Commerce 컴파일·Checkstyle과 40개 시험이 실패·오류·생략 없이 통과했습니다. PostgreSQL 18.3·Kafka 4.2.2에서 복구 주기를 1시간으로 둔 커밋 후 발행, 롤백 시 깨움 없음, 시작·복구 조회, ACK 뒤 DB 저장 실패와 원문 재발행을 확인했습니다. 단위 시험은 동시 신호 병합·실행 종료 경합·슬롯 재충전·실행기 거절·결과 저장 실패를 확인합니다. 주문·금융 업무의 전체 흐름이나 처리량은 이 검증에 포함하지 않습니다.

근거: [Transactional Outbox의 message relay](https://microservices.io/patterns/data/transactional-outbox.html), [Spring 트랜잭션 이벤트](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html), [PostgreSQL NOTIFY](https://www.postgresql.org/docs/18/sql-notify.html).

### Outbox 결과 저장 SQL의 비교 기준

2026-10-28의 비교 대상은 현재의 `SELECT … FOR UPDATE` 후 조건부 UPDATE와, 두 SQL을 `MATERIALIZED` CTE로 합치는 대안입니다. 잠금 대기 전에 유효했던 임대가 대기 중 만료될 수 있으므로, 잠금을 얻은 뒤의 DB 시각으로 임대·버전을 검사해야 합니다. 일반 UPDATE의 WHERE에 시각 조건을 두는 것만으로 이 순서를 보장하지 않습니다. 성공·실패 결과 저장에서 이 경합을 재현했고 현재 분리 SQL은 관련 21개 시험을 통과했습니다.

CTE 대안은 잠금을 얻은 결과의 `locked.lease_until`에 최종 시각 조건을 연결합니다. 다음은 성공 결과 저장의 비교 SQL이며, 실패 저장도 같은 잠금 CTE와 조건을 사용하고 기존 재시도·소진 갱신을 유지합니다.

```sql
WITH locked AS MATERIALIZED (
    SELECT id, version, status, lease_until
    FROM commerce.outbox
    WHERE id = :id AND version = :version AND status = 'RUNNING'
    FOR UPDATE
)
UPDATE commerce.outbox o
SET status = 'PUBLISHED', published_partition = :partition,
    published_offset = :offset, published_at = clock_timestamp(),
    lease_until = NULL, updated_at = clock_timestamp(), version = o.version + 1
FROM locked
WHERE o.id = locked.id AND o.version = locked.version AND o.status = locked.status
  AND locked.lease_until > clock_timestamp();
```

선점·재시도·원문·Kafka 설정은 동일하게 두고 결과 저장 SQL만 비교합니다. 분리 방식의 잠금 제한 설정·행 잠금·UPDATE 세 SQL을 CTE 방식에서는 두 SQL로 줄일 수 있다는 가설이며, JDBC `execute*` 호출을 계수해 확인합니다. 이 수에는 트랜잭션 제어문이 포함되지 않으며 네트워크 패킷 수와도 다릅니다. `MATERIALIZED`의 별도 계산과 잠금 후 시각 검사는 구분하여, 정확한 후보 SQL로 기존 경합 시험을 먼저 통과해야 성능 비교 대상으로 인정합니다. [PostgreSQL CTE](https://www.postgresql.org/docs/18/queries-with.html#QUERIES-WITH-CTE-MATERIALIZATION)

2026-10-28 비교 당시 발행기는 fixed delay 100ms마다 빈 슬롯을 최대 8개 선점합니다. I/O가 즉시 끝나도 인스턴스당 지속 처리량 상한은 대략 80건/초이며, 실제로는 선점·스케줄 지연만큼 더 낮아집니다. 이는 코드에서 도출한 상한이지 실측 처리량이 아닙니다. 이 제한과 SQL 비용을 구분하려고 당시 다음 조건을 결과를 보기 전에 고정했습니다. 아래는 첫 탐색 실험의 기록이며, 후속 실험은 뒤의 새 사전 설계를 따릅니다.

대안 구현과 계측은 임시 Gradle overlay에서 실행하고, 기준 작업폴더와 운영 코드를 유지했습니다. 이 일회성 하네스는 기본 CI나 영구 공통 도구로 추가하지 않습니다. 아래 결과는 정합성 통과와 SQL 수 감소를 확인했지만, SQL 성능의 우열을 판정할 근거는 불충분합니다. 당시 채택 기준 미충족을 CTE의 열등함이나 현재 방식의 최적성으로 해석하지 않고 현재 분리 SQL을 유지합니다. CDC는 이번 비교의 실행 대상이 아니므로 기존 보류 결정을 유지합니다.

- 성공 결과 콜백의 응용 SQL 실행 수는 모든 측정 건에서 분리 3개·CTE 2개로 확인했습니다. 이 감소를 전체 DB 부하나 처리량의 33% 개선으로 확대하지 않습니다.
- 기본군 40건/초의 짝별 전체 p99 개선은 7.36%·61.65%·1.32%입니다. 세 번 모두 10% 이상이라는 기준을 충족하지 못했고 중앙값 개선 7.89%도 분리 방식의 반복 편차 147.92%보다 작았습니다. 튄 값을 버리거나 가장 좋은 표본만 선택하지 않았습니다.
- 기본군 160건/초의 유효한 두 짝에서 CTE의 유입 구간 처리량 개선은 3.68%·6.41%로 10%에 못 미쳤고, 첫 짝은 유입률 미달로 채택 판단에 사용할 수 없습니다. 현재 자료로 지속적인 CTE 우위를 확인하지 못했습니다.
- 기본군 분리 방식은 유입 160건/초에서 62.4~73.6건/초를 발행했고 5초 적체 432~488건·배출 6.254~8.709초를 관측했습니다. 같은 분리 SQL의 10ms 감도군은 159.4~159.8건/초·적체 1~3건·배출 0.008~0.012초였습니다. 이는 조회 주기의 영향과 맞는 국소 관측이며, 10ms를 운영 기본값으로 즉시 채택하거나 장기 처리량 보장으로 해석하지 않습니다.

이번에는 성능 우열 판정이 불충분하므로 운영 SQL과 100ms 초기값을 유지합니다. 후속 비교에서는 결과 저장 SQL의 비용을 조회 간격·빈 슬롯 재충전 정책의 영향과 분리합니다. hot key·장기 유입·실제 주문/금융 처리·장애 중 유입/복구·운영 연결 풀 10개 조건은 이번에 검증하지 않았습니다. 고정된 군 순서·짧은 3회 반복과 JVM/공유 호스트 변동도 한계이며, 금융 1,000 TPS·15분 목표 달성과 별개입니다. 시험용 클라이언트 초기화의 timeout 설정 오류는 표본 생성 전에 수정했으며 실패한 초기화에서 성능 표본을 얻었다고 기록하지 않습니다.

임시 하네스는 이 비교의 근거 확인과 중단 복구에 필요한 동안만 보관합니다. 이 ADR은 SQL·기준 SHA·fixture·seed·조건·지표·모든 반복 결과를 남기지만, 하네스를 영구 배포하거나 동일 하네스의 자동 재실행성을 제공한 것으로 주장하지 않습니다.

#### 후속 실험 사전 고정 프로토콜

설계 갱신일: 2026-10-29.

앞의 24개 표본은 정합성과 조회 주기의 영향을 확인한 **탐색 자료**입니다. 5초·3회 반복과 폴링 상한 때문에 결과 저장 SQL의 성능 우열을 판정하기에는 부족했습니다. 직렬 입력기가 DB 응답을 기다렸고 실제 append 시작부터 지연을 재서, 예정 시각부터 밀린 시간을 전체 지연에서 누락했습니다. 평균 유입률이 허용 범위인 표본도 입력이 일정했다고 보장하지 않습니다. 예를 들어 100ms·40건/초 분리 방식 반복 2의 스케줄 지연 p99는 180.94ms였습니다. 앞의 채택 기준과 결과는 당시 기록으로 보존하며 후속 실험의 판정에 재사용하지 않습니다.

후속 질문은 둘로 나눕니다. **결과 저장 트랜잭션이 실제로 저렴해지는가**를 먼저 측정하고, **그 변경이 Kafka 전달 전체에 이득이나 회귀를 만드는가**를 별도로 확인합니다. 차이가 반드시 나오도록 조건을 조작하지 않으며, 감지 가능한 효과 크기와 불확실성을 함께 보고합니다. 아래는 실행 전에 고정한 프로토콜입니다. 실제 장치 보정·실행 결과는 뒤의 날짜별 기록으로 구분하며, 이 기준 자체를 검증 통과나 CTE 채택의 증거로 사용하지 않습니다.

**공통 조건과 실행 순서**

- A는 위 SHA의 분리 SQL, B는 위 CTE입니다. 두 후보의 성공·실패 경로, 실제 선택 Bean, 트랜잭션 경계를 고정합니다. 양쪽 DB 시험 18개와 공통 Dispatcher 시험 3개를 먼저 통과해야 합니다. 새 후보·하네스·분석기·fixture·실행 계획의 SHA, 이미지 digest, Java/JDBC/Kafka 버전과 호스트 자원을 실행 전에 기록합니다. 후보가 바뀌면 기존 결과를 전용하지 않습니다.
- 같은 격리 PostgreSQL 18.3을 사용하고 전체 전달 단계에만 Kafka 4.2.2를 추가합니다. 풀은 운영 초기값인 Hikari 최대 10개, Outbox 작업은 8개로 맞춥니다. DB 512MiB·Kafka 768MiB·시험 JVM 512MiB, Gradle worker 1개입니다. 동일 fixture 813bytes·독립 집계·인덱스·DB 설정·내구성 설정을 유지합니다. 운영 DB와 컨테이너를 재설정하지 않습니다.
- 한 쌍은 동일한 초기 데이터와 입력을 사용하는 A/B 두 실행입니다. 각 절반 전에 격리 시험 데이터를 같은 스냅샷으로 복원하고 동일하게 예열합니다. 절반 사이에는 캐시를 임의로 비우거나 서버를 재시작하지 않습니다. 쌍마다 새 시험 JVM을 사용하고, 순서는 seed 380028로 균형 있게 무작위 배치합니다. 모든 A를 끝낸 뒤 B를 돌리지 않습니다. [무작위 교차 반복과 예열 참고](https://google.github.io/benchmark/user_guide.html#random-interleaving)
- 예열 데이터 500,000행을 시계 시작 전에 한 번 준비하고 같은 worker가 연속 호출합니다. 각 절반의 접수 창은 최소 30초·최대 60초이며, 완료 시각 기준 5초 구간 평균의 마지막 세 값이 세 구간 중앙값의 ±10% 안에 들어야 합니다. 접수 중단 뒤 진행 중 트랜잭션을 배출하고 최종 구간값으로 다시 확인합니다. 준비·배출 시간은 별도로 기록하며 전체 4시간 예산에는 포함합니다. 60초 창에서도 안정 기준을 확인하지 못하면 본 측정에 진입하지 않고 관측된 실패 이유를 기록합니다. 예열 데이터는 본 측정에 섞지 않습니다. 본 측정의 GC·느린 실행·이상치를 사후 삭제하지 않습니다.
- 순서는 정합성 → DB 단계의 예비 측정·대조군 → DB 본 측정 → 전체 전달 단계입니다. 전체 실행의 벽시계 예산은 준비를 포함해 최대 4시간이며 마지막 60초는 정리에 유보합니다. 최초 3시간 상한은 DB 52쌍·전체 전달 20쌍의 최소 예열·측정만 164분이라는 실행 전 재점검에 따라 보정했습니다. 이 변경은 새 성능 관측 전에 고정하며 반복 수·효과 크기·판정 기준은 바꾸지 않습니다. 예산·안전 상한에 닿으면 남은 단계를 미측정으로 남기며, 유리한 결과가 나올 때까지 반복하지 않습니다. 호스트 자원 슬롯은 순차로 점유하고 임시 컨테이너·프로세스만 정리합니다.

**1. DB 결과 저장만 비교**

Kafka·폴링·append를 측정 경로에서 제거합니다. 별도 준비 단계에서 서로 다른 RUNNING 행과 유효한 Delivery를 만들고, 측정에서는 각 행의 성공 결과를 한 번만 저장합니다. 각 절반의 시작 직전에 임대 240초를 부여하며, 측정 중 임대 만료·행 재사용·저장 반환값 false가 생기면 실패로 기록하고 채택을 중단합니다. 실패 결과 저장은 정합성 시험을 유지하고 성능 우위의 일반화 대상에서 제외합니다.

| 항목 | 고정할 내용 |
| --- | --- |
| 주 조건 | 동시 작업 8개, closed loop로 다음 독립 행을 즉시 처리. 다른 DB 작업은 없음 |
| 주 지표 | 실제 Spring 프록시의 `OutboxDeliveryService.markPublished` 호출 직전부터 반환까지의 평균 지연. 풀 획득·트랜잭션 시작·제한 설정·잠금·갱신·커밋·연결 반환을 포함 |
| 보조 지표 | 같은 구간의 p50/p95/p99, 30초 안의 커밋 완료/초, DB CPU·풀 대기·GC·오류. 단일 작업 조건은 왕복 비용을 설명하는 별도 10쌍이며 채택 주 지표로 바꾸지 않음 |
| 측정 길이 | 예열 뒤 각 절반 30초. 구간 안에서 시작한 호출은 끝까지 관측해 지연에 포함하며, 완료/초는 구간 안에서 끝난 건수만 사용 |
| 데이터 | 예열과 본 측정 cohort를 분리. 본 측정은 예비 측정 최대 처리율×30초×2만큼 사전 준비하되 절반당 최대 500,000행. 예열은 별도 행으로 수행하며 본 측정 행은 새로 준비·동일하게 예열한 스냅샷을 사용. 행 부족이면 해당 실행 무효, 측정 중 재충전은 하지 않음 |
| 관측 비용 | SQL 수는 별도 계수 실행에서만 검증. 본 측정에서 JDBC 호출 프록시를 제거하고 같은 최소 타이머·메모리 버퍼로 기록. 로그·파일 쓰기는 측정 뒤에 수행 |

예비 측정은 6쌍이며 본 측정에 합산하지 않습니다. 예비 6쌍의 로그 비율 평균·표준편차를 사용하되 구간 계산의 n=20·자유도=19로 두어 예상 95% 구간 폭을 계산합니다. 개선율 구간의 전체 폭이 5%p를 넘을 것으로 예상되면 본 측정을 시작하지 않습니다. 이 추정은 정밀도 보장이 아니며, 결과를 보고 반복 수를 늘리거나 조건을 바꾸는 근거가 아닙니다. 보정이 필요하면 새 계획을 고정한 별도 실험으로 다룹니다.

같은 하네스로 다음 대조군을 각각 8쌍 실행합니다. A/A는 같은 분리 구현을 이름만 바꿔 비교하고, 평균 지연 비율의 95% 구간 전체가 `[0.975, 1.025]` 안에 있어야 합니다. 양성 대조군은 A와 A에 같은 트랜잭션의 추가 `SELECT 1` 한 번을 넣은 조건을 비교하며, 추가 SQL 조건의 평균 지연 비율 구간 하한이 1을 넘어야 합니다. 대조군은 후보의 결과에 합산하지 않습니다. 둘 중 하나라도 실패하면 작은 차이를 구분할 장치가 확인되지 않은 것이므로 본 측정을 중단합니다. 추가 SQL은 실제 CTE 이득의 크기나 네트워크 패킷 수를 대신하지 않으며, 인위적인 네트워크 지연을 넣어 차이를 키우지 않습니다.

본 측정의 주 조건은 **20쌍으로 고정**합니다. 통계 단위는 개별 수만 건의 호출이 아니라 쌍별 실행 요약입니다. 각 쌍의 `d = ln(B의 평균 지연 / A의 평균 지연)`에 대해 `평균(d) ± t(0.975, n−1) × 표준편차(d)/√n`를 계산하고 지수 변환합니다. 비율 구간이 `[L,U]`이면 개선율 구간은 `[100×(1−U), 100×(1−L)]%`입니다. 쌍간 독립성과 로그 비율의 근사 정규성을 전제로 한 구간이며, 실행 순서별 추세·자기상관·분포도 함께 공개합니다. 뚜렷한 추세나 가정 위반이 있으면 유리한 분석법으로 갈아타지 않고 판정 불충분으로 남깁니다. [짝 비교](https://www.itl.nist.gov/div898/handbook/eda/section3/eda353.htm), [평균의 t 구간](https://www.itl.nist.gov/div898/handbook/eda/section3/eda352.htm)

실용적 개선 기준은 **평균 트랜잭션 지연 5% 감소**로 사전 선택합니다. 작은 SQL 변경을 채택할 최소 효과에 대한 이번 엔지니어링 기준이며, 금융 SLO에서 도출한 값은 아닙니다. 절대 시간 차이도 µs로 함께 보고합니다.

- 95% 개선율 구간의 하한이 5%를 넘고 전체 폭이 5%p 이하면 DB 단계의 채택 후보입니다.
- 구간이 전부 `−5%~+5%` 안이면 이 조건에서는 실용적으로 비슷하다고 보고합니다. 0보다 크지만 5%에 못 미치는 이득과 통계적으로 검출되지 않은 차이를 구분해 적습니다.
- 구간 전체가 음수이면 CTE가 느린 증거로 기록하며, 같은 구간이 `−5%~0%` 안이면 실용적으로 비슷하다는 분류도 함께 적습니다. 그 밖에 기준을 걸치거나 구간이 넓으면 판정 불충분입니다. 20쌍이 차이를 반드시 검출한다고 보장하지 않습니다.

**2. 실제 Kafka 전달에서 확인**

DB 단계가 채택 후보가 된 경우 전체 흐름의 회귀를 확인합니다. DB 결과와 다른 질문이므로 효과를 합쳐 하나의 유의성으로 계산하지 않습니다. 100ms 폴링·in-flight 8개·실행기 thread/queue 각 8개·3파티션·복제 1·`acks=all`·멱등 Producer를 고정하고, 별도 JDBC 프록시를 쓰지 않습니다.

1. **입력 독립성:** 예정 시각과 ID가 있는 입력 trace를 먼저 만듭니다. 스케줄러 1개가 DB 완료를 기다리지 않고 bounded queue에 넣고, writer 4개가 append합니다. A/B는 같은 trace와 seed를 사용하며 쌍별 시작 위상을 무작위화합니다. 모든 시각은 같은 JVM의 monotonic clock으로 기록합니다.
2. **측정 구간:** 예정 입력 → enqueue → append 시작 → append `afterCommit` → Kafka send/ACK → PUBLISHED `afterCommit`을 남깁니다. 주 지연은 **예정 입력부터 PUBLISHED 관측까지**이며, writer 대기와 append 지연도 포함합니다. 실제 append부터의 지연은 분해용입니다. 각 구간의 p99를 더해 전체 p99로 만들지 않습니다. [예정 시각부터의 지연 측정 근거](https://github.com/giltene/wrk2#readme)
3. **발생기 검증:** DB 대신 즉시 반환하는 stub에서 최대 예정 유입률의 2배를 60초 발생시킵니다. 본 실행에서도 enqueue 지연 p99 ≤5ms·최대 ≤100ms, 매 1초 enqueue 건수가 trace의 ±`max(2건, 2%)` 안인지 확인합니다. 위반하면 발생기 한계로 표시하고 동등한 부하의 채택 근거에서 제외합니다. append 처리율이 낮다는 이유로 표본을 제외하지 않습니다.
4. **같은 부하:** 예비 실행에서 미리 쌓은 독립 행을 연속 발행해 A/B 각각 30초×3회 완료율을 측정합니다. 각 방식의 중앙값 중 작은 값을 `C`로 삼고, 본 입력률 `floor(0.5C)`·`floor(0.9C)`를 둘 다 동일하게 적용합니다. 0건/초이거나 두 값이 같으면 설계 가능 범위 밖으로 중단합니다. 예비 결과와 확정 trace·수치는 본 측정 전에 고정하며 사후에 유리한 부하를 선택하지 않습니다.
5. **길이와 적체:** 각 부하에서 10쌍, 절반마다 동일 예열 뒤 새 측정 cohort를 60초 입력하고 최대 120초 배출합니다. 입력 queue는 `max(100, ceil(2C))`건으로 고정합니다. 넘치면 손실 없이 성공한 것으로 처리하지 않고 접수 실패 수·미완료 수를 명시합니다. 예정·enqueue·append·PUBLISHED 각각의 누적 건수, 입력 대기와 Outbox 적체를 매초 기록합니다. 배출 종료 때도 미완료가 있으면 완료된 이벤트만의 p99를 전체 cohort 값으로 제시하지 않습니다.
6. **지표와 회귀:** 전체 cohort p99와 유입 60초 안의 PUBLISHED/초를 두 회귀 지표로 삼습니다. 부하별 쌍 요약의 로그 비율 t 구간을 같은 방식으로 계산합니다. 2개 부하×2개 지표를 동시에 확인하므로 각각 양측 **98.75% 구간**을 사용합니다. 모두 CTE의 p99 비율 상한 ≤1.10·처리량 비율 하한 ≥0.95여야 통과합니다. 이는 로컬 회귀 허용폭 10%·5%이며 운영 SLO가 아닙니다. 폭이 넓어 통과하지 못하면 회귀 없음으로 선언하지 않습니다. 각 cohort의 건수와 p99 상위 1%에 해당하는 표본 수도 적고, 모든 이벤트를 독립 반복처럼 합쳐 구간을 좁히지 않습니다.
7. **오류와 정합성:** cohort 전체의 Kafka ID·원문 누락/중복 0건, Outbox PUBLISHED·시도 횟수 1을 확인합니다. SQL 오류·임대 만료·재시도·queue 초과·미완료가 생기면 그 수와 지연을 보존하고 채택을 중단합니다. 발생기 오류나 외부 간섭의 무효 실행도 원자료에 남깁니다. 한쪽만 잘 나온 재실행으로 쌍을 바꾸지 않으며, 예정된 쌍이 무효면 해당 단계는 판정 불충분으로 종료합니다.

별도 10ms 폴링과 `1.2C` 과부하는 원인 분석이 필요할 때만 추가할 탐색 조건입니다. 본 확인 결과와 섞거나 CTE 채택의 대체 근거로 쓰지 않으며, 해당 조건의 실행 계획을 별도로 고정합니다. hot key·다중 인스턴스·실제 주문/금융 처리·장애 복구·장시간 용량 시험은 이 SQL 비교의 결론 범위 밖입니다.

**최종 결정:** 정합성·계측 대조군·DB 주 지표·전체 흐름 회귀 기준이 모두 통과해야 CTE 채택을 검토합니다. 통과해도 이 로컬 조건의 이득이며 범용 최적성이나 금융 1,000 TPS의 증거가 아닙니다. 미실행·감도 부족·불확실성·실패는 각각 그대로 기록하고 이 실험에서는 분리 SQL을 유지하고, 당시 비교 조건인 100ms 폴링 값의 변경 근거로 사용하지 않았습니다. 현재 발행기의 커밋 후 깨움과 1초 복구 조회는 위의 별도 결정입니다. 다음 실행에서는 확정 계획·하네스·분석기와 전체 원자료의 연결을 검토한 뒤, 결과와 판정을 이 절에 덧붙입니다.

### Inbox와 Worker

Consumer는 자동 offset 커밋을 끄고, 처리에 필요한 Inbox·실행 작업 또는 로컬 업무 반영을 같은 DB 트랜잭션으로 저장한 뒤 offset을 커밋합니다. 병렬 처리에서도 아직 영속 저장하지 못한 앞 offset을 건너뛰어 커밋하지 않습니다. 저장 뒤 커밋 전에 중단되면 `consumer+eventId`와 업무 유일성으로 재전달을 수용합니다. 같은 ID에 다른 본문이 오면 충돌로 보존하고 자동 적용하지 않습니다.

PG·환불·지급 호출과 장시간 대기는 Worker가 맡습니다. 외부 호출 동안 DB 잠금을 유지하지 않고, 동시 실행 수·호출 시간·임대·상태 조건으로 보호합니다. Consumer 동시 실행 수와 Worker 동시 실행 수는 각각 측정하며 DB 연결 풀·잠금·외부 대역 처리 한도도 함께 확인합니다. Kafka offset 커밋은 금융 업무 완료를 뜻하지 않습니다. Kafka 트랜잭션도 외부 DB·PG와의 원자 처리를 대신하지 않습니다. [전달 보장의 범위](https://kafka.apache.org/42/design/design/)

| --- | --- |
| DB·통신의 일시 장애 | 제한된 재시도·소비 일시 정지. 영속 인계 전에는 offset 커밋 금지 |
| 선행 결제·원장 미도착 | 원본과 다음 재판정 시각을 Inbox `WAITING`으로 보존하고 로컬 재개 |
| 스키마 오류·본문 충돌·금액 불일치 | 소비자별 DLT 또는 수동 확인 상태에 원본 위치·실패 이유를 보존. 무한 재시도·자동 금융 보상 금지 |
| 외부 금융 결과 미확정 | 원래 PG·업무 키로 조회·재개. 시간 경과만으로 실패 확정·예약 해제 금지 |

DLT 발행이 확인되거나 같은 DB의 격리 기록이 커밋되기 전에는 원본 offset을 커밋하지 않습니다. DLT 발행 뒤 offset 커밋 전 중단으로 생긴 중복은 원본 topic·partition·offset으로 식별합니다. 자동 재시도 소진 뒤에도 원래 Inbox·Job·업무 키를 보존하고 운영 재처리는 해당 상태를 재개합니다. offset 되감기나 새 이벤트 ID 발급만으로 재처리를 대신하지 않습니다. 새 조회 모델의 전체 재구축은 별도 소비자·저장 대상으로 구분하고 기존 금융 작업을 다시 실행하지 않습니다.

## TPS를 이벤트 부하로 환산

로컬의 결제 확정 1,000 TPS·15분 목표는 실측 수요나 달성 결과가 아닙니다. 기존 [측정 지표 결정](0002-performance-and-integrity-metrics.md)의 처리량·구간별 지연·오류 분류·금액 대조를 재사용합니다. 배포 환경 API p99 3초 목표를 비동기 결제·원장 반영 목표로 확대하지 않습니다.

설명용으로 모든 신규 결제가 성공하고 각 이벤트를 한 번 발행하는 정상 흐름을 가정합니다.

| 구간 | 초기 발행 이벤트 | 결제 확정 1,000 TPS의 발행량 |
| --- | --- | --- |
| 커머스 생산자 토픽 | `OrderPaymentRequested` | 약 1,000건/초 |
| Payment 생산자 토픽 | `PaymentAccepted`, `PaymentConfirmed`, `PaymentNoticeRequested` | 약 3,000건/초 |
| 합계 | 성공 결제 초기 흐름 | 약 4,000건/초 |

지연된 구매확정·정산/지급 알림과 환불·거절·취소·재발행은 별도로 더합니다. 과거 거래의 구매확정 작업이나 재처리가 한꺼번에 실행되는 순간 부하도 포함합니다. 결제 성공 비율이 낮으면 같은 확정 TPS를 만들기 위한 주문 접수량은 더 커집니다.

`토픽 유입량 = 흐름별 초당 발생량 × 해당 토픽의 이벤트 수`를 합산합니다. 한 이벤트를 여러 그룹이 읽어도 발행량은 늘지 않지만 소비·전송·DB 처리 비용은 늘어납니다. 생산자별 토픽의 관심 없는 이벤트를 읽고 거르는 비용도 그룹별로 측정합니다.

메시지 평균·상위 크기, 토픽별 유입량, 그룹별 읽기/반영량, 재전달량, 압축률을 기록합니다. 평균 1kB를 가정한 4,000건/초는 약 4MB/초, 15분에 360만 메시지·3.6GB이며 복제·인덱스 등은 별도입니다. 이는 용량 계산 예시이고 실제 메시지 크기·상시 유입량을 측정한 값이 아닙니다.

## 파티션·복구·보존

### 파티션과 동시 실행

첫 구현은 원본 토픽당 파티션 3개·그룹별 인스턴스당 Consumer 1개로 시작합니다. 작은 부하에서 정합성을 먼저 확인한 뒤 파티션 3·6·12개와 Consumer 동시 실행 수를 비교합니다. 1,000 TPS에 고정 파티션 수를 대응시키지 않습니다. 토픽마다 가장 느린 필수 그룹의 실제 처리량을 기준으로 다음 식과 메시지 크기·키 편향을 함께 봅니다.

```text
필요 파티션 수 ≈ ceil(토픽 유입량 / (파티션당 측정 처리량 × 목표 사용률))
```

목표 사용률과 시험 조건은 결과를 보기 전에 정합니다. 일반 Consumer 그룹에서 한 파티션은 동시에 한 Consumer에 배정되므로 파티션 수가 소비 병렬도의 상한이지만, DB 작업과 Worker의 실행 능력은 별도입니다. 판매자 2만 곳의 균등 분산과 상위 1%에 결제 70%가 몰리는 기존 시나리오를 비교합니다. 금융 key를 `sellerId`로 바꿔 인기 판매자의 모든 거래를 한 파티션에 묶지 않습니다.

파티션 증설은 key 배정을 바꿀 수 있으므로 기존 메시지와 신규 메시지가 서로 다른 파티션에서 처리될 때도 상태 전이가 안전한지 검증합니다. 병목이 DB 잠금·연결 대기·외부 호출이면 해당 경로를 먼저 조정하며 파티션 증설을 해결책으로 단정하지 않습니다. [파티션과 증설](https://kafka.apache.org/42/operations/basic-kafka-operations/)

### 장애 후 배출

정상 유입률과 같은 처리 능력만 확보하면 장애 때 쌓인 작업을 따라잡을 수 없습니다. 같은 업무 단계의 건수 단위로 다음을 계산합니다.

```text
적체 B = 초당 유입량 λ × 중단 시간 D
복구에 필요한 초당 처리량 μ >= λ + B / 허용 배출 시간 T
```

예를 들어 원장 반영이 초당 1,000건 유입되는 동안 5분 멈추면 30만 건이 쌓입니다. 유입을 유지하며 재개 후 5분 안에 배출하려면 최소 약 2,000건/초의 반영 능력이 필요합니다. 실제 토픽 읽기량·재시도·편향과 여유 용량은 별도로 반영합니다.

정상 원장 반영 p99 5초 이내, 5분 중단 후 재개부터 5분 이내 배출을 초기 시험 후보로 둡니다. 원장 반영 구간은 결제 확정부터 Settlement DB 반영까지이며, 탐지·서비스 복구·정합 복구 시간의 정의는 기존 측정 ADR을 따릅니다. 이 수치는 운영 보장이나 측정 결과가 아니며 환경·메시지 구성과 함께 시험 전에 확정합니다. 변경하면 적용 시점과 이전 기준을 남기고 실패한 시험을 소급 통과시키지 않습니다.

Kafka lag와 함께 미발행 Outbox·대기 Inbox·실행 Job의 건수와 최장 나이, 원장 반영 지연을 봅니다. Kafka lag가 0이어도 DB 작업이 남아 있으면 정합 복구 완료가 아닙니다. 저장 공간·작업 한도에 접근하면 신규 접수를 제한하되 이미 접수한 금융 작업을 버리지 않습니다. 초기 제한값·재개 조건과 거절 응답은 [신규 접수 정책](../policies.md#신규-접수-제한과-재개)을 따릅니다.

### 브로커와 보존

로컬은 단일 브로커를 유지하고 재시작·적체 복구를 시험합니다. 브로커 장애 내성이 필요한 별도 환경에서는 서로 다른 장애 영역의 브로커, 복제 계수 3·`min.insync.replicas=2`·`acks=all`을 후보로 검증합니다. 단일 브로커의 `acks=all`이나 같은 호스트의 컨테이너 증설을 호스트 장애 내성으로 보고하지 않습니다. 복제 수는 TPS만으로 정하지 않습니다. [복제와 최소 ISR](https://kafka.apache.org/42/configuration/topic-configs/)

Kafka 보존은 금융 원장의 보존과 구분합니다. 다음은 첫 구현의 보존·동시 실행·접수 제한 기준입니다. 현재 토픽·Consumer·Outbox Relay의 설정과 활성화 조건은 [Kafka 전달 기반](../development.md#kafka-전달-기반)에서 확인합니다. 초기값을 성능 목표 달성의 근거로 삼지 않으며, 금융 Worker의 임대·재시도·미확정 예약 정책을 대체하지 않습니다.

### 보존과 삭제 초기값

| 대상 | 첫 구현 기준 | 이유·만료 뒤 처리 |
| --- | --- | --- |
| 생산자별 원본 토픽 | `cleanup.policy=delete`, `retention.ms=86400000`(24시간), `retention.bytes=-1` | 5분 중단 시험과 당일 재개에 여유를 둔 출발점. 용량 상한에 의한 조기 삭제는 사용하지 않고 저장 공간 경보·신규 접수 제한으로 대응 |
| 소비자별 DLT | `cleanup.policy=delete`, `retention.ms=604800000`(7일), `retention.bytes=-1` | 원인 확인의 시간을 원본 토픽보다 길게 확보. DLT만 유일한 원본으로 쓰지 않음 |
| Outbox·Inbox·금융 Job·격리 기록 | 초기 자동 삭제 비활성. 완료·미완료 모두 DB에 보관 | Kafka·DLT 만료 뒤에도 원래 ID·본문·업무 상태와 대조 가능. 저장 증가 비용은 감수하고 별도 정리기를 먼저 만들지 않음 |
| 금융·주문 멱등 기록 | `expires_at=null`, 자동 삭제 금지 | 오래된 요청도 원업무에 연결하고 같은 키 다른 본문을 거절. 일반 관리·구매자 가입의 기존 24시간 정책은 유지 |
| 결제·환불·정산 원장·대역 원거래 | 기존 추가 전용·비삭제 정책 유지 | 전달 기록의 TTL을 금융 이력에 적용하지 않음 |

DLT로 옮기는 모든 오류는 해당 소비자 DB의 Inbox 또는 격리 기록에 원본 bytes·topic·partition·offset·eventId(해석 가능한 경우)·실패 사유를 먼저 영속 저장합니다. 스키마를 해석할 수 없는 bytes도 보관할 수 있어야 합니다. 그 뒤 DLT를 발행하며, DB 저장이 실패하면 offset을 커밋하지 않습니다. 기존의 “DLT 발행 확인 또는 DB 격리 커밋 후 ack” 중 첫 구현은 DB 격리를 필수 경로로 선택합니다. DLT 발행 실패는 기록된 원본으로 재개합니다.

24시간·7일은 조회 가능 기간의 운영 기준이며 세그먼트 정리가 정확히 그 시각에 끝난다는 뜻은 아닙니다. 필요한 시간 이전에 용량 제한으로 삭제되지 않는지 토픽 실제 설정을 검사합니다. `retention.bytes`는 파티션별 제한이므로 나중에 유한값을 사용하면 key 편향을 포함한 파티션별 유입량·보존 시간으로 산정하고 재검증합니다. [Kafka 보존 설정](https://kafka.apache.org/42/configuration/topic-configs/)

시험 전 실제 메시지 크기·시험 총 유입량·재발행·복제·인덱스·DB/WAL 증가량과 기존 점유를 합산하고 저장 공간에 30% 이상 여유를 둡니다. 약 3.6GB는 앞의 15분 원본 payload 예시일 뿐 전체 디스크 요구량이 아닙니다. 보존 기간 변경·DB 정리기 도입은 미완료/격리 건 보존, 모든 재전달 경로와 중복 방지 기록의 수명, 원업무 유일성·복구 검증을 함께 검토한 별도 변경으로 합니다. Kafka offset이 보존 범위를 벗어나면 `auto.offset.reset=none`으로 중단·경보하고, 기존 그룹을 임의 earliest/latest로 열지 않습니다. 원천 DB·Outbox와 대조해 원래 ID로 누락을 복구한 뒤 같은 업무를 재개합니다. 신규 그룹의 최초 offset은 빈 토픽 생성 뒤 생산자를 열기 전에 명시적으로 초기화하며, 기존 그룹의 offset 이탈 복구와 구분합니다.

### 동시 실행과 자원 초기값

첫 로컬 흐름은 각 실행 역할 1개 인스턴스로 시작합니다. 아래 값은 처리량 목표를 달성한 값이 아니라 제한 없는 실행을 피하기 위한 시작값입니다.

| 설정 | 초기값·범위 |
| --- | --- |
| 원본 토픽 파티션 | 토픽당 3개 |
| Consumer 동시 실행 | 그룹별·인스턴스당 1개, `max.poll.records=100`. 같은 그룹 전체의 활성 Consumer는 파티션 수 이내 |
| Outbox Relay | 커밋 후·결과 반영 후·시작 시 깨움, 복구 조회 기본 1초·묶음 상한 100건·미완료 발행 최대 8건. 빈 슬롯만 선점 |
| Payment 금융 Worker | 인스턴스당 승인·환불·결과 조회를 합쳐 최대 8건. 그중 2개 슬롯은 도래한 미확정 조회·중단 복구 전용이며 새 승인에 빌려주지 않음 |
| Settlement 지급 Worker | 인스턴스당 지급·결과 조회를 합쳐 최대 8건. 같은 방식으로 복구 전용 2개 슬롯 확보 |
| JDBC 연결 풀 | JDBC를 사용하는 JVM당 `maximumPoolSize=10`. HTTP 호출 중에는 연결·트랜잭션을 점유하지 않음 |

금융 Worker는 빈 슬롯만큼만 선점하며 실행 대기열을 무제한으로 만들지 않습니다. 복구 외 작업은 나머지 6개 슬롯을 공유하고, 복구 전용 슬롯만 기다리는 도래 작업은 우선 실행합니다. [금융 Worker 정책](../policies.md#금융-worker-임대와-결과-반영)의 조회 1초·임대 30초·HTTP 총 5초와 함께 적용합니다. Outbox의 8개 동시 발행도 같은 집계의 선행 이벤트 추월 금지를 완화하지 않습니다.

서버 설정으로 역할별 값을 명시하고 누락·0·음수·`복구 전용 슬롯>=전체 슬롯`·`HTTP 제한 시간>=임대 시간` 등 잘못된 조합은 시작 때 거절합니다. 인스턴스를 늘리면 Worker·발행 동시성·풀은 합산하고 외부 대역·DB의 한도와 비교합니다. 파티션만 늘려 외부 호출·DB 처리량이 같이 늘었다고 보지 않습니다.

### 신규 접수 제한과 재개

제한 대상·관측 기준·중단/재개 조건·응답·구현 상태는 [업무 정책](../policies.md#신규-접수-제한과-재개)이 소유합니다.

기존 작업의 배출·복구 공간을 남기기 위해 새 금융 부하를 만드는 접수만 조기에 제한하는 안을 선택했습니다. 관측 간격과 진행 중 요청 때문에 정확한 최대 행 수를 보장하지 못하고, 관측 시스템 장애에도 신규 접수가 닫히는 가용성 비용을 감수합니다.

### 초기값의 검증과 조정

기능 구현 PR에서 아래 입력과 실제 상태·응답·설정을 검사합니다. 이 문서의 수치 검토나 기존 smoke 통과를 아래 검증의 수행으로 보고하지 않습니다.

- 보존 24시간 직전/이후·DLT 7일 만료·Consumer offset 이탈을 작은 전용 토픽의 단축 TTL 시험으로 재현합니다. 원본 DB 보존, 무단 offset 초기화 없음, 원키 복구·중복 금융 효과 0건을 확인하고 실제 토픽 설정도 검사합니다.
- Consumer·발행기·Worker·HTTP 동시 호출과 DB 연결을 관측해 한도를 넘지 않는지, 일반 슬롯을 채운 동안 복구 전용 2개 슬롯이 진행하는지 확인합니다. 다른 key의 병렬 처리와 같은 key의 순서도 검사합니다.
- 건수 99,999/100,000·도래 지연 59/60초·디스크 79/80%·표본 나이 45초 초과·수집 실패를 각각 입력해 중단을 확인합니다. 재개 조건을 59/60초 유지하고 중간에 다시 나빠지는 경우도 검사합니다.
- 닫힌 동안 신규 503·Retry-After·예약/업무 부작용 없음, 기존 동일 키 결과 반환·본문 충돌409, 환불·취소·지급·조회·원키 복구 진행을 확인합니다. 두 인스턴스에서도 논리 대기열 중복 합산 없이 각 gate가 닫히는지 검사합니다.
- 작은 부하→목표 부하→5분 중단/복구 순서로 실제 메시지 크기·DB/WAL 증가·적체·호출 지연을 관측합니다. 8개 Worker 슬롯이 1,000 TPS를 처리한다는 가정은 하지 않습니다. 실패한 병목의 동시성·풀·파티션·접수 한도를 한 번에 하나씩 바꾸고 설정·이유·시험 조건·이전 결과를 남깁니다. 목표 부하에서 gate가 닫혀 거절된 요청도 별도 집계하며, 입력을 줄여 목표 TPS 달성으로 보고하지 않습니다. 수치를 바꾸면 다음 시험 전에 고정하고 이전 실패 기준을 소급 변경하지 않습니다. 성능·정합성 목표는 앞 절과 기존 측정 ADR을 유지합니다.

## 선택 이유와 대안

| 검토한 안 | 판단·이유 |
| --- | --- |
| 서비스 간 동기 호출만 사용 | 후속 처리·다중 소비의 장애와 지연이 호출 경로에 결합되므로 현재 연동에는 채택하지 않음 |
| 서비스 간 DB 작업 테이블 공유 | 다른 서비스 DB 직접 접근 금지와 소유권에 어긋남. 각 서비스 내부 Job은 유지 |
| Kafka + 폴링 Outbox·Inbox·Worker | 현재 DB·실행 구성을 재사용하고 안전한 인계와 금융 복구를 나눠 검증할 수 있어 채택 |
| 처음부터 Debezium CDC 사용 | 커넥터·복제 슬롯·WAL 보존·장애 복구 운영이 추가되므로 보류. 폴링의 DB 비용·발행 지연이 병목이면 비교 |
| 판매자별 금융 파티셔닝 | 인기 판매자의 거래가 한 파티션에 집중되므로 제외. 토픽·메시지 형식 대안은 위 비교를 따름 |
| Kafka 트랜잭션으로 금융 전체를 정확히 한 번 처리 | 외부 DB·PG 협력이 별도로 필요하므로 중복 방지·조회 계약의 대체안에서 제외 |

다중 소비와 원래 업무 재개가 필요해 Kafka를 선택하며 1,000 TPS 자체를 도입 근거로 삼지 않습니다. 폴링에서 CDC로 바꾸더라도 이벤트 ID·key·payload·중복 처리 계약을 보존해야 합니다. [Debezium Outbox](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)

## 감수하는 비용과 구현 검증

Outbox·Inbox·Job 저장과 중복 검사가 DB 쓰기를 늘리고, 비동기 상태 조회·메시지 호환성·격리·재처리·보존 운영이 필요합니다. 알림의 독립 그룹도 같은 앱·DB의 자원을 사용할 수 있으므로 금융 작업과의 경합을 확인합니다. 기능 분리만으로 처리량이나 장애 격리 개선을 달성했다고 보지 않습니다.

1. 주문 한 건부터 결제 확정·원장 반영을 연결하고 발행 직후 중단, DB 저장 후 offset 커밋 전 중단, 임대 인계·중복·역순·본문 충돌을 검증합니다.
2. 잘못된 메시지·DB 장애·선행 원장 대기·PG 응답 유실·DLT 발행 실패를 구분해 검증합니다. Kafka·Job 재개 뒤 원래 업무 키와 금액이 유지되어야 합니다.
3. 실제 업무 시나리오로 warm-up을 제외한 결제 확정 1,000 TPS·15분을 시험합니다. 기존 측정 ADR의 표본·응답·오류 기준과 함께 Outbox·Inbox·Kafka·Job 적체가 계속 증가하지 않는지 확인합니다.
4. Consumer·Worker·브로커를 각각 중단·재개하고 유입이 계속되는 동안 배출 시간을 측정합니다. 단일 브로커 재시작과 복제 환경의 브로커 장애 시험은 구분합니다.
5. 대기열 배출 후 기존 대조 쌍별 누락·중복·고아 항목 0건과 금액 차이 0원을 확인합니다. 별도 자원을 확보한 뒤 3천·5천·1만 TPS 확장 시험을 진행합니다.

시나리오·seed·데이터 건수·메시지 크기·파티션/그룹/동시 실행 수·압축·풀 크기·자원 한도·발생기 위치·목표·버전을 시험 전에 기록합니다. 기능이나 설정을 구현한 뒤의 실제 검증이며, 이 ADR이나 기존 smoke 통과가 금융 정합성·성능 달성을 뜻하지 않습니다.
