# 정산 배치 적용 범위·실행 시각·chunk 단위

- 상태: 제안·팀 검토 중 (D2·D3 팀 결정 완료)
- 제안일: 2026-10-28
- 범위: Settlement에서 Spring Batch로 실행할 작업과 이벤트·워커로 둘 작업의 경계, 정산 일배치와 정산 대조의 실행 시각·주기, 일배치의 chunk·트랜잭션·병렬 처리 단위, 비영업일 처리 여부, 지급 워커의 실행 위치와 임대 로직 공유 방식

## 결정

배치는 **정해진 마감 시각까지 쌓인 대상을 한꺼번에 고정해 처리하는 것이 업무상 맞는 작업**에만 씁니다. 바로 처리해야 하는 작업을 배치로 바꾸면 환불·구매확정·지급이 다음 실행까지 늦어지기 때문입니다. 이 기준으로 Spring Batch는 **정산 일배치**와 **정산 대조** 두 Job에만 쓰도록 제안합니다. 정산 정책은 [업무 정책](../policies.md#정산재처리), Spring Batch 도입 시점과 역할은 [상세 설계](../design.md#spring-batch-도입-전략)가 소유합니다. 업무 코드·Job 설정·메타데이터 migration은 아직 구현 전입니다.

### D1. 배치와 배치가 아닌 영역

| 작업 | 방식 | 이유 |
| --- | --- | --- |
| 정산 일배치: 대상 선점 → 합계 확정 → payout·payout_job 생성 | Spring Batch, 매일 1회 | 마감 시각으로 대상을 고정해야 하고, 판매자 단위로 나눠 처리하다 중단되면 이어서 재시작해야 함 |
| 정산 대조: 참조 대조·금액 대조 | Spring Batch, 매일 1회(D6) | 읽기 전용 대량 스캔. FK가 없어 고아 참조를 잡는 수단이 대조뿐임 |
| 원장 반영(`PaymentConfirmed`, `PurchaseConfirmed`) | Kafka 소비자, 즉시 | 원장 기록을 지급일까지 미루지 않음. 미루면 정산 반영 지연이 그대로 늘어남 |
| 환불 예약·상쇄·해제 | Kafka 소비자, 즉시 | 배치로 바꾸면 구매자 환불이 다음 실행까지 멈춤 |
| 지급 실행(`payout_jobs`) | 지급 워커. 도래한 작업을 임대해 한 건씩 처리, 미확정이면 5분마다 원거래 조회 | 건마다 성공·미확정·재시도로 경과가 달라 다음 시도 시각을 건별로 관리해야 함. 한 시각에 같은 처리를 하는 chunk 방식과 맞지 않음 |
| 선행 원장 대기 재처리, Outbox 발행 | 짧은 주기 스케줄러 | 대기 시간이 곧 반영 지연 |
| (참고) 커머스 모의 배송·자동 구매확정 | 매분 스케줄러([정책](../policies.md#배송환불-기한과-자동-구매확정)) | 하루 1회로 돌리면 `ready_at`이 밀려 지급이 하루 늦어질 수 있음 |
| (참고) 커머스 월간 우수고객 쿠폰 발급 | 매월 1일 00:10, 미완료 시 10분마다 재시도([데이터 모델](../data-model.md)) | 이미 정책에 정의됨. Settlement 범위 밖 |

일배치는 지급할 목록을 `payout_jobs`에 만들고 끝나며, 실제 송금은 지급 워커가 맡습니다. 같은 배치를 두 번 만들지 않는 것은 Spring Batch 실행 이력이 아니라 `UNIQUE(seller_id, batch_date, policy_version)`이 보장합니다. 지급 워커의 폴링 주기·임대 시간은 이 문서에서 정하지 않습니다.

### D2. 일배치 마감 시각

**결정: 10:00 KST.** [업무 정책](../policies.md#정산재처리)의 현재 값을 유지하고, 아래 비교를 그 근거로 남깁니다. 근무 시간 안에서 `REVIEW_REQUIRED`·배치 중단을 바로 확인·재실행할 수 있고, 같은 날 송금과 미확정 재조회까지 진행되며, 부하 시험에서 일배치와 트래픽의 겹침을 자연스럽게 검증할 수 있다는 점을 낮 트래픽과의 경합보다 우선했습니다.

| 기준 | 03:00 | 10:00 |
| --- | --- | --- |
| 서비스 트래픽과 DB 경합 | 결제·주문 트래픽과 덜 겹침 | 낮 트래픽과 겹침. 다만 판매자별 짧은 트랜잭션이고 잠그는 행이 `PAYABLE` 항목이라 신규 원장 INSERT와 직접 충돌할 일은 적음 |
| 장애 대응 | 운영자가 없어 `REVIEW_REQUIRED`·중단이 아침까지 방치될 수 있음 | 근무 시간이라 바로 확인·재실행 가능 |
| 지급 실행까지의 간격 | 대상은 일찍 고정되지만 실은행 연동이라면 송금은 영업시간까지 대기 | 같은 날 근무 시간 안에 송금과 미확정 재조회까지 진행 |
| 환불 마감과의 관계(수요일 10:00 환불 마감 예시) | 목요일 03:00 배치에 포함. 10:00보다 7시간 빠름 | 같은 날 배치에는 못 들어가고 목요일 10:00에 포함 |
| 부하 시험 | 일배치와 1,000 TPS 트래픽의 겹침을 시험에서 일부러 만들어야 함 | 겹침 시나리오가 자연스럽게 생김 |

10:00을 유지하므로 은행 영업시간 제약을 재현하기 위한 시간대 보류 규칙은 지급 워커에 추가하지 않습니다.

### D3. 비영업일 처리

**결정: 비영업일을 구분하지 않습니다.** 주말·공휴일에도 운영 인력이 근무한다고 가정하고, 정산 일배치는 매일 10:00에 실행하며 생성된 지급은 그날 바로 지급 워커가 실행합니다.

기존 정책은 지급 대역이 배송과 같은 영업일 달력([업무 정책](../policies.md#배송환불-기한과-자동-구매확정))으로 비영업일을 판정해 기존 지급을 `NON_BUSINESS_DAY`로 보류하고, 외부 거래·자금 선점 없이 `409 PAYOUT_NON_BUSINESS_DAY`를 반환하며, 다음 영업일 10:00에 같은 작업을 재개했습니다([정산 정책](../policies.md#정산재처리)). 이 결정으로 지급 쪽의 아래 동작이 사라집니다.

| 항목 | 기존 정책 | 결정 후 |
| --- | --- | --- |
| 일배치 실행 | 매일 실행, 비영업일 지급은 보류 | 매일 실행, 모든 날 동일하게 지급 |
| 지급 대역의 영업일 판정 | 달력으로 판정해 `409 PAYOUT_NON_BUSINESS_DAY` 반환 | 판정하지 않음. 해당 오류 코드 제거 |
| 보류·재개 | `hold_reason=NON_BUSINESS_DAY`, 다음 영업일 10:00 재개 | 없음. 보류 사유는 미확정·확정 거절만 남음 |
| 판매자 조회 | 주말 대상은 "보류"로 표시 | 평일과 같은 지급 경과로 표시 |

**검토한 안:** 비영업일을 유지하는 두 안(매일 실행 후 보류 / 영업일에만 실행)에서는 보류 지급의 재개 시각과 영업일 판정 주체를 함께 정해야 했고, 대역 판정을 유지하려면 `409` 응답에 `nextBusinessDate`·`calendarVersion`을 담는 계약 확장도 필요했습니다. 비영업일을 구분하지 않으면 이 질문과 계약 확장이 모두 필요 없어져 기각합니다. 월요일에 주말 몫 지급이 몰리는 일도 생기지 않아 매일의 지급 부하가 고르게 됩니다.

**범위:** 이 결정은 정산 일배치와 지급 실행에만 적용합니다. 모의 배송 소요일([업무 정책](../policies.md#배송환불-기한과-자동-구매확정))과 PG 입금 예정일의 영업일 달력은 이 ADR에서 바꾸지 않습니다.

**감수하는 점:** 실은행 연동이라면 주말·공휴일 송금이 불가능하거나 다음 영업일 처리될 수 있지만, 이 프로젝트는 모의 지급 대역만 쓰므로 재현하지 않습니다. 실연동을 검토할 때 다시 엽니다.

### D4. chunk 단위

Spring Batch의 chunk 크기는 한 트랜잭션에서 처리하는 item 수입니다. 정책상 판매자 하나의 대상 선점·합계·payout·payout_job을 한 트랜잭션에 저장해야 하므로 **item을 정산 항목이 아니라 판매자로 둡니다.** reader는 마감 전 대상 항목이 있는 `seller_id` 목록을 `seller_id` 순 keyset 페이징으로 읽고, 판매자 안의 항목 선점은 `UPDATE … SET payout_id … WHERE seller_id=? AND status='PAYABLE' AND ready_at<?` 한 문장으로 처리합니다.

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| 판매자 1명 = chunk 1(제안) | 한 판매자 실패가 다른 판매자를 롤백하지 않음. 재시작 지점이 판매자 단위로 명확 | 판매자 수만큼 커밋·메타데이터 갱신 |
| 판매자 N명 = chunk 1 | 커밋 횟수 감소 | 한 판매자 실패 시 N명 전체 롤백 뒤 skip/retry로 재처리. 판매자 원자성은 지켜지지만 실패 처리가 복잡해짐 |
| 정산 항목 N개 = chunk 1 | 항목 수가 많을 때 트랜잭션 크기 균일 | 한 판매자의 대상·합계가 여러 트랜잭션에 나뉘어 정책 위반 |

쏠림 규모는 부하 시험 가정으로 어림합니다. 1,000 TPS로 15분이면 약 90만 건이고, 상위 1% 판매자(200명)가 70%를 가져가면 판매자당 약 3,000건입니다. **이 값은 상위 200명의 평균이며 한 판매자의 최대치가 아닙니다.** 한 트랜잭션의 크기와 잠금 시간은 가장 큰 판매자가 정하므로, 부하 시험 데이터 생성기에 판매자 1명의 최대 점유율 상한을 따로 두고 그 판매자로 트랜잭션 시간을 잽니다. 예를 들어 1명이 전체의 10%를 가지면 약 9만 건입니다. 상한값은 데이터 생성기를 정할 때 고정합니다. 이 규모는 판매자 한 트랜잭션의 한 문장 UPDATE로 처리하는 것을 전제로 하며, 실측 전 추정입니다.

### D5. 병렬 처리

처음에는 단일 스레드 Step으로 구현하고, 부하 시험에서 일배치 소요 시간이 목표를 넘을 때 `seller_id` 해시 기준 파티셔닝을 도입합니다. 판매자 단위로 데이터가 겹치지 않아 파티션 사이 잠금 경합은 없습니다. 일배치 소요 시간 목표는 아직 없으며 [운영 알람](../policies.md#운영-알람)의 지급 지연 기준(마감 후 30분/60분)과 함께 정합니다.

### D6. 정산 대조

[ADR 0006](0006-no-foreign-keys-within-service.md)과 [ADR 0002](0002-performance-and-integrity-metrics.md#금액-불일치)는 대조를 부하 시험 종료 후·장애 복구 후에만 실행합니다. FK를 쓰지 않는다면 고아 참조를 운영 중에 발견할 수단이 대조뿐이므로 매일 정기 실행으로 올립니다. 정기 실행을 채택하면 두 ADR의 실행 시점을 함께 고칩니다.

부하 시험 종료 후와 달리 운영 중에는 일배치가 끝난 뒤에도 결제·환불·지급 반영이 계속됩니다. 미발행 Outbox·미처리 Inbox가 모두 0건이어도 Kafka에 발행됐지만 아직 소비되지 않은 이벤트는 양쪽 어디에도 보이지 않습니다. 그래서 "남은 것이 없다"는 확인 대신 **`T` 이전 이벤트가 정산 Consumer에 실제로 도달했는지**를 이벤트별로 확인해 전달 대기와 결함을 구분합니다.

| 항목 | 기준 |
| --- | --- |
| 대조 기준 시각 `T` | 그날 일배치의 마감 시각(`cutoff_at`). 원천에서 `T` 이전에 발생한 결제·환불·구매확정과 `T` 이전에 생성된 지급만 대조하고, 이후 거래는 다음 회차 대상 |
| 비교 시점 | 양쪽 모두 **이벤트의 `occurred_at` ≤ `T`** 로 자릅니다. 조회 시각·처리 시각은 쓰지 않습니다. Payment는 `T` 시점의 상태를 반환하고(`T` 이후 환불·상태 변경 제외), Settlement는 원장에 저장한 원천 이벤트 `occurred_at`으로 같은 범위를 집계합니다. Payment 조회는 `T` + 안전 여유(최대 업무 트랜잭션 시간보다 긴 값, 구현 때 정함) 이후에만 실행해 `T` 직전에 시작해 늦게 커밋된 거래가 빠지지 않게 합니다. 대조 시작 때 받은 Payment 응답을 그 회차의 기준선으로 고정하고, 이후 들어오는 이벤트는 기준선을 바꾸지 않습니다 |
| 전달 확인 (offset 워터마크) | 원천 Outbox는 발행 ack로 받은 `partition`·`offset`·발행 시각을 저장하고, 대조 조회는 `T` 이전 이벤트마다 `eventId`·`occurred_at`·`partition`·`offset`을 함께 반환합니다. Settlement는 해당 이벤트를 반영하는 **자기 Consumer 그룹**의 커밋 offset과 비교합니다. offset은 Inbox 저장 뒤에 커밋하므로([ADR 0005](0005-kafka-event-delivery-and-capacity.md)), 커밋 offset이 그 이벤트를 지났다면 Inbox 기록이 있어야 합니다 |
| 이벤트 상태 분류 | 원천에 있고 정산에서 맞지 않는 건은 아래 순서로 분류합니다. ① 커밋 offset이 이벤트 offset 이하 → **전달 대기** ② Inbox `RECEIVED`·`WAITING`·선행 원장 대기 → **반영 대기** ③ 소비자 격리 기록(topic·partition·offset)에 있음 → **격리** ④ 커밋 offset이 지났는데 Inbox 기록 없음, 또는 Inbox `APPLIED`인데 원장 금액·참조가 다름 → **결함** |
| 진행 중 거래 | 결제·환불·지급 `UNKNOWN`, 환불·지급 예약 중, 지급 `PROCESSING`·보류는 불일치로 세지 않고 "진행 중"으로 따로 집계. 오래 남은 건은 대조가 아니라 [운영 알람](../policies.md#운영-알람)의 금융 미확정·지급 지연 기준으로 다룸 |
| 재대조와 결함 판정 | 결함은 ④에서만 판정합니다. 전달 대기·반영 대기 건은 시간 경과가 아니라 **워터마크 통과(커밋 offset이 이벤트를 지남)와 Inbox 처리 완료**를 조건으로 그 키만 재대조합니다. 대기 상한(초기값 15분, [운영 알람](../policies.md#운영-알람)의 작업 적체 CRITICAL과 같음) 안에 조건을 만족하지 못하면 **전달 지연**으로 기록하고 결함 수에는 넣지 않습니다. 전달 지연은 Kafka lag·작업 적체 알람으로 다루고 다음 정기 대조에서 다시 확인합니다. 격리는 기존 격리 처리 절차를 따릅니다 |

결함 수에는 ④만 들어가고, 전달 대기·반영 대기·전달 지연·격리·진행 중은 건수와 최장 나이를 따로 보고합니다. 따라서 소비가 대기 상한보다 오래 밀려도 정산 누락으로 잘못 세지 않으며, 반대로 offset이 지났는데 기록이 없는 건은 대기 시간과 무관하게 바로 결함으로 잡힙니다.

**실행 경계:** 대조 Job은 `settlement` DB만 직접 읽습니다. Settlement가 실행하는 쌍은 Settlement 원장, 정산 ↔ 지급, [내부 참조](0006-no-foreign-keys-within-service.md), Payment ↔ Settlement, 지급 성공액 ↔ 대역 차감액입니다. Payment ↔ Settlement는 Payment가 제공하는 내부 조회 계약(기준 시각 `T`까지 발생한 결제·환불의 `paymentId`·E·M·P·B·F·N과 전달 확인용 `eventId`·`occurred_at`·`partition`·`offset`을 keyset 페이지로 반환)으로, 지급 쪽은 기존 [`GET /mock/payouts/{businessKey}`](../api.md) 또는 기간 목록 계약으로 비교합니다. Consumer 그룹 offset은 Kafka 관리 API로 Settlement 자기 그룹만 조회하므로 다른 서비스 DB 접근이 아닙니다. 결제 구성·마일리지·Payment ↔ `finance-mock`·재원 대조는 원천 서비스가 각자 실행하며 이 ADR은 그 주기를 정하지 않습니다. Payment 조회 계약은 새 `/internal` 작업이므로 API 명세·OpenAPI에 추가해야 하며, 이는 [서비스와 코드 경계](../architecture.md)의 "참조·금액 대조" 행과 맞춥니다.

실행 시각은 일배치 종료 뒤인 10:30(초기값)으로 둡니다. 판정은 실행 시각이 아니라 이벤트별 전달 확인에 따르므로, 실행 시각은 일배치와 읽기 부하가 겹치지 않게 하고 `T` + 안전 여유를 지나게 하는 용도입니다.

### D7. Job 실행 방식

Settlement 서비스 안의 스케줄러가 `batchDate`를 Job 파라미터로 넘겨 실행하고, 앱 기동 시 자동 실행(`spring.batch.job.enabled`)은 끕니다. 운영자의 [`POST /internal/settlement-batches`](../api.md)도 같은 경로를 씁니다.

같은 `batchDate`로 다시 요청해도 모든 경우가 재시작되지는 않습니다. Spring Batch는 완료된 인스턴스를 다시 실행하지 않고, 실행 이력이 `STARTED`로 남은 인스턴스도 실행 중으로 보고 거부합니다. 그래서 직전 실행의 종료 상태별로 처리를 나눕니다.

| 직전 실행 상태 | 처리 |
| --- | --- |
| 성공 완료(`COMPLETED`) | 새 실행을 시작하지 않고 `settlement_batches`에 저장된 그날의 기존 결과를 반환. Spring Batch의 "이미 완료" 예외를 오류로 노출하지 않음 |
| 실패·정상 중단(`FAILED`·`STOPPED`) | 같은 `batchDate`로 같은 JobInstance를 재시작. reader가 저장한 마지막 커밋 `seller_id` 다음부터 이어서 처리 |
| 강제 종료 후 `STARTED` 잔류 | 아래 복구 절차를 거친 뒤에만 재시작. 시간 경과만으로 실패 처리하지 않음 |
| 실행 이력 없음 | 새 JobInstance로 실행 |

**강제 종료 복구 절차:** 프로세스가 kill되거나 컨테이너가 내려가면 Spring Batch가 상태를 바꿀 기회가 없어 `STARTED`가 남습니다. 복구는 두 가지를 확인한 뒤에만 진행합니다.

1. **기존 실행자 부재:** 실행 기록에 실행 인스턴스 ID를 남기고, chunk 커밋마다 갱신되는 실행 갱신 시각(`last_updated`)이 임계 시간 넘게 멈췄으며 그 인스턴스가 살아 있지 않음을 확인합니다. 임계 시간은 판매자 1명의 최대 트랜잭션 시간(D4 상한)보다 충분히 길게 잡고 구현 때 정합니다. 실행자가 살아 있으면 복구하지 않고 기다립니다.
2. **저장된 진행 상태:** 마지막으로 커밋된 판매자까지의 `payouts`·`payout_jobs`가 존재하고, 커밋되지 않은 판매자의 항목 선점은 롤백돼 `PAYABLE`로 남았는지 확인합니다. 커밋된 chunk와 ExecutionContext의 재시작 지점이 어긋나면 업무 DB를 기준으로 삼습니다.

두 조건을 만족하면 해당 실행을 `FAILED`로 바꾸고(종료 시각 기록) 같은 `batchDate`로 재시작합니다. 앱 기동 시에는 이 확인만 하고 조건을 만족할 때 복구하며, 판정이 불확실하면 운영자 확인으로 넘깁니다. 실행자 판정이 틀려 두 실행이 겹치더라도 판매자 항목 선점의 조건부 UPDATE(`status='PAYABLE'`)와 `UNIQUE(seller_id, batch_date, policy_version)`이 중복 배정·중복 배치를 막습니다. 다만 이 제약은 마지막 방어선이며 복구 절차를 대신하지 않습니다. 메타데이터 테이블 migration은 [DB 정책](../migrations.md)을 따라 구현 때 추가합니다.

### D8. 지급 워커의 실행 위치와 임대 로직

지급 워커의 **도메인 책임은 Settlement**에 둡니다. 지급 성공을 반영할 때 `payout_jobs`·`payouts`·`settlement_items`·`settlement_batches`와 알림 Outbox를 한 로컬 트랜잭션으로 바꿔야 하는데, 이 테이블을 모두 `settlement` DB가 소유하기 때문입니다. Payment에 두면 지급 데이터를 이벤트로 복제하고 결과 반영을 서비스 간 보상 흐름으로 맞춰야 하며, 환불·지급 예약의 배타성도 다른 서비스 데이터로 판단해야 합니다. 별도 지급 서비스는 신규 앱·DB를 추가하지 않는다는 [서비스와 코드 경계](../architecture.md)에 따라 범위 밖입니다. 임대·결과 반영 규칙은 [금융 Worker 임대와 결과 반영](../policies.md#금융-worker-임대와-결과-반영), 동시 실행 초기값은 [ADR 0005](0005-kafka-event-delivery-and-capacity.md#동시-실행과-자원-초기값)를 따릅니다.

이 절의 두 항목은 팀 의견을 받아 다시 반영합니다.

#### D8-1. 실행 위치

Payment는 같은 jar를 `payment-api`·`payment-worker`로 나눠 실행하지만 Settlement는 `settlement` 하나뿐입니다. 그대로 두면 API·이벤트 소비자·일배치·지급 워커가 한 프로세스의 스레드와 DB 연결 풀을 함께 씁니다.

| 후보 | 판단 |
| --- | --- |
| `settlement` 한 프로세스(제안) | 구성이 단순함. 마감 직후 일배치와 지급이 몰리면 판매자 조회 API 응답과 연결 풀에 영향을 줄 수 있음 |
| 같은 jar를 `settlement-api`·`settlement-worker`로 분리 | 도메인·DB는 그대로이고 실행만 나뉘어 따로 확장할 수 있음. Compose 서비스·역할별 Bean 활성화·메트릭 태그를 Payment처럼 추가해야 함 |

한 프로세스로 시작하고, 부하 시험에서 마감 직후 판매자 API의 응답 시간이나 연결 풀 대기가 [측정 지표](0002-performance-and-integrity-metrics.md) 기준을 넘으면 분리합니다.

#### D8-2. 임대 로직 공유

Payment 금융 워커와 Settlement 지급 워커는 같은 임대 규칙(조회 1초·임대 30초·HTTP 5초, 슬롯 8개 중 복구 전용 2개)을 씁니다. 현재 Gradle 모듈에는 서비스 간 공통 모듈이 없습니다.

| 후보 | 판단 |
| --- | --- |
| 서비스마다 구현 | 서비스 간 코드 의존이 생기지 않음. 같은 규칙을 두 번 구현하므로 동일한 장애 시나리오 테스트로 두 구현을 맞춰야 함 |
| 공통 모듈로 추출 | 임대 획득·token 검사·슬롯 관리를 한 곳에서 관리. 모듈 경계와 변경 책임을 새로 정해야 하고, 한쪽 변경이 다른 서비스에 영향을 줌 |

## 선택 이유와 대안

| 검토한 안 | 판단 |
| --- | --- |
| 지급 실행까지 Spring Batch로 처리 | 건별 재시도·미확정 조회·보류를 chunk로 다루기 어렵고, Job 이력이 중복 지급을 막지 않아 보류 |
| 원장 반영·환불을 배치로 모아 처리 | 반영·환불 지연이 배치 주기만큼 늘어 보류 |
| 일배치 없이 구매확정마다 즉시 지급 | 판매자별 합산이 사라져 송금 건수가 늘고, [ADR 0001](0001-payout-after-purchase-confirmation.md)의 일배치 지급과 맞지 않아 보류 |
| 일배치·대조만 Spring Batch, 나머지는 이벤트·워커 | 마감 고정·재시작이 필요한 곳에만 배치를 써 채택 제안 |

## 감수하는 비용과 검증

배치·지급 워커·이벤트 소비자·짧은 주기 스케줄러로 실행 방식이 넷으로 나뉘어 운영자가 볼 지표와 장애 지점이 늘어납니다. 대조를 매일 실행하면 그만큼 읽기 부하가 생기고, Payment 대조 조회 계약이라는 서비스 간 계약이 늘어납니다. 전달 확인을 위해 Outbox에 발행 위치를 저장하고 정산 원장에 원천 이벤트 시각을 남겨야 하며, 대조 Job이 Kafka 관리 API에 의존합니다. 강제 종료 복구는 실행자 부재 판정을 구현해야 하며 판정이 불확실하면 운영자 확인이 필요합니다. 판매자 쏠림 수치는 가정이며 실측하지 않았습니다.

- 결정 후 함께 고칠 문서: D2는 현재 정책(10:00)과 같아 고칠 문서가 없습니다. D3은 [업무 정책](../policies.md#정산재처리)에서 지급 대역의 영업일 달력 사용·`NON_BUSINESS_DAY` 보류와 재개 문장 삭제, [API 명세](../api.md#오류와-완료-기준)·[OpenAPI](../openapi.json)에서 `PAYOUT_NON_BUSINESS_DAY` 오류 제거, [데이터 모델](../data-model.md)의 `payouts.hold_reason` 값과 `payout_jobs` 제약의 비영업일 보류 문장 삭제, [와이어프레임](../wirefrees.html)의 비영업일 보류 안내 삭제. D6은 ADR 0002·0006의 대조 시점·결함 판정, API 명세·OpenAPI에 Payment 대조 조회 계약(전달 확인 필드 포함) 추가, [데이터 모델](../data-model.md#outbox)의 `outbox`에 발행 `partition`·`offset`·발행 시각, `settlement_entries`에 원천 이벤트 `occurred_at` 컬럼 추가, 서비스와 코드 경계의 "참조·금액 대조" 행. D7은 [서비스와 코드 경계](../architecture.md)의 정산 배치 행에 재시작 경계 연결. D8-1에서 분리를 고르면 [서비스와 코드 경계](../architecture.md)의 실행 표와 Compose 구성. D8-2에서 공통 모듈을 고르면 서비스와 코드 경계의 모듈 구성.
- 검증: 아래를 주입한 Clock과 통합 테스트·부하 시험으로 확인합니다.
  - 재시작: 실패·정상 중단 뒤 재시작, 판매자 chunk 처리 중 프로세스 강제 종료 뒤 `STARTED` 잔류 상태에서 복구 절차를 거친 재시작. 어느 경우든 누락·중복 배정·중복 지급이 없고, 실행자가 살아 있는 동안에는 복구가 진행되지 않는지
  - 완료 후 재요청: `COMPLETED`인 `batchDate`를 스케줄러·운영자 API로 다시 요청하면 새 실행 없이 기존 배치를 반환하는지
  - 주말·공휴일: 토·일·공휴일에도 10:00 일배치가 실행되고, 생성된 지급이 보류 없이 그날 실행되는지
  - 운영 중 대조: 결제·환불 이벤트와 지급 반영이 계속 들어오는 중에 대조를 실행해, `T` 이후 거래·진행 중 거래가 결함으로 세지지 않고 고의 결함만 결함으로 분류되는지
  - 소비 지연: `T` 이전에 발행까지 끝난 이벤트를 정산 Consumer를 멈춰 대기 상한보다 오래 묶어 두면 결함이 아니라 전달 대기 → 전달 지연으로 분류되고, Consumer 재개 뒤 워터마크를 지나면 재대조로 정상 판정되는지. 반대로 offset을 커밋했지만 Inbox 기록을 지운 고의 유실은 대기 없이 결함으로 잡히는지
  - 늦은 커밋: `T` 직전에 시작해 `T` 뒤에 커밋된 결제가 안전 여유 이후 조회에서 기준선에 포함되는지
  - 쏠림: 평균 쏠림(판매자당 약 3,000건)과 최대 점유율 상한 판매자를 각각 넣어 판매자 트랜잭션 시간·잠금 대기와 일배치 전체 소요 시간을 부하 시험으로 확인
- 재검토 조건: 판매자 한 트랜잭션이 잠금 대기·타임아웃을 일으키면 판매자 내부 분할을, 단일 스레드 소요 시간이 지급 지연 알람 기준에 가까워지면 D5를 다시 검토합니다.

이 문서는 설계 판단이며 문서 검사나 리뷰가 실제 배치 실행·재시작·부하 검증을 대신하지 않습니다.
