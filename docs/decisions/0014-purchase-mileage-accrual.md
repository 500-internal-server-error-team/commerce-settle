# 구매 마일리지 적립 시점과 책임

- 상태: 방식·초기 정책값 결정([#259](https://github.com/500-internal-server-error-team/commerce-settle/issues/259)), 구현·통합 테스트 완료. 만료·적립 알림의 범위 제외와 Payment 검토자는 확인 요청 중
- 결정일: 2026-11-10
- 범위: 구매 적립의 대상·계산·적립 시점, 환불과의 관계, Commerce·Payment 책임과 이벤트·DB 계약. 만료·알림·충전은 제외

## 결정

**결제 완료가 주문에 반영되면 적립 예정(PENDING)으로 기록하고, 자동 구매확정 때 사용 가능(AVAILABLE)으로 바꿔 잔액에 더합니다. 구매확정 전에 환불이 완료되면 예정을 취소(CANCELLED)합니다.** 예정은 잔액·가용액에 들어가지 않으므로 사용할 수 없고, 사용 가능해진 적립금을 회수하는 경로는 두지 않습니다.

- 대상은 쿠폰 없는 주문이고 기준액은 외부 결제액 E입니다. 사용한 마일리지에는 적립하지 않습니다.
- 금액은 `min(주문당 한도, floor(E × 적립률bp / 10,000))`이고 0점이면 기록·이벤트를 만들지 않습니다.
- 초기 정책값은 1%(100bp)·주문당 1,000점(`mileage-accrual-v1`)입니다.
- Commerce가 주문 생성 때 정책 사본(버전·적립률·한도)과 예정액을 주문에 고정합니다. 정책을 바꿔도 이미 만든 주문의 약속은 바뀌지 않습니다.
- Payment가 적립 상태·지갑 증액·원장을 소유합니다. Settlement는 바뀌지 않습니다.

| 항목 | 값 | 상태 | 근거 |
| --- | --- | --- | --- |
| 적립 시점(예정 → 사용 가능 → 환불 시 취소) | 위 결정 | 확정 | #259 주문 담당 결정 |
| 적립률·주문당 한도 | 1%·1,000점 | 확정(초기값) | #259 결정. 효과는 측정하지 않음(아래 가정 1) |
| 쿠폰 주문 제외·사용 마일리지 재적립 없음 | — | 확정 | #259 결정, 아래 비용 비교 |
| 정책 사본을 주문 생성 때 고정 | — | 구현 판단 | 정책 변경 중 지연 수신에도 금액이 같아야 함 |
| 만료·적립 알림 제외 | — | 제안(확인 요청 중) | 첫 범위 축소 |

## 문제와 판단 기준

구매 → 적립 → 다음 구매에서 사용하는 흐름을 추가하려 합니다. 기존 Payment에는 지갑·예약·차감·원장(`SEED/RESERVE/RELEASE/DEBIT/RESTORE`)·전액 환불 복원이 있고 구매 적립은 없었습니다. 판단 기준은 다음과 같습니다.

1. 환불과 함께 쓰여도 잔액이 음수가 되거나 다른 서비스의 금액 계약이 바뀌지 않을 것
2. 이벤트 재전달·순서 뒤바뀜·커밋 뒤 ACK 전 중단에서도 결제당 한 번만 반영될 것
3. 기존 Outbox·Inbox·확인 대상 운영 규칙을 그대로 쓸 것

코드로 확인한 사실:

- 환불 마감은 배송완료 + 168시간(`refundDeadlineAt`)입니다. 자동 구매확정은 `현재 시각 > refundDeadlineAt`이고 진행 중 취소·반품·환불이 없을 때만 일어납니다(`Order.confirmPurchaseIfDue`).
- 환불 접수는 `PAID`이고 마감 전일 때만 가능합니다(`Order.beginRefund`). 그래서 구매확정 뒤에는 환불 경로가 없습니다.
- Payment 환불은 Commerce 주문 복구 확인(`RefundOrderRestored`)을 반영할 때 `COMPLETED`가 됩니다(`RefundEventHandler.orderRestored`).
- Settlement는 환불을 원결제 원액으로 상쇄합니다([API 이벤트 계약](../api.md#이벤트-전달-계약)). 외부 환불액을 줄이는 방식의 회수는 이 계약과 맞지 않습니다.

## 대안

| 안 | 내용 | 장점 | 비용·위험 |
| --- | --- | --- | --- |
| A. 결제 즉시 사용 가능 | 결제 완료 때 잔액에 더함 | 바로 쓸 수 있음 | 환불 때 이미 쓴 적립금을 회수해야 함. 잔액이 부족하면 음수 잔액, 외부 환불액 공제(Settlement 원액 상쇄와 충돌), 손실 처리 중 하나를 정해야 함 |
| B. 결제 완료 시 예정, 구매확정 시 사용 가능(**선택**) | 예정은 잔액 밖에 두고 구매확정 때 더함 | 결제 직후 예정액 안내 가능. 회수 불필요 | 이벤트 2종·적립 상태 테이블 필요. 사용까지 배송 + 7일 이상 걸림 |
| C. 구매확정 시 한 번에 적립 | 예정 없이 구매확정 이벤트 하나로 지급 | 이벤트·상태가 가장 적음 | 결제 직후 예정액을 보여 줄 근거가 Payment에 없음. 확정 전 환불 여부를 Payment가 따로 판단해야 함 |
| D. Commerce가 적립까지 소유 | 주문 서비스가 적립 잔액 관리 | 주문과 한 트랜잭션 | 마일리지 잔액이 Payment·Commerce 두 곳으로 갈라짐([ADR 0004](0004-domain-responsibilities.md)의 Payment 소유와 충돌) |

## B를 선택하는 근거와 감수하는 비용

- **회수가 필요 없습니다.** 사용 가능 시점이 환불 마감 이후라, 잔액에 들어간 적립금이 환불로 되돌려질 경로가 없습니다. 기준 1을 추가 규칙 없이 만족합니다.
- **기존 운영 규칙을 그대로 씁니다.** 두 이벤트는 기존 Commerce 토픽·`paymentId` key·Outbox로 보내고, Payment는 환불 이벤트와 같은 Inbox 선점·재시도·확인 대상 규칙으로 처리합니다. 주문 ID로 잠가 같은 주문의 환불 이벤트와 직렬화합니다.
- **결제당 한 번:** eventId를 종류와 `paymentId`로 고정하고, Payment는 결제당 적립 1건(UNIQUE)·PENDING에서 한 번만 바뀌는 상태 전이·`ACCRUAL` 원장 결제당 1건(부분 UNIQUE)으로 막습니다.

감수하는 비용:

- 사용 가능까지 최소 배송 기간 + 168시간이 걸립니다.
- 상태 테이블(`mileage_accruals`)·이벤트 2종·정합성 검사가 늘어납니다.
- 예정보다 확정이 먼저 처리되면 확정은 시도 상한(10회) 안에서 다시 처리되고, 그래도 예정이 없으면 확인 대상이 됩니다.
- 첫 적립이면 Payment가 0점 지갑을 엽니다. 같은 구매자의 동시 생성은 `buyer_id` 유일 조건으로 한쪽이 롤백된 뒤 재처리됩니다.

## 쿠폰 주문을 제외한 이유(비용 모형 비교)

[쿠폰 비용 모형](../policies.md#비용과-손익-기준)에서 등급 7,000원 쿠폰의 최소 주문(E 83,000원) 잔여액은 952원입니다. 1% 적립(830점)을 더하면 122원으로, 등급 쿠폰 기준 `H≥500원`을 밑돕니다. 이것은 기존 **미검증 비용 가정**에 따른 비교이며 실제 수익 측정이 아닙니다.

## 가정과 검증 방법

| # | 가정·추정 | 근거 | 검증 방법 |
| --- | --- | --- | --- |
| 1 | 1%·1,000점이 재구매를 유도할 만한 수준이다 | 정하지 않음. 팀 결정값 | 시연·운영 데이터로 적립 후 재구매율을 측정해야 하며 이번 범위에서는 측정하지 않음 |
| 2 | 구매확정 뒤 환불 경로는 계속 없다 | 현재 `Order.beginRefund` 조건 | 구매확정 뒤 환불을 추가하면 이 ADR을 재검토. Payment는 그 경우 AVAILABLE 적립을 바꾸지 않고 경고만 남김 |
| 3 | 플랫폼이 적립 비용을 부담하고 판매자 정산은 바뀌지 않는다 | 이벤트·정산 계약에 적립이 없음 | Settlement 변경 없음. 비용 회계 반영은 별도 결정 |

## 구현과 검증

- Commerce: 주문 생성 때 `orders.accrual_*` 고정, 결제 완료 반영 트랜잭션에서 `MileageAccrualScheduled`, 자동 구매확정 트랜잭션에서 `MileageAccrualConfirmed` 저장. 설정 `app.mileage-accrual.*`(기본 켬)
- Payment: `mileage_accruals`, 원장 `ACCRUAL`, 적립 처리기, 환불 완료 때 예정 취소, 지갑 조회 `pendingAccrualAmount`, 정합성 검사(`mileageBalance`에 ACCRUAL 포함, `mileageAccruals`)
- 검증: 계산 경계(0점·버림·한도·쿠폰), 예정 → 사용 가능·재전달 무변경·첫 지갑 생성, 예정 → 환불 완료 → 취소 → 뒤늦은 확정은 확인 대상, 예정보다 먼저 온 확정의 재처리, 잘못된 예정·같은 결제의 다른 예정, 이벤트 계약(OpenAPI)·고정 eventId·key. 실행 결과는 구현 PR에 남깁니다.

## 재검토 조건

- 구매확정 뒤 환불·부분 환불을 도입할 때
- 적립률·한도를 바꾸거나 쿠폰 주문에도 적립하려 할 때
- 만료·알림을 추가할 때
