# 회차별 시연 기한과 즉시 정산

- 상태: 구현, 전용 환경에서 명시적으로 활성화
- 결정일: 2026-11-14
- 연결 이슈: [#386](https://github.com/500-internal-server-error-team/commerce-settle/issues/386)

## 문제와 선택

일반 주문은 발송 후 2~3영업일의 배송과 배송완료 후 168시간의 환불 기간을 거칩니다. 구매확정·결제 원장이 모두 도착한 항목은 이후 첫 10시 일배치의 대상입니다. 배치 실행 버튼만으로 이 대기를 줄일 수 없습니다.

**전용 시연 환경에서 회차별 배송·환불 기간을 고정하고, 준비된 항목을 실제 현재 시각 마감으로 정산합니다.** EC2·앱·DB 시각과 인증·임대·재시도 시간은 유지합니다. 회차를 만들 때 각각 1~3600초를 선택하며, UI의 시작값은 배송 5초·환불 10초입니다. 다음 회차의 값은 재배포 없이 바꿀 수 있습니다.

전역 Clock 이동은 세션·임대·SQL 시각까지 영향을 주므로 제외했습니다. 구매확정·환불 검사를 생략하면 실제 상태 전이와 금액 보존을 보여줄 수 없습니다. 기존 전이·Outbox·Spring Batch·지급 워커를 재사용하고 회차 식별·대상·마감만 별도로 보존합니다.

현행 기한·배치 정책은 [회차별 시연 예외](../policies.md#회차별-시연-예외)가 소유합니다. 아래는 적용 경계와 선택 이유입니다.

## 활성화와 불변 조건

- 기본값은 비활성입니다. DB·Kafka·Redis를 분리한 모의 금융 환경에서 `app.demo.enabled=true`, `app.demo.isolated=true`로 켭니다. 격리는 운영자가 실제로 구성해야 합니다.
- Commerce의 자동 발송과 Settlement의 정기 일배치를 꺼야 기동합니다. 시연 모드에서는 기존 일반 정산 생성·일배치 실행도 막습니다.
- 각 서비스는 활성화 시 자기 DB에 `demo_environment` 표식을 남깁니다. 해당 DB를 시연 모드 없이 재기동할 수 없습니다. 표식 삭제로 환경을 전환하지 않고 [실험 환경 적용 절차](../migrations.md)를 따릅니다.
- 주문 생성의 선택 입력 `demoRunId`가 회차의 판매자·상품·이벤트와 일치해야 합니다. 배송·환불 초를 주문에 복사하고 변경하지 않습니다. 기존 금액·결제 정책 버전은 유지하고, 회차·시연 정산에는 `demo-periods-v1`을 기록합니다. 회차·환불 초 사본을 구매확정 이벤트에도 담아 소비자가 같은 기한을 검증합니다.
- 회차 고정과 신규 주문·거절 후 결제 재시도는 같은 회차 행 잠금으로 직렬화합니다. 고정 후 새 주문·재시도는 거절합니다. 결제·취소·환불 진행 중에는 고정할 수 없습니다. 이벤트 회차는 매진도 확인합니다.
- 고정된 모든 주문 ID를 보존합니다. 확정 거절·취소는 제외로, 전액 환불은 별도 제외 근거로 남깁니다. 최대 10000건·한 판매자·한 상품·선택한 한 이벤트를 지원합니다.

## 실행과 책임

| 단계 | 동작 | 소유 |
| --- | --- | --- |
| 회차 생성 | 판매자·상품·이벤트와 기간을 주문 생성 전에 저장 | Commerce |
| 대상 고정 | 매진·결제·취소·시연 환불의 완료를 확인하고 주문 ID를 고정 | Commerce |
| 발송 시작 | 고정 후 남은 결제 주문을 기존 발송 경로로 처리 | Commerce |
| 도래한 기한 처리 | 실제 배송 시각·환불 마감에 도달한 전이와 Outbox만 실행 | Commerce |
| 정산 실행 | 원장·구매확정·환불 반영을 확인하고 대상 ID·실제 마감 저장 후 비동기 Spring Batch 실행 | Settlement |
| 결과 확인 | 배치 완료·대상 수·환불 수·순액·모의 지급 상태를 각각 조회 | Settlement·기존 지급 워커 |

내부 API와 입력·응답은 [OpenAPI](../openapi.json), DB 정의는 [데이터 모델](../data-model.md#시연-회차)을 따릅니다. demo-control은 기존 운영 자격으로 호출을 중계하며 다른 서비스 DB를 수정하지 않습니다. Commerce의 정산 컨텍스트 조회만 `SERVICE:settlement`에 허용하고 나머지 명령·조회는 `OPERATOR`에 한정합니다.

발송·기한 처리는 요청당 50건으로 제한하고 `nextCursor`, `processedCount`, `waitingCount`를 반환합니다. UI가 페이지를 이어 호출하며 미도래 항목은 기다린 뒤 새 처리 요청으로 진행합니다. 부분 실패는 같은 키로 재개합니다. 배송·환불 마감 전에는 다음 상태를 만들지 않습니다. 일반 워크플로의 결제 대기 만료·취소 복구는 시연 주문에도 유지합니다.

## 정산과 재시작

1. 모든 지급 대상의 원장·구매확정과 환불 제외 결과가 도착해야 합니다. Settlement는 자기 원장에서 판매자·상태·예약 여부·정확한 주문 집합을 다시 확인합니다.
2. 서버의 실제 현재 시각을 마이크로초로 고정하고 모든 대상에 `readyAt < cutoffAt`을 적용합니다. 정각·미도래 항목은 저장 전에 대기로 돌려줍니다.
3. reader와 판매자 항목 선점 SQL 모두 저장한 항목 ID·마감을 사용합니다. 회차 밖 일반 항목은 가져오지 않습니다.
4. JobInstance는 `demoRunId`·고정 마감으로 식별합니다. 같은 날 같은 판매자의 다음 회차도 분리하며 기존 예약·지급을 다시 만들지 않습니다. 정책 버전에 임의 회차 값을 붙이지 않습니다.
5. 같은 회차의 PostgreSQL 실행자 잠금과 기존 Spring Batch 복구를 사용합니다. 실패는 건너뛴 완료로 숨기지 않고 같은 대상·마감으로 재시작합니다. 강제 종료 잔류는 실행자 부재·기존 정체 기준을 확인한 뒤 재시작합니다.
6. 완료 회차의 대상·마감은 확장하지 않습니다. 늦은 중복 실행이 `COMPLETED`를 되돌릴 수 없으며, 배치 완료와 모의 지급 성공은 별도 상태입니다.

## 화면과 촬영

기존 실험 화면에 회차 생성·불러오기, 대상 고정·발송·기한 처리·정산 실행을 배치합니다. 기간과 회차 ID를 항상 확인하고 **정산 준비 → 실제 배치 완료 → 모의 지급 성공**을 촬영합니다. 자막에는 `시연 모드: 배송 5초 · 환불 10초`처럼 실제 선택값과 대기 생략 여부를 표시합니다.

시연을 일반 정책의 영업일 경과나 10시 정기 실행으로 설명하지 않습니다. 부하·매진·환불·정산의 같은 거래 연결과 금액은 실제 조회 결과로 확인합니다. 구현 PR의 검증 결과와 공유 환경 배포 여부는 구분합니다. 실행 방법은 [개발 환경](../development.md#회차별-시연-기한과-즉시-정산)을 따릅니다.
