# 쿠폰·마일리지와 원장·정산·지급의 책임 분리

- 상태: 설계 기준·구현 예정
- 결정일: 2026-10-27
- 범위: 기존 서비스 안의 업무 책임 명확화. 서비스·DB·공통 업무 모듈을 추가하지 않음

## 결정

쿠폰은 커머스의 독립된 업무 도메인으로, 마일리지는 Payment의 잔액 도메인으로 관리합니다. 웰컴·월간 우수고객·판매자 쿠폰은 같은 쿠폰 도메인에서 발급 정책을 구분하고 예약·사용·복구를 공유합니다.

정산 원장·정산·지급은 각각 기록·대상 확정·외부 송금의 책임으로 나누고 기존 Settlement 서비스·DB 안에 둡니다. 마일리지 원장과 쿠폰 비용 이력, 금융 Mock의 현금 기록은 각각 기존 원천 서비스에 유지합니다. 전체 책임 표는 [서비스와 코드 경계](../architecture.md#ddd-집계와-검증)가 소유합니다.

앱·모듈·실행·패키지와 소유 DB·계정·스키마 이름을 `commerce`로 통일합니다. 문서의 커머스라는 업무 명칭과 실제 `seller` 앱 이름이 달라 구매자 가입·주문과 플랫폼 웰컴 쿠폰까지 판매자 업무로 오해할 수 있기 때문입니다. 판매자 업무의 `Seller`·`SELLER`·`sellerId`·`seller_accounts`·`/api/sellers`는 유지합니다. 배포 전 설계 단계이므로 초기 DB 구성과 초기 SQL의 스키마 명칭도 `commerce`, 비밀번호 변수는 `COMMERCE_DB_PASSWORD`로 맞춥니다.

`marketplace`도 여러 구매자·입점 판매자를 연결하는 제품을 표현할 수 있지만, 기존 커머스 업무 명칭을 다시 바꿀 만큼 책임·배포 경계가 달라지지는 않습니다. `commerce`는 계정·상품·주문·쿠폰·거래 이행을 포괄하기에 충분합니다. `storefront`·`sales`는 구매 화면이나 판매 측에 치우치고, `platform`·`commerce-core`는 맡은 책임을 더 구체적으로 드러내지 않아 채택하지 않습니다. 금융 실행은 Payment, 정산·지급은 Settlement가 소유하며 앱 이름이 그 책임을 합친다는 뜻은 아닙니다.

## 선택 이유와 대안

고객이 받는 혜택이라는 공통점만으로 쿠폰과 마일리지를 합치면 할인권의 자격·기한·상품·비용 부담과 결제 잔액의 예약·차감·복원을 한 모델에서 구분해야 합니다. 특히 판매자 쿠폰은 수수료 기준 상품대금을 줄이고 플랫폼 쿠폰은 플랫폼 지원액으로 보전하므로, 모두 같은 잔액으로 전환하면 최초 할인 조건과 부담자를 별도로 추적해야 합니다.

설명용으로, 월간 쿠폰을 사용한 주문을 쿠폰 만료 뒤 전액 환불하면 원쿠폰의 이력·비용은 상쇄하지만 재사용이나 대체 발급은 허용하지 않습니다. 마일리지 주문은 사용한 점수를 원계정에 복원합니다. 현재 마일리지에는 만료 정책이 없습니다. [쿠폰·마일리지 정책](../policies.md#쿠폰)의 이 차이가 별도 모델을 유지할 이유입니다. 월간 우수고객 선정에 쓰는 구매 실적도 사용 가능한 마일리지 잔액과 구분합니다.

반면 쿠폰 세 종류는 공통 발급 이력과 `ISSUED→RESERVED→USED` 상태를 사용합니다. 차이는 가입·월 구매 실적·판매자 캠페인이라는 발급 자격과 비용 부담·기간·수량 조건입니다. 종류별 처리 시스템을 만들면 같은 중복 사용 방지·미확정 예약 유지·원쿠폰 복구 규칙을 반복하게 됩니다.

정산 원장은 [정산 항목에 귀속된 금액 배분·상쇄 기록](../data-model.md#settlement_entries)입니다. Payment가 확정한 최초 금액을 기록하고 검증하며, 현재 쿠폰이나 구독 상태로 과거 수수료를 다시 결정하지 않습니다. 예를 들어 외부 환불이 성공해도 정산 원장 상쇄와 주문 복구가 남아 있으면 전체 환불은 완료되지 않습니다. 이를 추적하는 주체는 Payment의 환불 SAGA이며, 원장 자체가 다른 도메인의 상태를 직접 변경하지 않습니다.

| 검토한 안 | 판단·이유 |
| --- | --- |
| 쿠폰과 마일리지를 하나의 혜택 잔액으로 관리 | 할인 조건·부담자·만료 후 복구와 결제 잔액의 규칙이 달라 제외 |
| 쿠폰 종류마다 별도 도메인·처리 시스템 구성 | 공통 생애주기를 반복하므로 제외. 한 도메인에서 발급 정책을 구분 |
| 쿠폰을 독립 서비스·DB로 배포 | 가입·웰컴 발급과 주문·재고·쿠폰 예약의 원자 처리를 분산시켜 별도 대기·보상 계약이 필요하므로 보류 |
| 원장들을 하나의 Ledger 서비스로 통합 | 구매자 잔액·할인 비용·정산 배분·모의 현금의 원천과 원자 처리 경계가 달라 제외 |
| 정산 원장만 별도 Ledger 서비스로 배포 | 원장 반영과 정산 항목 생성·상쇄 사이의 대기·복구 계약이 늘어나므로 현재 범위에서는 보류 |
| 기존 서비스 내부에서 도메인 책임 구분 | 현재 원자 처리를 유지하며 규칙·모델의 변경 책임을 명확히 할 수 있어 채택 |

## 감수하는 비용과 재검토 조건

커머스 내부 도메인은 함께 배포·확장되며, 정산 원장의 저장 부하도 Settlement와 함께 관리합니다. 응용 서비스가 여러 집계의 원자 처리를 조율하고 각 도메인이 자기 규칙을 보호하도록 구현해야 합니다. 책임 구분만으로 장애 격리나 처리량 향상을 달성했다고 보지 않습니다.

여러 독립 제품이 쿠폰 또는 정산 원장을 함께 사용하거나, 특정 도메인에 독립적인 배포·확장·운영 책임이 생기면 서비스 분리를 재검토합니다. 이때 기존 원자 처리를 대체할 완료·재전달·복구 계약과 전체 운영 비용을 함께 비교합니다. 쿠폰 종류나 클래스 수가 늘었다는 사실만으로 배포 경계를 나누지 않습니다.

## 구현 검증

- 같은 쿠폰의 동시 주문과 미확정 결제에서 중복 사용·조기 예약 해제가 없는지 확인합니다.
- 쿠폰 만료 후 환불과 마일리지 환불이 각 원래 조건에 따라 한 번만 복구되는지 확인합니다.
- Payment의 최초 수수료·순액을 Settlement가 그대로 기록·상쇄하고 이벤트 중복·역순에도 중복 원장이 생기지 않는지 확인합니다.
- 같은 정산 항목의 환불/지급 단일 선점과 원장 반영 지연 중 지급 차단을 확인합니다.
- 주문 복구 확인 전에는 전체 환불을 완료하지 않고, 확인 재전달로 중복 복구하지 않는지 확인합니다.

구체적인 금액·상태·이벤트·저장 제약은 [업무 정책](../policies.md), [API](../api.md#이벤트-연동), [데이터 모델](../data-model.md)이 소유합니다. 이 결정은 업무 코드·초기 SQL·실행 정합성 검증 완료를 뜻하지 않습니다.
