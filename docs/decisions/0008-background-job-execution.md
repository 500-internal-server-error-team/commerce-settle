# 앱 내부 스케줄링과 월간 혜택 Job

- 상태: 설계 결정. Job·운영 API·메타데이터 migration은 구현 전
- 결정일: 2026-10-28
- 범위: 실행 계기와 처리 도구, 월간 혜택의 Step·재시작·오류 교정

## 결정

**각 앱의 Spring Scheduler가 Spring Batch Job을 시작합니다.** 별도 스케줄링 서버는 추가하지 않습니다. Commerce는 월간 혜택 Job 하나에서 **대상 확정·자동 검증 → 쿠폰 발급**을 순서대로 처리합니다. Settlement의 정산 일배치·대조는 별개 Job이며 실제 지급은 영속 작업을 임대하는 Worker가 맡습니다. 정산의 세부 선택 상태와 복구 기준은 [ADR 0007](0007-settlement-batch-scope-and-schedule.md)을 유지합니다.

집계 오류는 **발급 전 0건 회차에 한해 취소하고 대체 회차를 만드는 절차**로 교정합니다. 발급0건인 잘못된 빈 COMPLETED 회차도 원래 발급 기한 안에서는 교정할 수 있습니다. 정상 회차의 자동 실행·재시도에는 운영자 승인 단계를 추가하지 않습니다. [업무 정책](../policies.md#월간-회차-검증과-오류-교정)이 조건을, [데이터 모델](../data-model.md#coupon_issue_runs)·[운영 조회와 교정 API](../api.md#월간-혜택-운영-조회와-오류-교정)가 저장·호출 계약을 소유합니다.

## 실행 방식 비교

Scheduler는 언제 시작할지, Batch는 시작한 작업을 어떤 단계·진행 상태로 처리할지 맡습니다. 둘을 대체 기술로 비교하지 않습니다.

| 후보 | 이 프로젝트에서 가능한 구성 | 장점 | 감수하는 비용·선택 |
| --- | --- | --- | --- |
| 앱 내부 Scheduler → 응용 서비스 | 기존 발급 회차·대상 행에서 PENDING을 찾아 분할 처리 | 의존성·실행 메타데이터가 적음. 기존 업무 행으로도 중복 방지·재개 가능 | 단계 조율·실행 통계·중단 후 재시작 제어를 직접 관리. 충분히 가능한 단순안 |
| 앱 내부 Scheduler → Spring Batch Job | 같은 업무 행에 Job·Step 실행 이력과 재시작 제어를 연결 | 정산과 월간 혜택의 실행·실패 관측 방식이 같고 완료 Step을 재실행하지 않음 | **선택.** 각 소유 DB의 Batch 메타데이터·migration과 업무 상태의 정합성을 함께 관리해야 함 |
| 외부 스케줄러·독립 실행 프로세스 | 외부 시스템이 각 Job 실행을 요청 | 앱과 실행 자원을 독립적으로 운영하기 쉬움 | 현재 독립 운영·확장 요구가 없어 서버·배포·자격·장애 경계를 늘릴 근거가 부족함 |

월간이라는 이유나 대상이 많다는 추정만으로 Batch가 필수인 것은 아닙니다. 기존 `coupon_issue_runs`·`targets`로 단순안을 구현할 수 있습니다. 이 프로젝트는 **단계 재시작과 정산 Job의 운영 방식 일치**를 선택 근거로 삼고 추가 메타데이터 비용을 감수합니다. 업무 중복 방지의 원본은 계속 업무 DB입니다.

Scheduler 콜백은 실행 풀에 Job을 넘기고 오래 점유하지 않습니다. Job·API·Consumer·Worker의 풀과 동시성 상한, 공유 JDBC 풀의 대기를 검증합니다. Batch 라이브러리와 메타데이터 테이블이 별도 서버나 공통 업무 DB를 뜻하지는 않습니다. 상세 배치는 [실행 구조도](../diagrams/background-execution.svg)를 따릅니다.

## 두 Step과 세 Step 비교

| 기준 | 대상 확정·자동 검증 → 발급 | 대상 확정 → 검증 → 발급 |
| --- | --- | --- |
| 자동 검증 실패 | 첫 Step을 실패로 종료하고 발급하지 않음 | 검증 Step을 실패로 종료하고 발급하지 않음 |
| 재시작 | 첫 Step이 완료됐으면 건너뛰고 고정 대상의 미발급분 재개 | 완료된 확정·검증 Step을 건너뛰고 발급 재개 |
| 별도 검증 운영 | 첫 Step의 책임에 포함 | 검증만 재실행하거나 별도 담당·승인 대기를 둘 때 유리 |
| 현재 요구와 비용 | **선택.** 자동 점검만 필요하며 단계·상태 수가 적음 | 별도 검증 운영 요구 없이 Step·중간 상태가 늘어남 |

첫 Step은 동일 마감 자료의 대상·순위·등급·템플릿을 고정하고 검증합니다. PREPARING에서의 분할 저장·중단은 같은 원자료로 완성하며, 검증을 마친 대상 수·경계 금액과 ISSUING 전이를 확정한 뒤에만 발급 Step으로 넘어갑니다. 확정 이후에는 자동 재실행으로 순위를 다시 매기지 않습니다. 업무의 ISSUING 전이 뒤 Step 완료 이력이 실패·유실돼도 저장한 확정 결과를 확인해 재사용하며, 메타데이터 상태만으로 다시 선정하지 않습니다.

검증은 원자료와 대상의 일치, `RANK() <= 100`의 동점자 전원 포함, 중복 없음, 등급별 할인 합계를 확인합니다. **플랫폼 발급 수·월 할인 예산 상한은 없습니다.** 판매자 캠페인의 한도를 플랫폼 월간 혜택에 적용하지 않습니다. 계정 식별·자전거래 대응의 상용 검증을 이 구조 검사만으로 끝났다고 보지 않습니다. 별도의 검증 실행이나 승인 대기 요구가 생기면 업무 정책과 함께 Step 분리를 재검토합니다.

예를 들어 100위 동점자를 포함해 104명이 선정되고 60명 발급 뒤 중단되면, 첫 Step의 확정 결과와 60장의 쿠폰을 보존하고 나머지 44명만 처리합니다.

## 취소·재선정 비교

| 후보 | 장점 | 문제·선택 |
| --- | --- | --- |
| 같은 월은 어떤 경우에도 재선정 금지 | 회차 식별과 재시작이 단순 | 발급 전 집계 오류도 정식 절차로 교정할 수 없음 |
| 발급 전 0건 회차만 취소·대체 | 오류 교정 이력을 보존하면서 발급된 혜택을 보호 | **선택.** 취소·첫 발급의 경합, 월별 유일성·Job 식별을 함께 바꿔야 함 |
| 발급 뒤에도 회차 교체·쿠폰 회수 | 이미 발급된 오류도 정정 가능 | 사용·예약·환불·회수의 새 정책이 필요하므로 포함하지 않음 |

운영 교정은 원래 회차의 실행자 부재·종료 상태와 발급 0건을 확인한 뒤 한 트랜잭션에서 원회차 취소, 대체 회차 생성, 감사·멱등 결과를 저장합니다. 런처의 실행 등록·대상 저장·발급도 같은 회차 행 잠금을 사용하고 상태를 다시 확인합니다. 첫 발급이 먼저 커밋하면 교정을 거절하고, 취소가 먼저 커밋하면 이전 실행의 지연 저장을 거절합니다. 실행 이력이 STARTING/STARTED/STOPPING이면 먼저 정상 중단·복구하며 메타데이터를 임의로 바꿔 실행자 부재를 대신하지 않습니다.

대체 회차는 원래 대상월·마감·정책 버전·쿠폰 만료를 보존합니다. 운영자가 구매자 목록·순위·할인액을 입력하거나 현재 구매 실적으로 바꿀 수 없습니다. 취소된 회차의 대상·감사는 삭제하지 않으며 새 회차의 `replaces_run_id`로 연결합니다. 취소되지 않은 회차는 월당 하나이고, 기존 쿠폰의 구매자·혜택 월 중복 방지도 유지합니다.

## 실행 식별과 복구

- 월간 Job의 식별 파라미터는 `targetMonth`와 `runId`입니다. 정상 재시작은 같은 값을 쓰며 시각·증가 번호로 새 JobInstance를 만들지 않습니다. 대체 회차만 새 runId를 사용합니다.
- 월 시작 00:10 KST부터 도래 회차를 만들고 10분마다 미생성·미완료 회차를 확인합니다. 앱 복구 시 놓친 실행도 찾습니다. 월 마감 자료를 재구성할 수 없으면 발급을 미룹니다.
- COMPLETED는 기존 결과를 반환하고 CANCELLED는 실행하지 않습니다. FAILED/STOPPED는 같은 식별자로 재시작합니다. STARTED 잔류·업무 상태와 실행 이력의 불일치는 실행자·커밋된 진행 상태를 확인해 복구하며 새 파라미터로 우회하지 않습니다.
- 원래 쿠폰 만료 뒤에는 재선정·발급 없이 EXPIRED로 종결합니다. 지연·교정으로 만료를 연장하지 않습니다.
- 기동 시 Job 자동 실행을 끄고 Scheduler의 도래 회차 판단으로 시작합니다. 실행 DB는 각 서비스 소유 DB이며 Batch 메타데이터 migration을 Job 구현과 함께 관리합니다. 버전은 프로젝트 Spring Boot의 관리 버전을 사용합니다.

## 검증 기준

104명 동점자 선정과 예산 상한 없음, 중간 발급 뒤 재시작, 검증 실패 시 무발급, 발급 0건 교정과 첫 발급의 경합, 취소된 실행의 지연 저장, 같은 교정 요청의 응답 유실·재시도, 마감 자료 부재·월 만료·STARTED 잔류를 확인합니다. 기존 서비스별 DB 경계와 정산의 매일 지급·대조 조건도 보존합니다. 이 문서·명세 검토는 아직 없는 Job·API의 실행 검증을 대신하지 않습니다.
