# 상세 설계 초안

구매자의 주문·결제·환불과 판매자 정산의 정합성·장애 복구·부하 처리를 검증하는 기술 프로젝트의 설계 초안입니다. 구매자·판매자 계정, 구현 경계와 선택 이유, 업무 흐름과 검증 항목을 정리합니다. 업무 기능 구현·성능 검증은 별도로 수행합니다.

## 1. 기준과 책임

- [README](../README.md): 기본 기능·금액 정책·정합성·성능 목표의 기준입니다.
- [프로젝트 초안](proposal.md): 상품 범위·검증 목표·선택 확장·이름별 역할 배분을 관리합니다.
- 이 문서: 포함·제외 범위, 가정과 이유, 업무 흐름·검증 계약·예상 질문을 구체화합니다. 새 입력·처리 방안은 **설계 제안**으로 표시합니다.
- [서비스와 코드 경계](architecture.md), [DB 정책](migrations.md), [공통 구현 규약](../CONTRIBUTING.md#구현-규약): 코드·저장·요청·오류·이벤트 형식을 관리합니다.

설계는 서비스 경계와 각 도메인의 상태·금액 규칙·ERD·API·이벤트·동시성·복구·테스트 시나리오를 구체화합니다. 각 담당자는 자기 영역의 설계·구현·테스트를 맡고, 서비스 간 계약과 변경 영향을 함께 검토합니다. 합의한 변경은 기준 문서 한 곳에 반영하고, 개인 메모나 PR 설명만으로 계약을 바꾸지 않습니다.

## 2. 해결 범위

구매자가 우리 서비스에서 상품을 고르고 배송지·쿠폰·결제수단을 선택해 주문합니다. 구매자의 결제·환불과 판매자의 매출·정산·지급을 연결합니다. 프로모션의 요청 집중과 외부 금융 장애를 시험 조건으로 사용하고, [선택 확장](proposal.md#선택-확장-후보)은 기본 구현의 착수 조건이 아닙니다.

| 영역 | 포함 | 제외·외부 책임 | 선택 이유와 남는 책임 |
| --- | --- | --- | --- |
| 사용자·판매자 | 구매자·판매자 계정별 가입·로그인·권한, 판매 상태·정산 정보, 기본 배송지 | 계정 자동 연결·직원/다중 운영자·실제 사업자 심사·실계좌 검증 | 구매와 판매의 로그인·복구·접근 범위를 분리합니다. 같은 사람이 양쪽을 이용하려면 각각 가입합니다. |
| 상품·주문 | 상품 등록·조회·가격·판매 가능 수량, 한 상품의 수량 주문, 금액·배송지 사본, 재고 예약 | 검색 고도화·장바구니·다중 판매자 주문 | 구매자가 결제할 대상을 우리 서버가 확정합니다. 가격·주소 변경으로 기존 주문을 덮어쓰지 않습니다. |
| 쿠폰 | 사전 준비한 판매자 부담 정액 쿠폰 한 장, 적용 조건·예약·사용·복구 | 쿠폰 대량 발급 행사·중복 할인·플랫폼 분담금·적립금 | 할인 후 금액으로 결제·환불·정산을 일치시킵니다. 0원 결제는 기본 범위에서 제외합니다. |
| 배송·반품 | 배송지 저장, 판매자 발송 처리, 구매 확정, 취소·반품 요청/승인 상태 | 택배사 연동·배송 추적·실제 수거·검수·비용 계산 | 판매자 발송 입력과 실제 배송 증명을 구분합니다. 구매 확정과 환불 상태가 정산 가능 판단의 입력입니다. |
| 결제 | 접수·PG 승인·조회·멱등성·미확정 복구 | 실카드 정보 수집·실PG 계약·다중 결제수단별 특수 정책 | 외부 금융 실패를 모의하면서 내부 처리의 정확성을 검증합니다. |
| 환불 | 지급 예약 전 전액 환불·예약·보상·조회 | 부분 환불·교환·지급 후 환불·반품 분쟁 판정 | 첫 SAGA와 금액 보존에 집중합니다. 제외한 예외가 실제로 발생하지 않는다고 가정하지 않습니다. |
| 정산·지급 | 원장·수수료·지급 대상 예약·배치·모의 지급 | 선정산·대출·환전·세금 신고·실자금 운용 | 이미 정산 가능한 금액을 지급하는 모델입니다. 아직 받지 못한 자금을 만들어 지급하지 않습니다. |
| 운영 | 상태·추적·재처리·대조·부하 시험 | 상용 수준의 무중단·다중 리전·금융기관 운영 보장 | 단일 개발 환경에서 확인할 보장과 운영 한계를 구분합니다. |

기본 거래는 **로그인한 구매자 한 명·판매자 한 명·상품 한 종류의 수량 주문·KRW·전액 환불**을 제안합니다. 결제수단은 카드 결제 대역부터 구현합니다. 방송·영상 송출·채팅은 포함하지 않으며, 비회원 구매·다중 판매자 결제·부분 환불은 후속 확장입니다.

## 3. 가정과 선택 이유

가정은 현실의 사실이나 검증 결과가 아닙니다. 가정이 깨졌을 때의 처리까지 정하고, 외부 시스템이 항상 정상이라는 전제는 두지 않습니다.

| 가정·선택 | 이유 | 깨졌을 때의 처리·한계 |
| --- | --- | --- |
| 첫 상품은 비부패성 일반 완제품 | 식품 보관·유통기한·제작 취소 등 상품별 예외를 줄입니다. | 불량·오배송·변심은 남습니다. 미발송 취소와 판매자가 승인한 반품을 구분해 처리합니다. |
| 기본 시험은 쿠폰 할인 후 상품대금을 결제하고 배송비는 0원 | 배송비·반품비 배분 없이 전액 환불을 검증합니다. | 유료 배송비를 합친 주문에서 상품대금만 환불하는 동작은 이 범위로 검증하지 않습니다. 실제 도입 시 금액 모델을 확장해야 합니다. |
| 금액·수수료는 README의 원 단위·5%·버림 정책 | 재현 가능한 하나의 계산 기준으로 비교합니다. | 실제 PG 원가·세금·계약별 수수료를 대표하지 않습니다. 정책 변경은 버전으로 구분합니다. |
| 기본 쿠폰은 판매자 부담 정액 할인 한 장 | 플랫폼 지원금 없이 실제 결제액을 정산 기준으로 삼습니다. | 할인 분담·중복 쿠폰·적립금을 도입하면 금액 모델을 확장합니다. 할인 후 금액이 1원 미만이면 적용을 거절합니다. |
| 외부 금융 대역은 업무 키로 멱등 처리하고 최종 상태를 조회할 수 있음 | 응답 유실 후 중복 실행 없이 결과를 확인하기 위한 최소 계약입니다. | 조회도 실패하면 미확정을 유지하고 보류·알림·대조로 넘깁니다. 새 키로 성공을 추측하지 않습니다. |
| 메시지는 중복·지연·순서 역전될 수 있음 | 재전달과 서로 다른 스트림 사이의 순서 차이를 처리해야 합니다. | Inbox·업무 유니크 키·상태 전이로 방어합니다. Kafka만으로 외부 금융까지 정확히 한 번 실행된다고 주장하지 않습니다. |
| 주문·금액·배송지와 구매 확정은 우리 커머스 서비스가 소유 | 주문서에서 결제·정산까지 같은 거래를 추적하기 위함입니다. | 브라우저가 보낸 금액·역할을 신뢰하지 않습니다. 판매자 발송 입력만으로 실제 배송을 보증하지 않습니다. |
| 기본 지급은 받은 자금의 지급 가능 잔액 안에서 실행 | 선정산 자금 공급을 기본 범위에 섞지 않습니다. | 잔액 부족은 보류 사유이며, 원장상 정산 예정액과 현금을 같은 값으로 취급하지 않습니다. |
| 개발 인프라는 단일 브로커·PostgreSQL·Redis | 실행·비용·문제 재현을 단순하게 합니다. | 노드 장애 시 전체 영향이 있을 수 있습니다. 논리 분리와 물리 장애 격리는 다릅니다. |

배송비 0원은 구매자에게 배송비를 별도 청구하지 않는 무료배송 조건을 시험 대상으로 삼는 제안입니다. 판매자의 배송 원가나 반품비가 없다는 뜻은 아닙니다. 환불액에서 별도 비용을 공제해야 하는 거래는 부분 환불·비용 배분 모델을 추가해야 합니다.

## 4. 서비스 경계와 원천 데이터

| 소유자 | 소유 데이터·판단 | 다른 서비스에 전달할 결과 |
| --- | --- | --- |
| 커머스 (`seller` 모듈) | 구매자·판매자 계정·인증·상품·재고·주문·쿠폰·배송지·취소/반품 승인·구매 확정 | 확정 주문·결제 요청, 환불 승인, 구매 확정에 따른 정산 가능 정보 |
| Payment | 결제·승인 시도·환불·SAGA·외부 호출 작업 | 결제 확정 결과, 환불 예약 명령·성공·보상 명령 |
| Settlement | 금액 정책 적용 결과·원장·환불/지급 예약·정산 항목·배치·지급 | 예약 성공·거절·해제 결과, 지급 상태 |
| `finance-mock` | 모의 PG 승인·환불, 지급 기관의 실행 결과·잔액·자금 선점 | 접수·처리 중·확정 결과 조회, 지급 가능 잔액 |

Payment API와 Worker는 같은 서비스·DB의 실행 역할입니다. Spring Batch를 도입해도 처음에는 Settlement의 정산 작업으로 두며 별도 업무 서비스를 만들지 않습니다. 서비스 경계는 인원수가 아니라 데이터 소유권·외부 장애 영향·변경 책임을 기준으로 유지합니다.

커머스 안에는 회원·인증, 판매자, 상품, 주문, 쿠폰 도메인을 구분합니다. 회원·인증은 구매자와 판매자의 별도 계정을 처리합니다. 주문 금액과 재고·쿠폰 예약을 한 DB 트랜잭션에서 확정하고 기존 세 서비스의 실행 기반을 재사용하는 안입니다. 도메인마다 별도 서비스·DB를 만드는 안보다 초기 통신·복구 비용을 줄이는 대신, 커머스의 배포·확장 범위가 함께 움직이는 비용을 감수합니다. 물리 모듈·DB·패키지 이름은 `seller`를 유지합니다.

다른 서비스의 DB에 직접 접근하지 않습니다. Payment·Settlement에는 주문·구매자·판매자 식별자와 필요한 금액/상태만 전달하고 배송지·비밀번호·인증 토큰은 금융 이벤트에 넣지 않습니다. 판매자 조회 모델은 이벤트로 갱신할 수 있지만 정지·권한 폐기의 반영 지연을 숨기지 않습니다.

### 사용자와 거래 주체

| 개념 | 책임·관계 |
| --- | --- |
| 구매자 계정 (`Buyer`) | 구매자용 가입·로그인, 계정 상태·인증 정보·배송지. 주문의 `buyerId`가 이 계정을 참조합니다. |
| 판매자 계정 (`Seller`) | 판매자용 가입·로그인, 판매 상태·판매자 정보·정산 정보. 상품·주문·원장의 `sellerId`가 판매자 계정을 참조합니다. 첫 범위는 판매자 계정 한 개가 판매자 한 곳을 운영합니다. |
| 로그인·복구 | 구매자용과 판매자용 진입점·인증 범위를 구분합니다. 같은 이메일을 쓰더라도 계정을 자동 연결하지 않고 로그인·비밀번호 재설정도 계정 종류를 확인합니다. |
| 권한 | 인증 주체는 계정 종류와 계정 ID를 함께 식별합니다. 판매자 인증으로 구매자 주문을 만들거나 구매자 인증으로 상품·정산을 관리하지 않습니다. |
| 배송지 | 주소록은 구매자 소유입니다. 주문 생성 시 수령인·연락처·주소 사본을 주문에 저장하며 주소록 수정이 과거 주문을 바꾸지 않습니다. |

예를 들어 구매자 계정 `B1`로 판매자 `S2`의 상품을 주문하면 주문의 구매자는 `B1`, 정산 대상은 `S2`입니다. 같은 사람이 판매자 `S1`도 운영하려면 판매자 계정으로 별도 로그인합니다. `B1`과 `S1`을 같은 사람이라고 자동 추론하거나 권한을 합치지 않습니다.

인증 주체의 종류와 ID를 주문·주소의 `buyerId` 또는 상품·주문·정산의 `sellerId`와 대조합니다. ID 문자열이 우연히 같아도 계정 종류가 다르면 같은 주체가 아닙니다. 요청의 `buyerId`·`sellerId`·역할 문자열만으로 권한을 인정하지 않습니다. 판매자는 결제 완료 후 자신이 이행할 주문의 배송 정보만 볼 수 있고 구매자의 전체 주소록이나 다른 판매자 주문은 볼 수 없습니다. 구매자 계정 정지와 판매자 판매 자격 정지는 별도 상태로 관리합니다.

## 5. 입력과 신뢰 경계

다음은 필드 이름을 확정한 API 명세가 아닌 **입력 계약 제안**입니다. HTTP 경로·상태 코드·스키마는 호출자·소비자와 검토한 상세 명세에서 확정합니다.

| 입력 | 최소 정보 | 수신 측 검증 |
| --- | --- | --- |
| 주문 요청 | 상품·수량·배송지 선택/입력·쿠폰 선택·모의 결제수단·멱등키 | 로그인 사용자, 판매자·상품 상태, 서버 가격·재고·쿠폰 소유권/조건, 본인 배송지, 같은 키의 본문 일치 |
| 결제 요청 | 커머스가 확정한 주문 ID·버전·`buyerId`·`sellerId`·KRW 결제액·업무 키 | 신뢰한 커머스 생산자, 변경 불가 주문 사본·양수 금액·상한·중복. 브라우저의 금액을 결제 근거로 쓰지 않음 |
| 환불 요청 | 커머스 취소/반품 승인 ID·원주문/결제·요청 사용자·승인 버전·업무 키 | 구매자·판매자 소유권, 원결제 승인 상태·실제 결제액, 지급 예약 여부, 기존 환불 |
| 정산 가능 정보 | 구매 확정 주문/결제·판매자·업무 버전·적용 시각 | 신뢰한 커머스 생산자, 원거래 일치, 중복·오래된 버전, 취소·환불 및 지급 예약 상태 |
| PG·지급 결과 | 외부 업무 키·외부 거래 참조·상태·금액 | 등록된 대역·요청과의 대응, 금액 일치, 허용 상태 전이. 결과 통보만 신뢰하지 않고 필요 시 조회 |
| 운영 재처리 | 대상 작업 ID·실행 주체·사유 | 운영 권한, 현재 상태, 기존 시도의 결과, 감사 기록 |

정산 가능 정보는 우리 주문의 구매 확정에서 생성합니다. 구매 확정이 없거나 결제 미확정·취소/환불 중이면 지급 대상을 만들지 않습니다. 확정·취소 정보가 지연되거나 역순으로 도착할 때 주문 버전과 금융 예약 상태를 함께 확인하며, 오래된 이벤트가 취소 거래를 다시 지급 가능하게 만들지 않아야 합니다.

주문 금액은 커머스가 상품 가격·수량·쿠폰 조건으로 계산하고 저장합니다. Payment는 그 확정 주문을 근거로 승인하며 요청과 승인 사이에 금액·구매자·판매자가 바뀌지 않도록 합니다. 결제수단 선택은 카드 결제 대역의 식별 값으로 시작하고 실제 카드 번호·CVC는 받거나 저장하지 않습니다. [PG 요청·승인 사이의 주문/금액 검증](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)을 참고하되 실PG 연동 완료로 표현하지 않습니다.

## 6. 핵심 업무 흐름

### 주문·쿠폰·배송지

1. 구매자가 상품·수량·배송지·쿠폰을 선택합니다. 커머스는 로그인 사용자에서 구매자를 식별하고 판매자·상품·수량·주소 접근 권한을 확인합니다.
2. 서버가 상품대금과 쿠폰 할인 후 실제 결제액을 계산합니다. 주문에는 구매자·판매자·상품/가격·수량·할인·최종 금액·배송지의 사본과 버전을 저장합니다. 결제를 요청한 주문의 금액·주소는 덮어쓰지 않습니다.
3. 주문·판매 가능 재고 예약·쿠폰 예약·결제 요청 Outbox를 같은 커머스 DB 트랜잭션에 저장합니다. 수량 부족이나 이미 예약/사용한 쿠폰이면 함께 롤백합니다.
4. 결제 승인 결과를 수신하면 주문을 결제 완료로 바꾸고 재고·쿠폰 예약을 확정합니다. 확정 결제 실패는 예약을 해제합니다. 미결제 취소는 Payment가 취소 상태를 영속 확정해 이후 승인을 실행할 수 없게 한 뒤 예약을 해제합니다. 단순히 Worker가 아직 시작하지 않았다는 조회만으로 취소하지 않습니다. PG 결과가 미확정이면 예약을 유지하고 조회·대조로 복구합니다.
5. 판매자가 자기 주문을 발송 처리하고 구매자가 자기 주문을 구매 확정합니다. 결제 결과 미반영·취소/환불 중인 주문은 발송·구매 확정을 거절합니다. 구매 확정 결과를 Settlement에 전달합니다.

쿠폰은 유효기간·적용 판매자·최소 상품대금·소유 구매자·중복 사용을 검사합니다. 결제 실패 시 예약만 해제하고, 전액 환불 성공 시 최초 사용 기록을 되돌립니다. 유효기간이 지난 쿠폰은 복구 이력을 남기되 재사용이나 자동 재발급을 허용하지 않는 안입니다. 재고는 미발송 주문의 환불 완료 시 복구하며 발송 후에는 판매자의 실제 반품 입고 확인 뒤 복구합니다. 금융 환불 성공만으로 발송 상품을 자동 재입고하지 않습니다.

### 결제

1. 확정 주문에서 전달된 구매자·판매자·금액·주문 버전과 업무 키를 확인합니다. 동일 키·동일 요청은 기존 처리로 연결하고 다른 본문이면 충돌로 거절합니다.
2. 결제 접수와 Outbox를 같은 Payment DB 트랜잭션에 저장합니다. 접수 응답은 처리 ID와 조회 경로를 주며 승인 완료를 뜻하지 않습니다.
3. 수신 측은 Inbox·실행 작업을 영속 저장한 뒤 ack합니다. Worker는 DB 잠금을 유지하지 않은 상태에서 모의 PG를 호출합니다.
4. 명시적 승인·거절이면 결과와 Outbox를 저장합니다. 응답 유실·조회 실패는 미확정으로 추적하며 자동으로 실패 처리하지 않습니다.
5. 커머스는 주문·예약을 확정하고 Settlement는 승인 결과를 한 번만 원장에 반영합니다. 결과 전달이 지연되는 동안 각 서비스의 조회 결과가 일시적으로 다를 수 있으므로 결제 승인과 주문/원장 반영 완료를 구분해 표시합니다.

같은 주문에 진행 중이거나 승인된 결제를 중복 생성하지 않습니다. 확정 거절 뒤 같은 주문을 재시도하려면 커머스가 최초 주문 사본의 금액·쿠폰 조건을 확인하고 재고·쿠폰 예약을 다시 확보해야 합니다. 예약이 불가능하면 재시도를 거절합니다. 허용된 시도는 이전 시도와 연결해 기록하고 논리 거래 키와 외부 호출 시도 키의 관계를 명세로 정합니다. 미확정 거래를 재시도하기 위해 새 주문·업무 키를 발급하지 않습니다.

설명용 상태 흐름은 ‘접수 → 외부 처리 중 → 승인 또는 확정 거절’입니다. 외부 결과를 모르면 ‘미확정’을 거쳐 조회로 확정합니다. 저장할 enum 이름과 전이 조건은 이 의미를 보존해 명세화합니다.

### 환불 SAGA

1. 구매자는 자기 주문의 취소/반품을 요청합니다. 커머스는 미발송 취소와 해당 판매자의 반품 승인을 구분해 승인 정보를 저장합니다. Payment는 이 승인과 원결제를 확인하고 실제 결제액의 전액 환불을 접수합니다. 승인 미확정 결제는 먼저 결제 결과를 확인합니다.
2. Payment는 환불 상태와 정산금 예약 명령을 함께 저장합니다. Settlement는 해당 거래의 지급 대상 순액을 원자적으로 예약합니다.
3. 선행 승인 원장이 아직 없으면 의존 정보를 기다리는 작업으로 남깁니다. 동일 명령 재전달로 예약을 중복 생성하지 않습니다.
4. 지급 예약이 이미 있거나 환불 완료 상태라면 예약을 거절하고 PG 환불을 호출하지 않습니다. 같은 거래에서 진행 중·완료된 전액 환불이 다른 멱등키로 중복 실행되지 않게 합니다.
5. 예약 성공 후 PG에 원결제 전액 환불을 요청합니다. 성공하면 원장 상쇄를 요청하고 확인하며 커머스에 환불 결과를 전달합니다. 커머스는 주문·쿠폰·재고의 해당 복구를 같은 로컬 트랜잭션에서 처리합니다. PG 환불 성공만으로 주문·원장 반영까지 끝났다고 표시하지 않습니다.
6. PG가 확정 거절하면 예약 해제를 보상 명령으로 요청합니다. 해제가 확인되기 전까지 보상 대기 상태를 추적합니다. 결과가 미확정이면 예약을 유지하고 조회합니다.

예를 들어 원결제 10,000원·수수료 500원·판매자 몫 9,500원이면, 지급과 충돌하지 않도록 보호할 판매자 순액은 9,500원이고 구매자의 PG 환불액은 10,000원입니다. 성공 시 최초 수수료 500원과 순정산액 9,500원을 상쇄합니다. 이후 수수료율로 재계산하지 않습니다.

취소/반품 승인과 금융 환불 완료는 다른 결과입니다. 지급 예약 후·지급 후 환불은 첫 구현에서 지원하지 않으며 처리 불가 사유와 운영 확인 경로를 남깁니다. 정산금 예약이 거절되거나 PG 환불이 확정 실패하면 커머스의 환불 진행 상태도 결과에 맞춰 해제·갱신합니다. 미확정이면 취소·재입고·쿠폰 복구를 성공으로 추측하지 않습니다.

### 정산·지급

1. 결제·환불 결과를 지속적으로 원장에 반영합니다. 지급 주기가 길어도 원장 기록을 해당 날짜까지 미루지 않습니다.
2. 배치 실행의 마감 기준을 고정하고 구매 확정 정보가 반영된 미환불·미예약 항목을 선점합니다. 결제 승인만 있고 구매 확정이 없으면 지급하지 않습니다.
3. 지급 건별로 항목 선점·합계·지급 레코드·실행 작업을 같은 Settlement DB 트랜잭션에 저장합니다. 환불 예약과 지급 예약은 같은 항목에서 동시에 성공할 수 없습니다. 항목만 예약되고 실행 작업은 없는 상태를 남기지 않습니다.
4. 저장한 작업으로 지급 기관에 실행을 요청합니다. 사전 잔액 조회는 참고 값이며, 실행 시점의 원자적 잔액 검사·선점이 지급 가능 여부를 결정합니다. 외부 호출은 항목 예약 트랜잭션 밖에서 수행합니다.
5. 실제 지급 성공을 확인한 뒤 지급 완료로 기록합니다. 지급 요청 접수와 지급 완료를 구분합니다.
6. 미확정 지급은 예약을 유지하고 같은 외부 업무 키로 조회·복구합니다. 확정 결과에 따른 지급·항목·작업 상태 변경은 같은 DB 트랜잭션에 저장합니다. 확정 거절 뒤 예약 해제·재시도 허용 조건은 명세로 고정합니다.

대역의 결제 승인액·입금 상태·지급 가능 잔액도 구분하는 설계 제안입니다. 성공한 결제액 전부를 즉시 지급 가능한 현금으로 간주하지 않으며, 시험에서는 지급 가능 잔액과 부족 상황을 별도로 준비합니다.

**지급 기관 대역의 계약 제안:** `finance-mock`은 자기 DB에서 지급 업무 키·금액의 기록과 잔액 검사·자금 선점을 원자적으로 처리합니다. 처리 중인 금액은 가용 잔액에서 제외하고, 성공 시 한 번만 차감하며 확정 실패 시 선점을 해제합니다. 응답 유실만으로 자금을 반환하지 않습니다. 같은 키·같은 요청은 기존 결과로 연결하고 다른 금액은 거절합니다. Settlement의 거래별 지급 예약과 대역의 자금 선점은 서로 다른 DB의 책임이며 한 트랜잭션으로 묶지 않습니다.

**배치 제안:** 마감 이전에 수신·반영된 미처리 항목을 대상으로 하고, 늦게 들어온 과거 거래도 다음 배치에서 누락 없이 선택합니다. 원거래 발생일의 하한만으로 조회해 늦은 거래를 제외하지 않습니다. 같은 실행의 재시작에서는 마감 값과 업무 키를 유지합니다. 업무 시간대는 Asia/Seoul, 저장·전송 시각은 공통 규약의 UTC를 제안합니다. 실제 지급 주기·마감 시각은 팀 결정 전입니다.

| 중복 승인·환불 방지 | 주문별 진행 중·승인 결제와 원결제별 진행 중·완료 환불의 중복을 DB에서 차단합니다. 확정 거절 뒤의 시도 이력은 구분합니다. | 다른 키로 같은 주문을 중복 결제하거나 같은 원결제를 중복 환불 |
| 원장 중복 반영 방지 | 이벤트 ID뿐 아니라 원거래·업무 종류의 유일성도 둡니다. | 다른 이벤트 ID로 동일 승인 결과 재전달 |
| 금액 보존 | 원금액·정책 버전·수수료·순정산액을 보존하고 상쇄 기록을 추가합니다. | 199원의 수수료 9원·판매자 몫 190원, 전액 환불 후 각각 상쇄 |
| 예약 상호 배제 | 같은 정산 항목의 환불 예약과 지급 예약을 DB의 조건부 전이·제약으로 배타 처리합니다. | 두 요청을 동시에 시작해 한쪽만 선점하는지 확인 |
| 지급 합계·작업 인계 | 지급액은 선점한 항목의 합계이며 항목·지급·작업을 원자 저장합니다. 다른 배치가 같은 항목을 중복 배정하지 않습니다. | 예약 중단 시 함께 롤백, 커밋 후 재시작 시 저장된 작업 재개, 항목별 배정·지급 건수 대조 |
| 가용 자금 초과 방지 | 지급 기관 대역이 자금 선점·차감과 업무 키의 중복을 원자적으로 검증합니다. | 잔액 10,000원에서 서로 다른 7,000원 지급 두 건을 동시에 요청해 한 건만 선점, 같은 키 재요청 시 추가 차감 없음 |
| 외부 결과와 내부 상태 구분 | 외부 성공·내부 반영 대기·미확정을 기록하고 끝까지 대조합니다. | PG 성공 직후 프로세스 중단, 내부 완료 이벤트 지연 |
| 이력 보존 | 원장과 결제·환불·지급 이력은 물리 삭제하거나 금액을 덮어쓰지 않습니다. | 정정 후 원거래와 상쇄·추가 항목을 함께 추적 |

기본 금액은 `상품 단가 × 수량 − 판매자 부담 쿠폰 할인액 = 실제 결제액`입니다. 배송비는 0원이며, 수수료는 실제 결제액의 5%를 원 미만 버림하고 순정산액은 실제 결제액에서 그 수수료를 뺀 값입니다. 쿠폰 할인액을 PG 환불액이나 판매자 지급액에 다시 더하지 않습니다.

설명용 예: 상품대금 10,000원에서 쿠폰 1,000원을 적용하면 PG 결제·전액 환불액은 9,000원입니다. 수수료는 450원, 판매자 순정산액은 8,550원이며 환불 성공 시 최초 450원과 8,550원을 상쇄합니다. 쿠폰 사용 복구는 현금 1,000원 환불과 구분합니다.

물리 ERD는 서비스별로 작성합니다. 커머스의 후보는 구매자 계정·판매자 계정·배송지·상품·재고 예약·주문/주문 당시 사본·쿠폰/예약/사용 이력입니다. Payment는 결제·시도·환불·SAGA·작업, Settlement는 원장·정산 항목·예약·배치·지급을 소유합니다. Outbox·Inbox는 각 소유 DB에 둡니다. 후보 이름만으로 테이블을 생성하지 않고 키·타입·유니크·인덱스·삭제·보존 조건을 명세와 migration으로 연결합니다.

FK를 두지 않는 기존 정책은 유지하되 애플리케이션의 참조 확인과 DB의 `NOT NULL`·`UNIQUE`·`CHECK`를 함께 사용합니다. Redis 잠금이나 Kafka 순서만으로 금액 불변식을 대신하지 않습니다. [데이터 정책](migrations.md#데이터-보존과-제약-조건)을 따릅니다.

## 8. 인증·이벤트·캐시·배치 선택

### 인증과 접근

인증 담당자는 구매자·판매자 계정별 가입·로그인·복구와 인증 정보 수명·폐기·권한을 상세화하고 구현합니다. 인증 정보에는 계정 종류와 ID를 구분해 결합하며, 종류가 다른 계정의 인증 정보를 바꿔 쓸 수 없어야 합니다. JWT와 Redis 공유 세션 중 어느 방식도 이 문서만으로 확정하지 않습니다. 어떤 방식을 택하든 Gateway 검사와 별도로 백엔드에서 계정 종류·주문/주소/판매자 소유권·허용 작업을 확인합니다. 내부 네트워크와 요청 헤더를 신원 증명으로 취급하지 않습니다.

JWT 선택 시 서명·발급자·만료·대상 검증과 폐기 반영 방식을, 세션 선택 시 저장소 장애·만료·로그아웃·동시 세션 정책을 정합니다. 판매자 상태 캐시와 유효한 인증 정보 사이에 차이가 날 때 신규 금융 요청을 허용할 기준도 정합니다. 인증 정보 재조회·중단 기준과 허용할 반영 지연은 구현 전 결정 사항입니다. [Spring Security의 JWT 검증 모델](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html)

### Kafka와 복구

원자 저장·ack·중복 처리의 기준은 [정합성 설계](../README.md#정합성-설계)를 따릅니다. Kafka는 후속 작업을 분리하고 대기 작업을 전달하기 위한 선택이며, 사용만으로 응답 지연이나 처리량 향상을 보장하지 않습니다.

재시도는 일시적 통신·저장 실패, 선행 이벤트 대기, 외부 미확정 조회를 구분합니다. 잘못된 입력·권한·금액 불일치는 무한 재시도하지 않습니다. 횟수·간격·대기 기한·DLT·운영 재처리 기준은 이벤트별로 정합니다. 메시지의 처리 완료와 금융 업무의 완료도 구분합니다. Inbox와 실행 작업을 저장한 시점의 ack는 외부 지급이 끝났다는 뜻이 아닙니다.

작업 실행자가 죽으면 임대 만료 후 다른 실행자가 인계할 수 있도록 제안합니다. 중복 인계가 발생해도 같은 외부 업무 키와 DB 상태 조건으로 보호해야 합니다. 임대 시간만 믿고 미확정 작업을 새 거래로 실행하지 않습니다.

### PG 3종과 장애 시나리오

`finance-mock` 하나 안에 거래 영역을 구분한 PG A·B·C와 지급 기관 대역을 구현합니다. 아래 값은 **초기 시험 설정 제안**이며 실제 PG의 성능·실패율이나 현재 구현된 설정을 뜻하지 않습니다. 서로 다른 PG의 프로세스·장비 장애 격리는 이 구성으로 검증하지 않습니다. [대역 연결 구조](architecture.md#pg-대역-3종-설계)를 함께 확인합니다.

| PG ID | 기본 응답 지연 | 신규 업무의 확정 실패확률 | 기본 응답 유실확률 |
| --- | --- | --- | --- |
| `PG_A` | 80~150ms | 0.5% | 0% |
| `PG_B` | 300~700ms | 3% | 0% |
| `PG_C` | 800~1,500ms | 8% | 0% |

지연은 범위 안의 균등 분포를 제안합니다. 표의 값은 주입하는 응답 대기 시간이며 실제 요청 지연에는 DB·작업 대기·전송 시간이 더해집니다. 확정 실패는 PG가 승인·환불을 거절하고 금액을 변경하지 않은 결과입니다. HTTP 오류·타임아웃·응답 유실과 구분하며 확정 실패확률의 분모는 같은 요청을 재시도한 횟수가 아닌 서로 다른 신규 업무 키입니다. 승인·환불·조회별 설정은 분리하고, 위 표는 승인·환불의 출발 값으로 사용합니다. 정상 프로필의 조회는 장애 없이 결과를 반환하도록 시작합니다.

PG별 설정 계약에는 응답 지연 최솟값/최댓값, 확정 실패확률, 응답 유실확률, 조회 실패확률, 사용 가능 상태와 시나리오 버전·seed를 포함합니다. 지연은 음수가 아니고 최댓값은 최솟값 이상이며 확률은 0~1로 검증합니다. 예를 들어 0.5%는 0.005입니다. 강제 장애 시나리오가 확률 설정을 덮어쓰면 적용 값과 우선순위를 기록합니다. 설정 이름·주입 경로는 구현 시 명세화하며 아직 `application.yml`에 적용된 속성으로 간주하지 않습니다.

재현성은 seed·PG ID·작업 종류·업무 키로 지연·신규 처리 결과를 결정해 확보합니다. 스레드 실행 순서에 따라 결과가 바뀌는 전역 난수 순서에 의존하지 않습니다. 중복 요청은 기존 처리 결과를 먼저 조회하고, 확정 결과·금액을 다시 추첨하지 않습니다. PG ID·작업·업무 키와 처리 결과를 저장하며 재시작이나 설정 변경 후에도 기존 결과를 유지합니다. 응답 유실·조회 장애는 저장된 금융 결과를 바꾸지 않는 통신 장애로 주입합니다.

Payment는 최초 PG 선택을 결제 시도와 함께 저장합니다. PG별 단독 시험 후 1:1:1 혼합 시험부터 시작하고 선택 비율을 기록합니다. 미확정 거래의 재요청·조회는 같은 PG·업무 키로 보내고, 승인된 결제의 환불도 원래 승인 PG로 보냅니다. 타임아웃을 이유로 다른 PG에서 새 승인을 실행하지 않습니다. 다른 PG를 선택한 새 시도는 이전 PG의 확정 거절과 재고·쿠폰 재예약이 확인된 경우에만 허용합니다.

| 시험 상황 | 주입 방법 | 확인할 결과 |
| --- | --- | --- |
| 정상 분포·확정 거절 | 세 PG의 표 설정을 각각 적용 | PG별 신규 승인/거절 비율과 응답 지연, 잘못된 금액 변경 없음 |
| 성공했지만 타임아웃 | PG C의 성공 결과 저장 후 응답만 3,000ms 지연, Worker 제한 시간 2,000ms인 시험 | Payment는 미확정 유지, 원 PG 조회 후 성공으로 수렴, 다른 PG 승인·예약 조기 해제 없음 |
| 성공 응답 유실 | PG B의 성공 결과 저장 후 연결 종료 또는 제한 시간 초과로 응답 유실 | 같은 PG·업무 키 조회로 복구, 중복 승인·차감 없음 |
| 한 PG의 조회도 불가 | PG B의 승인·조회 오류를 함께 주입하고 이후 복구 | 미확정·재조회 작업 보존, 다른 PG로 중복 결제하지 않고 복구 후 대조 |
| 환불 거절·응답 유실 | 원 승인 PG에 환불 거절 또는 성공 후 응답 유실을 각각 주입 | 확정 거절이면 정산금 예약 해제·보상, 미확정이면 예약 유지·조회 후 원장 상쇄 |

응답 지연·유실 시험은 결과를 짧은 DB 트랜잭션으로 먼저 저장한 뒤 주입하며 지연 동안 DB 잠금을 유지하지 않습니다. 따라서 위 타임아웃 시험은 ‘응답이 늦었지만 PG에서는 이미 처리된 경우’를 검증합니다. PG 처리 자체가 아직 끝나지 않은 상황은 별도 처리 중 상태로 정의해야 하며 같은 시험 결과로 검증했다고 하지 않습니다.

지표는 `pgId`·작업 종류·결과 종류별로 구분합니다. Grafana에서 PG별 지연 p50/p95/p99, 확정 거절률, HTTP 오류·타임아웃, 미확정 건수·복구 시간, 승인 완료 TPS와 Worker 적체를 비교하도록 안내합니다. 거래 ID·주문 ID는 메트릭 label로 넣지 않고 추적·대조 기록에서 사용합니다. 결과 보고에는 seed·시나리오 버전·적용 설정·선택 비율·신규 업무 건수와 재시도 횟수를 남깁니다.

서로 다른 시험 실행은 업무 키의 범위를 나눠 이전 거래를 신규 표본에 섞지 않습니다. 동일 조건 재현은 격리된 시험 데이터와 같은 seed·입력으로 수행하고 기존 공용 DB·볼륨을 임의 초기화하지 않습니다.

현재 k6 스크립트는 명세 조회용입니다. PG 업무 부하는 별도 시나리오로 작성하고, 의도한 거절·장애와 애플리케이션 결함을 구분합니다. 모든 HTTP 오류를 무조건 0으로 요구하는 대신 지정한 기대 결과·중복 승인 0·최종 금액 대조·미확정 복구를 완료 조건으로 둡니다.

### Redis

조회 캐시·인증 저장 등 용도를 먼저 정하고 TTL·무효화·장애 시 동작을 설계합니다. 세션 방식이 미선택인 상태에서 세션 클러스터링을 완료했다고 기록하지 않습니다. 금융 원장·예약·멱등성의 최종 기준은 DB에 두며, 캐시가 사라져도 거래 이력과 금액이 달라지지 않아야 합니다.

### Spring Batch 도입 전략

원장 반영 한 건과 환불 예약을 먼저 연결한 뒤, Settlement의 정산 배치 구현 단계에 Spring Batch 도입을 제안합니다. 대량 항목 분할 처리·실행 이력·재시작이 필요한 이유이며, 현재 실행 기반에 의존성만 미리 추가하지 않습니다. [Spring Batch 기능](https://spring.io/projects/spring-batch/)

배치는 지급 대상 예약·합계 확정·영속 지급 작업 생성까지 담당하고 외부 지급은 작업자가 수행하도록 제안합니다. Job 실행 이력이 중복 지급을 막아주는 것은 아니므로 항목 선점·지급 업무 키·외부 조회가 필요합니다. 실행 스케줄, 앱 기동 시 자동 실행 여부, 마감·재시작 파라미터와 메타데이터 migration을 함께 정의합니다. 버전은 프로젝트의 Spring Boot와 호환되는 관리 버전을 사용합니다.

## 9. 실패·공격·범위 이탈에 대한 검증

## 10. 예상 질문과 답변

### 이 프로젝트에서 무엇을 검증하나요?

부하와 외부 금융 장애가 겹쳐도 결제·환불·정산의 최종 상태와 금액을 맞추는지 검증합니다. 접수·승인 처리량과 정산 지연을 측정하고, 중복·역순·응답 유실·재시작 후 거래별 이력과 잔액을 대조합니다. 범위와 시험 조건은 재현 가능하게 고정합니다.

### 배송을 빼면 중요한 문제를 피한 것 아닌가요?

배송지 입력·주문 당시 주소 보관·판매자 발송 처리·구매 확정은 포함합니다. 택배사 연동과 배송 추적만 제외합니다. 지급은 결제 승인만으로 하지 않고 구매 확정·환불/예약 상태를 확인합니다.

### 구매자와 판매자는 같은 계정인가요?

아닙니다. 구매자용과 판매자용 계정을 각각 만들고 로그인합니다. 같은 사람이 두 계정을 가질 수 있지만 이메일이 같다는 이유로 연결하지 않습니다. 계정 분리는 인증 서버나 서비스를 두 개 배포한다는 뜻이 아닙니다. 하나의 회원·인증 도메인이 두 계정 종류의 신원·권한을 검증할 수 있습니다.

### 실제로 배송되지 않았는데 발송·구매 확정을 입력하면요?

이 시스템은 실제 배송 증명까지 수행하지 않습니다. 자기 주문에 대한 구매자·판매자 권한과 상태를 확인하고, 시험에서는 미확정·지연·잘못된 입력을 구분합니다. 실제 물류 연동과 분쟁 판단은 추가 설계 범위입니다.

### 상하지 않는 상품이면 환불이 단순해지나요?

부패 관련 예외를 줄일 뿐 불량·변심·오배송은 남습니다. 구매자의 취소/반품 요청, 판매자의 반품 승인과 금융 환불 상태를 구분합니다. 상품 종류로 환불 자체가 불필요하다고 가정하지 않습니다.

### 왜 지급 전 전액 환불만 지원하나요?

첫 구현에서 실제 결제액·수수료·순정산액의 정확한 상쇄와 예약 경쟁을 검증하기 위한 범위입니다. 부분 환불과 지급 후 환불은 배분·회수 모델이 추가됩니다. 지원하지 않는 요청은 처리 불가 사유와 운영 확인 경로를 안내하며, 기술 구현 범위를 실제 반품 권리가 사라진다는 뜻으로 사용하지 않습니다.

### 배송비가 있는 주문은 어떻게 하나요?

기본 시험은 상품대금에서 쿠폰을 뺀 금액을 결제하고 배송비 0원을 가정합니다. 유료 배송과 반품비 공제는 별도 금액 모델이 필요하므로 기본 주문에서 지원하지 않습니다. 무료배송이어도 판매자의 실제 물류 원가가 없다는 뜻은 아닙니다.

### 쿠폰을 쓰면 카드 대신 쿠폰으로 결제하나요?

기본 쿠폰은 할인이고 카드는 나머지 금액의 결제수단입니다. 10,000원 상품에 1,000원 쿠폰을 쓰면 9,000원을 카드 대역으로 결제합니다. 전액 환불도 9,000원이며 쿠폰 복구와 정산 상쇄는 [금액 규칙](#7-금액데이터-불변식)을 따릅니다.

### PG 타임아웃이면 실패로 돌리고 다시 결제하면 되지 않나요?

외부에서는 성공했지만 응답만 유실됐을 수 있습니다. 같은 업무 키로 조회·복구하고 확인 전에는 새 금융 작업으로 바꾸지 않습니다. 멱등성은 외부 호출과 내부 업무 키 양쪽에 필요합니다. [토스페이먼츠 멱등성 설명](https://docs.tosspayments.com/blog/what-is-idempotency)

### Kafka를 쓰면 중복과 유실이 모두 해결되나요?

DB 저장과 메시지 발행은 별개의 실패 지점입니다. 상태·Outbox를 함께 저장하고 수신 측은 Inbox·작업을 저장한 뒤 ack합니다. 중복 전달은 업무 키로 처리하며, 외부 PG 호출은 별도의 멱등·조회 계약으로 보호합니다.

### 왜 세 서비스인가요? 한 서비스로도 가능한 것 아닌가요?

단일 서비스도 가능한 대안입니다. 현재안은 구매자/판매자·주문/재고/쿠폰을 함께 확정하는 커머스, 외부 금융 호출·환불의 Payment, 원장·지급의 Settlement로 나눕니다. Payment는 API와 Worker를 따로 확장합니다. 사용자 도메인은 필요하지만 별도 배포 서비스가 필수인 것은 아닙니다. 커머스 내부 도메인을 더 쪼개는 대신 결합된 배포·확장 범위를 감수합니다.

### DB 한 대인데 MSA라고 할 수 있나요?

서비스별 논리 DB·계정·스키마를 소유하고 API·이벤트로 연동합니다. 물리 DB 장애 격리는 확보하지 못한 개발 구성입니다. 서비스 경계가 있다는 사실을 고가용성이나 물리 분산 성과로 확대하지 않습니다.

### FK가 없거나 논리 삭제하면 금융 이력이 깨지지 않나요?

FK 생략은 유효성 검사를 없앤다는 뜻이 아닙니다. 애플리케이션 참조 검사·업무 상태·DB 유니크와 금액 제약을 사용합니다. 논리 삭제는 판매자 같은 관리 데이터에 적용하고, 금융 이력은 삭제 없이 정정·상쇄 기록으로 보존합니다.

### Redis나 분산 잠금으로 중복 지급을 막으면 안 되나요?

캐시 만료·유실·임대 만료 뒤 중복 실행이 가능하다고 보고 DB의 예약 상태와 업무 유일성으로 마지막 방어를 둡니다. Redis는 필요한 캐시·인증·조율 용도에서 검증합니다.

### 왜 Spring Batch를 쓰나요? 배치가 끝나면 지급도 안전한가요?

대량 항목 처리와 재시작 관리를 위한 도구 후보입니다. 배치 메타데이터와 실제 지급 결과는 다르므로 지급 작업·외부 업무 키·미확정 조회가 필요합니다. 배치를 사용했다고 금융 처리가 정확히 한 번 완료됐다고 설명하지 않습니다.

### PG를 Mock으로 만들면 성능 시험에 의미가 있나요?

명시한 지연·실패·응답 유실 조건에서 우리 접수·작업·이벤트·DB 경로의 처리량과 복구를 비교할 수 있습니다. 실제 PG의 성능·가용성·계약을 검증한 것은 아닙니다. [PG 3종 시험](#pg-3종과-장애-시나리오)의 정상·장애 프로필을 나누고 실제 적용 값과 PG별 결과를 기록합니다.

### 왜 1,000 TPS이며 1만 TPS도 가능한가요?

현재 목표와 완료 TPS 정의는 [성능 목표](../README.md#성능-목표와-검증)를 따릅니다. 추가 근거는 대상 규모·피크 시간의 시험 가정으로 설명하고 실제 수요 통계와 구분합니다. 1만 TPS는 자원 확보 후 확장 시험 목표이며 달성 결과가 아닙니다. 같은 장비의 부하 발생기가 서버 자원을 쓰는 영향도 기록합니다.

### 2주 정산은 선정산인가요?

이미 받은 자금을 2주마다 지급하면 지급 일정 조정입니다. 받기 전에 지급하려면 별도 자금 공급·한도·회수 모델이 필요합니다. 기본안은 그 자금 조달을 포함하지 않습니다. [선택 확장](proposal.md#선택-확장-후보)으로 도입할 때 지급 후 환불과 회수까지 함께 설계합니다.
