# 상세 설계 초안

구매자의 주문·결제·환불과 판매자 정산의 정합성·장애 복구·부하 처리를 검증하는 기술 프로젝트의 설계 초안입니다. 구매자·판매자 계정, 구현 경계와 선택 이유, 업무 흐름과 검증 항목을 정리합니다. 업무 기능 구현·성능 검증은 별도로 수행합니다.

## 1. 기준과 책임

- [README](../README.md): 문제·자동지급의 선택 이유와 기본 기능·금액·정합성·성능 목표의 진입점입니다.
- [업무 정책](policies.md): 쿠폰 기간·금액/수량 한도·인증·일배치·재처리 기본값을 소유합니다.
- [API](api.md)·[OpenAPI](openapi.json)·[데이터 모델](data-model.md): 경로·필드·상태·이벤트·컬럼·제약·인덱스를 정의합니다.
- [프로젝트 초안](proposal.md): 상품 범위·검증 목표·선택 확장·이름별 역할 배분을 관리합니다.
- 이 문서: 포함·제외 범위, 가정과 이유, 업무 흐름·검증 계약·예상 질문을 구체화합니다. 새 입력·처리 방안은 **설계 제안**으로 표시합니다.
- [서비스와 코드 경계](architecture.md), [DB 정책](migrations.md), [공통 구현 규약](../CONTRIBUTING.md#구현-규약): 코드·저장·요청·오류·이벤트 형식을 관리합니다.

설계는 서비스 경계와 각 도메인의 상태·금액 규칙·ERD·API·이벤트·동시성·복구·테스트 시나리오를 구체화합니다. 각 담당자는 자기 영역의 설계·구현·테스트를 맡고, 서비스 간 계약과 변경 영향을 함께 검토합니다. 합의한 변경은 기준 문서 한 곳에 반영하고, 개인 메모나 PR 설명만으로 계약을 바꾸지 않습니다.

## 2. 해결 범위

구매자가 우리 서비스에서 상품을 고르고 배송지·쿠폰·결제수단을 선택해 주문합니다. 구매자의 결제·환불과 판매자의 매출·정산·지급을 연결합니다. 프로모션의 요청 집중과 외부 금융 장애를 시험 조건으로 사용하고, [선택 확장](proposal.md#선택-확장-후보)은 기본 구현의 착수 조건이 아닙니다.

| 영역 | 포함 | 제외·외부 책임 | 선택 이유와 남는 책임 |
| --- | --- | --- | --- |
| 사용자·판매자 | 구매자·판매자 계정별 가입·로그인·권한, 판매 상태·정산 정보, 기본 배송지 | 계정 자동 연결·직원/다중 운영자·실제 사업자 심사·실계좌 검증 | 구매와 판매의 로그인·복구·접근 범위를 분리합니다. 같은 사람이 양쪽을 이용하려면 각각 가입합니다. |
| 상품·주문 | 상품 등록·조회·가격·판매 가능 수량, 한 상품의 수량 주문, 금액·배송지 사본, 재고 예약 | 검색 고도화·장바구니·다중 판매자 주문 | 구매자가 결제할 대상을 우리 서버가 확정합니다. 가격·주소 변경으로 기존 주문을 덮어쓰지 않습니다. |
| 쿠폰 | 웰컴·월간 우수고객·판매자 쿠폰 한 장, 자동 발급·판매자 캠페인 예산·예약·사용·복구 | 대량 선착순 발급 행사·중복 쿠폰·쿠폰/마일리지 동시 사용 | 쿠폰은 결제수단과 구분하고 할인 후 주문 결제액은 1원 이상으로 합니다. |
| 선착순 이벤트 | 판매자의 특정 상품·이벤트 가격·한정 수량·기간 설정, 예약·판매 진행률·매진 종료 | 방송·영상·채팅·목표 달성형 공동구매 | 판매 시작에 특정 상품으로 요청이 집중되는 상황과 마지막 수량 경쟁을 검증합니다. |
| 배송·반품 | 배송지 저장, 판매자 발송·모의 배송완료, 기한 후 자동 구매확정, 취소·반품 요청/승인 상태 | 택배사 연동·배송 추적·실제 수거·검수·비용 계산 | 판매자 발송 입력과 실제 배송 증명을 구분합니다. 구매 확정과 환불 상태가 정산 가능 판단의 입력입니다. |
| 결제·마일리지 | 신용카드·체크카드·간편결제 대역, 우리 마일리지 사용·예약·원장, 접수·조회·미확정 복구 | 상품권 결제·실결제 계약·실카드 정보, 마일리지 충전·현금 인출·구매 적립·만료 | 외부 승인과 내부 잔액의 실패 경계, 복합 결제의 금액 보존을 검증합니다. |
| 환불 | 지급 예약 전 전액 환불·예약·보상·조회, 원결제수단 취소와 사용 마일리지 복원 | 부분 환불·교환·지급 후 환불·반품 분쟁 판정 | 반환 구성과 최초 원장을 보존합니다. 제외한 예외가 실제로 발생하지 않는다고 가정하지 않습니다. |
| 정산·지급 | 원장·수수료·판매자별 일배치·모의 선지급/PG 회수 | 대출·환전·세금 신고·실자금 조달 | 선지급 재원은 항상 충분하다고 가정하고 구매확정 뒤 PG 입금 전에도 지급합니다. |
| 운영 | 상태·추적·재처리·대조·부하 시험 | 상용 수준의 무중단·다중 리전·금융기관 운영 보장 | 단일 개발 환경에서 확인할 보장과 운영 한계를 구분합니다. |

기본 거래는 **로그인한 구매자 한 명·판매자 한 명·상품 한 종류의 수량 주문·KRW·전액 환불**입니다. 카드 한 건을 먼저 연결한 뒤 아래 결제수단·마일리지·선착순 이벤트까지 구현합니다. 비회원 구매·다중 판매자 결제·부분 환불은 후속 확장이며, 방송·영상 송출·채팅은 계속 제외합니다.

## 3. 가정과 선택 이유

가정은 현실의 사실이나 검증 결과가 아닙니다. 가정이 깨졌을 때의 처리까지 정하고, 외부 시스템이 항상 정상이라는 전제는 두지 않습니다.

| 가정·선택 | 이유 | 깨졌을 때의 처리·한계 |
| --- | --- | --- |
| 첫 상품은 비부패성 일반 완제품 | 식품 보관·유통기한·제작 취소 등 상품별 예외를 줄입니다. | 불량·오배송·변심은 남습니다. 미발송 취소와 판매자가 승인한 반품을 구분해 처리합니다. |
| 기본 시험은 쿠폰 할인 후 상품대금을 결제하고 배송비는 0원 | 배송비·반품비 배분 없이 전액 환불을 검증합니다. | 유료 배송비를 합친 주문에서 상품대금만 환불하는 동작은 이 범위로 검증하지 않습니다. 실제 도입 시 금액 모델을 확장해야 합니다. |
| 금액·수수료는 업무 정책의 원 단위·15%·버림 정책 | 재현 가능한 하나의 계산 기준으로 비교합니다. | 실제 PG 원가·세금·계약별 수수료를 대표하지 않습니다. 거래 당시 원금액·요율·조건 사본을 보존합니다. |
| 웰컴·월간 우수고객은 플랫폼 부담, 판매자 쿠폰은 판매자 부담인 정액 쿠폰 한 장 | 할인과 마일리지 결제 재원을 구분합니다. | 같은 주문에서 두 부담자의 쿠폰이나 마일리지를 겹치지 않습니다. 할인 후 주문 결제액이 1원 미만이면 적용을 거절합니다. |
| 우리 마일리지는 플랫폼 부담, 1점=1원, 시험용 사전 지급 잔액 | 판매자 부담 할인과 달리 결제 재원으로 처리하고 사용액을 판매자 정산에서 다시 빼지 않습니다. | 실자금 조달·충전·적립·만료는 구현 범위 밖입니다. 모의 지급 잔액도 따로 준비하며 마일리지 사용만으로 실제 현금이 생겼다고 보지 않습니다. |
| 외부 금융 대역은 업무 키로 멱등 처리하고 최종 상태를 조회할 수 있음 | 응답 유실 후 중복 실행 없이 결과를 확인하기 위한 최소 계약입니다. | 조회도 실패하면 미확정을 유지하고 보류·알림·대조로 넘깁니다. 새 키로 성공을 추측하지 않습니다. |
| 메시지는 중복·지연·순서 역전될 수 있음 | 재전달과 서로 다른 스트림 사이의 순서 차이를 처리해야 합니다. | Inbox·업무 유니크 키·상태 전이로 방어합니다. Kafka만으로 외부 금융까지 정확히 한 번 실행된다고 주장하지 않습니다. |
| 주문·금액·배송지와 구매 확정은 우리 커머스 서비스가 소유 | 주문서에서 결제·정산까지 같은 거래를 추적하기 위함입니다. | 브라우저가 보낸 금액·역할을 신뢰하지 않습니다. 판매자 발송 입력만으로 실제 배송을 보증하지 않습니다. |
| 선지급 재원은 항상 충분하며 구매확정 후 선지급 | 준비된 거래의 추가 대기를 줄입니다. | 시험 전 전체 지급·환불에 충분한 모의 자금을 준비합니다. PG 입금과 잔액을 따로 기록하며 실자금 조달은 제외합니다. |
| 개발 인프라는 단일 브로커·PostgreSQL·Redis | 실행·비용·문제 재현을 단순하게 합니다. | 노드 장애 시 전체 영향이 있을 수 있습니다. 논리 분리와 물리 장애 격리는 다릅니다. |

배송비 0원은 구매자에게 배송비를 별도 청구하지 않는 무료배송 조건을 시험 대상으로 삼는 제안입니다. 판매자의 배송 원가나 반품비가 없다는 뜻은 아닙니다. 환불액에서 별도 비용을 공제해야 하는 거래는 부분 환불·비용 배분 모델을 추가해야 합니다.

## 4. 서비스 경계와 원천 데이터

| 소유자 | 소유 데이터·판단 | 다른 서비스에 전달할 결과 |
| --- | --- | --- |
| 커머스 (`commerce` 모듈) | 구매자·판매자 계정·인증·상품·재고·주문·쿠폰·배송지·선착순 이벤트/참여·취소/반품 승인·구매 확정 | 확정 주문·결제 요청, 환불 승인, 구매 확정에 따른 정산 가능 정보 |
| Payment | 결제·승인 시도·마일리지 잔액/예약/원장·환불·SAGA·외부 호출 작업 | 결제 구성별 확정 결과, 환불 예약 명령·외부 환불/마일리지 복원 결과·보상 명령 |
| Settlement | 금액 정책 적용 결과·원장·환불/지급 예약·정산 항목·배치·지급 | 예약 성공·거절·해제 결과, 지급 상태 |
| `finance-mock` | PG 3종과 간편결제 1종의 모의 승인·환불, 간편결제 시험 잔액, 지급 기관의 실행 결과·잔액·자금 선점 | 접수·처리 중·확정 결과 조회, 지급 가능 잔액 |

Payment API와 Worker는 같은 서비스·DB의 실행 역할입니다. Spring Batch를 도입해도 처음에는 Settlement의 정산 작업으로 두며 별도 업무 서비스를 만들지 않습니다. 서비스 경계는 인원수가 아니라 데이터 소유권·외부 장애 영향·변경 책임을 기준으로 유지합니다.

서비스 내부의 [도메인별 최종 판단과 집계](architecture.md#ddd-집계와-검증)를 구분합니다. 주문 금액과 재고·쿠폰·이벤트 수량 예약은 커머스 한 트랜잭션에서 확정하고, 마일리지 잔액·예약·원장은 Payment의 결제 상태와 함께 저장합니다. 커머스 주문에는 마일리지 사용 요청액을 보존하고 Payment의 확정 결과를 반영합니다. 배포 경계와 서비스별 DB 소유권은 유지하며 분리 이유와 감수하는 비용은 [도메인 책임 분리 결정](decisions/0004-domain-responsibilities.md)을 따릅니다.

다른 서비스의 DB에 직접 접근하지 않습니다. Payment·Settlement에는 주문·구매자·판매자 식별자와 필요한 금액/상태만 전달하고 배송지·비밀번호·인증 토큰은 금융 이벤트에 넣지 않습니다. 판매자 조회 모델은 이벤트로 갱신할 수 있지만 정지·권한 폐기의 반영 지연을 숨기지 않습니다.

### 사용자와 거래 주체

| 개념 | 책임·관계 |
| --- | --- |
| 구매자 계정 (`Buyer`) | 구매자용 가입·로그인, 계정 상태·인증 정보·배송지. 주문의 `buyerId`가 이 계정을 참조합니다. |
| 판매자 계정 (`Seller`) | 판매자용 가입·로그인, 판매 상태·판매자 정보·정산 정보. 상품·주문·원장의 `sellerId`가 판매자 계정을 참조합니다. 첫 범위는 판매자 계정 한 개가 판매자 한 곳을 운영합니다. |
| 로그인·복구 | 구매자용과 판매자용 진입점·인증 범위를 구분합니다. 같은 이메일을 쓰더라도 계정을 자동 연결하지 않고 로그인·비밀번호 재설정도 계정 종류를 확인합니다. |
| 권한 | 인증 주체는 계정 종류와 계정 ID를 함께 식별합니다. 판매자 인증으로 구매자 주문을 만들거나 구매자 인증으로 상품·정산을 관리하지 않습니다. |
| 배송지 | 주소록은 구매자 소유입니다. 주문 생성 시 수령인·연락처·주소 사본을 주문에 저장하며 주소록 수정이 과거 주문을 바꾸지 않습니다. |

예를 들어 구매자 계정 `B1`로 판매자 `S2`의 상품을 주문하면 주문의 구매자는 `B1`, 정산 대상은 `S2`입니다. 같은 사람이 판매자 `S1`도 운영하려면 판매자 계정으로 별도 로그인합니다. `B1`과 `S1`을 같은 사람이라고 자동 추론하거나 권한을 합치지 않습니다.

인증 주체의 종류와 ID를 주문·주소의 `buyerId` 또는 상품·주문·정산의 `sellerId`와 대조합니다. ID 문자열이 우연히 같아도 계정 종류가 다르면 같은 주체가 아닙니다. 요청의 `buyerId`·`sellerId`·역할 문자열만으로 권한을 인정하지 않습니다. 판매자는 결제 완료 후 자신이 이행할 주문의 배송 정보만 볼 수 있고 구매자의 전체 주소록이나 다른 판매자 주문은 볼 수 없습니다. 구매자 계정 정지와 판매자 판매 자격 정지는 별도 상태로 관리합니다.

DDD 집계·요청/도메인/DB 검증과 생성/수정 시각·행위 감사 기록은 [구현 경계](architecture.md#ddd-집계와-검증)를 따릅니다. 감사 로그는 각 서비스 DB에 두며 금융 원장을 대체하지 않습니다.

### 판매자 구독과 수수료 적용 제안

[수익 모델과 가격 비교](../README.md#수익-모델과-판매자-구독)를 위한 후속 설계입니다. 기본 15% 정책 위에 구독 할인을 추가하는 안이며, 구독 기간·해지·환급과 API·이벤트·DB 계약은 구현 전에 담당자 간 합의를 확정합니다.

판매자 구독은 기존 커머스의 판매자 영역에 둡니다. 판매자·플랜·유효기간·갱신 여부·기간별 결제 근거를 관리하는 작은 객체로 시작합니다. 구독 여부는 유효한 납부 기간에서 계산하며 별도 서비스·DB·범용 구독 엔진은 추가하지 않습니다.

- 커머스는 주문 금액 확정 시점의 구독 자격을 확인하고 적용 플랜·수수료율·정책 버전·판정 시각을 주문 사본에 고정합니다. 기간 경계의 판정과 저장은 같은 DB 트랜잭션으로 보호하며 재전달·결제 재시도에서도 최초 요율을 유지합니다.
- Payment는 수수료 기준액 B와 주문에 고정한 요율로 `F=floor(B×rateBps/10,000)`, `N=B−F`를 계산합니다. 15%는 1,500, 14.75%는 1,475입니다. PG·부가세는 F에 포함하고 `E+M+P=B=N+F`를 각 원장 측에서 보존합니다. Settlement는 원래 금액을 반영·상쇄하며 구독 변경으로 과거 거래를 다시 계산하지 않습니다.
- 구독료는 판매자가 플랫폼에 지불하는 별도 요금으로, 상품 주문·구매자 계정을 만들어 청구하지 않습니다. 상품 매출·판매자 지급 대상과 구분하고 외부 승인·조회·중복 방지는 기존 Payment 경계를 활용합니다.
- 구독료 결제가 확정된 기간에만 혜택을 부여합니다. 정상 해지는 다음 갱신을 중단하고 납부한 기간의 혜택은 종료 시각까지 유지합니다. 갱신 실패가 남은 기간을 취소하지 않으며 미확정 청구로 혜택을 연장하지 않습니다. 같은 판매자·청구 회차를 중복 결제하거나 중복 연장하지 않습니다.
- 구독료 환급과 상품 환불은 분리합니다. 구독료 환급·일할 계산으로 이미 확정한 상품 거래 요율을 덮어쓰지 않습니다.

기본 요율로 발생한 1만원 거래의 수수료 1,500원은 가입 후에도 유지되고, Pro 거래의 1,475원도 만료 뒤에 바뀌지 않습니다. 가입/만료 정각·갱신 실패·중복 청구·과거 거래 환불을 최초 금액으로 검증합니다.

[쿠폰 손익 기준](policies.md#비용과-손익-기준)의 최소 주문금액·PG 총비용 상한 4%·기타 변동비 1천원을 그대로 적용한 비교입니다. 쿠폰을 사용할 수 있는 카드·간편결제 거래(M=0)가 대상이며 마일리지 재원의 수익성까지 대표하지 않습니다. 잔여액 H는 부가세 상당액을 제외한 수수료에서 플랫폼 쿠폰·PG 비용·기타 변동비를 뺀 값이며 월 구독료를 배분해 더하지 않습니다.

| 쿠폰 | 기본 15%의 H | Pro 14.75%의 H | 기존 목표 |
| --- | --- | --- | --- |
| 웰컴 3천원 | −1,953원 | −1,999원 | −2,000원 이상 |
| 브론즈 3천원 | 938원 | 824원 | 500원 이상 |
| 실버 5천원 | 945원 | 786원 | 500원 이상 |
| 골드 7천원 | 952원 | 748원 | 500원 이상 |
| 판매자 3천원 | 927원 | 881원 | 500원 이상 |

14.5%는 같은 웰컴 조건의 H가 −2,044원으로 목표를 벗어나 비교안에서 제외합니다. 14.75%도 웰컴 손실 한도까지 여유가 1원뿐인 시험 요율이므로 실측 원가·쿠폰 구성과 판매자 수용성을 확인해 조정해야 합니다. 이 계산은 실제 순이익이나 최적 가격을 검증한 결과가 아닙니다.

| 주문 요청 | 상품·수량·배송지·쿠폰·사용 마일리지·외부 결제수단·이벤트 ID(해당 시)·멱등키 | 로그인 사용자, 판매자·상품 상태, 서버 가격·재고·쿠폰 조건, 본인 배송지, 이벤트 참여 조건, 같은 키의 본문 일치 |

| 정산 가능 정보 | 구매 확정 주문/결제·판매자·업무 버전·적용 시각 | 신뢰한 커머스 생산자, 원거래 일치, 중복·오래된 버전, 취소·환불 및 지급 예약 상태 |

| 운영 재처리 | 대상 작업 ID·실행 주체·사유 | 운영 권한, 현재 상태, 기존 시도의 결과, 감사 기록 |

정산 가능 정보는 우리 주문의 기한 후 자동 구매확정에서 생성합니다. 자동 구매확정이 없거나 결제 미확정·취소/환불 중이면 지급 대상을 만들지 않습니다. 확정·취소 정보가 지연되거나 역순으로 도착할 때 주문 버전과 금융 예약 상태를 함께 확인하며, 오래된 이벤트가 취소 거래를 다시 지급 가능하게 만들지 않아야 합니다.

주문 금액은 커머스가 상품/이벤트 가격·수량·쿠폰 조건으로 계산하고 저장합니다. Payment는 확정 주문과 결제 구성에 근거해 처리하며 금액·구매자·판매자가 바뀌지 않도록 합니다. 실제 카드 번호·CVC·간편결제 비밀번호 대신 시험용 수단 ID만 받습니다. 실PG 연동 완료로 표현하지 않습니다.

## 6. 핵심 업무 흐름

### 주문·쿠폰·배송지

1. 구매자가 상품·수량·배송지·쿠폰·사용 마일리지·외부 수단을 선택합니다. 커머스는 로그인 사용자에서 구매자를 식별하고 판매자·상품·수량·주소 접근 권한을 확인합니다.
2. 서버가 상품대금과 쿠폰 할인 후 주문 결제액을 계산합니다. 주문에는 구매자·판매자·상품/이벤트 가격·수량·할인·최종 금액·요청한 결제 구성·배송지의 사본과 버전을 저장합니다. 결제를 요청한 주문의 금액·주소는 덮어쓰지 않습니다.
3. 주문·판매 가능 재고 예약·쿠폰 예약·이벤트 참여/수량 예약(해당 시)·결제 요청 Outbox를 같은 커머스 DB 트랜잭션에 저장합니다. 한 조건이라도 충족하지 못하면 함께 롤백합니다.
4. Payment의 결제 확정 결과를 수신하면 주문을 결제 완료로 바꾸고 재고·쿠폰·이벤트 예약을 확정합니다. 확정 결제 실패는 예약을 해제합니다. 미결제 취소는 Payment가 취소 상태를 영속 확정해 이후 승인을 실행할 수 없게 한 뒤 예약을 해제합니다. 단순히 Worker가 아직 시작하지 않았다는 조회만으로 취소하지 않습니다. 외부 결과가 미확정이면 예약을 유지하고 조회·대조로 복구합니다.
5. 판매자가 자기 주문을 발송 처리합니다. 환불 가능 기간이 끝나면 아래 정책으로 자동 구매확정합니다. 결제 결과 미반영·취소/환불 중인 주문은 발송·구매 확정을 거절합니다. 구매 확정 결과를 Settlement에 전달합니다.

쿠폰은 종류·부담자·적용 상품·결제수단·유효기간·최소 상품대금·소유 구매자와 마일리지 병용 금지를 검사합니다. 가입 시 웰컴, 월 배치로 플랫폼 전체 상위 100위와 동점자에게 우수고객 쿠폰을 발급합니다. 판매자 쿠폰은 판매자가 정한 대상·기간·수량으로 발급하며 [쿠폰 정책](policies.md#쿠폰)의 대상·비용 기록·유일성 기준을 적용합니다. 결제 실패 시 예약만 해제하고, 전액 환불 성공 시 최초 사용 기록을 되돌립니다. 유효기간이 지난 쿠폰은 복구 이력을 남기되 재사용이나 자동 재발급을 허용하지 않는 안입니다. 재고는 미발송 주문의 환불 완료 시 복구하며 발송 후에는 판매자의 실제 반품 입고 확인 뒤 복구합니다. 금융 환불 성공만으로 발송 상품을 자동 재입고하지 않습니다.

### 결제수단과 마일리지

| 구분 | 처리·검증 범위 |
| --- | --- |
| 신용카드·체크카드 | PG A/B/C 중 선택한 한 곳에 외부 결제액을 승인·조회·취소합니다. 수단 종류를 기록하되 실제 카드망·한도·매입 주기의 차이는 모의하지 않습니다. |
| 간편결제 | 별도 논리 대역 `EASY_PAY` 한 곳을 추가합니다. 시험용 지갑 잔액의 승인·조회·취소를 모의하며 같은 결제로 PG를 추가 호출하지 않습니다. 실제 브랜드·SDK·로그인은 연동하지 않습니다. |
| 우리 마일리지 | Payment가 구매자별 가용 잔액·예약·사용·복원 원장을 소유합니다. `1점=1원`, 플랫폼 부담, 사전 지급한 시험 잔액으로 시작하며 충전·적립·만료는 제외합니다. |
| 프로모션 쿠폰 | 커머스의 웰컴·월간 우수고객·판매자 할인입니다. 플랫폼/판매자 부담을 구분하고 마일리지와 동시에 쓰지 않습니다. 구매자 결제수단이나 현금 환불 대상은 아니며, 플랫폼 부담액은 별도 지원 원장으로 보전합니다. 예약·사용 복구 규칙을 유지합니다. |

외부 수단은 한 결제에 최대 한 가지이며 우리 마일리지와 함께 쓸 수 있습니다. 여러 외부 수단으로 나누는 결제는 제외합니다. 주문 결제액 전부를 마일리지로 내면 외부 호출 없이 처리합니다. 마일리지 부족·음수·주문 금액 초과는 거절하며, 외부 결제액을 임의로 늘리거나 다른 수단으로 자동 전환하지 않습니다.

Payment는 결제 접수·마일리지 예약·Outbox를 같은 로컬 트랜잭션에 저장합니다. 다른 주문과 동시에 잔액을 쓰더라도 `가용 잔액 = 잔액 − 진행 중 예약액`이 음수가 되지 않게 DB에서 검사합니다. 필요한 외부 승인이 확인되면 마일리지 차감·사용 원장·결제 확정·결과 Outbox를 원자 저장합니다. 외부 결제액이 0원이면 같은 원자 저장으로 바로 확정합니다. 내부 저장 실패는 원래 외부 거래를 조회해 재개하며 중복 차감하지 않습니다.

외부 결과가 미확정이면 마일리지 예약을 유지합니다. 확정 거절 또는 이후 승인이 실행될 수 없도록 영속 확정한 취소만 예약을 해제합니다. 재시도 전 커머스의 재고·쿠폰·이벤트 예약과 Payment의 마일리지 예약을 모두 다시 확보해야 합니다. 예약·사용·복원은 원결제와 작업 종류별 유일성으로 보호합니다.

### 선착순 상품 이벤트

판매자는 자기 상품 하나의 양수 이벤트 가격·한정 수량·시작/종료 시각을 정해 공개합니다. 한정 수량은 1개 이상·배정 가능한 재고 이하이고 종료 시각은 시작 시각보다 뒤여야 합니다. 공개 시 판매 가능 재고에서 이벤트 수량을 같은 DB 트랜잭션으로 배정해 일반 주문과 중복 판매하지 않습니다. 같은 상품의 행사 기간 중복은 허용하지 않고, 공개 후 가격·한정 수량을 바꿔 기존 참여 조건이나 게이지 분모를 덮어쓰지 않습니다. 서버 시각으로 시작·종료를 판단합니다.

첫 범위는 이벤트당 구매자 1명·상품 1개를 제안합니다. 진행 중 예약 또는 확정 구매가 있으면 다른 멱등키로 중복 참여할 수 없고, 확정 실패·승인 차단이 확정된 미결제 취소만 기간 내 재참여할 수 있습니다. 결제 확정 후 환불로 참여 한도를 다시 얻지는 않습니다. 선착순은 **DB에서 수량 예약이 커밋된 순서**이며 HTTP 도착 순서나 PG 처리 속도의 공정성을 보장한다는 뜻은 아닙니다.

- `한정 수량 Q`, `누적 결제 확정 수량 S`, `결제 대기 예약 수량 R`을 구분합니다. 항상 `0 ≤ S + R ≤ Q`이며 남은 신청 가능 수량은 `Q − S − R`입니다.
- 게이지는 `floor(100 × S / Q)%`입니다. 예를 들어 1,000개 중 결제 확정 700개·예약 300개면 **70%·결제 확인 중**, 신청은 일시 마감입니다. 예약만으로 100%나 매진을 표시하지 않습니다.
- 결제 확정 이벤트를 한 번 반영할 때 `R`을 줄이고 `S`를 늘립니다. `S=Q`면 100%·매진 종료이며 새 예약을 받지 않습니다. 외부 결제 미확정은 `R`을 유지하고 조회합니다. 확정 실패는 예약을 해제하며 기간 내 남은 수량만 다시 신청할 수 있습니다.
- 게이지는 환불을 뺀 순판매량이 아닌 **누적 확정 판매 진행률**입니다. 환불 후에도 이벤트 판매 이력·사용한 한도는 되돌리지 않고 자동 재개하지 않습니다. 환불 수량·순판매량은 따로 조회하며 실제 재입고는 기존 배송/반품 규칙을 따릅니다.
- 기간 종료나 판매자의 조기 종료는 신규 참여를 막고 미사용 배정 재고만 일반 재고로 돌립니다. 이미 예약된 주문은 계속 조회·확정/환불 처리하며 기간 종료를 이유로 예약을 먼저 해제하지 않습니다. 종료 뒤 확정 실패로 풀린 배정분도 일반 재고로 반환합니다.

화면은 판매 진행률·예약 상태·마지막 갱신 시각을 HTTP로 주기 조회하도록 설계합니다. Redis 조회 캐시는 허용하지만 참가·매진 판정은 커머스 DB가 결정합니다. 캐시의 100% 미만 표시나 오래된 남은 수량을 신규 구매 권한으로 사용하지 않습니다. 첫 갱신 간격·허용 표시 지연은 각각 1초를 시험 가정으로 두고 실제 부하·지연을 확인합니다. 방송 기능을 추가할 필요는 없습니다.

### 결제

1. 확정 주문에서 전달된 구매자·판매자·금액·주문 버전과 업무 키를 확인합니다. 동일 키·동일 요청은 기존 처리로 연결하고 다른 본문이면 충돌로 거절합니다.
2. 결제 접수와 Outbox를 같은 Payment DB 트랜잭션에 저장합니다. 접수 응답은 처리 ID와 조회 경로를 주며 승인 완료를 뜻하지 않습니다.
3. 수신 측은 Inbox·실행 작업을 영속 저장한 뒤 ack합니다. Worker는 DB 잠금을 유지하지 않은 상태에서 선택한 PG 또는 간편결제 대역을 호출합니다. 외부 결제액 0원인 마일리지 전액 결제는 호출을 생략합니다.
4. 명시적 승인·거절이면 결과와 Outbox를 저장합니다. Payment는 확정 주문의 수수료 기준액 B와 적용 정책으로 수수료·판매자 순액을 계산해 최초 금액으로 보존합니다. 응답 유실·조회 실패는 미확정으로 추적하며 자동으로 실패 처리하지 않습니다.
5. Payment의 결제 확정에는 필요한 외부 승인과 마일리지 차감이 모두 포함됩니다. 커머스는 주문·예약·이벤트 판매량을 확정하고 Settlement는 구성별 결제액과 플랫폼 부담 마일리지 금액을 한 번만 원장에 반영합니다. 결과 전달이 지연되는 동안 결제 확정과 주문/원장 반영 완료를 구분해 표시합니다.

같은 주문에 진행 중이거나 확정된 결제를 중복 생성하지 않습니다. 확정 거절 뒤 재시도는 최초 주문 사본과 모든 예약 조건을 재검증하고, 이전 시도와 연결해 기록합니다. 논리 거래 키와 외부 호출 시도 키의 관계를 명세로 정하며 미확정 거래를 재시도하기 위해 새 주문·업무 키를 발급하지 않습니다.

설명용 상태 흐름은 ‘접수 → 외부 처리 중 → 승인 또는 확정 거절’입니다. 외부 결과를 모르면 ‘미확정’을 거쳐 조회로 확정합니다. 구체 상태명과 허용 전이는 [데이터 모델](data-model.md#저장-상태와-전이)을 따릅니다.

### 모의 배송·환불과 자동 구매확정

배송완료부터 달력일 7일을 환불 요청 기간으로 사용합니다. 발송부터 2~3영업일의 모의 배송을 주문별로 고정하고, 배송·환불 접수·자동 구매확정은 같은 주문 상태와 버전으로 경합합니다. 구체적인 시각·달력·재시작 기준은 [배송·환불 정책](policies.md#배송환불-기한과-자동-구매확정)을 따릅니다.

월요일 10시 발송·2영업일 배송·공휴일 없음이라면 수요일 10시 배송완료, 다음 수요일 10시 환불 마감입니다. 마감 정각 요청은 허용하고 자동 확정은 마감 초과 후에만 가능합니다. 목요일 발송·3영업일 배송이면 다음 화요일에 도착합니다. 배송 작업이 늦어도 원래 기한을 늘리지 않으며, 배송 전 취소·기한 내 접수된 반품은 지급을 막습니다.

택배사 연동·실제 배송 증명·지급 후 환불은 포함하지 않습니다. 기간 내 환불은 원수단 취소·마일리지 복원·원장 상쇄·주문 복구까지 처리하고, 발송 상품 재고는 판매자 입고 확인 후 복원합니다. 시험에서는 Clock을 이동시켜 주말·공휴일·마감 정각·진행 중 환불을 재현합니다.

### 환불 SAGA

1. 구매자는 자기 주문의 취소/반품을 요청합니다. 커머스는 환불 요청 기한과 미발송 취소/해당 판매자의 반품 승인을 확인해 승인 정보를 저장합니다. Payment는 원결제의 외부 결제액·사용 마일리지를 보존한 전액 환불을 접수합니다. 결제 미확정은 먼저 원결제 결과를 확인합니다.
2. Payment는 환불 상태와 정산금 예약 명령을 함께 저장합니다. Settlement는 해당 거래의 지급 대상 순액을 원자적으로 예약합니다.
3. 선행 승인 원장이 아직 없으면 의존 정보를 기다리는 작업으로 남깁니다. 동일 명령 재전달로 예약을 중복 생성하지 않습니다.
4. 지급 예약이 이미 있거나 환불 완료 상태라면 예약을 거절하고 PG 환불을 호출하지 않습니다. 같은 거래에서 진행 중·완료된 전액 환불이 다른 멱등키로 중복 실행되지 않게 합니다.
5. 예약 성공 후 원래 PG·간편결제 거래에 **외부 결제액만** 취소 요청합니다. 외부 결제액 0원이면 호출을 생략합니다. 외부 환불 성공 확인 뒤 사용 마일리지 전액을 원래 구매자 잔액에 복원하고, 복원 원장·금융 환불 상태·Outbox를 같은 Payment DB 트랜잭션에 저장합니다. 원결제별 복원 유일성으로 이벤트 재전달·새 환불 키에도 두 번 반환하지 않습니다.
6. 원장 상쇄 확인 뒤 Payment는 기존 v1 `RefundCompleted`로 커머스에 주문 복구를 전달하고 `INTERNAL_PENDING`을 유지합니다. 커머스는 주문·쿠폰·재고의 해당 복구와 `RefundOrderRestored` Outbox를 같은 로컬 트랜잭션으로 저장합니다. Payment가 이 확인을 수신·반영한 뒤에만 금융 환불을 `COMPLETED`로 전이합니다. 외부 환불 직후 중단되거나 마일리지/원장/주문 반영이 늦으면 같은 환불을 조회·재개하며 전체 완료로 표시하지 않습니다.
7. 외부 환불이 확정 거절되면 마일리지를 복원하지 않고 정산금 예약 해제를 보상 요청합니다. 해제가 확인되기 전까지 보상 대기를 추적합니다. 미확정이면 예약을 유지하고 조회합니다. 이미 확인한 외부 환불 성공을 내부 반영 지연 때문에 실패로 되돌리거나 외부 환불을 새 키로 반복하지 않습니다.

예를 들어 쿠폰 없는 원결제 10,000원·수수료 1,500원·판매자 몫 8,500원이면, 지급과 충돌하지 않도록 보호할 판매자 순액은 8,500원이고 구매자의 PG 환불액은 10,000원입니다. 성공 시 최초 수수료 1,500원과 순정산액 8,500원을 상쇄합니다. 이후 수수료율로 재계산하지 않습니다.

취소/반품 승인과 금융 환불 완료는 다른 결과입니다. 지급 예약 후·지급 후 환불은 지원하지 않으며 처리 불가 사유와 운영 확인 경로를 남깁니다. 정산금 예약이 거절되거나 외부 환불이 확정 실패하면 커머스의 진행 상태도 결과에 맞춰 해제·갱신합니다. 미확정이면 마일리지·쿠폰·재고를 먼저 복구하지 않습니다. 시험 범위의 마일리지는 만료가 없으며 계정 이용 제한 중에도 복원 이력과 잔액은 보존합니다.

### 정산·지급

1. 결제·환불 결과를 지속적으로 원장에 반영합니다. 지급 주기가 길어도 원장 기록을 해당 날짜까지 미루지 않습니다.
2. 배치 실행의 마감 기준을 고정하고 구매 확정 정보가 반영된 미환불·미예약 항목을 선점합니다. 결제 승인만 있고 구매 확정이 없으면 지급하지 않습니다.
3. 지급 건별로 항목 선점·합계·지급 레코드·실행 작업을 같은 Settlement DB 트랜잭션에 저장합니다. 환불 예약과 지급 예약은 같은 항목에서 동시에 성공할 수 없습니다. 항목만 예약되고 실행 작업은 없는 상태를 남기지 않습니다.
4. 저장한 작업으로 지급 기관에 실행을 요청합니다. 사전 잔액 조회는 참고 값이며, 실행 시점의 원자적 잔액 검사·선점이 지급 가능 여부를 결정합니다. 외부 호출은 항목 예약 트랜잭션 밖에서 수행합니다.
5. 실제 지급 성공을 확인한 뒤 지급 완료로 기록합니다. 지급 요청 접수와 지급 완료를 구분합니다.
6. 미확정 지급은 예약을 유지하고 같은 외부 업무 키로 조회·복구합니다. 확정 결과에 따른 지급·항목·작업 상태 변경은 같은 DB 트랜잭션에 저장합니다. 확정 거절은 REVIEW_REQUIRED로 보존하고 자동 해제·새 업무 키 발급을 금지합니다.

일배치 마감·판매자별 합산·계정 사본·보류/재개는 [정산 정책](policies.md#정산재처리)을 따릅니다. Settlement 항목 예약과 대역의 현금 선점은 다른 DB 책임입니다. 외부 호출 동안 Settlement 잠금을 유지하지 않고, 배치 재시작은 원래 대상·합계·업무 키를 유지합니다.

충분한 플랫폼 초기 자금·PG 입금과 환불/지급 차감은 [재원 정책](policies.md#선지급-재원과-pg-회수)과 [금융 Mock 저장 구조](data-model.md#금융-mock)를 사용합니다. 결제 승인액·P/M 원장·미수금은 가용 현금이 아닙니다.

상품대금을 G, 판매자 쿠폰액을 S, 플랫폼 쿠폰액을 P라 하면 `B=G−S`, `T=B−P=E+M`입니다. 수수료는 `F=floor(B×15/100)`, 판매자 몫은 `N=B−F`이며 `E+M+P=B=N+F`를 각 원장 측에서 보존합니다. PG·부가세는 총수수료에 포함하고 플랫폼 지원액을 판매자 몫에서 다시 빼지 않습니다. 쿠폰 사용 시 M=0이고, 쿠폰 없는 마일리지 전액 결제는 외부 호출을 생략합니다. 배송비는 0원입니다. 기본값과 비용 조건은 [업무 정책](policies.md#금액과-주문)을 따릅니다.

설명용 예: 상품대금 23,000원·웰컴 3,000원이면 고객 결제는 20,000원, 플랫폼 지원 3,000원, 수수료 3,450원, 판매자 몫 19,550원입니다. 전액 환불은 외부 20,000원과 지원 원장 3,000원을 각각 상쇄하며 쿠폰을 고객에게 현금으로 반환하지 않습니다. 쿠폰 없는 10,000원 주문에 마일리지 2,000점을 쓰면 외부 8,000원을 취소하고 2,000점을 복원하며 수수료 1,500원·판매자 몫 8,500원을 상쇄합니다.

물리 ERD는 서비스별로 작성합니다. 커머스 후보는 계정·배송지·상품·재고 예약·주문 사본·쿠폰 이력·이벤트/참여/수량 예약입니다. Payment는 결제 구성·시도·마일리지 잔액/예약/원장·환불·SAGA·작업, Settlement는 원장·정산 항목·예약·배치·지급을 소유합니다. Outbox·Inbox는 각 소유 DB에 둡니다. 후보 이름만으로 테이블을 생성하지 않고 키·타입·유니크·인덱스·삭제·보존 조건을 명세와 migration으로 연결합니다.

FK를 두지 않는 기존 정책은 유지하되 애플리케이션의 참조 확인과 DB의 `NOT NULL`·`UNIQUE`·`CHECK`를 함께 사용합니다. Redis 잠금이나 Kafka 순서만으로 금액 불변식을 대신하지 않습니다. [데이터 정책](migrations.md#데이터-보존과-제약-조건)을 따릅니다.

## 8. 인증·이벤트·캐시·배치 선택

### 인증과 접근

첫 구현의 인증은 [정책의 Redis 기반 불투명 Bearer 세션](policies.md#인증공통-api-기준)을 사용합니다. 커머스는 PostgreSQL에서 계정·비밀번호를 확인하고 Redis에 로그인 세션을 발급합니다. Gateway는 Redis의 고정 만료·계정별 인증 가드·버전을 검사하고, 백엔드는 검증된 Gateway/서비스 신원과 역할·소유권을 확인합니다. 계정·비밀번호·복구 토큰·인증 버전은 PostgreSQL에 남깁니다. 세션과 DB의 폐기 반영은 한 트랜잭션으로 취급하지 않으며 정책의 차단·재조정을 적용합니다. 관련 로그인·복구 DTO와 권한은 [API](api.md), 저장 구조는 [인증 데이터](data-model.md#redis-인증-데이터)를 따릅니다. 아직 인증 코드는 구현 전입니다.

### Kafka와 복구

원자 저장·ack·중복 처리의 기준은 [정합성 설계](../README.md#정합성-설계)를 따릅니다. Kafka는 후속 작업을 분리하고 대기 작업을 전달하기 위한 선택이며, 사용만으로 응답 지연이나 처리량 향상을 보장하지 않습니다. 폴링 Outbox·소비와 금융 실행 분리·이벤트 부하 환산·파티션 및 복구 시험의 선택 이유는 [Kafka 결정](decisions/0005-kafka-event-delivery-and-capacity.md)을 따릅니다.

재시도는 일시적 통신·저장 실패, 선행 이벤트 대기, 외부 미확정 조회를 구분합니다. 잘못된 입력·권한·금액 불일치는 무한 재시도하지 않습니다. 기본 재시도·DLT·운영 재처리 기준은 [정책](policies.md#정산재처리), 이벤트 종류·key·consumer는 [API 이벤트 계약](api.md#이벤트-연동)을 따릅니다. 메시지의 처리 완료와 금융 업무의 완료도 구분합니다. Inbox와 실행 작업을 저장한 시점의 ack는 외부 지급이 끝났다는 뜻이 아닙니다.

금융 Worker는 [공통 복구 정책](policies.md#공통-복구)의 임대·token·상태/버전 검사로 인계합니다. 외부 호출 직전 중단해 거래 조회가 404인 경우의 원키 재요청과, 외부 성공 후 내부 반영 전 중단을 구분합니다. 늦은 실행자의 내부 반영은 거절하고 겹친 외부 호출은 대역의 영속 멱등 처리로 보호합니다. 임대 만료나 조회 404로 금융 실패·취소를 확정하지 않습니다.

### PG 3종과 장애 시나리오

`finance-mock` 하나 안에 거래 영역을 구분한 PG A·B·C와 지급 기관 대역을 구현합니다. 아래 값은 **초기 시험 설정 제안**이며 실제 PG의 성능·실패율이나 현재 구현된 설정을 뜻하지 않습니다. 서로 다른 PG의 프로세스·장비 장애 격리는 이 구성으로 검증하지 않습니다. [대역 연결 구조](architecture.md#pg-대역-3종-설계)를 함께 확인합니다.

| PG ID | 기본 응답 지연 | 신규 업무의 확정 실패확률 | 기본 응답 유실확률 |
| --- | --- | --- | --- |
| `PG_A` | 80~150ms | 0.5% | 0% |
| `PG_B` | 300~700ms | 3% | 0% |
| `PG_C` | 800~1,500ms | 8% | 0% |

지연은 범위 안의 균등 분포를 제안합니다. 표의 값은 주입하는 응답 대기 시간이며 실제 요청 지연에는 DB·작업 대기·전송 시간이 더해집니다. 확정 실패는 PG가 승인·환불을 거절하고 금액을 변경하지 않은 결과입니다. HTTP 오류·타임아웃·응답 유실과 구분하며 확정 실패확률의 분모는 같은 요청을 재시도한 횟수가 아닌 서로 다른 신규 업무 키입니다. 승인·환불·조회별 설정은 분리하고, 위 표는 승인·환불의 출발 값으로 사용합니다. 정상 프로필의 조회는 장애 없이 결과를 반환하도록 시작합니다.

PG별 설정은 기존 provider·시나리오 버전 한 묶음 안에서 작업별로 구분합니다. 승인/PAYOUT 실행은 `minDelayMs`·`maxDelayMs`·`rejectionRate`·`responseLossRate`, 환불은 `refundMinDelayMs`·`refundMaxDelayMs`·`refundRejectionRate`·`refundResponseLossRate`, 조회는 `lookupMinDelayMs`·`lookupMaxDelayMs`·`lookupFailureRate`를 사용합니다. PAYOUT의 환불 필드는 모두 null입니다. 시나리오는 생성 후 불변이고 원승인의 환불은 같은 버전의 환불 설정을 사용합니다. 지연은 음수가 아니고 각 최댓값은 대응 최솟값 이상이며 확률은 0~1입니다. 예를 들어 0.5%는 0.005입니다. 위 표를 승인·환불의 초기값으로 쓰고 정상 조회는 지연·실패확률 0으로 시작합니다. 대역의 사용 가능 상태와 강제 장애 시나리오도 시험 입력으로 기록합니다. 강제 장애가 확률 설정을 덮어쓰면 적용 값과 우선순위를 남깁니다. API 필드는 [OpenAPI](openapi.json), 저장 컬럼은 [금융 Mock 모델](data-model.md#mock_scenarios)이 소유하며 아직 실행 설정에 적용된 값은 아닙니다.

원대역 GET 조회에는 Worker 서버 설정에서 선택한 `scenarioVersion` 쿼리를 전달합니다. 이 버전은 조회 지연/실패만 정하며 저장 거래의 금융 시나리오 버전·결과를 바꾸지 않습니다. 거래가 없어도 지정한 조회 프로필을 적용한 뒤 404를 반환하고, 해당 provider·버전의 설정이 없으면 503입니다. 조회 실패확률 100%인 시험 뒤 새 조회 버전을 선택하면 원거래의 금융 결과를 바꾸지 않고 복구할 수 있습니다. 동일 버전의 확률을 수정하거나 기존 승인을 다시 추첨하지 않습니다.

재현성은 seed·PG ID·작업 종류·업무 키로 지연·신규 처리 결과를 결정해 확보합니다. 스레드 실행 순서에 따라 결과가 바뀌는 전역 난수 순서에 의존하지 않습니다. 중복 요청은 기존 처리 결과를 먼저 조회하고, 확정 결과·금액을 다시 추첨하지 않습니다. PG ID·작업·업무 키와 처리 결과를 저장하며 재시작이나 설정 변경 후에도 기존 결과를 유지합니다. 응답 유실·조회 장애는 저장된 금융 결과를 바꾸지 않는 통신 장애로 주입합니다.

Payment는 최초 PG 선택을 결제 시도와 함께 저장합니다. PG별 단독 시험 후 1:1:1 혼합 시험부터 시작하고 선택 비율을 기록합니다. 미확정 거래의 재요청·조회는 같은 PG·업무 키로 보내고, 승인된 결제의 환불도 원래 승인 PG로 보냅니다. 타임아웃을 이유로 다른 PG에서 새 승인을 실행하지 않습니다. 다른 PG를 선택한 새 시도는 이전 PG의 확정 거절과 재고·쿠폰 재예약이 확인된 경우에만 허용합니다.

| 시험 상황 | 주입 방법 | 확인할 결과 |
| --- | --- | --- |
| 정상 분포·확정 거절 | 세 PG의 표 설정을 각각 적용 | PG별 신규 승인/거절 비율과 응답 지연, 잘못된 금액 변경 없음 |
| 성공했지만 타임아웃 | PG C의 성공 결과 저장 후 응답만 3,000ms 지연, Worker 제한 시간 2,000ms인 시험 | Payment는 미확정 유지, 원 PG 조회 후 성공으로 수렴, 다른 PG 승인·예약 조기 해제 없음 |
| 성공 응답 유실 | PG B의 성공 결과 저장 후 연결 종료 또는 제한 시간 초과로 응답 유실 | 같은 PG·업무 키 조회로 복구, 중복 승인·차감 없음 |
| 한 PG의 조회도 불가 | PG B의 승인·조회 오류를 함께 주입하고 이후 복구 | 미확정·재조회 작업 보존, 다른 PG로 중복 결제하지 않고 복구 후 대조 |
| 환불 거절·응답 유실 | 원 승인 PG에 환불 거절 또는 성공 후 응답 유실을 각각 주입 | 확정 거절이면 정산금 예약 해제·보상, 미확정이면 예약 유지·조회 후 원장 상쇄 |

응답 지연·유실 시험은 결과를 짧은 DB 트랜잭션으로 먼저 저장한 뒤 주입하며 지연 동안 DB 잠금을 유지하지 않습니다. 따라서 위 타임아웃 시험은 ‘응답이 늦었지만 PG에서는 이미 처리된 경우’를 검증합니다. PROCESSING 응답의 재조회 분기와 호출 전 중단으로 거래가 없는 경우는 별도 fixture로 검증하고, 응답 지연만으로 그 상황까지 검증했다고 하지 않습니다. PROCESSING은 실행 재전송 없이 조회하고, 거래 없음의 원키 재전송·임대 인계는 [복구 정책](policies.md#금융-결과-조회와-원키-재요청)을 따릅니다.

지표는 `pgId`·작업 종류·결과 종류별로 구분합니다. Grafana에서 PG별 지연 p50/p95/p99, 확정 거절률, HTTP 오류·타임아웃, 미확정 건수·복구 시간, 승인 완료 TPS와 Worker 적체를 비교하도록 안내합니다. 거래 ID·주문 ID는 메트릭 label로 넣지 않고 추적·대조 기록에서 사용합니다. 결과 보고에는 seed·시나리오 버전·적용 설정·선택 비율·신규 업무 건수와 재시도 횟수를 남깁니다.

서로 다른 시험 실행은 업무 키의 범위를 나눠 이전 거래를 신규 표본에 섞지 않습니다. 동일 조건 재현은 격리된 시험 데이터와 같은 seed·입력으로 수행하고 기존 공용 DB·볼륨을 임의 초기화하지 않습니다.

현재 k6 스크립트는 명세 조회용입니다. PG 업무 부하는 별도 시나리오로 작성하고, 의도한 거절·장애와 애플리케이션 결함을 구분합니다. 모든 HTTP 오류를 무조건 0으로 요구하는 대신 지정한 기대 결과·중복 승인 0·최종 금액 대조·미확정 복구를 완료 조건으로 둡니다.

### Redis

Redis는 로그인 세션의 원본 저장소로 사용합니다. 인증 데이터는 [고정 만료·폐기·복구 정책](policies.md#인증공통-api-기준)을 적용하고 캐시와 접근 권한을 구분합니다. Redis 공유 세션 연동과 부하 검증은 구현 단계에서 수행합니다. 금융 원장·예약·멱등성의 최종 기준은 DB에 두며, Redis 유실로 거래 이력과 금액이 달라지지 않아야 합니다.

### 간편결제 대역

`EASY_PAY`는 PG A/B/C와 같은 `finance-mock` 앱 안의 별도 거래 영역입니다. 간편결제는 이 대역만, 신용카드·체크카드는 선택한 PG 한 곳만 호출합니다. 최초 수단·대역·업무 키·외부 결제액을 저장하고, 미확정 조회와 환불도 원래 대역으로 보냅니다. 마일리지 전액 결제는 외부 거래를 만들지 않습니다.

간편결제의 첫 시험 설정은 응답 지연 100~300ms·신규 업무 확정 거절 1%·기본 응답 유실 0%를 제안합니다. 실제 서비스 성능이 아니며, PG와 같은 설정 검증·seed·결과 저장·응답 유실/조회 장애 계약을 적용합니다. 대역 ID와 수단 종류를 지표에 함께 기록하고 세 PG의 설정과 섞어 해석하지 않습니다.

간편결제 대역은 시험 계정의 잔액 검사·선점·거래 기록을 원자 저장합니다. 성공 시 한 번만 차감하고 확정 실패 시 선점을 해제하며, 성공 응답 유실로 잔액을 돌리지 않습니다. 환불은 원거래 금액을 원래 계정에 한 번만 반환합니다. 이 잔액은 Payment의 우리 마일리지와 별개입니다.

간편결제는 서버가 확인한 `EASY_PAY`·purpose=WALLET 시험 계정만 사용합니다. 미등록 계정·다른 제공자·지급 계정은 거절하고 가용 잔액을 원자 선점합니다. 원거래 키·계정·금액을 보존해 중복 요청·마지막 잔액 경쟁·응답 유실·전액 환불을 검증합니다. 실제 SDK·로그인·PIN은 연동하지 않습니다. 상품권은 [지원 범위](policies.md#금액과-주문)에서 제외합니다.

### 선착순 이벤트 집중 부하

시험용 가정으로 이벤트 상품 1개·한정 수량 1,000개에 서로 다른 구매자의 주문 요청 60,000건을 60초 동안 보냅니다. 90%는 이벤트 상품, 나머지는 일반 상품으로 보내고 첫 5초에 전체 요청의 50%를 집중시킵니다. 평균은 1,000요청/초, 첫 5초는 6,000요청/초인 **입력 목표**이며 측정 결과가 아닙니다. 이벤트 수량으로 확정 건수가 제한되므로 지속 결제 확정 1,000 TPS 시험과 분리합니다.

마지막 수량 동시 예약·구매자 중복 참여·여러 주문의 같은 마일리지 사용·PG/간편결제 응답 유실·환불 재전달·매진 이후 요청을 섞습니다. 신청 접수/거절·결제 대기·결제 확정·환불 복원·게이지 조회 지연과 피크 이후 적체 배출을 따로 기록합니다. 게이지 주기 조회를 켠 경우와 끈 경우의 발생기 부하도 구분합니다.

완료 조건은 초과 판매·중복 참여·마일리지 과차감/과복원 0건, 모든 확정 거래의 `T=E+M`, 복구 후 남은 미확정과 최종 원장/잔액 대조, DB 판매량과 게이지의 일치입니다. 의도한 매진 거절은 결함률로 합치지 않습니다. Redis 캐시 사용 여부·TTL·조회 빈도·허용 표시 지연을 기록하고 캐시 유실에도 구매 한도가 지켜지는지 확인합니다. 아직 이벤트 API·캐시·업무 부하 스크립트를 구현하거나 이 시험을 실행한 상태는 아닙니다.

### 거래 알림과 운영 알람

구매자·판매자가 결제·환불·마일리지·정산의 결과를 확인하도록 커머스에 거래 알림을 둡니다. 카카오 알림톡은 모의 수신으로 시작하며 새 업무 서비스·DB를 만들지 않습니다. Payment·Settlement의 알림 요청은 기존 Kafka·Outbox·Inbox를 재사용하고, 발송 실패는 금융 처리를 되돌리지 않습니다. 판매 집중 시 판매자 알림은 1분 묶음으로 처리합니다.

[알림 정책](policies.md#거래-알림)이 수신자·발송 시점·원키 복구를, [운영 알람](policies.md#운영-알람)이 금융 지연·작업 적체·서비스·자원 기준을 소유합니다. [API](api.md#거래-알림-사용-순서)·[알림 ERD](data-model.md#거래-알림)·[인프라 구조도](architecture.md#거래-알림)를 함께 적용합니다. 실제 외부 전달과 업무 지표·Alertmanager·Slack 연결은 구현 전입니다.

### Spring Batch 도입 전략

원장 반영 한 건과 환불 예약을 먼저 연결한 뒤, Settlement의 정산 배치 구현 단계에 Spring Batch 도입을 제안합니다. 대량 항목 분할 처리·실행 이력·재시작이 필요한 이유이며, 현재 실행 기반에 의존성만 미리 추가하지 않습니다. [Spring Batch 기능](https://spring.io/projects/spring-batch/)

배치는 지급 대상 예약·합계 확정·영속 지급 작업 생성까지 담당하고 외부 지급은 작업자가 수행하도록 제안합니다. Job 실행 이력이 중복 지급을 막아주는 것은 아니므로 항목 선점·지급 업무 키·외부 조회가 필요합니다. 실행 스케줄, 앱 기동 시 자동 실행 여부, 마감·재시작 파라미터와 메타데이터 migration을 함께 정의합니다. 버전은 프로젝트의 Spring Boot와 호환되는 관리 버전을 사용합니다.

## 9. 실패·공격·범위 이탈에 대한 검증

‘예상 질문’은 설계 이유를 설명하고, 보안 시험은 실제 경계 위반을 확인합니다. 설득력 있는 설명만으로 아래 보장이 검증됐다고 판단하지 않습니다.

| PG C 타임아웃 후 다른 PG로 재승인 시도 | 저장된 최초 PG·업무 키 유지, 미확정이면 PG 변경 거절 | 다른 PG에서 같은 주문을 중복 승인·환불하지 않음 |
| Outbox 발행 직후 프로세스 중단 | 재발행·Inbox·업무 키로 중복 수용 | 최종 반영 누락·중복 없음 |
| 환불 예약이 승인 원장보다 먼저 도착 | 선행 반영 대기 | 잘못된 실패 확정이나 예약 중복 없음 |
| 환불과 지급 예약 동시 요청 | 한쪽만 선점 | 같은 항목의 이중 사용 없음 |
| PG 환불 거절 후 예약 해제 이벤트 유실 | 보상 작업 추적·재전달 | PG 미환불·예약 해제 상태로 수렴 |
| 같은 알림 재전달·모의 수신 후 응답 유실·발송자 재시작 | 원 deliveryId 조회·같은 본문으로 재개 | 원알림 항목/모의 수신 1건, 금융 상태 불변 |
| 판매 묶음 마감과 늦은 판매 이벤트 경합 | 닫힌 본문 불변·새 열린 구간 수용 | 누락/중복 집계 없음, 수신자 혼용·구매자 잔액 노출 없음 |
| 배치·지급 작업 중간 재시작 | 같은 실행 경계·업무 키로 재개 | 누락·중복 배정·중복 지급 없음 |
| 구매 확정 누락·취소 정보 역순 | 버전·금융 상태 확인과 지급 보류 | 구매 확정 없이 지급하거나 취소 거래를 다시 활성화하지 않음 |
| 여러 지급 작업의 동시 실행 | 충분히 준비한 모의 재원에서 대역 자금 선점·차감을 원자 저장 | 지급 누락·중복 차감 없음, 응답 유실 후 같은 키 조회·재요청에도 결과 유지 |
| Redis 장애·캐시 만료 | 설계한 재조회·접근 제한 정책 적용 | 권한 우회·금액 변경 없음 |
| 정지·자격 폐기·위조된 통보 | 정한 신원 검증·신선도 정책 적용 | 허용 범위 밖 금융 작업 없음 |

판매자의 발송/반품 입고 입력이나 기한에 따른 자동 구매확정이 실제 물류를 증명한다고 주장하지 않습니다. 실행 주체·내용·처리 이력을 보존해 대조하고 실제 금융기관의 계약·가용성을 검증한 결과와도 구분합니다.

## 10. 예상 질문과 답변

### 이 프로젝트에서 무엇을 검증하나요?

부하와 외부 금융 장애가 겹쳐도 결제·환불·정산의 최종 상태와 금액을 맞추는지 검증합니다. 접수·승인 처리량과 정산 지연을 측정하고, 중복·역순·응답 유실·재시작 후 거래별 이력과 잔액을 대조합니다. 범위와 시험 조건은 재현 가능하게 고정합니다.

### 배송을 빼면 중요한 문제를 피한 것 아닌가요?

배송지 입력·주문 당시 주소 보관·판매자 발송 처리·구매 확정은 포함합니다. 택배사 연동과 배송 추적만 제외합니다. 지급은 결제 승인만으로 하지 않고 구매 확정·환불/예약 상태를 확인합니다.

### 구매자와 판매자는 같은 계정인가요?

아닙니다. 구매자용과 판매자용 계정을 각각 만들고 로그인합니다. 같은 사람이 두 계정을 가질 수 있지만 이메일이 같다는 이유로 연결하지 않습니다. 계정 분리는 인증 서버나 서비스를 두 개 배포한다는 뜻이 아닙니다. 하나의 회원·인증 도메인이 두 계정 종류의 신원·권한을 검증할 수 있습니다.

### 실제 배송과 자동 구매확정이 다르면요?

이 시스템은 실제 배송 증명까지 수행하지 않습니다. 자기 주문에 대한 구매자·판매자 권한과 상태를 확인하고, 시험에서는 미확정·지연·잘못된 입력을 구분합니다. 실제 물류 연동과 분쟁 판단은 추가 설계 범위입니다.

### 상하지 않는 상품이면 환불이 단순해지나요?

부패 관련 예외를 줄일 뿐 불량·변심·오배송은 남습니다. 구매자의 취소/반품 요청, 판매자의 반품 승인과 금융 환불 상태를 구분합니다. 상품 종류로 환불 자체가 불필요하다고 가정하지 않습니다.

### 왜 지급 전 전액 환불만 지원하나요?

첫 구현에서 원래 결제 구성·수수료·순정산액의 정확한 상쇄와 예약 경쟁을 검증하기 위한 범위입니다. 부분 환불과 지급 후 환불은 배분·회수 모델이 추가됩니다. 지원하지 않는 요청은 처리 불가 사유와 운영 확인 경로를 안내하며, 기술 구현 범위를 실제 반품 권리가 사라진다는 뜻으로 사용하지 않습니다.

### 배송비가 있는 주문은 어떻게 하나요?

기본 시험은 배송비 0원인 주문 결제액을 외부 수단과 마일리지로 부담합니다. 유료 배송과 반품비 공제는 별도 금액 모델이 필요하므로 기본 주문에서 지원하지 않습니다. 무료배송이어도 판매자의 실제 물류 원가가 없다는 뜻은 아닙니다.

### 쿠폰·마일리지·간편결제는 같은 것인가요?

쿠폰은 할인, 우리 마일리지는 Payment의 내부 잔액, 간편결제는 별도 외부 수단입니다. 환불은 사용 구성을 보존해 외부 취소와 내부 잔액 복원을 각각 처리합니다. 할인액을 현금으로 더 돌려주거나 외부 결제액만 보고 판매자 정산을 줄이지 않습니다. 구체 예는 [금액 규칙](#7-금액데이터-불변식)을 따릅니다.

### PG 타임아웃이면 실패로 돌리고 다시 결제하면 되지 않나요?

외부에서는 성공했지만 응답만 유실됐을 수 있습니다. 같은 업무 키로 조회·복구하고 확인 전에는 새 금융 작업으로 바꾸지 않습니다. 멱등성은 외부 호출과 내부 업무 키 양쪽에 필요합니다. [토스페이먼츠 멱등성 설명](https://docs.tosspayments.com/blog/what-is-idempotency)

### Kafka를 쓰면 중복과 유실이 모두 해결되나요?

DB 저장과 메시지 발행은 별개의 실패 지점입니다. 상태·Outbox를 함께 저장하고 수신 측은 Inbox·작업을 저장한 뒤 ack합니다. 중복 전달은 업무 키로 처리하며, 외부 PG 호출은 별도의 멱등·조회 계약으로 보호합니다.

### 왜 세 서비스인가요? 한 서비스로도 가능한 것 아닌가요?

단일 서비스도 가능한 대안입니다. 현재안은 구매자/판매자·주문/재고/쿠폰을 함께 확정하는 커머스, 외부 금융 호출·환불의 Payment, 원장·지급의 Settlement로 나눕니다. Payment는 API와 Worker를 따로 확장합니다. 사용자 도메인은 필요하지만 별도 배포 서비스가 필수인 것은 아닙니다. 커머스 내부 도메인을 더 쪼개는 대신 결합된 배포·확장 범위를 감수합니다.

### DB 한 대인데 MSA라고 할 수 있나요?

서비스별 논리 DB·계정·스키마를 소유하고 API·이벤트로 연동합니다. 물리 DB 장애 격리는 확보하지 못한 개발 구성입니다. 서비스 경계가 있다는 사실을 고가용성이나 물리 분산 성과로 확대하지 않습니다.

### FK가 없거나 논리 삭제하면 금융 이력이 깨지지 않나요?

FK 생략은 유효성 검사를 없앤다는 뜻이 아닙니다. 애플리케이션 참조 검사·업무 상태·DB 유니크와 금액 제약을 사용합니다. 논리 삭제는 판매자 같은 관리 데이터에 적용하고, 금융 이력은 삭제 없이 정정·상쇄 기록으로 보존합니다.

### Redis나 분산 잠금으로 중복 지급을 막으면 안 되나요?

캐시 만료·유실·임대 만료 뒤 중복 실행이 가능하다고 보고 DB의 예약 상태와 업무 유일성으로 마지막 방어를 둡니다. Redis는 필요한 캐시·인증·조율 용도에서 검증합니다.

### 왜 Spring Batch를 쓰나요? 배치가 끝나면 지급도 안전한가요?

대량 항목 처리와 재시작 관리를 위한 도구 후보입니다. 배치 메타데이터와 실제 지급 결과는 다르므로 지급 작업·외부 업무 키·미확정 조회가 필요합니다. 배치를 사용했다고 금융 처리가 정확히 한 번 완료됐다고 설명하지 않습니다.

### PG를 Mock으로 만들면 성능 시험에 의미가 있나요?

명시한 지연·실패·응답 유실 조건에서 우리 접수·작업·이벤트·DB 경로의 처리량과 복구를 비교할 수 있습니다. 실제 PG의 성능·가용성·계약을 검증한 것은 아닙니다. [PG 3종 시험](#pg-3종과-장애-시나리오)의 정상·장애 프로필을 나누고 실제 적용 값과 PG별 결과를 기록합니다.

### 왜 1,000 TPS이며 1만 TPS도 가능한가요?

현재 목표와 완료 TPS 정의는 [성능 목표](../README.md#성능-목표와-검증)를 따릅니다. 추가 근거는 대상 규모·피크 시간의 시험 가정으로 설명하고 실제 수요 통계와 구분합니다. 1만 TPS는 자원 확보 후 확장 시험 목표이며 달성 결과가 아닙니다. 같은 장비의 부하 발생기가 서버 자원을 쓰는 영향도 기록합니다.

### PG 입금 전에 지급하나요?

선지급 재원은 항상 충분하다고 가정하므로 구매확정된 거래는 PG 입금 전에도 지급합니다. 시험 전 전체 지급·환불에 충분한 모의 자금을 준비하고, PG 입금·선지급·플랫폼 쿠폰/마일리지 부담을 구분해 대조합니다. 실자금 조달·대출 상품은 제외합니다. [채택한 결정](decisions/0001-payout-after-purchase-confirmation.md)을 따릅니다.
