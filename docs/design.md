# 상세 설계 초안

결제·환불·정산의 정합성·장애 복구·부하 처리를 검증하는 기술 프로젝트의 설계 초안입니다. 구현 경계와 선택 이유를 정리하고, 김민식이 전체 상세 설계를 작성해 각 구현 담당자와 계약을 맞춥니다. 구현·성능 검증은 별도로 수행합니다.

## 1. 기준과 책임

- [README](../README.md): 기본 기능·금액 정책·정합성·성능 목표의 기준입니다.
- [프로젝트 초안](proposal.md): 상품 범위·검증 목표·선택 확장·이름별 역할 배분을 관리합니다.
- 이 문서: 포함·제외 범위, 가정과 이유, 업무 흐름·검증 계약·예상 질문을 구체화합니다. 새 입력·처리 방안은 **설계 제안**으로 표시합니다.
- [서비스와 코드 경계](architecture.md), [DB 정책](migrations.md), [공통 구현 규약](../CONTRIBUTING.md#구현-규약): 코드·저장·요청·오류·이벤트 형식을 관리합니다.

전체 설계는 서비스 경계부터 각 도메인의 상태·금액 규칙·ERD·API·이벤트·동시성·복구·테스트 시나리오까지 김민식이 작성합니다. 구현 담당자는 자기 영역을 검토하고 구현·테스트하며, 변경이 필요하면 이유와 영향을 전달합니다. 합의한 변경은 기준 문서 한 곳에 반영하고, 개인 메모나 PR 설명만으로 계약을 바꾸지 않습니다.

## 2. 해결 범위

기존 커머스 플랫폼에 붙는 금융 처리 서비스입니다. 승인된 결제를 판매자별 원장에 반영하고, 환불과 지급이 겹쳐도 같은 금액이 중복 처리되지 않도록 설계합니다. 행사 시작의 요청 집중과 외부 금융 장애를 시험 조건으로 사용하며, [선택 확장](proposal.md#선택-확장-후보)은 기본 구현의 착수 조건이 아닙니다.

| 영역 | 포함 | 제외·외부 책임 | 선택 이유와 남는 책임 |
| --- | --- | --- | --- |
| 판매자·인증 | 판매자·사용자·연동 자격, 판매자별 접근 권한 | 실제 사업자 심사·금융기관 계약·실계좌 검증 연동 | 금융 데이터 소유권을 식별합니다. 계정 등록만으로 실제 사업자 적격성을 보증하지 않습니다. |
| 상품·주문 | 외부 주문 참조·판매자·확정 금액의 검증 | 상품 등록·가격 검색·장바구니·재고·주문 이행 | 결제 대상과 금액은 필요하지만 커머스 전체를 만들지는 않습니다. 외부 원천 정보와의 일치 계약이 필요합니다. |
| 방송 | 방송·행사로 발생한 부하 시나리오 | 영상 송출·채팅·스트리밍 품질 | 피크의 배경으로 사용합니다. 영상 처리 성능을 주장하지 않습니다. |
| 배송·반품 | 금융 처리에 필요한 외부 승인 정보 | 운송장·택배사·배송 추적·수거·검수·비용 계산 | 물류와 금융 판단을 나눕니다. 배송 미완료 거래의 지급 가능 여부는 별도 입력 계약으로 통제해야 합니다. |
| 결제 | 접수·PG 승인·조회·멱등성·미확정 복구 | 실카드 정보 수집·실PG 계약·다중 결제수단별 특수 정책 | 외부 금융 실패를 모의하면서 내부 처리의 정확성을 검증합니다. |
| 환불 | 지급 예약 전 전액 환불·예약·보상·조회 | 부분 환불·교환·지급 후 환불·반품 분쟁 판정 | 첫 SAGA와 금액 보존에 집중합니다. 제외한 예외가 실제로 발생하지 않는다고 가정하지 않습니다. |
| 정산·지급 | 원장·수수료·지급 대상 예약·배치·모의 지급 | 선정산·대출·환전·세금 신고·실자금 운용 | 이미 정산 가능한 금액을 지급하는 모델입니다. 아직 받지 못한 자금을 만들어 지급하지 않습니다. |
| 운영 | 상태·추적·재처리·대조·부하 시험 | 상용 수준의 무중단·다중 리전·금융기관 운영 보장 | 단일 개발 환경에서 확인할 보장과 운영 한계를 구분합니다. |

기본 거래는 **결제 한 건·판매자 한 명·KRW·전액 환불**로 제한하는 설계 제안입니다. 다중 판매자 결제와 부분 환불을 선택하면 이 문서와 원장·환불 계약을 함께 확장합니다.

## 3. 가정과 선택 이유

가정은 현실의 사실이나 검증 결과가 아닙니다. 가정이 깨졌을 때의 처리까지 정하고, 외부 시스템이 항상 정상이라는 전제는 두지 않습니다.

| 가정·선택 | 이유 | 깨졌을 때의 처리·한계 |
| --- | --- | --- |
| 첫 상품은 비부패성 일반 완제품 | 식품 보관·유통기한·제작 취소 등 상품별 예외를 줄입니다. | 불량·오배송·변심 판단은 남습니다. 외부 커머스가 승인한 환불을 금융 상태에 따라 처리합니다. |
| 기본 시험 결제는 상품대금만 포함하고 배송비는 0원 | 배송비·반품비 배분 없이 전액 환불을 검증합니다. | 유료 배송비를 합친 주문에서 상품대금만 환불하는 동작은 이 범위로 검증하지 않습니다. 실제 도입 시 금액 모델을 확장해야 합니다. |
| 금액·수수료는 README의 원 단위·5%·버림 정책 | 재현 가능한 하나의 계산 기준으로 비교합니다. | 실제 PG 원가·세금·계약별 수수료를 대표하지 않습니다. 정책 변경은 버전으로 구분합니다. |
| 외부 금융 대역은 업무 키로 멱등 처리하고 최종 상태를 조회할 수 있음 | 응답 유실 후 중복 실행 없이 결과를 확인하기 위한 최소 계약입니다. | 조회도 실패하면 미확정을 유지하고 보류·알림·대조로 넘깁니다. 새 키로 성공을 추측하지 않습니다. |
| 메시지는 중복·지연·순서 역전될 수 있음 | 재전달과 서로 다른 스트림 사이의 순서 차이를 처리해야 합니다. | Inbox·업무 유니크 키·상태 전이로 방어합니다. Kafka만으로 외부 금융까지 정확히 한 번 실행된다고 주장하지 않습니다. |
| 외부 플랫폼은 인증된 연동 주체로 주문·환불·정산 승인 정보를 제공 | 우리가 소유하지 않는 실물 상태를 전달받기 위함입니다. | 호출 권한·판매자 소속·참조·금액·중복을 검증합니다. 실제 배송의 진위까지 보증하지는 못합니다. |
| 기본 지급은 받은 자금의 지급 가능 잔액 안에서 실행 | 선정산 자금 공급을 기본 범위에 섞지 않습니다. | 잔액 부족은 보류 사유이며, 원장상 정산 예정액과 현금을 같은 값으로 취급하지 않습니다. |
| 개발 인프라는 단일 브로커·PostgreSQL·Redis | 실행·비용·문제 재현을 단순하게 합니다. | 노드 장애 시 전체 영향이 있을 수 있습니다. 논리 분리와 물리 장애 격리는 다릅니다. |

배송비 0원은 구매자에게 배송비를 별도 청구하지 않는 무료배송 조건을 시험 대상으로 삼는 제안입니다. 판매자의 배송 원가나 반품비가 없다는 뜻은 아닙니다. 환불액에서 별도 비용을 공제해야 하는 거래는 부분 환불·비용 배분 모델을 추가해야 합니다.

## 4. 서비스 경계와 원천 데이터

| 소유자 | 소유 데이터·판단 | 다른 서비스에 전달할 결과 |
| --- | --- | --- |
| 외부 커머스 | 주문·상품·배송·반품 승인, 지급 가능 여부의 업무 근거 | 주문 참조·확정 금액·승인 참조·정산 가능 정보 |
| Seller | 사용자·판매자·연동 자격·판매자 상태 | 인증·권한 판정에 필요한 정보, 판매자 변경 |
| Payment | 결제·승인 시도·환불·SAGA·외부 호출 작업 | 결제 확정 결과, 환불 예약 명령·성공·보상 명령 |
| Settlement | 금액 정책 적용 결과·원장·환불/지급 예약·정산 항목·배치·지급 | 예약 성공·거절·해제 결과, 지급 상태 |
| `finance-mock` | 모의 PG 승인·환불, 지급 기관의 실행 결과·잔액·자금 선점 | 접수·처리 중·확정 결과 조회, 지급 가능 잔액 |

Payment API와 Worker는 같은 서비스·DB의 실행 역할입니다. Spring Batch를 도입해도 처음에는 Settlement의 정산 작업으로 두며 별도 업무 서비스를 만들지 않습니다. 서비스 경계는 인원수가 아니라 데이터 소유권·외부 장애 영향·변경 책임을 기준으로 유지합니다.

다른 서비스의 DB에 직접 접근하지 않습니다. 판매자 조회 모델은 이벤트로 갱신할 수 있지만, 정지·자격 폐기의 반영 지연을 숨기지 않습니다. 인증과 중요 작업에서 최신성을 확보할 방법은 11절의 결정 항목입니다.

## 5. 입력과 신뢰 경계

다음은 필드 이름을 확정한 API 명세가 아닌 **입력 계약 제안**입니다. HTTP 경로·상태 코드·스키마는 김민식이 상세 명세에서 고정합니다.

| 입력 | 최소 정보 | 수신 측 검증 |
| --- | --- | --- |
| 결제 요청 | 외부 주문 참조·판매자·KRW 금액·멱등키 | 인증된 호출자의 판매자 권한, 양수 금액·상한, 주문과 결제의 중복, 같은 키의 본문 일치 |
| 환불 요청 | 원결제 참조·외부 승인 참조·멱등키 | 승인 주체 권한, 원결제 소유권·승인 상태·원금액, 지급 예약 여부, 기존 환불 |
| 정산 가능 승인 | 주문/결제 참조·승인 ID·업무 버전·적용 시각 | 호출 권한, 판매자·원거래 일치, 중복·오래된 버전, 이미 끝난 거래의 부적절한 변경 |
| PG·지급 결과 | 외부 업무 키·외부 거래 참조·상태·금액 | 등록된 대역·요청과의 대응, 금액 일치, 허용 상태 전이. 결과 통보만 신뢰하지 않고 필요 시 조회 |
| 운영 재처리 | 대상 작업 ID·실행 주체·사유 | 운영 권한, 현재 상태, 기존 시도의 결과, 감사 기록 |

정산 가능 승인은 실물 거래의 지급 기준을 명확히 하기 위한 새 설계 제안입니다. 기존안에 입력 계약까지 정해져 있던 기능은 아닙니다. 도입한다면 이를 확인하기 전에는 지급 대상을 만들지 않으며, 시험 데이터에서도 승인·미승인·승인 지연을 구분합니다. 승인 취소와 지급이 겹칠 때의 전이도 명세에 포함합니다.

외부 원천과 일치하는 주문 금액을 어떤 절차로 확정할지도 연동 계약에 적습니다. 구매자 화면이 보낸 금액·`sellerId`·임의 헤더만으로 거래를 만들지 않습니다. 인증된 판매자 서버라도 요청한 범위를 넘어 다른 판매자의 거래를 조회·처리할 수 없어야 합니다.

## 6. 핵심 업무 흐름

### 결제

1. 호출자·판매자 권한·입력·멱등키를 확인합니다. 동일 키·동일 요청은 기존 처리로 연결하고 다른 본문이면 충돌로 거절합니다.
2. 결제 접수와 Outbox를 같은 Payment DB 트랜잭션에 저장합니다. 접수 응답은 처리 ID와 조회 경로를 주며 승인 완료를 뜻하지 않습니다.
3. 수신 측은 Inbox·실행 작업을 영속 저장한 뒤 ack합니다. Worker는 DB 잠금을 유지하지 않은 상태에서 모의 PG를 호출합니다.
4. 명시적 승인·거절이면 결과와 Outbox를 저장합니다. 응답 유실·조회 실패는 미확정으로 추적하며 자동으로 실패 처리하지 않습니다.
5. Settlement는 승인 결과를 한 번만 원장에 반영합니다. 승인 결과 전달이 지연되는 동안 Payment와 Settlement의 조회 결과가 일시적으로 다를 수 있습니다.

같은 주문에 진행 중이거나 승인된 결제를 중복 생성하지 않습니다. 확정 거절 뒤 다시 시도하는 경우는 이전 시도와 연결해 기록하고, 논리 거래 키와 외부 호출 시도 키의 관계를 명세로 정합니다. 미확정 거래를 재시도하기 위해 새 주문·업무 키를 발급하지 않습니다.

설명용 상태 흐름은 ‘접수 → 외부 처리 중 → 승인 또는 확정 거절’입니다. 외부 결과를 모르면 ‘미확정’을 거쳐 조회로 확정합니다. 저장할 enum 이름과 전이 조건은 이 의미를 보존해 명세화합니다.

### 환불 SAGA

1. 외부 환불 승인을 확인하고 전액 환불 요청을 접수합니다. 승인 미확정 결제는 먼저 결제 결과를 확인하며 원금액을 추측하지 않습니다.
2. Payment는 환불 상태와 정산금 예약 명령을 함께 저장합니다. Settlement는 해당 거래의 지급 대상 순액을 원자적으로 예약합니다.
3. 선행 승인 원장이 아직 없으면 의존 정보를 기다리는 작업으로 남깁니다. 동일 명령 재전달로 예약을 중복 생성하지 않습니다.
4. 지급 예약이 이미 있거나 환불 완료 상태라면 예약을 거절하고 PG 환불을 호출하지 않습니다. 같은 거래에서 진행 중·완료된 전액 환불이 다른 멱등키로 중복 실행되지 않게 합니다.
5. 예약 성공 후 PG에 원결제 전액 환불을 요청합니다. 성공하면 원장 상쇄를 요청하고 확인합니다. PG 환불 성공만으로 내부 반영까지 끝났다고 표시하지 않습니다.
6. PG가 확정 거절하면 예약 해제를 보상 명령으로 요청합니다. 해제가 확인되기 전까지 보상 대기 상태를 추적합니다. 결과가 미확정이면 예약을 유지하고 조회합니다.

예를 들어 원결제 10,000원·수수료 500원·판매자 몫 9,500원이면, 지급과 충돌하지 않도록 보호할 판매자 순액은 9,500원이고 구매자의 PG 환불액은 10,000원입니다. 성공 시 최초 수수료 500원과 순정산액 9,500원을 상쇄합니다. 이후 수수료율로 재계산하지 않습니다.

외부 반품 승인과 금융 환불 완료는 다른 결과입니다. 지급 예약 후·지급 후 환불은 첫 구현에서 지원하지 않으며, 연동 실패 응답과 운영 확인 경로를 정의합니다. 그 응답을 소비자의 반품 권리가 사라졌다는 의미로 사용하지 않습니다.

### 정산·지급

1. 결제·환불 결과를 지속적으로 원장에 반영합니다. 지급 주기가 길어도 원장 기록을 해당 날짜까지 미루지 않습니다.
2. 배치 실행의 마감 기준을 고정하고, 미환불·미예약·정산 가능 조건을 만족하는 항목을 선점합니다. 새 정산 가능 승인 계약을 채택하면 그 승인도 필수 조건입니다.
3. 지급 건별로 항목 선점·합계·지급 레코드·실행 작업을 같은 Settlement DB 트랜잭션에 저장합니다. 환불 예약과 지급 예약은 같은 항목에서 동시에 성공할 수 없습니다. 항목만 예약되고 실행 작업은 없는 상태를 남기지 않습니다.
4. 저장한 작업으로 지급 기관에 실행을 요청합니다. 사전 잔액 조회는 참고 값이며, 실행 시점의 원자적 잔액 검사·선점이 지급 가능 여부를 결정합니다. 외부 호출은 항목 예약 트랜잭션 밖에서 수행합니다.
5. 실제 지급 성공을 확인한 뒤 지급 완료로 기록합니다. 지급 요청 접수와 지급 완료를 구분합니다.
6. 미확정 지급은 예약을 유지하고 같은 외부 업무 키로 조회·복구합니다. 확정 결과에 따른 지급·항목·작업 상태 변경은 같은 DB 트랜잭션에 저장합니다. 확정 거절 뒤 예약 해제·재시도 허용 조건은 명세로 고정합니다.

대역의 결제 승인액·입금 상태·지급 가능 잔액도 구분하는 설계 제안입니다. 성공한 결제액 전부를 즉시 지급 가능한 현금으로 간주하지 않으며, 시험에서는 지급 가능 잔액과 부족 상황을 별도로 준비합니다.

**지급 기관 대역의 계약 제안:** `finance-mock`은 자기 DB에서 지급 업무 키·금액의 기록과 잔액 검사·자금 선점을 원자적으로 처리합니다. 처리 중인 금액은 가용 잔액에서 제외하고, 성공 시 한 번만 차감하며 확정 실패 시 선점을 해제합니다. 응답 유실만으로 자금을 반환하지 않습니다. 같은 키·같은 요청은 기존 결과로 연결하고 다른 금액은 거절합니다. Settlement의 거래별 지급 예약과 대역의 자금 선점은 서로 다른 DB의 책임이며 한 트랜잭션으로 묶지 않습니다.

**배치 제안:** 마감 이전에 수신·반영된 미처리 항목을 대상으로 하고, 늦게 들어온 과거 거래도 다음 배치에서 누락 없이 선택합니다. 원거래 발생일의 하한만으로 조회해 늦은 거래를 제외하지 않습니다. 같은 실행의 재시작에서는 마감 값과 업무 키를 유지합니다. 업무 시간대는 Asia/Seoul, 저장·전송 시각은 공통 규약의 UTC를 제안합니다. 실제 지급 주기·마감 시각은 팀 결정 전입니다.

## 7. 금액·데이터 불변식

| 불변식 | 저장·처리에서 지킬 조건 | 검증 예 |
| --- | --- | --- |
| 중복 승인·환불 방지 | 주문별 진행 중·승인 결제와 원결제별 진행 중·완료 환불의 중복을 DB에서 차단합니다. 확정 거절 뒤의 시도 이력은 구분합니다. | 다른 키로 같은 주문을 중복 결제하거나 같은 원결제를 중복 환불 |
| 원장 중복 반영 방지 | 이벤트 ID뿐 아니라 원거래·업무 종류의 유일성도 둡니다. | 다른 이벤트 ID로 동일 승인 결과 재전달 |

| 지급 합계·작업 인계 | 지급액은 선점한 항목의 합계이며 항목·지급·작업을 원자 저장합니다. 다른 배치가 같은 항목을 중복 배정하지 않습니다. | 예약 중단 시 함께 롤백, 커밋 후 재시작 시 저장된 작업 재개, 항목별 배정·지급 건수 대조 |
| 가용 자금 초과 방지 | 지급 기관 대역이 자금 선점·차감과 업무 키의 중복을 원자적으로 검증합니다. | 잔액 10,000원에서 서로 다른 7,000원 지급 두 건을 동시에 요청해 한 건만 선점, 같은 키 재요청 시 추가 차감 없음 |

| 이력 보존 | 원장과 결제·환불·지급 이력은 물리 삭제하거나 금액을 덮어쓰지 않습니다. | 정정 후 원거래와 상쇄·추가 항목을 함께 추적 |

물리 ERD는 서비스별로 작성합니다. 최소 후보는 Seller의 판매자·사용자·연동 자격, Payment의 결제·시도·환불·SAGA·작업, Settlement의 원장·정산 항목·예약·배치·지급입니다. Outbox·Inbox는 각 소유 DB에 둡니다. 후보 이름만으로 테이블을 생성하지 않고 키·타입·유니크·인덱스·삭제·보존 조건을 명세와 migration으로 연결합니다.

FK를 두지 않는 기존 정책은 유지하되 애플리케이션의 참조 확인과 DB의 `NOT NULL`·`UNIQUE`·`CHECK`를 함께 사용합니다. Redis 잠금이나 Kafka 순서만으로 금액 불변식을 대신하지 않습니다. [데이터 정책](migrations.md#데이터-보존과-제약-조건)을 따릅니다.

## 8. 인증·이벤트·캐시·배치 선택

### 인증과 접근

김민식이 인증 방식·토큰 또는 세션 수명·폐기·권한을 상세화하고 구현합니다. JWT와 Redis 공유 세션 중 어느 방식도 이 문서만으로 확정하지 않습니다. 어떤 방식을 택하든 Gateway 검사와 별도로 백엔드에서 호출자·판매자 소유권·허용 작업을 확인합니다. 내부 네트워크와 요청 헤더를 신원 증명으로 취급하지 않습니다.

JWT 선택 시 서명·발급자·만료·대상 검증과 폐기 반영 방식을, 세션 선택 시 저장소 장애·만료·로그아웃·동시 세션 정책을 정합니다. 판매자 상태 캐시와 유효한 인증 정보 사이에 차이가 날 때 신규 금융 요청을 허용할 기준도 정합니다. 인증 정보 재조회·중단 기준과 허용할 반영 지연은 구현 전 결정 사항입니다. [Spring Security의 JWT 검증 모델](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html)

### Kafka와 복구

원자 저장·ack·중복 처리의 기준은 [정합성 설계](../README.md#정합성-설계)를 따릅니다. Kafka는 후속 작업을 분리하고 대기 작업을 전달하기 위한 선택이며, 사용만으로 응답 지연이나 처리량 향상을 보장하지 않습니다.

재시도는 일시적 통신·저장 실패, 선행 이벤트 대기, 외부 미확정 조회를 구분합니다. 잘못된 입력·권한·금액 불일치는 무한 재시도하지 않습니다. 횟수·간격·대기 기한·DLT·운영 재처리 기준은 이벤트별로 정합니다. 메시지의 처리 완료와 금융 업무의 완료도 구분합니다. Inbox와 실행 작업을 저장한 시점의 ack는 외부 지급이 끝났다는 뜻이 아닙니다.

작업 실행자가 죽으면 임대 만료 후 다른 실행자가 인계할 수 있도록 제안합니다. 중복 인계가 발생해도 같은 외부 업무 키와 DB 상태 조건으로 보호해야 합니다. 임대 시간만 믿고 미확정 작업을 새 거래로 실행하지 않습니다.

### Redis

조회 캐시·인증 저장 등 용도를 먼저 정하고 TTL·무효화·장애 시 동작을 설계합니다. 세션 방식이 미선택인 상태에서 세션 클러스터링을 완료했다고 기록하지 않습니다. 금융 원장·예약·멱등성의 최종 기준은 DB에 두며, 캐시가 사라져도 거래 이력과 금액이 달라지지 않아야 합니다.

### Spring Batch 도입 전략

원장 반영 한 건과 환불 예약을 먼저 연결한 뒤, Settlement의 정산 배치 구현 단계에 Spring Batch 도입을 제안합니다. 대량 항목 분할 처리·실행 이력·재시작이 필요한 이유이며, 현재 실행 기반에 의존성만 미리 추가하지 않습니다. [Spring Batch 기능](https://spring.io/projects/spring-batch/)

배치는 지급 대상 예약·합계 확정·영속 지급 작업 생성까지 담당하고 외부 지급은 작업자가 수행하도록 제안합니다. Job 실행 이력이 중복 지급을 막아주는 것은 아니므로 항목 선점·지급 업무 키·외부 조회가 필요합니다. 실행 스케줄, 앱 기동 시 자동 실행 여부, 마감·재시작 파라미터와 메타데이터 migration을 함께 정의합니다. 버전은 프로젝트의 Spring Boot와 호환되는 관리 버전을 사용합니다.

## 9. 실패·공격·범위 이탈에 대한 검증

‘예상 질문’은 설계 이유를 설명하고, 보안 시험은 실제 경계 위반을 확인합니다. 설득력 있는 설명만으로 아래 보장이 검증됐다고 판단하지 않습니다.

| 상황 | 기대 동작 | 검증할 최종 결과 |
| --- | --- | --- |
| 다른 판매자의 ID·결제 ID로 요청 | 호출자 권한과 소유권에서 거절 | 타 판매자 데이터·금액 변경·외부 호출 없음 |
| 동일 멱등키에 금액 변경 | 충돌로 거절 | 원거래와 기존 응답 의미 유지 |
| 진행 중·완료 거래를 새 키로 중복 요청 | 업무 유니크 키·상태 조건으로 중복 차단 | 승인·환불·원장 중복 0건. 확정 거절 뒤의 허용된 재시도와 구분 |
| PG 처리 성공 후 응답 유실 | 미확정으로 기록하고 조회 | 동일 업무의 외부 실행 결과 1건과 내부 상태 수렴 |
| Outbox 발행 직후 프로세스 중단 | 재발행·Inbox·업무 키로 중복 수용 | 최종 반영 누락·중복 없음 |
| 환불 예약이 승인 원장보다 먼저 도착 | 선행 반영 대기 | 잘못된 실패 확정이나 예약 중복 없음 |
| 환불과 지급 예약 동시 요청 | 한쪽만 선점 | 같은 항목의 이중 사용 없음 |
| PG 환불 거절 후 예약 해제 이벤트 유실 | 보상 작업 추적·재전달 | PG 미환불·예약 해제 상태로 수렴 |
| 배치·지급 작업 중간 재시작 | 같은 실행 경계·업무 키로 재개 | 누락·중복 배정·중복 지급 없음 |
| 정산 가능 승인 누락·지급 잔액 부족 | 지급 보류 | 승인이나 자금 없이 지급 완료로 전이하지 않음 |
| 여러 지급 작업이 같은 가용 잔액 사용 | 대역의 원자적 자금 선점으로 초과 요청 거절 | 가용 잔액 음수·중복 차감 없음, 응답 유실 후 같은 키 조회·재요청에도 결과 유지 |
| Redis 장애·캐시 만료 | 설계한 재조회·접근 제한 정책 적용 | 권한 우회·금액 변경 없음 |
| 정지·자격 폐기·위조된 통보 | 정한 신원 검증·신선도 정책 적용 | 허용 범위 밖 금융 작업 없음 |

실물 상태를 허위로 승인하는 외부 플랫폼이나 실제 금융기관의 계약 위반까지 막는 시스템이라고 주장하지 않습니다. 승인 출처·내용·처리 이력을 보존해 대조할 수 있게 하고, 확인할 수 없는 상태는 보류합니다.

## 10. 예상 질문과 답변

### 이 프로젝트에서 무엇을 검증하나요?

부하와 외부 금융 장애가 겹쳐도 결제·환불·정산의 최종 상태와 금액을 맞추는지 검증합니다. 접수·승인 처리량과 정산 지연을 측정하고, 중복·역순·응답 유실·재시작 후 거래별 이력과 잔액을 대조합니다. 범위와 시험 조건은 재현 가능하게 고정합니다.

### 배송을 빼면 중요한 문제를 피한 것 아닌가요?

기존 플랫폼이 상품·물류를 소유한다는 제품 경계입니다. 대신 지급 판단에 필요한 외부 승인 정보를 계약으로 받아야 합니다. 배송 기능을 제외한 것과 승인 없이 지급해도 된다는 가정은 다릅니다.

### 실제로 배송되지 않았는데 외부에서 승인하면요?

승인 주체·판매자·참조·금액·버전을 검증하지만 실물 상태를 직접 확인하지는 않습니다. 시험에서는 외부 승인 입력을 명시하고 승인 누락·위조·지연을 재현합니다. 승인 이력·대조·지급 보류·운영 확인 경로를 검증하되, 실제 배송 확인을 보장했다고 설명하지 않습니다.

### 상하지 않는 상품이면 환불이 단순해지나요?

부패 관련 예외를 줄일 뿐 불량·변심·오배송은 남습니다. 외부 커머스가 사유를 판단하고 우리는 승인된 요청의 금융 처리와 상태를 책임집니다. 상품 종류로 환불 자체가 불필요하다고 가정하지 않습니다.

### 왜 지급 전 전액 환불만 지원하나요?

첫 구현에서 원금액·수수료·순정산액의 정확한 상쇄와 예약 경쟁을 검증하기 위한 범위입니다. 부분 환불과 지급 후 환불은 배분·회수 모델이 추가됩니다. 지원하지 않는 요청은 명시적으로 거절하고 처리 경로를 안내합니다. 상품의 반품 조건은 외부 커머스의 책임으로 둡니다.

### 배송비가 있는 주문은 어떻게 하나요?

기본 시험은 상품대금만 결제하고 배송비 0원을 가정합니다. 배송비가 합쳐진 금액에서 상품만 취소하는 동작은 부분 환불·비용 배분에 해당하므로 별도 확장입니다. 외부 플랫폼에 계산을 맡긴다는 말만으로 금융 처리의 누락을 감추지 않습니다.

### PG 타임아웃이면 실패로 돌리고 다시 결제하면 되지 않나요?

외부에서는 성공했지만 응답만 유실됐을 수 있습니다. 같은 업무 키로 조회·복구하고 확인 전에는 새 금융 작업으로 바꾸지 않습니다. 멱등성은 외부 호출과 내부 업무 키 양쪽에 필요합니다. [토스페이먼츠 멱등성 설명](https://docs.tosspayments.com/blog/what-is-idempotency)

### Kafka를 쓰면 중복과 유실이 모두 해결되나요?

DB 저장과 메시지 발행은 별개의 실패 지점입니다. 상태·Outbox를 함께 저장하고 수신 측은 Inbox·작업을 저장한 뒤 ack합니다. 중복 전달은 업무 키로 처리하며, 외부 PG 호출은 별도의 멱등·조회 계약으로 보호합니다.

### 왜 세 서비스인가요? 한 서비스로도 가능한 것 아닌가요?

단일 서비스도 가능한 대안입니다. 현재안은 판매자·인증, 외부 승인·환불, 원장·지급의 소유권과 변경 책임을 구분합니다. Payment는 API와 Worker를 나눠 확장할 수 있습니다. 그 대가로 이벤트 지연·계약 관리·복구 비용을 감수하며, 인원수 때문에 더 나누지는 않습니다.

### DB 한 대인데 MSA라고 할 수 있나요?

서비스별 논리 DB·계정·스키마를 소유하고 API·이벤트로 연동합니다. 물리 DB 장애 격리는 확보하지 못한 개발 구성입니다. 서비스 경계가 있다는 사실을 고가용성이나 물리 분산 성과로 확대하지 않습니다.

### FK가 없거나 논리 삭제하면 금융 이력이 깨지지 않나요?

FK 생략은 유효성 검사를 없앤다는 뜻이 아닙니다. 애플리케이션 참조 검사·업무 상태·DB 유니크와 금액 제약을 사용합니다. 논리 삭제는 판매자 같은 관리 데이터에 적용하고, 금융 이력은 삭제 없이 정정·상쇄 기록으로 보존합니다.

### Redis나 분산 잠금으로 중복 지급을 막으면 안 되나요?

캐시 만료·유실·임대 만료 뒤 중복 실행이 가능하다고 보고 DB의 예약 상태와 업무 유일성으로 마지막 방어를 둡니다. Redis는 필요한 캐시·인증·조율 용도에서 검증합니다.

### 왜 Spring Batch를 쓰나요? 배치가 끝나면 지급도 안전한가요?

대량 항목 처리와 재시작 관리를 위한 도구 후보입니다. 배치 메타데이터와 실제 지급 결과는 다르므로 지급 작업·외부 업무 키·미확정 조회가 필요합니다. 배치를 사용했다고 금융 처리가 정확히 한 번 완료됐다고 설명하지 않습니다.

### PG를 Mock으로 만들면 성능 시험에 의미가 있나요?

명시한 지연·실패·응답 유실 조건에서 우리 접수·작업·이벤트·DB 경로의 처리량과 복구를 비교할 수 있습니다. 실제 PG의 성능·가용성·계약을 검증한 것은 아닙니다. 정상 프로필과 장애 프로필을 나누고 실제 적용 값을 기록합니다.

### 왜 1,000 TPS이며 1만 TPS도 가능한가요?

현재 목표와 완료 TPS 정의는 [성능 목표](../README.md#성능-목표와-검증)를 따릅니다. 추가 근거는 대상 규모·피크 시간의 시험 가정으로 설명하고 실제 수요 통계와 구분합니다. 1만 TPS는 자원 확보 후 확장 시험 목표이며 달성 결과가 아닙니다. 같은 장비의 부하 발생기가 서버 자원을 쓰는 영향도 기록합니다.

### 2주 정산은 선정산인가요?

이미 받은 자금을 2주마다 지급하면 지급 일정 조정입니다. 받기 전에 지급하려면 별도 자금 공급·한도·회수 모델이 필요합니다. 기본안은 그 자금 조달을 포함하지 않습니다. [선택 확장](proposal.md#선택-확장-후보)으로 도입할 때 지급 후 환불과 회수까지 함께 설계합니다.

### 설계를 한 명이 모두 작성하면 병목이 생기지 않나요?

상세 설계 작성 책임은 김민식에게 모으되, 담당자는 자기 영역의 구현 가능성과 누락·변경 영향을 검토합니다. 설계를 기능 단위로 공개하고 연동 계약부터 맞춰 구현을 진행합니다. 변경이 한 사람에게 몰리는 비용을 감수하므로 큰 문서를 모두 완성할 때까지 각 구현을 기다리게 하지 않습니다.

## 11. 구현 전 결정할 항목과 완료 기준

이 문서는 범위·흐름·가정의 초안입니다. 아래 결정과 실제 명세·실행 검증을 끝내기 전에는 ‘모든 상세 설계 완료’라고 판단하지 않습니다. 김민식이 작성·정리하고 해당 구현 담당자가 대조합니다.

| 결정 | 필요한 산출물·검증 | 구현 협의 대상 |
| --- | --- | --- |
| 최초 검증 시나리오·거래 범위 | 기본 상품·금액 가정, 결제→원장→환불/지급 흐름, 정상·장애 입력과 기대 결과 | 팀 전체 |
| 인증·권한·폐기·신선도 | 신원 전달·권한표·내부 호출 계약, 만료·폐기·정지·타 판매자 접근 시험 | 이성호·모든 API 담당 |
| 외부 주문·환불·정산 가능 승인 | 필드·승인 주체·금액 확인·버전·취소·보류 규칙 | 김지현·김은지·권민혁 |
| 물리 ERD·금액·상태 전이 | 컬럼·키·제약·인덱스·정책 버전·이력·migration, 금액·동시성 시나리오 | 각 도메인 구현 담당 |
| API·이벤트·복구 | 경로·요청·응답·오류·업무 키, 토픽·key·그룹·재시도·DLT·임대 | 생산자·호출자·소비자 |
| 정산 마감·지급·Spring Batch | 항목·자금 선점, 잔액·실패/미확정·재시작 계약, Job·메타데이터 관리 | 권민혁·이성호 |

| 시연·시험 데이터 | 최소 시연 방식과 준비 담당, 각 도메인 데이터·정상/장애 부하·최종 대조 | 팀 전체 |

설계 검토는 범위 이탈·서로 다른 금액 기준·실패 분기·권한 우회·예약 경쟁·책임 공백을 대조합니다. 구현 검증은 별도로 수행하며, 기존 기동 smoke나 문서 리뷰가 금융 SAGA·실물 상태·성능 검증을 대신하지 않습니다.
