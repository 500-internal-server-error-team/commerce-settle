# 업무 설계

구매자의 주문·결제·환불과 판매자 정산의 범위·가정·업무 흐름과 검증 시나리오를 정의합니다. 실행 설정은 개발 환경 문서가, 필드·권한·응답은 OpenAPI가 소유합니다. 시험 기준과 실제 통과한 결과를 구분합니다.

## 1. 기준과 책임

문서별 기준 위치와 추가·변경 방식은 [문서와 기록](../CONTRIBUTING.md#문서와-기록)을 따릅니다. 이 문서는 여러 도메인을 연결하는 흐름과 그 가정·검증 조건을 설명하고, 정책값·API·저장 구조·실행 구성은 각 담당 문서를 참조합니다.

기능 착수·연동 검토는 [협업 규칙](../CONTRIBUTING.md#기능-착수와-연동-계약)을 따릅니다. 담당과 진행은 기능별 이슈·PR에서 관리합니다. 이 문서의 시나리오를 구현·테스트에 연결하되 문서 검사를 업무 검증 완료로 간주하지 않습니다.

## 2. 해결 범위

구매자가 우리 서비스에서 상품을 고르고 배송지·쿠폰·결제수단을 선택해 주문합니다. 구매자의 결제·환불과 판매자의 매출·정산·지급을 연결합니다. 프로모션의 요청 집중과 외부 금융 장애를 시험합니다. 제외 항목은 기본 흐름의 완료 조건에 포함하지 않습니다.

| 영역 | 포함 | 제외·외부 책임 | 선택 이유와 남는 책임 |
| --- | --- | --- | --- |
| 사용자·판매자 | 구매자·판매자 계정별 가입·로그인·권한, 판매 상태·정산 정보, 기본 배송지 | 계정 자동 연결·직원/다중 운영자·실제 사업자 심사·실계좌 검증 | 구매와 판매의 로그인·복구·접근 범위를 분리합니다. 같은 사람이 양쪽을 이용하려면 각각 가입합니다. |
| 상품·주문 | 상품 등록·조회·가격·판매 가능 수량, 한 상품의 수량 주문, 금액·배송지 사본, 재고 예약 | 검색 고도화·장바구니·다중 판매자 주문 | 구매자가 결제할 대상을 우리 서버가 확정합니다. 가격·주소 변경으로 기존 주문을 덮어쓰지 않습니다. |
| 쿠폰 | 웰컴·월간 우수고객·판매자 쿠폰 한 장, 자동 발급·판매자 캠페인 예산·예약·사용·복구 | 대량 선착순 발급 행사·중복 쿠폰·쿠폰/마일리지 동시 사용 | 쿠폰은 결제수단과 구분하고 할인 후 주문 결제액은 1원 이상으로 합니다. |
| 선착순 이벤트 | 판매자의 특정 상품·이벤트 가격·한정 수량·기간 설정, 예약·판매 진행률·매진 종료 | 방송·영상·채팅·목표 달성형 공동구매 | 판매 시작에 특정 상품으로 요청이 집중되는 상황과 마지막 수량 경쟁을 검증합니다. |
| 배송·반품 | 배송지 저장, 판매자 발송·모의 배송완료, 기한 후 자동 구매확정, 취소·반품 요청/승인 상태 | 택배사 연동·배송 추적·실제 수거·검수·비용 계산 | 판매자 발송 입력과 실제 배송 증명을 구분합니다. 구매 확정과 환불 상태가 정산 가능 판단의 입력입니다. |
| 결제·마일리지 | 신용카드·체크카드·간편결제 대역, 우리 마일리지 사용·예약·원장, 접수·조회·미확정 복구 | 상품권 결제·실결제 계약·실카드 정보, 마일리지 충전·현금 인출·구매 적립·만료 | 외부 승인과 내부 잔액의 실패 경계, 복합 결제의 금액 보존을 검증합니다. |
| 환불 | 지급 예약 전 전액 환불·예약·보상·조회, 원결제수단 취소와 사용 마일리지 복원 | 부분 환불·교환·지급 후 환불·반품 분쟁 판정 | 최초 금액을 상쇄합니다. 부분 환불·지급 후 환불은 배분·회수 모델이 필요해 제외하며 지원하지 않는 요청은 운영 확인으로 안내합니다. 기술 범위가 실제 반품 권리의 제한을 뜻하지는 않습니다. |
| 정산·지급 | 원장·수수료·판매자별 일배치·모의 선지급/PG 회수 | 대출·환전·세금 신고·실자금 조달 | 선지급 재원은 항상 충분하다고 가정하고 구매확정 뒤 PG 입금 전에도 지급합니다. |
| 운영 | 상태·추적·재처리·대조·부하 시험 | 상용 수준의 무중단·다중 리전·금융기관 운영 보장 | 단일 개발 환경에서 확인할 보장과 운영 한계를 구분합니다. |

기본 거래는 **로그인한 구매자 한 명·판매자 한 명·상품 한 종류의 수량 주문·KRW·전액 환불**입니다. 카드 한 건을 먼저 연결한 뒤 아래 결제수단·마일리지·선착순 이벤트까지 구현합니다. 비회원 구매·다중 판매자 결제·부분 환불은 후속 확장이며, 방송·영상 송출·채팅은 계속 제외합니다.

## 3. 가정과 선택 이유

가정은 현실의 사실이나 검증 결과가 아닙니다. 가정이 깨졌을 때의 처리까지 정하고, 외부 시스템이 항상 정상이라는 전제는 두지 않습니다.

| 가정·선택 | 이유 | 깨졌을 때의 처리·한계 |
| --- | --- | --- |
| 첫 상품은 비부패성 일반 완제품 | 식품 보관·유통기한·제작 취소 등 상품별 예외를 줄입니다. | 불량·오배송·변심은 남습니다. 미발송 취소와 판매자가 승인한 반품을 구분해 처리합니다. |
| 기본 시험은 쿠폰 할인 후 상품대금을 결제하고 배송비는 0원 | 배송비·반품비 배분 없이 전액 환불을 검증합니다. | 유료 배송비를 합친 주문에서 상품대금만 환불하는 동작은 이 범위로 검증하지 않습니다. 실제 도입 시 금액 모델을 확장해야 합니다. |
| 금액·수수료는 업무 정책의 원 단위·15%·버림 정책 | 재현 가능한 하나의 계산 기준으로 비교합니다. | 실제 PG 원가·세금·계약별 수수료를 대표하지 않습니다. 거래 당시 원금액·요율·조건 사본을 보존합니다. |
| 웰컴·월간 우수고객은 플랫폼 부담, 판매자 쿠폰은 판매자 부담인 정액 쿠폰 한 장 | 할인과 마일리지 결제 재원을 구분합니다. | 같은 주문에서 두 부담자의 쿠폰이나 마일리지를 겹치지 않습니다. 할인 후 주문 결제액이 1원 미만이면 적용을 거절합니다. |
| 우리 마일리지는 플랫폼 부담, 1점=1원, 시험용 사전 지급 잔액 | 판매자 부담 할인과 달리 결제 재원으로 처리하고 사용액을 판매자 정산에서 다시 빼지 않습니다. | 실자금 조달·충전·적립·만료는 구현 범위 밖입니다. 모의 지급 잔액도 따로 준비하며 마일리지 사용만으로 실제 현금이 생겼다고 보지 않습니다. |
| 외부 금융 대역은 업무 키로 멱등 처리하고 최종 상태를 조회할 수 있음 | 응답 유실 후 중복 실행 없이 결과를 확인하기 위한 최소 계약입니다. | 조회도 실패하면 미확정을 유지하고 보류·알림·대조로 넘깁니다. 새 키로 성공을 추측하지 않습니다. |
| 메시지는 중복·지연·순서 역전될 수 있음 | 재전달과 서로 다른 스트림 사이의 순서 차이를 처리해야 합니다. | Inbox·업무 유니크 키·상태 전이로 방어합니다. Kafka만으로 외부 금융까지 정확히 한 번 실행된다고 주장하지 않습니다. |
| 주문·금액·배송지와 구매 확정은 우리 커머스 서비스가 소유 | 주문서에서 결제·정산까지 같은 거래를 추적하기 위함입니다. | 브라우저가 보낸 금액·역할을 신뢰하지 않습니다. 판매자 발송 입력만으로 실제 배송을 보증하지 않습니다. |
| 선지급 재원은 항상 충분하며 구매확정 후 선지급 | 준비된 거래의 추가 대기를 줄입니다. | 시험 전 전체 지급·환불에 충분한 모의 자금을 준비합니다. PG 입금과 잔액을 따로 기록하며 실자금 조달은 제외합니다. |
| 개발 인프라는 단일 브로커·PostgreSQL·Redis | 실행·비용·문제 재현을 단순하게 합니다. | 노드 장애 시 전체 영향이 있을 수 있습니다. 논리 분리와 물리 장애 격리는 다릅니다. |

기본 시험은 구매자에게 배송비를 별도 청구하지 않는 무료배송 조건입니다. 판매자의 배송 원가나 반품비가 없다는 뜻은 아닙니다. 환불액에서 별도 비용을 공제해야 하는 거래는 부분 환불·비용 배분 모델을 추가해야 합니다.

## 4. 서비스 경계와 원천 데이터

| 소유자 | 소유 데이터·판단 | 다른 서비스에 전달할 결과 |
| --- | --- | --- |
| 커머스 (`commerce` 모듈) | 구매자·판매자 계정·인증·상품·재고·주문·쿠폰·배송지·선착순 이벤트/참여·취소/반품 승인·구매 확정 | 확정 주문·결제 요청, 환불 승인, 구매 확정에 따른 정산 가능 정보 |
| Payment | 결제·승인 시도·마일리지 잔액/예약/원장·환불·SAGA·외부 호출 작업 | 결제 구성별 확정 결과, 환불 예약 명령·외부 환불/마일리지 복원 결과·보상 명령 |
| Settlement | 금액 정책 적용 결과·원장·환불/지급 예약·정산 항목·배치·지급 | 예약 성공·거절·해제 결과, 지급 상태 |
| `finance-mock` | PG 3종과 간편결제 1종의 모의 승인·환불, 간편결제 시험 잔액, 지급 기관의 실행 결과·잔액·자금 선점 | 접수·처리 중·확정 결과 조회, 지급 가능 잔액 |

Payment API와 Worker는 같은 서비스·DB의 실행 역할입니다. Spring Batch는 Settlement의 정산 일배치와 Commerce의 월간 혜택을 각 소유 앱에서 실행하며 별도 업무 서비스를 만들지 않습니다. 서비스 경계는 인원수가 아니라 데이터 소유권·외부 장애 영향·변경 책임을 기준으로 유지합니다.

서비스 내부의 [도메인별 최종 판단과 집계](architecture.md#ddd-집계와-검증)를 구분합니다. 주문 금액과 재고·쿠폰·이벤트 수량 예약은 커머스 한 트랜잭션에서 확정하고, 마일리지 잔액·예약·원장은 Payment의 결제 상태와 함께 저장합니다. 커머스 주문에는 마일리지 사용 요청액을 보존하고 Payment의 확정 결과를 반영합니다. 배포 경계와 서비스별 DB 소유권을 유지합니다.

다른 서비스의 DB에 직접 접근하지 않습니다. Payment·Settlement에는 주문·구매자·판매자 식별자와 필요한 금액/상태만 전달하고 배송지·비밀번호·인증 토큰은 금융 이벤트에 넣지 않습니다. 판매자 조회 모델은 이벤트로 갱신할 수 있지만 정지·권한 폐기의 반영 지연을 숨기지 않습니다.

### 사용자와 거래 주체

| 개념 | 책임·관계 |
| --- | --- |
| 구매자 계정 (`Buyer`) | 구매자용 가입·로그인, 계정 상태·인증 정보·배송지. 주문의 `buyerId`가 이 계정을 참조합니다. |
| 판매자 계정 (`Seller`) | 판매자용 가입·로그인, 판매 상태·판매자 정보·정산 정보. 상품·주문·원장의 `sellerId`가 판매자 계정을 참조합니다. 첫 범위는 판매자 계정 한 개가 판매자 한 곳을 운영합니다. |
| 로그인·복구 | 구매자용과 판매자용 진입점·인증 범위를 구분합니다. 같은 이메일을 쓰더라도 계정을 자동 연결하지 않고 로그인·비밀번호 재설정도 계정 종류를 확인합니다. |
| 권한 | 인증 주체는 계정 종류와 계정 ID를 함께 식별합니다. 판매자 인증으로 구매자 주문을 만들거나 구매자 인증으로 상품·정산을 관리하지 않습니다. |
| 배송지 | 주소록은 구매자 소유입니다. 주문 생성 시 수령인·연락처·주소 사본을 주문에 저장하며 주소록 수정이 과거 주문을 바꾸지 않습니다. |

예를 들어 구매자 계정 `B1`로 판매자 `S2`의 상품을 주문하면 주문의 구매자는 `B1`, 정산 대상은 `S2`입니다. 같은 사람이 판매자 `S1`도 운영하려면 판매자 계정으로 별도 로그인합니다. `B1`과 `S1`을 같은 사람이라고 자동 추론하거나 권한을 합치지 않습니다.

인증 주체의 종류와 ID를 주문·주소의 `buyerId` 또는 상품·주문·정산의 `sellerId`와 대조합니다. ID 문자열이 우연히 같아도 계정 종류가 다르면 같은 주체가 아닙니다. 요청의 `buyerId`·`sellerId`·역할 문자열만으로 권한을 인정하지 않습니다. 판매자는 결제 완료 후 자신이 이행할 주문의 배송 정보만 볼 수 있고 구매자의 전체 주소록이나 다른 판매자 주문은 볼 수 없습니다. 구매자 계정 정지와 판매자 판매 자격 정지는 별도 상태로 관리합니다.

DDD 집계·요청/도메인/DB 검증과 생성/수정 시각·행위 감사 기록은 [구현 경계](architecture.md#ddd-집계와-검증)를 따릅니다. 감사 로그는 각 서비스 DB에 두며 금융 원장을 대체하지 않습니다.

<a id="판매자-구독과-수수료-적용-제안"></a>
### 판매자 수수료

기본 수수료는 PG·부가세 포함 15%이며 거래 당시 요율·수수료·판매자 지급액을 주문에 고정합니다. 쿠폰 부담·수수료 기준금액·원 미만 버림은 [금액·비용 정책](policies.md#금액과-주문)을 따릅니다. 판매자 구독·자동 청구·구독 할인은 지원하지 않습니다.

정산 가능 정보는 우리 주문의 기한 후 자동 구매확정에서 생성합니다. 자동 구매확정이 없거나 결제 미확정·취소/환불 중이면 지급 대상을 만들지 않습니다. 확정·취소 정보가 지연되거나 역순으로 도착할 때 주문 버전과 금융 예약 상태를 함께 확인하며, 오래된 이벤트가 취소 거래를 다시 지급 가능하게 만들지 않아야 합니다.

주문 금액은 커머스가 상품/이벤트 가격·수량·쿠폰 조건으로 계산하고 저장합니다. Payment는 확정 주문과 결제 구성에 근거해 처리하며 금액·구매자·판매자가 바뀌지 않도록 합니다. 실제 카드 번호·CVC·간편결제 비밀번호 대신 시험용 수단 ID만 받습니다. 실PG 연동 완료로 표현하지 않습니다.

## 6. 핵심 업무 흐름

### 주문·쿠폰·배송지

1. 구매자가 상품·수량·배송지·쿠폰·사용 마일리지·외부 수단을 선택합니다. 커머스는 로그인 사용자에서 구매자를 식별하고 판매자·상품·수량·주소 접근 권한을 확인합니다.
2. 서버가 상품대금과 쿠폰 할인 후 주문 결제액을 계산합니다. 주문에는 구매자·판매자·상품/이벤트 가격·수량·할인·최종 금액·요청한 결제 구성·배송지의 사본과 버전을 저장합니다. 결제를 요청한 주문의 금액·주소는 덮어쓰지 않습니다.
3. 주문·판매 가능 재고 예약·쿠폰 예약·이벤트 참여/수량 예약(해당 시)·결제 요청 Outbox를 같은 커머스 DB 트랜잭션에 저장합니다. 한 조건이라도 충족하지 못하면 함께 롤백합니다.
4. Payment의 결제 확정 결과를 수신하면 주문을 결제 완료로 바꾸고 재고·쿠폰·이벤트 예약을 확정합니다. 확정 결제 실패는 재고·이벤트 예약을 해제하고, 쿠폰 예약은 재시도를 위해 미결제 취소가 확정될 때까지 유지합니다. 미결제 취소는 Payment가 취소 상태를 영속 확정해 이후 승인을 실행할 수 없게 한 뒤 예약을 해제합니다. 단순히 Worker가 아직 시작하지 않았다는 조회만으로 취소하지 않습니다. 외부 결과가 미확정이면 예약을 유지하고 조회·대조로 복구합니다.
5. 판매자가 자기 주문을 발송 처리합니다. 환불 가능 기간이 끝나면 아래 정책으로 자동 구매확정합니다. 결제 결과 미반영·취소/환불 중인 주문은 발송·구매 확정을 거절합니다. 구매 확정 결과를 Settlement에 전달합니다.

쿠폰의 발급·사용·예약·환불 복구는 [쿠폰 정책](policies.md#쿠폰)을 따릅니다. 재고는 미발송 환불 완료 또는 판매자의 실제 반품 입고 확인 뒤 복구하며 금융 환불 성공만으로 발송 상품을 재입고하지 않습니다.

### 결제수단과 마일리지

| 구분 | 처리·검증 범위 |
| --- | --- |
| 신용카드·체크카드 | PG A/B/C 중 선택한 한 곳에 외부 결제액을 승인·조회·취소합니다. 수단 종류를 기록하되 실제 카드망·한도·매입 주기의 차이는 모의하지 않습니다. |
| 간편결제 | 별도 논리 대역 `EASY_PAY` 한 곳을 추가합니다. 시험용 지갑 잔액의 승인·조회·취소를 모의하며 같은 결제로 PG를 추가 호출하지 않습니다. 실제 브랜드·SDK·로그인은 연동하지 않습니다. |
| 우리 마일리지 | Payment가 구매자별 가용 잔액·예약·사용·복원 원장을 소유합니다. `1점=1원`, 플랫폼 부담, 사전 지급한 시험 잔액으로 시작하며 충전·적립·만료는 제외합니다. |
| 프로모션 쿠폰 | 커머스의 웰컴·월간 우수고객·판매자 할인입니다. 플랫폼/판매자 부담을 구분하고 마일리지와 동시에 쓰지 않습니다. 구매자 결제수단이나 현금 환불 대상은 아니며, 플랫폼 부담액은 별도 지원 원장으로 보전합니다. 예약·사용 복구 규칙을 유지합니다. |

외부 수단은 한 결제에 최대 한 가지이며 우리 마일리지와 함께 쓸 수 있습니다. 여러 외부 수단으로 나누는 결제는 제외합니다. 주문 결제액 전부를 마일리지로 내면 외부 호출 없이 처리합니다. 마일리지 부족·음수·주문 금액 초과는 거절하며, 외부 결제액을 임의로 늘리거나 다른 수단으로 자동 전환하지 않습니다.

Payment는 결제 접수·마일리지 예약·Outbox를 같은 로컬 트랜잭션에 저장합니다. 다른 주문과 동시에 잔액을 쓰더라도 `가용 잔액 = 잔액 − 진행 중 예약액`이 음수가 되지 않게 DB에서 검사합니다. 필요한 외부 승인이 확인되면 마일리지 차감·사용 원장·결제 확정·결과 Outbox를 원자 저장합니다. 외부 결제액이 0원이면 같은 원자 저장으로 바로 확정합니다. 내부 저장 실패는 원래 외부 거래를 조회해 재개하며 중복 차감하지 않습니다.

외부 결과가 미확정이면 마일리지 예약을 유지합니다. 확정 거절 또는 이후 승인이 실행될 수 없도록 영속 확정한 취소만 예약을 해제합니다. 재시도 전 커머스의 재고·이벤트 예약과 Payment의 마일리지 예약을 모두 다시 확보해야 하며, 쿠폰 예약은 확정 거절 뒤에도 유지합니다. 예약·사용·복원은 원결제와 작업 종류별 유일성으로 보호합니다.

### 선착순 상품 이벤트

판매자는 자기 상품 하나의 양수 이벤트 가격·한정 수량·시작/종료 시각을 정해 공개합니다. 한정 수량은 1개 이상·배정 가능한 재고 이하이고 종료 시각은 시작 시각보다 뒤여야 합니다. 공개 시 판매 가능 재고에서 이벤트 수량을 같은 DB 트랜잭션으로 배정해 일반 주문과 중복 판매하지 않습니다. 같은 상품의 행사 기간 중복은 허용하지 않고, 공개 후 가격·한정 수량을 바꿔 기존 참여 조건이나 게이지 분모를 덮어쓰지 않습니다. 서버 시각으로 시작·종료를 판단합니다.

이벤트는 구매자당 한 상품의 수량 1개만 허용합니다. 진행 중 예약 또는 확정 구매가 있으면 다른 멱등키로 중복 참여할 수 없고, 확정 실패·승인 차단이 확정된 미결제 취소만 기간 내 재참여할 수 있습니다. 결제 확정 후 환불로 참여 한도를 다시 얻지는 않습니다. 선착순은 **DB에서 수량 예약이 커밋된 순서**이며 HTTP 도착 순서나 PG 처리 속도의 공정성을 보장한다는 뜻은 아닙니다.

- `한정 수량 Q`, `누적 결제 확정 수량 S`, `결제 대기 예약 수량 R`을 구분합니다. 항상 `0 ≤ S + R ≤ Q`이며 남은 신청 가능 수량은 `Q − S − R`입니다.
- 게이지는 `floor(100 × S / Q)%`입니다. 예를 들어 1,000개 중 결제 확정 700개·예약 300개면 **70%·결제 확인 중**, 신청은 일시 마감입니다. 예약만으로 100%나 매진을 표시하지 않습니다.
- 결제 확정 이벤트를 한 번 반영할 때 `R`을 줄이고 `S`를 늘립니다. `S=Q`면 100%·매진 종료이며 새 예약을 받지 않습니다. 외부 결제 미확정은 `R`을 유지하고 조회합니다. 확정 실패는 예약을 해제하며 기간 내 남은 수량만 다시 신청할 수 있습니다.
- 게이지는 환불을 뺀 순판매량이 아닌 **누적 확정 판매 진행률**입니다. 환불 후에도 이벤트 판매 이력·사용한 한도는 되돌리지 않고 자동 재개하지 않습니다. 환불 수량·순판매량은 따로 조회하며 실제 재입고는 기존 배송/반품 규칙을 따릅니다.
- 기간 종료나 판매자의 조기 종료는 신규 참여를 막고 미사용 배정 재고만 일반 재고로 돌립니다. 이미 예약된 주문은 계속 조회·확정/환불 처리하며 기간 종료를 이유로 예약을 먼저 해제하지 않습니다. 종료 뒤 확정 실패로 풀린 배정분도 일반 재고로 반환합니다.

화면은 판매 진행률·예약 상태·마지막 갱신 시각을 HTTP로 주기 조회하도록 설계합니다. Redis 조회 캐시는 허용하지만 참가·매진 판정은 커머스 DB가 결정합니다. 캐시의 100% 미만 표시나 오래된 남은 수량을 신규 구매 권한으로 사용하지 않습니다. 첫 갱신 간격·허용 표시 지연은 각각 1초를 시험 가정으로 두고 실제 부하·지연을 확인합니다. 방송 기능을 추가할 필요는 없습니다.

### 결제

1. 확정 주문에서 전달된 구매자·판매자·금액·주문 버전과 업무 키를 확인합니다. 동일 키·동일 요청은 기존 처리로 연결하고 다른 본문이면 충돌로 거절합니다.
2. 결제 접수와 Outbox를 같은 Payment DB 트랜잭션에 저장합니다. 접수 응답은 처리 ID와 조회 경로를 주며 승인 완료를 뜻하지 않습니다.
3. 수신 측은 Inbox·실행 작업을 영속 저장한 뒤 ack합니다. Worker는 DB 잠금을 유지하지 않은 상태에서 선택한 PG 또는 간편결제 대역을 호출합니다. 외부 결제액 0원인 마일리지 전액 결제는 호출을 생략합니다.
4. 명시적 승인·거절이면 결과와 Outbox를 저장합니다. Payment는 확정 주문의 수수료 기준액 B와 적용 정책으로 수수료·판매자 순액을 계산해 최초 금액으로 보존합니다. 응답 유실·조회 실패는 미확정으로 추적하며 자동으로 실패 처리하지 않습니다.
5. Payment의 결제 확정에는 필요한 외부 승인과 마일리지 차감이 모두 포함됩니다. 커머스는 주문·예약·이벤트 판매량을 확정하고 Settlement는 구성별 결제액과 플랫폼 부담 마일리지 금액을 한 번만 원장에 반영합니다. 결과 전달이 지연되는 동안 결제 확정과 주문/원장 반영 완료를 구분해 표시합니다.

새 회차 재시도는 주문 측 예약·이벤트 생성까지만 지원합니다. Payment의 동일 주문 다른 회차 접수·마일리지 재예약은 지원하지 않으므로 전체 결제 재시도가 완료된 것으로 보지 않습니다. 같은 주문에 진행 중이거나 확정된 결제를 중복 생성하지 않습니다. 확정 거절 뒤 재시도는 최초 주문 사본과 모든 예약 조건을 재검증하고, 이전 시도와 연결해 기록합니다. 논리 거래 키와 외부 호출 시도 키의 관계를 명세로 정하며 미확정 거래를 재시도하기 위해 새 주문·업무 키를 발급하지 않습니다.

설명용 상태 흐름은 ‘접수 → 외부 처리 중 → 승인 또는 확정 거절’입니다. 외부 결과를 모르면 ‘미확정’을 거쳐 조회로 확정합니다. 구체 상태명과 허용 전이는 [데이터 모델](data-model.md#저장-상태와-전이)을 따릅니다.

### 모의 배송·환불과 자동 구매확정

배송완료부터 달력일 7일을 환불 요청 기간으로 사용합니다. 발송부터 2~3영업일의 모의 배송을 주문별로 고정하고, 배송·환불 접수·자동 구매확정은 같은 주문 상태와 버전으로 경합합니다. 구체적인 시각·달력·재시작 기준은 [배송·환불 정책](policies.md#배송환불-기한과-자동-구매확정)을 따릅니다.

월요일 10시 발송·2영업일 배송·공휴일 없음이라면 수요일 10시 배송완료, 다음 수요일 10시 환불 마감입니다. 마감 정각 요청은 허용하고 자동 확정은 마감 초과 후에만 가능합니다. 목요일 발송·3영업일 배송이면 다음 화요일에 도착합니다. 배송 작업이 늦어도 원래 기한을 늘리지 않으며, 배송 전 취소·기한 내 접수된 반품은 지급을 막습니다.

택배사 연동·실제 배송 증명·지급 후 환불은 포함하지 않습니다. 기간 내 환불은 원수단 취소·마일리지 복원·원장 상쇄·주문 복구까지 처리하고, 발송 상품 재고는 판매자 입고 확인 후 복원합니다. 시험에서는 Clock을 이동시켜 주말·공휴일·마감 정각·진행 중 환불을 재현합니다.

### 환불 SAGA

1. 구매자는 자기 주문의 취소/반품을 요청합니다. 커머스는 환불 요청 기한과 미발송 취소/해당 판매자의 반품 승인을 확인해 승인 정보를 저장합니다. Payment는 원결제의 외부 결제액·사용 마일리지를 보존한 전액 환불을 접수합니다. 결제 미확정은 먼저 원결제 결과를 확인합니다.
2. Payment는 환불 상태와 정산금 예약 명령을 함께 저장합니다. Settlement는 해당 거래의 지급 대상 순액을 원자적으로 예약합니다.
3. 선행 승인 원장이 아직 없으면 의존 정보를 기다리는 작업으로 남깁니다. 동일 명령 재전달로 예약을 중복 생성하지 않습니다.
4. 지급 예약이 이미 있거나 환불 완료 상태라면 예약을 거절하고 PG 환불을 호출하지 않습니다. 같은 거래에서 진행 중·완료된 전액 환불이 다른 멱등키로 중복 실행되지 않게 합니다.
5. 예약 성공 후 원래 PG·간편결제 거래에 **외부 결제액만** 취소 요청합니다. 외부 결제액 0원이면 호출을 생략합니다. 외부 환불 성공 확인 뒤 사용 마일리지 전액을 원래 구매자 잔액에 복원하고, 복원 원장·금융 환불 상태·Outbox를 같은 Payment DB 트랜잭션에 저장합니다. 원결제별 복원 유일성으로 이벤트 재전달·새 환불 키에도 두 번 반환하지 않습니다.
6. 원장 상쇄 확인 뒤 Payment는 기존 v1 `RefundCompleted`로 커머스에 주문 복구를 전달하고 `INTERNAL_PENDING`을 유지합니다. 커머스는 주문·쿠폰과 미발송 주문의 재고 복구와 `RefundOrderRestored` Outbox를 같은 로컬 트랜잭션으로 저장합니다. Payment가 이 확인을 수신·반영한 뒤에만 금융 환불을 `COMPLETED`로 전이합니다. 외부 환불 직후 중단되거나 마일리지/원장/주문 반영이 늦으면 같은 환불을 조회·재개하며 전체 완료로 표시하지 않습니다.
7. 외부 환불이 확정 거절되면 마일리지를 복원하지 않고 정산금 예약 해제를 보상 요청합니다. 해제가 확인되기 전까지 보상 대기를 추적합니다. 미확정이면 예약을 유지하고 조회합니다. 이미 확인한 외부 환불 성공을 내부 반영 지연 때문에 실패로 되돌리거나 외부 환불을 새 키로 반복하지 않습니다.

예를 들어 쿠폰 없는 원결제 10,000원·수수료 1,500원·판매자 몫 8,500원이면, 지급과 충돌하지 않도록 보호할 판매자 순액은 8,500원이고 구매자의 PG 환불액은 10,000원입니다. 성공 시 최초 수수료 1,500원과 순정산액 8,500원을 상쇄합니다. 이후 수수료율로 재계산하지 않습니다.

취소/반품 승인과 금융 환불 완료는 다른 결과입니다. 지급 예약 후·지급 후 환불은 지원하지 않으며 처리 불가 사유와 운영 확인 경로를 남깁니다. 정산금 예약이 거절되거나 외부 환불이 확정 실패하면 커머스의 진행 상태도 결과에 맞춰 해제·갱신합니다. 금융 결과가 미확정이면 마일리지·쿠폰·미발송 주문의 재고를 먼저 복구하지 않습니다. 발송 상품의 재고는 금융 환불과 별도로, 승인된 반품의 입고·재판매 가능 확인 시 한 번 복원합니다([재고 예약과 복원](policies.md#재고-예약과-복원)). 시험 범위의 마일리지는 만료가 없으며 계정 이용 제한 중에도 복원 이력과 잔액은 보존합니다.

### 정산·지급

1. 결제·환불 결과를 지속적으로 원장에 반영합니다. 지급 주기가 길어도 원장 기록을 해당 날짜까지 미루지 않습니다.
2. 배치 실행의 마감 기준을 고정하고 구매 확정 정보가 반영된 미환불·미예약 항목을 선점합니다. 결제 승인만 있고 구매 확정이 없으면 지급하지 않습니다.
3. 지급 건별로 항목 선점·합계·지급 레코드·실행 작업을 같은 Settlement DB 트랜잭션에 저장합니다. 환불 예약과 지급 예약은 같은 항목에서 동시에 성공할 수 없습니다. 항목만 예약되고 실행 작업은 없는 상태를 남기지 않습니다.
4. 저장한 작업으로 지급 기관에 실행을 요청합니다. 사전 잔액 조회는 참고 값이며, 실행 시점의 원자적 잔액 검사·선점이 지급 가능 여부를 결정합니다. 외부 호출은 항목 예약 트랜잭션 밖에서 수행합니다.
5. 실제 지급 성공을 확인한 뒤 지급 완료로 기록합니다. 지급 요청 접수와 지급 완료를 구분합니다.
6. 미확정 지급은 예약을 유지하고 같은 외부 업무 키로 조회·복구합니다. 확정 결과에 따른 지급·항목·작업 상태 변경은 같은 DB 트랜잭션에 저장합니다. 확정 거절은 REVIEW_REQUIRED로 보존하고 자동 해제·새 업무 키 발급을 금지합니다.

일배치 마감·판매자별 합산·계정 사본·미확정 복구는 [정산 정책](policies.md#정산재처리)을 따릅니다. Settlement 항목 예약과 대역의 현금 선점은 다른 DB 책임입니다. 외부 호출 동안 Settlement 잠금을 유지하지 않고, 배치 재시작은 원래 대상·합계·업무 키를 유지합니다.

충분한 플랫폼 초기 자금·PG 입금과 환불/지급 차감은 [재원 정책](policies.md#선지급-재원과-pg-회수)과 [금융 Mock 저장 구조](data-model.md#금융-mock)를 사용합니다. 결제 승인액·P/M 원장·미수금은 가용 현금이 아닙니다.

## 7. 금액·데이터 불변식

거래 당시 금액·정책·당사자·배송지 사본을 보존하고 정정은 원거래의 상쇄로 남깁니다. 예약·원장·외부 업무 키의 유일성은 DB에서 보호하며, 환불과 지급은 같은 항목을 동시에 선점할 수 없습니다. 메시지·작업 인계가 끝나도 외부 결과와 내부 반영을 모두 확인하기 전에는 업무 완료로 판단하지 않습니다.

금액식·원금액 상쇄와 계산 예는 [금액과 주문](policies.md#금액과-주문), 저장 키·제약·인덱스는 [데이터 모델](data-model.md)을 기준으로 합니다. 시험의 기대값을 계산식 복사로 만들지 않고 원금액·정책 사본과 대조합니다.

FK를 두지 않는 기존 정책은 유지하되 애플리케이션의 참조 확인과 DB의 `NOT NULL`·`UNIQUE`·`CHECK`를 함께 사용합니다. Redis 잠금이나 Kafka 순서만으로 금액 불변식을 대신하지 않습니다. [데이터 정책](migrations.md#데이터-보존과-제약-조건)을 따릅니다.

## 8. 인증·이벤트·캐시·배치 선택

### 인증과 접근

사용자는 [Redis 불투명 Bearer 세션](policies.md#인증공통-api-기준)으로 인증합니다. Gateway 검증과 백엔드 역할·소유권 검사를 구분하며, Redis와 계정 DB의 변경은 단일 트랜잭션이 아니므로 [차단·재조정 정책](policies.md#폐기와-저장소-복구)을 적용합니다. 현재 경계는 [아키텍처](architecture.md#사용자-인증과-내부-신원-전달)를 따릅니다.

### Kafka와 복구

Kafka는 후속 작업 전달을 분리하기 위한 선택이며 그 자체로 처리량·정확히 한 번 실행을 보장하지 않습니다. 원자 저장·ack·업무 멱등성·용량은 [Kafka 전달·용량 기준](architecture.md#kafka), 이벤트 종류·key·consumer는 [API 연동](api.md#이벤트-연동)이 기준입니다.

메시지 저장·ACK와 금융 완료를 구분합니다. 임대 만료·조회 404·타임아웃만으로 금융 실패나 예약 해제를 확정하지 않으며 [원키 조회·재요청과 Worker 인계](policies.md#공통-복구)를 따릅니다.

### PG 3종과 장애 시나리오

`finance-mock` 하나 안에 거래 영역을 구분한 PG A·B·C와 지급 기관 대역을 구현합니다. 아래 값은 장애 주입용 시험 입력이며 실제 PG 성능·실패율을 뜻하지 않습니다. 실행 시 선택한 프로필을 결과에 함께 기록합니다. 서로 다른 PG의 프로세스·장비 장애 격리는 이 구성으로 검증하지 않습니다. [대역 연결 구조](architecture.md#pg-대역-3종-설계)를 함께 확인합니다.

| PG ID | 기본 응답 지연 | 신규 업무의 확정 실패확률 | 기본 응답 유실확률 |
| --- | --- | --- | --- |
| `PG_A` | 80~150ms | 0.5% | 0% |
| `PG_B` | 300~700ms | 3% | 0% |
| `PG_C` | 800~1,500ms | 8% | 0% |

지연은 지정 범위의 균등 분포로 주입합니다. 표의 값은 주입하는 응답 대기 시간이며 실제 요청 지연에는 DB·작업 대기·전송 시간이 더해집니다. 확정 실패는 PG가 승인·환불을 거절하고 금액을 변경하지 않은 결과입니다. HTTP 오류·타임아웃·응답 유실과 구분하며 확정 실패확률의 분모는 같은 요청을 재시도한 횟수가 아닌 서로 다른 신규 업무 키입니다. 승인·환불·조회별 설정은 분리하고, 위 표는 승인·환불의 출발 값으로 사용합니다. 정상 프로필의 조회는 장애 없이 결과를 반환하도록 시작합니다.

PG별 시나리오는 승인·환불·조회 설정을 구분하고 생성 뒤 불변으로 유지합니다. 원승인의 환불은 같은 버전의 환불 설정을 사용합니다. 필드·범위는 [OpenAPI의 MockScenarioCreate](openapi.json), 저장 제약은 [mock_scenarios](data-model.md#mock_scenarios)를 따릅니다. 확률 0.5%는 0.005로 입력하며 정상 조회는 지연·실패확률 0으로 시작합니다. 강제 장애가 확률 설정을 덮어쓰면 적용 값·우선순위와 대역 상태를 시험 입력에 남깁니다.

원대역 GET 조회에는 Worker 서버 설정에서 선택한 `scenarioVersion` 쿼리를 전달합니다. 이 버전은 조회 지연/실패만 정하며 저장 거래의 금융 시나리오 버전·결과를 바꾸지 않습니다. 거래가 없어도 지정한 조회 프로필을 적용한 뒤 404를 반환하고, 해당 provider·버전의 설정이 없으면 503입니다. 조회 실패확률 100%인 시험 뒤 새 조회 버전을 선택하면 원거래의 금융 결과를 바꾸지 않고 복구할 수 있습니다. 동일 버전의 확률을 수정하거나 기존 승인을 다시 추첨하지 않습니다.

재현성은 seed·PG ID·작업 종류·업무 키로 지연·신규 처리 결과를 결정해 확보합니다. 스레드 실행 순서에 따라 결과가 바뀌는 전역 난수 순서에 의존하지 않습니다. 중복 요청은 기존 처리 결과를 먼저 조회하고, 확정 결과·금액을 다시 추첨하지 않습니다. PG ID·작업·업무 키와 처리 결과를 저장하며 재시작이나 설정 변경 후에도 기존 결과를 유지합니다. 응답 유실·조회 장애는 저장된 금융 결과를 바꾸지 않는 통신 장애로 주입합니다.

Payment는 최초 PG 선택을 결제 시도와 함께 저장합니다. PG별 단독 시험 후 1:1:1 혼합 시험부터 시작하고 선택 비율을 기록합니다. 미확정 거래의 재요청·조회는 같은 PG·업무 키로 보내고, 승인된 결제의 환불도 원래 승인 PG로 보냅니다. 타임아웃을 이유로 다른 PG에서 새 승인을 실행하지 않습니다. 다른 PG를 선택한 새 시도는 이전 PG의 확정 거절과 재고·쿠폰 재예약이 확인된 경우에만 허용합니다.

| 시험 상황 | 주입 방법 | 확인할 결과 |
| --- | --- | --- |
| 정상 분포·확정 거절 | 세 PG의 표 설정을 각각 적용 | PG별 신규 승인/거절 비율과 응답 지연, 잘못된 금액 변경 없음 |
| 성공했지만 타임아웃 | PG C의 성공 결과 저장 후 응답만 3,000ms 지연, Worker 제한 시간 2,000ms인 시험 | Payment는 미확정 유지, 원 PG 조회 후 성공으로 수렴, 다른 PG 승인·예약 조기 해제 없음 |
| 성공 응답 유실 | PG B의 성공 결과 저장 후 연결 종료 또는 제한 시간 초과로 응답 유실 | 같은 PG·업무 키 조회로 복구, 중복 승인·차감 없음 |
| 한 PG의 조회도 불가 | PG B의 승인·조회 오류를 함께 주입하고 이후 복구 | 미확정·재조회 작업 보존, 다른 PG로 중복 결제하지 않고 복구 후 대조 |
| 환불 거절·응답 유실 | 원 승인 PG에 환불 거절 또는 성공 후 응답 유실을 각각 주입 | 확정 거절이면 정산금 예약 해제·보상, 미확정이면 예약 유지·조회 후 원장 상쇄 |

응답 지연·유실 시험은 결과를 짧은 DB 트랜잭션으로 먼저 저장한 뒤 주입하며 지연 동안 DB 잠금을 유지하지 않습니다. 따라서 위 타임아웃 시험은 ‘응답이 늦었지만 PG에서는 이미 처리된 경우’를 검증합니다. PROCESSING 응답의 재조회 분기와 호출 전 중단으로 거래가 없는 경우는 별도 fixture로 검증하고, 응답 지연만으로 그 상황까지 검증했다고 하지 않습니다. PROCESSING은 실행 재전송 없이 조회하고, 거래 없음의 원키 재전송·임대 인계는 [복구 정책](policies.md#금융-결과-조회와-원키-재요청)을 따릅니다.

지표는 `pgId`·작업 종류·결과 종류별로 구분합니다. Grafana에서 PG별 지연 p50/p95/p99, 확정 거절률, HTTP 오류·타임아웃, 미확정 건수·복구 시간, 승인 완료 TPS와 Worker 적체를 비교하도록 안내합니다. 거래 ID·주문 ID는 메트릭 label로 넣지 않고 추적·대조 기록에서 사용합니다. 결과 보고에는 seed·시나리오 버전·적용 설정·선택 비율·신규 업무 건수와 재시도 횟수를 남깁니다.

서로 다른 시험 실행은 업무 키의 범위를 나눠 이전 거래를 신규 표본에 섞지 않습니다. 동일 조건 재현은 격리된 시험 데이터와 같은 seed·입력으로 수행하고 기존 공용 DB·볼륨을 임의 초기화하지 않습니다.

기본 k6 스크립트는 명세 조회용이며 결제·PG 부하는 [부하·복구 도구](../tests/load/README.md)를 사용합니다. 의도한 거절·장애와 애플리케이션 결함을 구분합니다. 모든 HTTP 오류를 무조건 0으로 요구하는 대신 지정한 기대 결과·중복 승인 0·최종 금액 대조·미확정 복구를 완료 조건으로 둡니다.

### Redis

Redis는 로그인 세션의 원본 저장소로 사용합니다. 인증 데이터는 [고정 만료·폐기·복구 정책](policies.md#인증공통-api-기준)을 적용하고 캐시와 접근 권한을 구분합니다. 공유 세션 검증·Redis 장애·재기동 시험은 [인증 실행·복구](development.md#redis-세션-검증과-복구)를 따릅니다. 금융 원장·예약·멱등성의 최종 기준은 DB에 두며, Redis 유실로 거래 이력과 금액이 달라지지 않아야 합니다.

### 간편결제 대역

`EASY_PAY`는 PG A/B/C와 같은 `finance-mock` 앱 안의 별도 거래 영역입니다. 간편결제는 이 대역만, 신용카드·체크카드는 선택한 PG 한 곳만 호출합니다. 최초 수단·대역·업무 키·외부 결제액을 저장하고, 미확정 조회와 환불도 원래 대역으로 보냅니다. 마일리지 전액 결제는 외부 거래를 만들지 않습니다.

간편결제 시험 입력은 응답 지연 100~300ms·신규 업무 확정 거절 1%·기본 응답 유실 0%입니다. 실제 서비스 성능이 아니며, PG와 같은 설정 검증·seed·결과 저장·응답 유실/조회 장애 계약을 적용합니다. 대역 ID와 수단 종류를 지표에 함께 기록하고 세 PG의 설정과 섞어 해석하지 않습니다.

간편결제 대역은 시험 계정의 잔액 검사·선점·거래 기록을 원자 저장합니다. 성공 시 한 번만 차감하고 확정 실패 시 선점을 해제하며, 성공 응답 유실로 잔액을 돌리지 않습니다. 환불은 원거래 금액을 원래 계정에 한 번만 반환합니다. 이 잔액은 Payment의 우리 마일리지와 별개입니다.

간편결제는 서버가 확인한 `EASY_PAY`·purpose=WALLET 시험 계정만 사용합니다. 미등록 계정·다른 제공자·지급 계정은 거절하고 가용 잔액을 원자 선점합니다. 원거래 키·계정·금액을 보존해 중복 요청·마지막 잔액 경쟁·응답 유실·전액 환불을 검증합니다. 실제 SDK·로그인·PIN은 연동하지 않습니다. 상품권은 [지원 범위](policies.md#금액과-주문)에서 제외합니다.

### 선착순 이벤트 집중 부하

시험용 가정으로 이벤트 상품 1개·한정 수량 1,000개에 서로 다른 구매자의 주문 요청 60,000건을 60초 동안 보냅니다. 90%는 이벤트 상품, 나머지는 일반 상품으로 보내고 첫 5초에 전체 요청의 50%를 집중시킵니다. 평균은 1,000요청/초, 첫 5초는 6,000요청/초인 **입력 목표**이며 측정 결과가 아닙니다. 이벤트 수량으로 확정 건수가 제한되므로 지속 결제 확정 1,000 TPS 시험과 분리합니다.

마지막 수량 동시 예약·구매자 중복 참여·여러 주문의 같은 마일리지 사용·PG/간편결제 응답 유실·환불 재전달·매진 이후 요청을 섞습니다. 신청 접수/거절·결제 대기·결제 확정·환불 복원·게이지 조회 지연과 피크 이후 적체 배출을 따로 기록합니다. 게이지 주기 조회를 켠 경우와 끈 경우의 발생기 부하도 구분합니다.

완료 조건은 초과 판매·중복 참여·마일리지 과차감/과복원 0건, 모든 확정 거래의 `T=E+M`, 복구 후 남은 미확정과 최종 원장/잔액 대조, 이벤트의 DB 확정 판매량 `S`와 게이지의 일치입니다. 환불을 뺀 상품 순판매량과 비교하지 않습니다. 의도한 매진 거절은 결함률로 합치지 않습니다. 게이지 인스턴스 메모리 캐시의 TTL·조회 빈도·허용 표시 지연을 기록하고 캐시 유실에도 구매 한도가 지켜지는지 확인합니다. 기본 TTL은 1초이며 구매 허용은 주문 시 DB로 판단합니다. 실행 결과에는 적용한 코드·캐시 설정·입력·최종 대조를 함께 남깁니다.

### 거래 알림과 운영 알람

구매자·판매자가 결제·환불·마일리지·정산의 결과를 확인하도록 커머스에 거래 알림을 둡니다. 카카오 알림톡은 모의 수신으로 시작하며 새 업무 서비스·DB를 만들지 않습니다. Payment·Settlement의 알림 요청은 기존 Kafka·Outbox·Inbox를 재사용하고, 발송 실패는 금융 처리를 되돌리지 않습니다. 판매 집중 시 판매자 알림은 1분 묶음으로 처리합니다.

[알림 정책](policies.md#거래-알림)이 수신자·발송 시점·원키 복구를, [운영 알람](policies.md#운영-알람)이 금융 지연·작업 적체·서비스·자원 기준을 소유합니다. [API](api.md#거래-알림-사용-순서)·[알림 ERD](data-model.md#거래-알림)·[인프라 구조도](architecture.md#거래-알림)를 함께 적용합니다. 활성화·모의/실제 수신 확인은 [알림 실행 안내](development.md#모의-거래-알림)를 따릅니다.

### Spring Batch 도입 전략

앱 내부 Scheduler가 소유 앱의 Spring Batch Job을 시작합니다. 정산 Job은 대상·합계·지급 작업을 고정하고 외부 지급은 Worker가 맡습니다. 실행·재시작은 [일배치 복구](development.md#정산-일배치-실행과-복구)를 따릅니다. Batch 이력만으로 중복 지급을 방지하지는 않습니다.

## 9. 실패·공격·범위 이탈에 대한 검증

아래 입력과 기대 결과를 실제 DB·대역 시험에 연결합니다. 문서·명세·다이어그램의 구조 검사만으로 업무 동작을 검증했다고 판단하지 않습니다.

| --- | --- | --- |
| 구매자 인증으로 판매자 API 호출 또는 반대 종류의 계정으로 로그인/복구 | 계정 종류·허용 작업 검증에서 거절 | 구매자·판매자 권한 혼용이나 다른 계정의 비밀번호 변경 없음 |

| 다른 판매자의 ID·결제 ID로 요청 | 호출자 권한과 소유권에서 거절 | 타 판매자 데이터·금액 변경·외부 호출 없음 |

### 검증 지표와 완료 기준

지속 가능 TPS는 결제 확정 처리량을 15분 유지하면서 적체·오류·응답 기준을 만족한 값입니다. arrival-rate 부하를 단계별로 올리고 `dropped_iterations`, 미완료 결제(`PENDING`·`PROCESSING`·`UNKNOWN`), 대기 Inbox·Job·Outbox·Kafka lag를 각각 기록합니다. 적체가 계속 늘면 지속 가능 처리량으로 인정하지 않습니다. 확정 거절은 미완료에서 제외하며 `접수량−확정량`으로 적체를 계산하지 않습니다. 환불 완료 TPS는 외부 환불·마일리지 복원·원장 상쇄·주문 복구까지 완료한 건수입니다.

API 응답, 접수→결제 확정, 외부 호출, Outbox 저장→발행, 이벤트 발생→소비 반영, 결제 확정→정산 반영, 배치 실행을 나눠 p50/p95/p99를 계산합니다. p99는 구간별 1만 건 이상에서 warm-up을 제외하고 계산합니다. 발생기 위치·데이터 건수·연결 풀·서비스 자원을 기록합니다. 배포 API p99 3초 목표는 비동기 결제 확정·배치 지연이나 로컬 시험에 적용하지 않습니다.

정상 부하의 시스템 오류는 5xx·타임아웃·연결 실패입니다. 경로별 HTTP 요청 시도 수를 분모로 계산하고 재시도도 별도 시도로 셉니다. 타임아웃·연결 실패는 발생기에서 집계하며 요청 1만 건 미만인 경로는 오류 건수만 보고합니다. 의도한 4xx·잔액 부족·PG 확정 거절·매진은 따로 집계하고, 내부 PG 호출의 오류율은 PG 호출 수를 분모로 둡니다. `UNKNOWN`·`REVIEW_REQUIRED`·DLT는 건수·최장 나이·원인을 확인합니다. 시험별 허용 오류율과 주입 조건은 실행 전에 명시합니다.

장애 주입부터 알람 발생까지는 탐지 시간, 오류율이 시험 기준으로 돌아올 때까지는 서비스 복구 시간입니다. 정합 복구는 미확정 금융·미발행 Outbox·미처리 Inbox·Kafka lag가 0이고 아래 대조가 모두 맞을 때 완료합니다. PG 응답 유실·조회 장애, Worker 종료, Kafka 중단, DB 재시작, 배치 대상 고정 뒤 중단, 지급 응답 유실을 원업무 키로 복구합니다.

#### 금액 대조

| 대조 | 완료 조건 |
| --- | --- |
| 결제 구성 | 확정 결제마다 `T=E+M` |
| Payment ↔ 금융 대역 | 승인·환불별 금액·상태 일치, 원결제별 금융 효과 각 1회 |
| 마일리지 | `현재 잔액=사전 지급−차감+복원`, `잔액−예약 합계≥0` |
| Payment ↔ Settlement | 환불 포함 확정 결제마다 동일 `paymentId`의 항목 1개, 최초 E·M·P·B·F·N 일치. 누락·중복·고아를 각각 집계 |
| Settlement 원장 | `E+M+P=B=N+F`, 완료 전액 환불은 최초 금액을 반대 부호로 상쇄 |
| 정산 ↔ 지급 | 지급액=선점 항목 합계, 항목당 배정 1회, 성공액=대역 차감액 |
| 재원·PG 입금 | `기초잔액+PG입금−입금후환불−성공지급=현재잔액`, 원승인별 E 입금 1회, 입금 전 전액 환불은 0원 종결 |

대조 쌍별 불일치 건수·차액과 중복 승인·환불·지급·원장 반영을 따로 셉니다. 부하·장애 시험 후에는 모든 대조 0건·0원과 [내부 참조 검사](data-model.md#내부-참조-대조) 0건이 완료 조건입니다. 대기·격리 건을 제외해 0으로 만든 결과는 완료가 아닙니다. 자동 정산 대조는 지원하지 않으며 [서비스별 검사 범위](policies.md#정산-대조)와 부하 도구의 실제 대조 범위를 구분합니다.
