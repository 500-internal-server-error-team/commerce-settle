# 프로젝트 초안

문제 후보·취급 상품·역할 배분을 검토하기 위한 초안입니다. 팀 논의에 따라 변경할 수 있으며, 후보 전체를 구현 범위로 확정하지 않습니다. 기본 기능과 서비스 경계는 [README](../README.md)를 기준으로 합니다. 아래 사례·수치는 시험용 가정이며 고객 수요나 성능 측정 결과가 아닙니다.

## 대상과 범위

기존 커머스 플랫폼에 입점한 판매자의 결제·환불·정산을 처리합니다. 판매자는 정산금을 받는 주체이며, 여러 판매자가 같은 서비스를 사용합니다.

첫 상품 범위는 **부패 위험이 없는 일반 완제품**을 제안합니다. 문구·소형 수납용품·일반 생활잡화부터 검토하고 식품·의류·전자기기·주문제작 상품은 제외해 상품별 예외를 줄입니다. 상하지 않는 상품도 불량·오배송·변심에 따른 반품은 발생할 수 있습니다.

상품·재고·방송·배송은 외부 커머스의 책임입니다. 환불 사유와 반품 상태도 외부 커머스가 판단하고, 승인된 환불 요청을 우리가 실행하는 연동을 제안합니다. 승인 주체·권한·승인 정보의 요청 계약은 기능 착수 전에 정의합니다.

기본 환불 범위는 **판매자 지급 예약 전 전액 환불**입니다. PG 결과가 미확정이면 환불용 정산금 예약을 유지하고 조회로 확인합니다. 확정 실패하면 예약을 해제하고, 성공하면 최초 수수료·순정산액을 상쇄합니다. [환불·금액 보존 규칙](../README.md#정합성-설계)을 따릅니다.

부분 환불·지급 후 환불·다중 판매자 묶음 결제는 기본 범위에 포함하지 않습니다. 이는 첫 구현 범위이며, 소비자의 환불 가능 여부를 일괄 제한하는 상품 정책이 아닙니다. 배송비·반품비의 계산과 부담 판단도 외부 커머스에 둡니다.

## 해결할 문제 후보

정확한 결제·정산과 장애 복구는 공통 기반입니다. 추가 사업 문제는 아래에서 하나를 선택하고, 고객의 구체 사례로 필요성을 확인합니다. 행사는 그 문제가 집중되는 상황과 부하 시험의 배경으로 사용합니다.

| 후보 | 문제 가정과 제공할 가치 | 필요한 확장·선택 시 비용 |
| --- | --- | --- |
| 공동 행사 할인비용 정산 | 플랫폼과 판매자가 나눠 부담한 할인액을 매번 따로 맞춥니다. 거래별 부담액·실수령액을 계산하고 취소 시 함께 상쇄합니다. | 행사 계약·지원금·할인 분담 원장. 쿠폰 발급은 외부 기능으로 유지할 수 있습니다. |
| 조기정산·선정산 | 매출은 발생했지만 입금 전까지 다음 매입 자금이 부족합니다. 승인된 한도 안에서 정산금을 먼저 지급합니다. | 자금 공급자·정산채권·선지급·회수와 선지급 후 환불. 단순 주기 변경과 구분해야 합니다. |
| 브랜드·크리에이터 수익 배분 | 취소까지 반영한 판매 보수를 반복 계산합니다. 계약별 보수를 보류·확정해 지급 근거를 제공합니다. | 판매자와 별개인 수익자, 배분 계약과 지급 보류 기간. |
| 구매 후 가격 보호 | 가격이 더 내려갈까 구매를 미루거나 취소 후 재구매합니다. 약정 조건을 충족하면 차액을 돌려줍니다. | 가격 이력·판매자의 비용 부담 동의·부분 환불·정산 조정. |
| 취소 전 환불액 안내 | 쿠폰을 쓴 주문 일부를 취소할 때 실제 환불액을 알기 어렵습니다. 실행 전 계산 근거를 제공합니다. | 주문 항목·할인 배분·부분 환불. 독립 주제보다 환불 보조 기능에 가깝습니다. |
| 여러 판매자 상품의 통합 결제 | 판매자마다 결제와 취소를 반복합니다. 한 번 결제하고 판매자별 금액을 배분하며 원하는 항목만 환불합니다. | 다중 판매자 결제·주문 항목·부분 환불. 기본 결제·환불 계약이 커집니다. |
| 여러 채널의 정산 통합 관리 | 채널별 수수료·정산 예정액·입금을 따로 확인합니다. 같은 기준으로 모아 차이와 근거를 보여줍니다. | 채널별 데이터 수집·매핑·입금 대조. 조회 통합만으로 서로 다른 지급 주체의 돈을 합쳐 지급할 수는 없습니다. |
| 목표 달성형 공동구매 | 최소 주문량을 모으기 전에 매입·제작 위험을 떠안습니다. 목표 미달 시 전액 환불하는 거래를 지원합니다. | 마감·유효 결제 집계·목표 판정·대량 환불. 주문제작·취소 조건이 늘어나 첫 범위에서는 우선순위를 낮춥니다. |

### 공동 행사 할인비용 정산 예시

일반 생활잡화 공동 행사에서 20,000원 상품에 5,000원 쿠폰을 적용합니다. 할인비용은 플랫폼 3,000원·판매자 2,000원으로 분담합니다. 수수료를 제외한 단순 예에서 구매자는 15,000원을 내고, 판매자 몫은 플랫폼 지원금을 합친 18,000원입니다.

결제 시점의 계약 버전을 보존하고 일반 결제와 행사 결제를 같은 원장 기준으로 처리합니다. 전액 취소 시 최초 분담액을 상쇄합니다. 플랫폼 지원금은 별도 재원이 필요하며, 예산 한도를 보장하려면 외부의 지원금 예약을 확인하거나 우리가 예약까지 맡아야 합니다.

포트원도 쿠폰·프로모션 할인액에 대한 파트너 분담률을 제공합니다. 이 사례는 할인 분담 모델의 근거이며, 대상 판매자에게 실제로 수작업이 발생한다는 검증을 대신하지 않습니다. [포트원 할인 분담 정책](https://help.portone.io/category/admin-console/platform-settlement)

### 조기정산과 선정산의 차이

이미 받은 자금을 2주마다 지급하는 것은 지급 일정 조정입니다. PG에서 받기 전에 먼저 지급하는 것은 별도 자금 공급이 필요한 선정산입니다. 정산 주기는 계약 가정이며 모든 PG가 월 단위로 정산한다고 보지 않습니다.

순정산 예정액 100만 원 중 80만 원을 먼저 지급한 뒤 PG에서 100만 원을 받았다면, 선지급액 80만 원을 회수하고 잔액 20만 원을 지급합니다. 환불·이용료를 제외한 설명용 예이며, 80%를 안전한 지급 비율로 검증한 것은 아닙니다.

선택 시 `finance-mock`에서 자금 공급자의 승인·지급·조회도 모의하고, 중복 선지급·한도 초과·환불·회수 부족을 검증해야 합니다. 실제 자금 조달과 금융 계약·심사는 별도 검토 대상입니다. 이미 이체한 자금은 DB 상태를 되돌리는 것으로 회수할 수 없습니다.

KB셀러론은 은행이 정산금을 먼저 지급하고 이후 마켓·PG 정산금으로 대출금을 상환하는 사례입니다. 토스페이먼츠 지급대행도 지급 가능한 잔액과 아직 정산받지 못한 잔액을 구분합니다. [KB셀러론](https://zloan.kbstar.com/quics?page=C108424) · [토스페이먼츠 지급대행](https://docs.tosspayments.com/guides/v2/payouts)

### 다른 후보의 참고와 보류 이유

- **수익 배분:** Shopify Collabs는 보류 기간 중 취소·전액 환불된 주문의 크리에이터 보수를 취소합니다. 판매자 외 수익자를 관리하는 모델의 사례입니다. [Shopify 지급 정책](https://help.shopify.com/en/manual/promoting-marketing/collabs/merchants/payments)
- **가격 보호:** Target은 일정 조건의 동일 상품에 구매 후 가격 조정을 요청할 수 있게 합니다. 자동 차액 환불은 별도의 제안이며, 비용 부담과 적용 조건을 정해야 합니다. [Target 가격 보장](https://www.target.com/help/articles/policies-guidelines/price-match-guarantee?redirect=true)
- **통합 결제:** Stripe는 한 결제의 자금을 여러 수익자에게 배분하는 구조를 제공합니다. 모델 참고이며 국내 실연동 지원 여부를 전제하지 않습니다. [Stripe 자금 배분](https://docs.stripe.com/connect/separate-charges-and-transfers)
- **AI 에이전트 구매:** 상품 정보·구매 위임·결제 권한까지 범위가 넓어져 후속 후보로 둡니다. 에이전트 여부에 따른 할인만으로 고객 문제를 확정하지 않습니다.

기본 환불 범위를 유지하려면 공동 행사 할인비용 정산을 먼저 검토할 수 있습니다. 선정산은 자금 공백이라는 문제가 선명하지만 지급 후 환불과 회수까지 범위가 커집니다. 후보 하나의 필요성과 비용을 비교한 뒤 선택하며, 부분 환불이나 새 계약이 필요한 후보를 함께 묶어 시작하지 않습니다.

## 5인 역할 배분안

김민식은 인증·전체 설계·통합을 주로 맡습니다. 나머지 네 명의 담당은 팀 합의 전 초안이며, 역할과 범위는 조정할 수 있습니다.

| 담당 | 책임 |
| --- | --- |
| 김민식 — 통합리드·인증 | 인증·권한·Gateway, 전체 아키텍처와 API·이벤트·DB 경계 조율, 공통 오류·CI·공용 환경, 통합 부하·복구 검증 |
| 김지현 — 결제 | 결제 접수·PG 승인·멱등성, Payment API·Worker, 결제 이벤트 |
| 김은지 — 환불 | 환불 SAGA·보상, 미확정 결과 조회, 환불 동시성 |
| 권민혁 — 정산·지급 | 거래별 원장·수수료·환불금 예약·정산 배치, 지급 실행·조회·재처리 |
| 이성호 — 판매자·외부 Mock | 판매자 정보·상태·변경 이벤트, `finance-mock`의 승인·환불·지급·조회와 장애 시나리오 |

공통 방향과 연동 계약은 통합리드가 조율하고, 각 담당자가 자기 영역의 상세 설계·구현·테스트·Kafka 처리·부하 시나리오를 맡습니다. Redis는 조회·캐시 목적과 무효화·장애 시 동작을 정한 뒤 효과를 비교합니다. 인증 담당자도 필요한 캐시 검증과 통합 부하·복구 시험에 참여합니다.

인증과 판매자 기능은 Seller 모듈 안에서 나눠 작업하고, 결제·환불은 Payment, 원장·지급은 Settlement 안에서 작업합니다. 인원수 때문에 서비스를 추가하지 않습니다. Mock 계약은 결제·환불·정산 담당자와 맞추고, 기능별로 필요한 응답과 장애 상황을 함께 검증합니다.

## 부하·정합성 검증 가정

공동 행사 시작 후 60초에 결제 요청 60,000건이 들어온다면 평균 1,000요청/초입니다. 행사 결제 70%·일반 결제 30%를 시험용 분포로 사용할 수 있습니다. 실제 이용량 통계나 승인 완료 성능을 뜻하지 않습니다.

- 요청량과 승인 완료 TPS를 분리합니다. 승인 완료의 정의와 지속 시험 목표는 [성능 목표](../README.md#성능-목표와-검증)를 따릅니다.
- 중복 요청·PG 응답 유실·이벤트 재전달·환불과 지급의 경쟁을 시험합니다. 미확정 외부 결과는 조회로 확인합니다.
- 지연·승인 완료량·정산 반영 지연·대기열 회복과 함께 PG·Payment·Settlement의 거래별 금액을 대조합니다.
- 선택한 후보에 맞춰 할인 분담·선지급·수익 배분 등의 불변식을 추가합니다. 처리 성능으로 고객 수요나 사업 효과를 증명했다고 표현하지 않습니다.

## 선택 전에 확인할 것

1. 판매자·플랫폼·구매자 중 대상과 반복되는 불편 하나를 정하고, 실제 사례·소요 시간·자금 공백 등을 확인합니다.
2. 상품 범위, 환불 승인 주체, 할인비용·수수료·지원금의 기준과 책임을 정합니다.
3. 역할 배분을 맞추고 선택한 문제의 상태 흐름 → 데이터 소유권 → 서비스 경계 → ERD·API·이벤트 계약 순서로 상세화합니다. 새 정책을 선택하면 README와 관련 계약도 함께 갱신합니다.
