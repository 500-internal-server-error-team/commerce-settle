# 프로젝트 초안

결제·환불·정산의 기술 검증을 위한 범위·역할·시험 초안입니다. 기본 기능과 서비스 경계는 [README](../README.md), 상세 흐름과 선택 이유는 [상세 설계 초안](design.md)을 기준으로 합니다. 아래 수치는 시험용 가정이며 측정 결과가 아닙니다.

## 대상과 범위

기존 커머스 플랫폼에 입점한 판매자의 결제·환불·정산을 처리합니다. 판매자는 정산금을 받는 주체이며, 여러 판매자가 같은 서비스를 사용합니다.

첫 상품 범위는 **부패 위험이 없는 일반 완제품**을 제안합니다. 문구·소형 수납용품·일반 생활잡화부터 검토하고 식품·의류·전자기기·주문제작 상품은 제외해 상품별 예외를 줄입니다. 상하지 않는 상품도 불량·오배송·변심에 따른 반품은 발생할 수 있습니다.

상품·재고·방송·배송은 외부 커머스의 책임입니다. 환불 사유와 반품 상태도 외부 커머스가 판단하고, 승인된 환불 요청을 우리가 실행하는 연동을 제안합니다. 승인 주체·권한·승인 정보의 요청 계약은 기능 착수 전에 정의합니다.

기본 환불 범위는 **판매자 지급 예약 전 전액 환불**입니다. PG 결과가 미확정이면 환불용 정산금 예약을 유지하고 조회로 확인합니다. 확정 실패하면 예약을 해제하고, 성공하면 최초 수수료·순정산액을 상쇄합니다. [환불·금액 보존 규칙](../README.md#정합성-설계)을 따릅니다.

부분 환불·지급 후 환불·다중 판매자 묶음 결제는 기본 범위에 포함하지 않습니다. 이는 첫 구현 범위이며, 소비자의 환불 가능 여부를 일괄 제한하는 상품 정책이 아닙니다. 배송비·반품비의 계산과 부담 판단도 외부 커머스에 둡니다.

## 기술 검증 목표

행사 시작에 결제 요청이 몰리고 PG 응답이 지연·유실되는 조건을 재현합니다. 이때 접수·승인·원장 반영을 분리하고, 중복 요청과 환불·지급 경쟁에서도 최종 상태와 금액이 수렴하는지 확인합니다.

| 검증 대상 | 확인할 결과 |
| --- | --- |
| 결제 처리량·적체 | 접수량과 승인 완료량을 구분하고 피크 이후 대기 작업을 배출 |
| 외부 결과 미확정 | 응답 유실 후 같은 업무 키로 결과를 확인하고 중복 실행 방지 |
| 이벤트 전달·복구 | 중복·역순·재시작 후 원장 누락·중복 반영 없음 |
| 환불 SAGA | 예약·PG 환불·원장 상쇄, 확정 실패 시 예약 해제 |
| 정산·지급 | 환불과 지급의 이중 선점, 중복 지급, 지급 가능 잔액 초과 방지 |

행사는 부하가 집중되는 시험 배경입니다. 기본 결제·환불·정산 흐름만으로 위 항목을 검증하며, 추가 기능 선택을 착수 조건으로 두지 않습니다.

## 선택 확장 후보

앞서 검토한 아이디어는 후속 기능 후보로 둡니다. 기본 흐름과 실패 복구를 먼저 검증하고, 확장을 선택하면 금액 규칙·상태·API·이벤트·시험 범위를 함께 바꿉니다.

| 후보 | 추가 설계·보류 이유 |
| --- | --- |
| 공동 행사 할인비용 정산 | 플랫폼·판매자 부담액, 지원금 한도·예약, 최초 분담액의 환불 상쇄가 필요합니다. 쿠폰 발급은 외부 기능으로 둘 수 있습니다. |
| 선정산 | 자금 공급·한도·선지급·회수와 지급 후 환불이 필요합니다. 이미 받은 자금의 지급 주기를 바꾸는 것과 구분합니다. |
| 브랜드·크리에이터 수익 배분 | 수익자·배분 계약·보류 기간과 취소 시 보수 상쇄가 추가됩니다. |
| 가격 보호·환불액 사전 안내 | 가격 이력 또는 주문 항목·할인 배분과 부분 환불이 필요합니다. |
| 여러 판매자 상품의 통합 결제 | 단일 판매자 경계를 넘어 금액 배분·항목별 환불 계약을 확장해야 합니다. |
| 여러 채널의 정산 통합 | 외부 데이터 매핑·대조와 채널별 지급 주체를 구분해야 합니다. |
| 목표 달성형 공동구매 | 마감·유효 결제 집계·목표 판정·대량 환불이 필요합니다. |
| AI 에이전트 구매 | 상품 검색·구매 위임·결제 권한까지 범위가 넓어집니다. |

## 5인 역할 배분안

김민식이 **전체 상세 설계·인증·통합**을 맡습니다. 공통 구조와 각 도메인의 업무 규칙·상태 전이·ERD·API·이벤트·실패 복구·검증 시나리오를 작성합니다. 나머지 네 명의 구현 담당 배분은 팀 합의 전 초안이며 조정할 수 있습니다.

| 담당 | 책임 |
| --- | --- |
| 김민식 — 전체 상세 설계·인증·통합 | 전체 도메인의 상세 설계와 계약 관리, 인증·권한·Gateway 구현, 공통 오류·CI·공용 환경, 통합 부하·복구 검증 |
| 김지현 — 결제 | 결제 접수·PG 승인·멱등성, Payment API·Worker, 결제 이벤트 |
| 김은지 — 환불 | 환불 SAGA·보상, 미확정 결과 조회, 환불 동시성 |
| 권민혁 — 정산·지급 | 거래별 원장·수수료·환불금 예약·정산 배치, 지급 실행·조회·재처리 |
| 이성호 — 판매자·외부 Mock | 판매자 정보·상태·변경 이벤트, `finance-mock`의 승인·환불·지급·조회와 장애 시나리오 |

각 구현 담당자는 김민식이 작성한 자기 영역의 설계를 읽고 구현 가능성·누락·연동 영향을 확인한 뒤 구현·테스트·Kafka 처리·부하 시나리오를 맡습니다. 구현 중 발견한 제약과 변경안은 김민식과 맞추고 기준 설계에 반영합니다. 상세 설계의 작성 책임을 김민식에게 두되, 구현자의 검증과 피드백을 생략하지 않습니다. 팀원 PR 승인 여부는 기존 [협업 규칙](../CONTRIBUTING.md#pr과-리뷰)을 따릅니다.

인증과 판매자 기능은 Seller 모듈 안에서 나눠 작업하고, 결제·환불은 Payment, 원장·지급은 Settlement 안에서 작업합니다. 인원수 때문에 서비스를 추가하지 않습니다. Mock 계약은 결제·환불·정산 담당자와 맞추고, 기능별로 필요한 응답과 장애 상황을 함께 검증합니다.

## 부하·정합성 검증 가정

공동 행사 시작 후 60초에 결제 요청 60,000건이 들어온다면 평균 1,000요청/초입니다. 이를 피크 시험의 입력으로 사용하고 판매자별 편중도 함께 비교합니다. 행사 결제에도 기본 결제와 같은 금액 규칙을 적용합니다. 이 수치는 실제 이용량 통계나 승인 완료 성능을 뜻하지 않습니다.

- 요청량과 승인 완료 TPS를 분리합니다. 승인 완료의 정의와 지속 시험 목표는 [성능 목표](../README.md#성능-목표와-검증)를 따릅니다.
- 중복 요청·PG 응답 유실·이벤트 재전달·환불과 지급의 경쟁을 시험합니다. 미확정 외부 결과는 조회로 확인합니다.
- 지연·승인 완료량·정산 반영 지연·대기열 회복과 함께 PG·Payment·Settlement의 거래별 금액을 대조합니다.
- 선택 확장을 도입할 때만 할인 분담·선지급·수익 배분 등의 불변식과 시험을 추가합니다.

## 구현 준비 순서

1. 기본 상품·거래 범위와 외부 주문·환불·정산 승인 입력을 정합니다.
2. 김민식이 [상세 설계 초안](design.md)을 기준으로 상태 흐름 → 데이터 소유권 → 서비스 경계 → ERD·API·이벤트 계약을 상세화하고 구현 담당자와 맞춥니다.
3. 결제 한 건 → 원장 반영 → 환불·보상 → 정산·지급 순서로 연결하고, 각 단계의 중복·실패·복구를 검증한 뒤 부하를 늘립니다. 새 정책을 선택하면 README와 관련 계약도 함께 갱신합니다.
