# 프로젝트 초안

구매자의 주문·결제·환불과 판매자 정산의 기술 검증을 위한 범위·역할·시험 초안입니다. 기본 기능과 서비스 경계는 [README](../README.md), 상세 흐름과 선택 이유는 [상세 설계 초안](design.md)을 기준으로 합니다. 아래 수치는 시험용 가정이며 측정 결과가 아닙니다.

## 대상과 범위

구매자가 우리 서비스에서 상품을 주문하고 결제하며, 취소·반품 승인에 따라 환불받습니다. 판매자별로 매출·환불·수수료를 계산해 정산금을 지급합니다. 결제하는 사람은 구매자이고, 정산금을 받는 주체는 판매자입니다.

구매자와 판매자는 각각 가입·로그인합니다. 구매자 계정은 주문·결제·환불과 배송지를, 판매자 계정은 상품·발송·반품 승인과 정산을 이용합니다. 같은 사람이 구매와 판매를 모두 하려면 각각 계정을 만듭니다. [사용자와 거래 주체](design.md#사용자와-거래-주체)가 계정·권한·소유권의 기준입니다.

첫 상품 범위는 **부패 위험이 없는 일반 완제품**을 제안합니다. 문구·소형 수납용품·일반 생활잡화부터 검토하고 식품·의류·전자기기·주문제작 상품은 제외해 상품별 예외를 줄입니다. 상하지 않는 상품도 불량·오배송·변심에 따른 반품은 발생할 수 있습니다.

상품·가격·재고·주문·배송지·쿠폰은 우리 서비스가 관리합니다. 구매자는 배송지를 입력하거나 저장된 배송지를 선택하고, 쿠폰 적용 후 결제수단을 선택합니다. 기본 쿠폰은 사전 준비한 판매자 부담 정액 쿠폰 한 장이며, 기본 결제수단은 카드 결제를 모의합니다. 쿠폰은 할인이고 카드는 남은 금액의 결제수단입니다.

배송은 판매자의 발송 처리와 구매자의 구매 확정까지 관리하고, 택배사 연동·배송 추적·실제 수거·검수는 제외합니다. 미발송 주문의 구매자 취소와 발송 후 판매자가 승인한 반품 환불을 구분합니다. 방송·영상 송출·채팅은 구현 범위에서 제외합니다.

기본 환불 범위는 **판매자 지급 예약 전 전액 환불**입니다. PG 결과가 미확정이면 환불용 정산금 예약을 유지하고 조회로 확인합니다. 확정 실패하면 예약을 해제하고, 성공하면 최초 수수료·순정산액을 상쇄합니다. [환불·금액 보존 규칙](../README.md#정합성-설계)을 따릅니다.

첫 주문 범위는 판매자 한 명의 상품 한 종류와 수량이며 장바구니·다중 판매자 묶음 결제·부분 환불·지급 후 환불은 제외합니다. 기본 시험은 배송비·반품비 0원을 가정합니다. 이는 기술 검증 범위이며, 실제 거래의 반품 권리나 판매자 물류 비용이 없다는 뜻은 아닙니다.

## 기능 우선순위

1. 구매자·판매자 계정별 인증과 최소 상품·주문 기능을 연결합니다. 쿠폰 없이 주문 한 건 → 카드 모의 결제 → 주문 확정·원장 반영을 먼저 검증합니다.
2. 배송지 저장·주문 당시 사본, 재고·쿠폰 예약과 해제, 전액 환불 SAGA, 구매 확정 → 정산·지급을 연결합니다.
3. 중복·금액 변조·응답 유실·재시작·환불/지급 경쟁과 부하를 검증합니다. 여러 결제수단·부분 환불·공동 할인비용 정산은 이후 확장입니다.

## 기술 검증 목표

프로모션 시작에 구매자의 주문·결제 요청이 몰리고 PG 응답이 지연·유실되는 조건을 재현합니다. 이때 주문 접수·결제 승인·원장 반영을 분리하고, 중복 요청과 환불·지급 경쟁에서도 최종 상태와 금액이 수렴하는지 확인합니다.

| 검증 대상 | 확인할 결과 |
| --- | --- |
| 사용자·거래 소유권 | 구매자·판매자 로그인 구분, 다른 계정의 주문·주소·판매자 데이터 접근 차단 |
| 주문·재고·쿠폰 | 서버 금액 확정, 재고 초과 예약·쿠폰 중복 사용 방지, 실패·미확정·환불 결과에 맞는 예약 처리 |
| 결제 처리량·적체 | 접수량과 승인 완료량을 구분하고 피크 이후 대기 작업을 배출 |
| 외부 결과 미확정 | 응답 유실 후 같은 업무 키로 결과를 확인하고 중복 실행 방지 |
| 이벤트 전달·복구 | 중복·역순·재시작 후 원장 누락·중복 반영 없음 |
| 환불 SAGA | 예약·PG 환불·원장 상쇄, 확정 실패 시 예약 해제 |
| 정산·지급 | 환불과 지급의 이중 선점, 중복 지급, 지급 가능 잔액 초과 방지 |

행사는 부하가 집중되는 시험 배경입니다. 기본 결제·환불·정산 흐름만으로 위 항목을 검증하며, 추가 기능 선택을 착수 조건으로 두지 않습니다.

## 선택 확장 후보

앞서 검토한 아이디어는 후속 기능 후보로 둡니다. 기본 흐름과 실패 복구를 먼저 검증하고, 확장을 선택하면 금액 규칙·상태·API·이벤트·시험 범위를 함께 바꿉니다.

| 후보 | 추가 설계·보류 이유 |
| --- | --- |
| 공동 행사 할인비용 정산 | 기본 판매자 부담 쿠폰과 달리 플랫폼 부담액·지원금 한도·예약, 최초 분담액의 환불 상쇄가 필요합니다. |
| 선정산 | 자금 공급·한도·선지급·회수와 지급 후 환불이 필요합니다. 이미 받은 자금의 지급 주기를 바꾸는 것과 구분합니다. |
| 브랜드·크리에이터 수익 배분 | 수익자·배분 계약·보류 기간과 취소 시 보수 상쇄가 추가됩니다. |
| 가격 보호·환불액 사전 안내 | 가격 이력 또는 주문 항목·할인 배분과 부분 환불이 필요합니다. |
| 여러 판매자 상품의 통합 결제 | 단일 판매자 경계를 넘어 금액 배분·항목별 환불 계약을 확장해야 합니다. |
| 여러 채널의 정산 통합 | 외부 데이터 매핑·대조와 채널별 지급 주체를 구분해야 합니다. |
| 목표 달성형 공동구매 | 마감·유효 결제 집계·목표 판정·대량 환불이 필요합니다. |
| AI 에이전트 구매 | 상품 검색·구매 위임·결제 권한까지 범위가 넓어집니다. |

## 5인 역할 배분안

김은지는 인증 담당으로 정리했습니다. 사용자·주문 범위 확대에 따른 나머지 배분은 팀 합의 전 조정안입니다.

| 담당 | 책임 |
| --- | --- |
| 김민식 — 전체 상세 설계·통합 | 전체 상세 설계와 연동 계약 조율, Gateway 구성, 공통 오류·CI·공용 환경, 통합 부하·복구 검증 |
| 김지현 — 결제·환불 | 결제 접수·PG 승인·조회·멱등성, 환불 SAGA·보상, Payment API·Worker, PG Mock 동작 |
| 김은지 — 사용자·인증 | 구매자·판매자 계정별 가입·로그인·인증 정보 발급·갱신·폐기, 권한·계정/판매 상태, 기본 배송지, Gateway·서비스 인증 연동 |
| 권민혁 — 정산·지급 | 거래별 원장·수수료·환불금 예약·정산 배치, 지급 실행·조회·재처리, 지급 기관 Mock 동작 |
| 이성호 — 상품·주문·쿠폰 | 상품·가격·재고, 주문·배송지 사본·최종 금액, 쿠폰·재고 예약과 복구, 발송·구매 확정·취소/반품 승인 흐름 |

결제·환불과 상품·주문의 구현량이 크므로 기능별 완료 조건을 나눠 작업량을 대조합니다. 특히 환불 SAGA와 서비스 간 복구는 통합 담당도 함께 검증합니다. 위 표를 작업량이 균등하거나 팀 합의가 끝났다는 뜻으로 사용하지 않습니다.

각 담당자는 자기 영역의 설계·구현·테스트·Kafka 처리·부하 시나리오를 맡습니다. 서비스 간 연동 계약과 변경 영향은 관련 담당자가 함께 검토하고, 합의한 변경은 기준 문서에 반영합니다. 팀원 PR 승인 여부는 기존 [협업 규칙](../CONTRIBUTING.md#pr과-리뷰)을 따릅니다.

구매자·판매자 계정과 인증, 상품·주문·쿠폰은 기존 `seller` 모듈 안에서 도메인별로 나눠 작업하고, 결제·환불은 Payment, 원장·지급은 Settlement 안에서 작업합니다. 로그인 계정·도메인·독립 배포 서비스는 서로 다른 구분입니다. 계정을 분리하더라도 인증 서버를 두 개 만들지는 않습니다. `finance-mock`은 하나로 유지하고 PG·지급 담당자가 각 동작과 장애 계약을 맞춥니다.

## 부하·정합성 검증 가정

공동 행사 시작 후 60초에 결제 요청 60,000건이 들어온다면 평균 1,000요청/초입니다. 이를 피크 시험의 입력으로 사용하고 판매자별 편중도 함께 비교합니다. 행사 결제에도 기본 결제와 같은 금액 규칙을 적용합니다. 이 수치는 실제 이용량 통계나 승인 완료 성능을 뜻하지 않습니다.

- 요청량과 승인 완료 TPS를 분리합니다. 승인 완료의 정의와 지속 시험 목표는 [성능 목표](../README.md#성능-목표와-검증)를 따릅니다.
- 중복 요청·PG 응답 유실·이벤트 재전달·환불과 지급의 경쟁을 시험합니다. 미확정 외부 결과는 조회로 확인합니다.
- 지연·승인 완료량·정산 반영 지연·대기열 회복과 함께 PG·Payment·Settlement의 거래별 금액을 대조합니다.
- 선택 확장을 도입할 때만 할인 분담·선지급·수익 배분 등의 불변식과 시험을 추가합니다.

## 구현 준비 순서

1. 구매자·판매자 계정별 권한, 단일 상품 주문·쿠폰·금액·환불 범위와 구매 확정에 따른 정산 가능 조건을 정합니다.
2. [상세 설계 초안](design.md)을 기준으로 상태 흐름 → 데이터 소유권 → 서비스 경계 → ERD·API·이벤트 계약을 상세화하고 관련 담당자가 함께 검토합니다.
3. 결제 한 건 → 원장 반영 → 환불·보상 → 정산·지급 순서로 연결하고, 각 단계의 중복·실패·복구를 검증한 뒤 부하를 늘립니다. 새 정책을 선택하면 README와 관련 계약도 함께 갱신합니다.
