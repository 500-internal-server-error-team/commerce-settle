# 프로젝트 계획

구현 우선순위·역할 배분·선택 확장·준비 순서를 정리합니다. 범위·가정·업무 흐름은 [업무 설계](design.md), 문서별 기준 위치는 [문서와 기록](../CONTRIBUTING.md#문서와-기록)을 따릅니다. 계획의 수치는 시험용 가정이며 측정 결과가 아닙니다.

## 대상과 범위

계정·거래 단위·배송·환불·알림의 포함·제외 범위는 [업무 설계](design.md#2-해결-범위)를 따릅니다. 선택 확장은 아래 후보에서 별도로 검토하며 기본 구현의 착수 조건으로 삼지 않습니다.

첫 상품 범위는 **부패 위험이 없는 일반 완제품**을 제안합니다. 문구·소형 수납용품·일반 생활잡화부터 검토하고 식품·의류·전자기기·주문제작 상품은 제외해 상품별 예외를 줄입니다. 상하지 않는 상품도 불량·오배송·변심에 따른 반품은 발생할 수 있습니다.

## 기능 우선순위

1. 구매자·판매자 계정별 인증과 최소 상품·주문 기능을 연결합니다. 쿠폰 없이 주문 한 건 → 카드 모의 결제 → 주문 확정·원장 반영을 먼저 검증합니다.
2. 신용/체크카드·간편결제 대역과 마일리지 혼합/전액 결제를 연결합니다. 배송지 사본·재고·쿠폰 예약, 원수단 환불·마일리지 복원, 구매 확정 → 정산·지급을 검증합니다.
3. 판매자의 선착순 이벤트 등록·참여·게이지·매진 종료를 연결하고 특정 상품 집중 부하·중복·응답 유실·재시작·환불/지급 경쟁을 검증합니다. 부분 환불·공동 할인비용 정산은 이후 확장입니다.

## 문제와 자동지급

지급 대기를 줄이려는 목적과 선택 이유는 [프로젝트 소개](../README.md#해결하려는-문제와-자동지급)에 정리합니다. 지급 가능 조건·마감·보류·재개는 [정산 정책](policies.md#정산재처리)을 따릅니다.

## 기술 검증 목표

프로모션 시작에 구매자의 주문·결제 요청이 몰리고 PG 응답이 지연·유실되는 조건을 재현합니다. 이때 주문 접수·결제 승인·원장 반영을 분리하고, 중복 요청과 환불·지급 경쟁에서도 최종 상태와 금액이 수렴하는지 확인합니다.

| 검증 대상 | 확인할 결과 |
| --- | --- |
| 사용자·거래 소유권 | 구매자·판매자 로그인 구분, 다른 계정의 주문·주소·판매자 데이터 접근 차단 |
| 주문·재고·쿠폰 | 서버 금액 확정, 재고 초과 예약·쿠폰 중복 사용 방지, 실패·미확정·환불 결과에 맞는 예약 처리 |
| 선착순 이벤트 | 마지막 수량·중복 참여 경쟁, 확정 판매량과 예약 구분, 100% 매진 종료·캐시 지연 중 초과 판매 방지 |
| 결제 구성·마일리지 | 외부 금액+마일리지 합계, 가용 잔액 경쟁, 원수단 환불과 마일리지 한 번 복원 |
| 결제 처리량·적체 | 접수량과 결제 확정량을 구분하고 피크 이후 대기 작업을 배출 |
| 외부 결과 미확정 | 응답 유실 후 같은 업무 키로 결과를 확인하고 중복 실행 방지 |
| 이벤트 전달·복구 | 중복·역순·재시작 후 원장 누락·중복 반영 없음 |
| 환불 SAGA | 예약·PG 환불·원장 상쇄, 확정 실패 시 예약 해제 |
| 정산·지급 | 환불과 지급의 이중 선점, 중복 지급, 지급 가능 잔액 초과 방지 |

선착순 이벤트는 이번 구현 범위에 포함합니다. 방송 기능 없이 실제 이벤트 시작·신청·결제·매진 흐름을 부하의 원인으로 사용하며, 아래 선택 확장과 구분합니다.

## 선택 확장 후보

앞서 검토한 아이디어는 후속 기능 후보로 둡니다. 기본 흐름과 실패 복구를 먼저 검증하고, 확장을 선택하면 금액 규칙·상태·API·이벤트·시험 범위를 함께 바꿉니다.

| 후보 | 추가 설계·보류 이유 |
| --- | --- |
| 공동 행사 할인비용 정산 | 기본 판매자 부담 쿠폰과 달리 플랫폼 부담액·지원금 한도·예약, 최초 분담액의 환불 상쇄가 필요합니다. |
| 실자금 선정산·지급 후 회수 | 기본 모의 선지급을 넘어 실제 자금 조달·계약·지급 후 환불/회수가 필요합니다. |
| 브랜드·크리에이터 수익 배분 | 수익자·배분 계약·보류 기간과 취소 시 보수 상쇄가 추가됩니다. |
| 가격 보호·환불액 사전 안내 | 가격 이력 또는 주문 항목·할인 배분과 부분 환불이 필요합니다. |
| 여러 판매자 상품의 통합 결제 | 단일 판매자 경계를 넘어 금액 배분·항목별 환불 계약을 확장해야 합니다. |
| 여러 채널의 정산 통합 | 외부 데이터 매핑·대조와 채널별 지급 주체를 구분해야 합니다. |
| 목표 달성형 공동구매 | 마감·유효 결제 집계·목표 판정·대량 환불이 필요합니다. |
| AI 에이전트 구매 | 상품 검색·구매 위임·결제 권한까지 범위가 넓어집니다. |

## 5인 역할 배분안

김은지는 인증, 김민식은 주문 담당으로 정리했습니다. 나머지 배분은 팀 합의 전 조정안입니다.

| 담당 | 책임 |
| --- | --- |
| 김민식 — 주문·전체 상세 설계·통합 | 주문·배송지 사본·최종 금액·취소/반품 승인·자동 구매확정, 전체 상세 설계와 연동 계약·Gateway·공통 환경·통합 검증 |
| 김지현 — 결제·환불 | 결제수단·마일리지 잔액/원장·원수단 환불/복원·SAGA, Payment API·Worker, PG Mock 3종·간편결제 Mock·장애 시나리오 |
| 김은지 — 사용자·인증 | 구매자·판매자 계정별 가입·로그인·인증 정보 발급·갱신·폐기, 권한·계정/판매 상태, 기본 배송지, Gateway·서비스 인증 연동 |
| 권민혁 — 정산·지급 | 거래별 원장·수수료·환불금 예약·정산 배치, 지급 실행·조회·재처리, 지급 기관 Mock 동작 |
| 이성호 — 상품·쿠폰·선착순 이벤트 | 상품·가격·재고·쿠폰, 이벤트 등록/참여/게이지·수량 예약, 발송·반품 입고, 주문 담당과 예약/복구 계약 연동 |

결제·환불·주문·이벤트의 구현량이 크므로 기능별 완료 조건을 나눠 작업량을 대조합니다. 특히 환불 SAGA와 서비스 간 복구는 통합 담당도 함께 검증합니다. 위 표를 작업량이 균등하거나 팀 합의가 끝났다는 뜻으로 사용하지 않습니다.

각 담당자는 자기 영역의 설계·구현·테스트·Kafka 처리·부하 시나리오를 맡습니다. 서비스 간 연동 계약과 변경 영향은 관련 담당자가 함께 검토하고, 합의한 변경은 기준 문서에 반영합니다. 팀원 PR 승인 여부는 기존 [협업 규칙](../CONTRIBUTING.md#pr과-리뷰)을 따릅니다.

구매자·판매자 계정과 인증, 상품·주문·쿠폰은 `commerce` 모듈 안에서 도메인별로 나눠 작업하고, 결제·환불은 Payment, 원장·지급은 Settlement 안에서 작업합니다. 로그인 계정·도메인·독립 배포 서비스는 서로 다른 구분입니다. 계정을 분리하더라도 인증 서버를 두 개 만들지는 않습니다. `finance-mock`은 하나로 유지하고 PG·지급 담당자가 각 동작과 장애 계약을 맞춥니다.

## 부하·정합성 검증 가정

[선착순 이벤트 집중 부하](design.md#선착순-이벤트-집중-부하)와 [지속 결제 처리량 시험](../README.md#성능-목표와-검증)을 나누고, [PG 장애 시나리오](design.md#pg-3종과-장애-시나리오)·[간편결제 대역](design.md#간편결제-대역)의 입력으로 정상·중복·미확정·재시작·환불/지급 경쟁을 확인합니다. 지연·적체·최종 상태·금액 대조의 기준은 [측정 지표 결정](decisions/0002-performance-and-integrity-metrics.md)을 따릅니다. 시험 입력 가정이며 실제 이용량 통계나 성능 결과가 아닙니다.

## 구현 준비 순서

1. 구매자·판매자 권한, 단일 상품·선착순 이벤트 참여, 결제수단·마일리지·쿠폰·환불 구성과 구매 확정에 따른 정산 가능 조건을 정합니다.
2. [API](api.md)·[데이터 모델](data-model.md)·[정책](policies.md)을 기준으로 관련 담당자가 구현 영향을 검토하고 서비스별 스키마 구현·컨트롤러·이벤트 처리를 연결합니다.
3. 결제 한 건 → 원장 반영 → 환불·보상 → 정산·지급 순서로 연결하고, 각 단계의 중복·실패·복구를 검증한 뒤 부하를 늘립니다. 새 정책을 선택하면 README와 관련 계약도 함께 갱신합니다.
