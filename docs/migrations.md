# DB 스키마와 데이터 정책

업무 설계와 [데이터 모델](data-model.md)은 테이블·컬럼·제약·인덱스와 시험 중 데이터 정합성을 정의합니다. 스키마 적용과 실험 데이터 초기화는 이 문서가, 환경별 실행 명령은 [개발 환경](development.md)이 소유합니다. 결정 이유는 [실험 데이터 초기화 ADR](decisions/0016-experimental-data-reset.md)에 기록합니다.

현재 배포는 개발·시연·부하 시험을 위한 실험 환경입니다. 스키마 변경이나 새 독립 실험에서는 기존 시험 데이터를 초기화하고 다시 준비하며, 이전 버전 데이터의 업그레이드를 지원하지 않습니다.

| DB | 현재 스키마 DDL |
| --- | --- |
| commerce | [commerce.sql](../infra/postgres/schema/commerce.sql) |
| payment | [payment.sql](../infra/postgres/schema/payment.sql) |
| settlement | [settlement.sql](../infra/postgres/schema/settlement.sql) |
| finance_mock | [finance_mock.sql](../infra/postgres/schema/finance_mock.sql) |

위 DDL은 현재 구현된 스키마의 생성 정의이며, 데이터 모델의 모든 테이블이 구현됐다는 뜻은 아닙니다.

## 현재 개발 환경의 적용 방식

**서비스 DB마다 초기 SQL 한 파일**을 관리하며 Flyway·버전별 증분 마이그레이션을 사용하지 않습니다.

1. 새 테이블·컬럼·제약·인덱스는 위 파일의 생성 정의에 반영합니다. 변경마다 ALTER·데이터 이관 SQL이나 구스키마 호환 코드를 추가하지 않습니다.
2. PostgreSQL의 빈 데이터 볼륨 초기화 때 [01-init.sh](../infra/postgres/01-init.sh)가 DB·계정·권한을 만든 뒤 각 서비스 역할로 자기 DDL을 한 트랜잭션에서 실행합니다. 테이블·인덱스는 서비스 계정이 소유하며 다른 서비스 DB를 참조하지 않습니다.
3. 앱은 DDL을 실행하지 않고 `spring.sql.init.mode=never`·`ddl-auto=validate`를 유지합니다. 초기화 실패를 무시하거나 Hibernate `update`·`create`로 보완하지 않습니다.
4. DB 통합 시험은 같은 파일을 테스트 리소스로 복사해 빈 전용 PostgreSQL에 적용합니다. Compose의 빈 볼륨 기동과 같은 스키마에서 데이터를 유지한 재기동도 확인합니다.

**기존 볼륨에서는 초기 SQL이 다시 실행되지 않습니다.** 파일 수정·이미지 재빌드·앱 재시작만으로 기존 DB 구조가 바뀌지 않으므로, 스키마가 바뀌면 아래 초기화 절차로 적용합니다. 기존 DB에 전체 생성 SQL을 덧실행하지 않습니다. 과거 업그레이드 SQL은 새 실험 환경의 표준 배포 절차로 사용하지 않습니다.

## 최초 배포와 기존 데이터 변경

최초 배포는 빈 DB에 현재 초기 SQL을 적용합니다. 기존 실험 환경에서 스키마를 바꾸거나 새 독립 실험을 시작할 때는 다음 순서로 초기화합니다.

1. 대상 환경과 시험 시간을 정하고, 같은 환경을 쓰는 팀의 실행을 멈춥니다. 공유 AWS 환경도 초기화 대상이지만 다른 진행 중인 시험과 섞지 않습니다.
2. 이전 시험의 입력 조건·코드/설정 버전·요청 원장·지표·정합성 대조 결과와 필요한 오류 분석 자료를 초기화 대상 밖에 남깁니다.
3. 해당 환경의 앱·Worker를 멈추고 **네 업무 DB·Kafka 메시지와 소비 위치·Redis 상태를 함께 초기화**합니다. 이전 메시지가 새 DB에 재처리되지 않게 합니다. 비밀번호·키·설정과 다른 환경의 데이터는 삭제 대상이 아닙니다.
4. 현재 초기 SQL과 시험 초기 데이터를 적용하고 Kafka 최초 소비 위치·Redis 실행 식별자·인증 상태를 다시 준비합니다. 연결·스키마·업무 정합성을 확인한 뒤 워밍업과 주입을 시작합니다.

로컬 명령은 [종료·재실행·초기화](development.md#종료재실행초기화), AWS 데이터 서비스의 배치·영속 경로는 [ECS EC2 데이터 서비스](development.md#ecs-ec2-데이터-서비스)를 따릅니다. 로컬 Compose 볼륨 삭제 명령을 AWS 호스트에 그대로 적용하지 않습니다. 기존 실행기는 이 정책만으로 데이터를 자동 삭제하지 않습니다.

장애 복구·재시작·누적 데이터 시험과 진행 중인 같은 거래의 재시도에서는 검증이 끝날 때까지 데이터를 유지합니다. 실패·미확정을 초기화로 없애 시험 통과로 처리하지 않습니다. 같은 스키마의 앱 재배포나 단순 재시작에는 초기화가 필요하지 않습니다.

## 데이터 보존과 제약 조건

아래 규칙은 **한 시험의 업무 처리와 복구**에 적용합니다. 실험 환경 전체의 초기화는 위 절차를 따릅니다.

- 구매자·판매자 계정과 상품처럼 삭제가 필요한 업무 데이터는 `deleted_at`으로 논리삭제하고 일반 조회에서 제외합니다. 삭제 상태의 접근·재등록·유니크 기준은 해당 테이블 명세에 적습니다. 구매자·판매자 계정의 로그인 식별자 유일성은 계정 종류별로 정하고 같은 이메일이라는 이유로 계정을 합치지 않습니다.
- 구매자 주소록과 주문 당시 배송지 사본은 구분합니다. 주소록 수정이 기존 주문을 덮어쓰지 않으며, 배송지의 접근·보존·삭제 기준을 명세에 적고 금융 원장 보존을 이유로 주소를 무기한 보존하지 않습니다.
- 결제·환불·정산 이력은 시험의 업무 처리 중 삭제하지 않고 상태 전이와 추가 기록으로 보존합니다. 확정 원장의 금액은 덮어쓰지 않으며 정정·상쇄 항목을 추가합니다.
- 서비스 간·같은 서비스 내부 모두 FK constraint를 두지 않습니다. 참조 유효성은 애플리케이션에서 검증하며, `NOT NULL`·`UNIQUE`·`CHECK`와 조회 인덱스는 필요한 불변식에 맞게 둡니다. FK를 생략해도 중복 방지·금액 제약은 유지합니다. 내부 참조 대조·재검토 조건은 [내부 참조 검증](data-model.md#내부-참조-대조)을 따릅니다.
- 시각 컬럼은 `timestamptz`를 사용합니다. 삭제·보존 정책을 바꾸거나 데이터를 물리적으로 제거할 때는 접근 영향·보존 범위·복구 절차를 PR에서 검토합니다.
