# 업무 정책

기본 구현에 적용할 `v1` 설계 기준입니다. 7일 환불·자동 구매확정·마일리지 반환·선착순 매진은 확정 요구사항이며, 쿠폰 기간·주문 한도·세션·배치 주기는 이를 구현하기 위한 프로젝트 기본값입니다. 실제 운영 약관이나 금융기관 계약을 대신하지 않습니다. API와 저장 구조는 [API](api.md)·[데이터 모델](data-model.md)을 따릅니다. 아직 업무 코드에 적용된 정책은 아닙니다.

## 금액과 주문

| 항목 | 기준 |
| --- | --- |
| 금액 | KRW 정수. 상품 단가 1~10,000,000원, 일반 주문 수량 1~10개, 쿠폰 적용 전 상품대금도 최대 10,000,000원. 선착순 주문 수량은 1개입니다. |
| 계산 | `G=주문 당시 단가×수량`, `D=판매자 부담 쿠폰`, `T=G−D`, `M=우리 마일리지`, `E=T−M`. `T≥1`, `0≤M≤T`, `E≥0`. 실제 외부 결제액은 `E`입니다. |
| 수수료 | `floor(T×5/100)`, 판매자 순정산액 `T−수수료`. 플랫폼 부담 마일리지 `M`을 판매자 몫에서 다시 빼지 않습니다. 주문·결제·정산에 원금액과 정책 버전을 보존합니다. |
| 결제 구성 | 외부 수단 최대 1개와 마일리지를 함께 사용할 수 있습니다. `E=0`이면 외부 수단/대역/시험 계정을 요구하거나 호출하지 않습니다. `E>0`이면 등록된 외부 수단과 시험 계정이 필요합니다. |
| 원천 | 구매자·판매자·가격·주소·쿠폰 조건은 커머스가 확정합니다. 클라이언트는 가격이나 `buyerId`를 지정하지 않습니다. 마일리지 가용액은 Payment가 검증합니다. |
| 주문 사본 | 결제 요청 뒤 가격·구성·배송지를 덮어쓰지 않습니다. 주소록 수정과 판매가 변경은 새 주문에만 적용합니다. |
| 미결제 대기 | 주문 생성 후 10분이 기본 대기 기한입니다. 기한은 취소 요청을 시작할 조건이며 예약을 즉시 해제할 조건이 아닙니다. Payment가 이후 승인을 차단한 취소를 확정해야 재고·쿠폰·마일리지를 해제합니다. 미확정 외부 결과는 기한 이후에도 조회합니다. |
| 재시도 | 확정 거절 후 같은 주문 사본의 재고·쿠폰·이벤트·마일리지 예약을 다시 확보한 경우에만 새 승인 시도를 만듭니다. 같은 주문 결제 구성은 유지합니다. 미확정 시도에 새 키/대역을 주지 않습니다. |

설명용 예: `G=10,000, D=1,000, T=9,000, M=2,000, E=7,000`. 전액 환불은 외부 7,000원 취소와 마일리지 2,000점 복원이며 수수료 450원·판매자 몫 8,550원을 상쇄합니다. 쿠폰 1,000원을 현금으로 더 돌려주지 않습니다.

## 쿠폰

| 항목 | 기준 |
| --- | --- |
| 종류·부담 | 판매자 부담 정액 프로모션 쿠폰 1장. 판매자 전체 상품 또는 지정 상품 1개에 적용합니다. 이벤트 상품에도 조건이 맞으면 쓸 수 있습니다. 중복 쿠폰·플랫폼 공동 할인은 제외합니다. |
| 발급 | 판매자가 본인 템플릿으로 지정 구매자에게 사전 발급합니다. 구매자당 템플릿별 1장, 전체 발급 한도 안에서만 발급합니다. 발급 이력은 삭제해 재발급하지 않습니다. 쿠폰 대량 선착순 발급 기능은 제외합니다. |
| 기간 | 템플릿에 `validFrom`, `validUntil`을 필수로 정합니다. `validFrom<validUntil`. 발급 시 `expiresAt=min(issuedAt+30일, validUntil)`을 저장합니다. 발급은 템플릿 유효기간 안에서만 가능하며 이미 발급한 기간은 변경하지 않습니다. |
| 사용 판단 | 서버의 주문 예약 시각이 `validFrom≤시각<expiresAt`일 때만 가능합니다. 만료 시각 정각에는 새 예약을 거절합니다. 만료 정리 작업이 늦어도 시각 검사로 차단합니다. |
| 금액 조건 | 로그인한 소유 구매자·판매자/상품·최소 상품대금·미사용 상태를 검사합니다. 최소 금액은 할인 전 `G` 기준이며 할인 후 `T≥1`이어야 합니다. 상품가격·할인액·조건 버전은 주문에 복사합니다. |
| 예약 중 만료 | 만료 전에 유효하게 예약한 주문의 조건을 보존합니다. 이미 진행 중인 결제나 미확정 결과 때문에 쿠폰을 다른 주문에 내주지 않습니다. 예약 뒤 만료됐다는 이유로 승인액을 바꾸지 않습니다. |
| 실패·미결제 취소 | 안전한 결제 종료가 확인되면 예약을 해제합니다. 아직 유효하면 다시 사용 가능하고 이미 만료됐으면 `EXPIRED`로 남깁니다. |
| 전액 환불 | 원사용을 한 번 복구합니다. 원래 만료 시각을 유지하고, 만료 후 환불이면 이력만 복구하며 재사용·기간 연장·대체 쿠폰 자동 발급은 하지 않습니다. |
| 템플릿 종료 | 새 발급만 중단합니다. 이미 발급한 쿠폰의 할인·유효기간은 보존합니다. 사용·예약 이력은 템플릿 수정이나 삭제로 지우지 않습니다. |

`ISSUED→RESERVED→USED`가 정상 흐름입니다. 확정 실패는 `RESERVED→ISSUED/EXPIRED`, 환불 복구는 `USED→ISSUED/EXPIRED`로 한 번만 전이합니다. 상태만으로 만료를 판단하지 않고 시각을 함께 검사합니다.

## 선착순 상품 이벤트

판매자는 이벤트 이름(`name`, 1~80자)을 직접 정합니다. 예: ‘주말 특가’, ‘오픈 기념 한정 판매’. 특정 행사명이나 방송에 종속되지 않습니다. 상품 1개·가격·수량·시작/종료 시각을 정하고 공개할 때 재고를 배정합니다. 같은 상품의 겹치는 공개 기간은 상품 재고 행 잠금 아래 검사합니다. 공개 후 이름·가격·수량·기간은 고정하고 조기 종료만 허용합니다.

`Q=한정 수량`, `S=누적 결제 확정 수량`, `R=대기 예약 수량`, `0≤S+R≤Q`. 선착순은 DB 예약 커밋 순서이고, 구매자당 진행 중/확정 참여는 1건입니다. 게이지는 `floor(100×S/Q)%`; 예약 마감과 100% 매진은 다른 상태입니다. `S=Q`면 종료하고 환불로 재개하지 않습니다. 기한 종료·조기 종료 후에도 기존 예약의 결과는 끝까지 확인합니다. [수량 복구 흐름](design.md#선착순-상품-이벤트)을 따릅니다.

게이지 조회 캐시 TTL과 화면 기본 조회 간격은 1초입니다. 응답에 `asOf`를 포함합니다. 캐시 장애 시 DB 조회를 제한하거나 `503`으로 재시도를 안내하며 구매 허용 판단을 캐시로 대체하지 않습니다. 이 값은 시험할 시작 설정이며 성능·최신성 달성 결과는 아닙니다.

## 마일리지와 외부 대역

우리 마일리지는 Payment 소유의 1점=1원 플랫폼 부담 잔액입니다. 시험용 사전 지급·예약·차감·전액 복원만 포함하고 충전·현금 인출·구매 적립·만료는 제외합니다. `잔액−예약 합계≥0`을 DB에서 보호합니다. 원결제별 사용/복원은 한 번뿐이며, 계정 이용 제한 중에도 반환 잔액·이력은 보존합니다.

신용/체크카드·상품권은 선택한 PG A/B/C, 간편결제는 `EASY_PAY`만 호출합니다. 상품권·간편결제의 모의 잔액은 우리 마일리지와 다릅니다. 원대역·업무 키·결과·금액을 영속 저장하고 원거래로 조회·취소합니다. 수단·PG별 처리 중/미확정/성공/거절을 구분하며 타임아웃만으로 잔액·예약을 반환하지 않습니다.

## 환불 기한과 자동 구매확정

`환불 요청 마감=Payment 결제 확정 시각+168시간`입니다. UTC 시각과 마이크로초 정밀도로 저장합니다. 커머스가 주문 행을 확보해 기록한 서버 접수 시각이 마감 이하인 요청만 받습니다. 브라우저 전송 시각은 기준이 아닙니다. 마감 이후 신규 환불은 거절하며 외부 취소·마일리지 복원·정산 예약을 실행하지 않습니다.

미발송 주문은 취소 요청을 자동 승인하고, 발송 후에는 기한 내 접수한 반품에 판매자 승인이 필요합니다. 이미 접수한 환불은 승인·외부 처리가 기한 이후에 끝나도 계속 처리합니다. 외부 환불 성공과 마일리지 복원·원장 상쇄·주문 복구를 구분하며 모두 반영되기 전에는 전체 완료로 표시하지 않습니다. 부분 환불·교환·지급 예약 후/지급 후 환불은 제외합니다.

자동 구매확정은 매분 `현재 시각>마감`인 유효 결제 완료 주문을 찾습니다. 진행 중인 취소·반품·환불이 있으면 보류하고 수동 조기 확정은 제공하지 않습니다. 환불 접수와 같은 주문의 조건부 전이·버전을 사용해 경합하며 확정 상태와 정산 가능 Outbox를 한 번만 저장합니다. 재시작 뒤에도 모든 미처리 마감 주문을 다시 찾습니다. 처리 지연으로 마감 시각을 연장하지 않습니다.

금융 환불이 거절됐다고 고객의 취소·반품 의사까지 자동 철회하지 않습니다. 실패 사유를 기록하고 주문이 계속 유효한 것으로 해당 절차가 종결된 경우에만 자동 확정을 재판정합니다. 발송 상품의 재고는 금융 환불과 별도로 판매자 반품 입고 확인 뒤 복원합니다.

## 정산·재처리

정산 기준일은 **상품 최초 등록 시각(created_at)**이며 수정·재공개로 바꾸지 않습니다. 주문과 금융 이벤트에 사본을 보존합니다. 상품별 회차 `n≥1`의 마감은 `기준일+n×14일`입니다. 스케줄은 10분마다 도래한 회차를 찾아 상품별로 배치를 만들고, `상품ID+회차+정책버전`이 같으면 기존 배치를 재개합니다. 상품별 일정이므로 한 판매자의 여러 상품 지급일은 서로 다를 수 있습니다.

마감보다 앞서 자동 구매확정과 선행 결제 원장이 모두 수신·반영된 미환불·미예약 거래만 해당 회차에 배정합니다. `eligibleReceivedAt`은 두 선행 정보가 모두 준비된 시각이며 `max(자동확정시각, eligibleReceivedAt)`보다 엄격히 뒤인 첫 마감을 `scheduledCutoffAt`으로 저장합니다. 마감 정각의 확정·늦은 이벤트는 다음 회차로 넘기고, 발생일 하한으로 누락시키거나 완료된 배치에 뒤늦게 끼워 넣지 않습니다.

예: 등록 11월 1일 10:00 → 마감 11월 15일·29일 10:00. 등록 13일째 결제는 환불 기간 7일이 남아 첫 마감에서 제외되고 다음 회차로 갑니다. 따라서 ‘상품 기준 14일 주기’는 ‘모든 거래의 결제일 D+14 보장’과 다릅니다. 배치 금액은 선점한 거래의 순액 합계이고 지급 가능 자금은 외부 대역에서 따로 확보합니다. 자금 부족·외부 미확정은 해당 배치의 보류 사유로 남기며 다음 회차에 중복 배정하지 않습니다. 예정 마감과 실제 지급 성공 시각을 구분합니다. `succeededAt`은 원대역의 최초 성공 시각을 한 번 저장한 값이며 미성공/미확정이면 null입니다.

지급 생성 전 커머스의 서비스 인증 컨텍스트에서 상품/판매자 일치·판매자 상태·수취 시험계정·버전을 검증합니다. 수취 계정과 출금 시험계정은 지급 레코드에 사본으로 저장하고, 프로필/설정 변경 뒤에도 기존 지급의 재조회·재시도에서는 바꾸지 않습니다. 환불 예약은 구매확정 전 WAITING_CONFIRMATION과 구매확정 후 PAYABLE 모두에서 가능하며, 지급 예약은 PAYABLE에서만 가능합니다. 예약은 원상태를 기록하고 보상 시 최신 상태와 대조해 복귀합니다.

일시적 실패는 최대 10회, 1초부터 지수 증가해 최대 60초 간격으로 재시도합니다. 이후 작업은 `REVIEW_REQUIRED`로 보존하고 운영 확인 대상으로 표시합니다. 미확정 금융 작업은 실패/예약 해제로 바꾸지 않고 5분마다 같은 원거래 조회·대조를 계속합니다. 메시지 자동 재시도 초과는 DLT로 넘기되 영속 작업과 상태를 잃지 않습니다. 운영 재처리는 원래 업무 키를 유지하고 실행 주체·사유를 기록합니다.

승인 작업은 외부 호출 전에 Payment 상태를 `PROCESSING`으로 원자 전이합니다. 미결제 취소는 아직 외부 호출을 시작하지 않은 결제만 `CANCELLED`로 전이하고 작업을 차단할 수 있습니다. 처리 중/미확정이면 예약을 유지하고 결과를 조회합니다. 요청 순서 역전으로 취소가 먼저 오면 불변 주문 컨텍스트를 확인해 취소 상태를 먼저 저장하며, 늦은 결제 요청이 이를 다시 활성화하지 않습니다. 재시도 회차(`paymentCycleId`)가 다른 오래된 실패·취소 이벤트로 새 예약을 해제하지 않습니다.

## 인증·공통 API 기준

첫 구현은 **DB에 해시를 저장하는 불투명 Bearer 세션**으로 정합니다. 구매자/판매자 로그인 경로와 계정 종류를 구분하고, 256비트 이상 임의 토큰 원문은 발급 때만 반환합니다. 세션은 고정 30분이며 재로그인이 필요합니다. 로그아웃·계정 정지는 DB에서 즉시 차단하고 인증 저장소 장애 시 보호 요청을 허용하지 않습니다. 금융 쓰기에는 오래된 긍정 인증 캐시를 사용하지 않습니다. 서비스 간 신원은 개별 서비스 자격으로 확인하며 Gateway에 내부·Mock API를 공개하지 않습니다.

비밀번호는 12~128자로 받고 Argon2id와 사용자별 salt를 사용합니다. 시작 설정은 메모리 19MiB·반복 2·병렬 1이며 대상 환경에서 로그인 부하를 검증합니다. [OWASP 비밀번호 저장 기준](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)을 참고합니다. 비밀번호 재설정 토큰은 별도 목적·10분·일회용이며 세션 토큰으로 쓸 수 없습니다. 계정 존재 여부와 무관하게 요청 응답은 같고, 등록된 수신 경로에만 전달합니다.

역할 불일치는 `403`, 같은 역할의 타인 소유 리소스는 `404`로 처리합니다. 목록은 `page≥0`, `1≤size≤100`·기본 20, 정렬은 `createdAt DESC, id DESC`입니다. 목록 응답은 `items/page/size/totalElements/totalPages`를 사용합니다. 상태 변경에는 `expectedVersion`을 검증하고 충돌은 `409`입니다.

멱등키는 8~128자이며 계정 종류·ID·작업에 묶습니다. 같은 키와 정규화한 같은 요청은 기존 리소스로 연결하고 본문이 다르면 `409`입니다. 금융·주문 키는 해당 거래 이력과 함께 보존하며 일반 관리 작업의 키는 24시간 보존합니다. 키 만료로 도메인 중복 제약을 없애지 않습니다. 비밀번호·토큰·멱등키 원문·실결제 비밀값은 로그에 남기지 않습니다.

## 거래 알림

구매자·판매자에게 필요한 거래 결과는 카카오 알림톡 형식으로 안내합니다. 첫 구현은 `MOCK_KAKAO` 채널로 **모의 발송 기록만 저장**하며 실제 카카오·문자·전화번호를 사용하지 않습니다. 수신처는 계정 종류와 ID에서 만든 `mock:<BUYER|SELLER>:<UUID>`입니다. 구매자·판매자 알림을 합치지 않으며, 거래 내역은 원래 주문·결제·정산 API에서도 확인합니다.

### 대상과 발송 시점

| 종류 | 수신자 | 발송 조건·내용 |
| --- | --- | --- |
| `PAYMENT_COMPLETED` | 구매자 | 외부 승인과 마일리지 차감 확정 뒤 주문 반영 확인. 외부 결제액·사용 마일리지·차감 직후 잔액 |
| `SHIPMENT_STARTED` | 구매자 | 판매자의 발송 처리 저장. 택배사 배송 완료를 추정하지 않음 |
| `PURCHASE_CONFIRMED` | 구매자 | 환불 기한 후 자동 구매확정 저장 |
| `CANCELLATION_COMPLETED` | 구매자·판매자 | 미결제 주문 취소 확정. 결제한 주문의 취소는 환불 결과로 안내 |
| `RETURN_REQUESTED` | 구매자·판매자 | 기한 내 취소·반품 요청 접수. 구매자는 접수 확인, 판매자는 승인 필요 여부 확인 |
| `RETURN_DECIDED` | 구매자 | 판매자의 반품 승인·거절 저장. 승인을 환불 완료로 안내하지 않음 |
| `REFUND_COMPLETED` | 구매자·판매자 | 원외부 결제액 환불·마일리지 복원·원장 상쇄·주문 복구 완료. 구매자에게 복원액·복원 직후 잔액 안내 |
| `REFUND_ACTION_REQUIRED` | 구매자·판매자 | 금융 환불 확정 실패가 주문에 반영됨. 미환불 상태와 문의 경로 안내; 미확정을 확정 실패로 바꾸지 않음 |
| `SALE_COMPLETED` | 판매자 | 주문의 결제 확정 반영. 판매자별 1분 동안 받은 판매를 묶어 건수·주문 결제액 합계 안내 |
| `SETTLEMENT_READY` | 판매자 | 회차 대상 예약·금액 확정. 회차·마감·정산액과 지급 처리 중임을 안내 |
| `PAYOUT_COMPLETED` | 판매자 | 원지급 `SUCCEEDED` 확인. 실제 지급액·원대역의 최초 성공 시각 안내 |
| `PAYOUT_ACTION_REQUIRED` | 판매자 | 확정 거절 또는 지급 재원 부족으로 보류. 확인 경로 안내 |

마일리지 잔액은 Payment가 원장 변경과 같은 트랜잭션에서 저장한 **해당 처리 직후 값과 walletVersion**입니다. 늦은 알림의 잔액을 현재 잔액으로 표시하지 않습니다. 마일리지 미사용 결제에는 잔액 안내를 생략할 수 있고 구매 적립 알림은 만들지 않습니다. 요청 철회·운영 종결 결과는 기존 요청 조회에 남기며 완료되지 않은 환불을 성공으로 알리지 않습니다.

### 소유권과 복구

- 커머스 `seller`가 알림 이력·묶음·발송을 소유합니다. 로컬 주문 전이는 상태와 알림 항목을 같은 DB 트랜잭션으로 저장합니다. Payment·Settlement는 자기 상태와 알림 요청 Outbox를 함께 저장합니다. 커머스의 `seller-notifications.v1` 소비자는 Inbox와 알림 항목을 저장한 뒤 ack합니다. 금융 거래를 발송과 묶어 롤백하지 않습니다.
- Payment는 DEBIT/RESTORE와 같은 트랜잭션에서 알림 요청 Outbox에 원거래 ID·결제 회차·금액·처리 직후 잔액/지갑 버전 사본을 저장합니다. 마일리지 미사용이면 결제/외부 환불 확정 트랜잭션에서 잔액·지갑 버전을 함께 null로 저장합니다. `REFUND_COMPLETED`는 복원 때 발송을 준비하는 종류 이름이며 실제 안내는 아래 주문 복구 확인까지 대기합니다. 주문/회차가 아직 연결되지 않았으면 Inbox의 원본 payload·다음 실행 시각을 보존해 기다립니다. 결제 알림은 해당 회차의 확정 반영, 환불 알림은 해당 환불의 주문 복구를 확인한 뒤 생성합니다. 뒤에 반품·구매확정이 진행됐다는 이유만으로 앞선 확정 사실을 누락하지 않습니다.
- 같은 `sourceService + kind + businessRef + recipientKind + recipientId`는 한 알림 항목입니다. 판매 묶음은 **접수 시각**의 UTC 1분 구간으로 모으고 종료 때 건수·합계·본문을 고정합니다. 늦은 이벤트는 새 열린 구간에 넣고 닫힌 묶음을 수정하지 않습니다. 다른 종류는 항목 하나당 발송 하나입니다. 판매 합계는 순매출·정산액이 아니며 환불은 따로 안내합니다.
- 발송 작업은 1초마다 도래 건을 임대합니다. 임대 30초·호출 제한 5초가 기본값이며 leaseToken·버전으로 결과 반영 주체를 검사합니다. 응답 유실·임대 만료는 `UNKNOWN`으로 두고 원래 deliveryId로 모의 수신 기록을 조회합니다. 기록이 없을 때만 같은 키·본문으로 재요청합니다. 수신부의 `UNIQUE(delivery_id)`와 본문 해시로 중복·같은 키 다른 본문을 차단합니다.
- 일시적 오류는 1초부터 최대 60초 간격으로 지수 재시도하고 조회·발송을 합쳐 한 라운드 최대 10회입니다. 확정 거절·본문 충돌·상한 초과는 `REVIEW_REQUIRED`로 보존합니다. 운영 재처리는 원키·수신자·본문을 유지해 새 라운드만 열고 실행자·사유를 남깁니다. `SENT`와 유효 임대 중인 작업의 재처리는 409입니다.
- `SENT`는 모의 수신 기록 확인이며 실제 카카오 전달·읽음을 뜻하지 않습니다. 실패해도 주문·환불·마일리지·지급 상태를 바꾸지 않습니다. 발송 순서 역전을 허용하되 거래 발생 시각을 표시합니다. 주소·전화번호·토큰을 이벤트·Slack에 싣지 않습니다.

실제 알림톡 전환은 비즈니스 채널·공식 딜러 연동, 사용 가능한 공용/승인 템플릿, 수신처 검증과 개인정보 처리를 갖춘 별도 구현입니다. [카카오 공식 안내](https://kakaobusiness.gitbook.io/main/ad/infotalk)를 따릅니다.

## 운영 알람

조치가 필요한 장애는 `Prometheus → Alertmanager → Slack`으로 전달하도록 설계합니다. Grafana는 원인 확인에 사용하고 알람 규칙은 Prometheus에서 관리합니다. **현재 Compose에는 Alertmanager·자원 수집기·Slack 연결·아래 업무 지표가 없습니다.** 다음은 구현·시험할 초기 기준입니다.

| 조건 | 초기 기준 | 등급·조치 |
| --- | --- | --- |
| 금융 미확정 | 결제·환불·지급 `UNKNOWN` 최장 나이 5분/15분 초과 | WARNING/CRITICAL. 원거래 조회·대조; 새 금융 거래 금지 |
| 환불 지연 | 미완료 환불 최장 나이 10분/30분 초과 | WARNING/CRITICAL. 외부 환불·복원·원장·주문 단계 확인 |
| 지급 지연 | 확정 배치가 회차 마감 후 30분/60분 동안 미지급 | WARNING/CRITICAL. 정상적인 다음 회차 이월 제외 |
| 수동 확인·재원 부족 | 새 `REVIEW_REQUIRED`, 신규 DLT, 지급 재원 부족 | CRITICAL. 원업무·재처리 사유 확인 |
| 작업 적체 | 미발행 Outbox·미처리 Inbox·실행 작업 최장 나이 5분/15분 초과 | WARNING/CRITICAL. Kafka lag·소비율·작업자 확인 |
| 알림 지연 | 준비된 발송 최장 대기 5분/15분 초과, 새 발송 수동 확인 건 | WARNING/CRITICAL. 원수신 기록 조회·재처리 |
| 서비스 장애 | 수집 대상 `up=0` 1분, OOM/컨테이너 비정상 종료 | CRITICAL. 기동·메모리·의존 서비스 확인 |
| HTTP 장애 | 5분간 요청 100건 이상에서 5xx 비율 5% 초과가 5분 지속 | WARNING. 서비스·경로 템플릿별 오류·trace 확인 |
| 자원 부족 | 메모리 제한 90% 초과 5분, 디스크 가용 10% 미만 5분, CPU 할당량 90% 초과 10분 | WARNING. 부하 중단·자원 조정 판단; 여유 메모리 5% 미만/OOM은 CRITICAL |

최장 나이·상태별 건수는 각 소유 서비스가 DB에서 계산해 `/actuator/prometheus`로 노출할 계획입니다. 계정/주문 ID를 메트릭 label로 사용하지 않습니다. 무작업이면 나이·건수는 0이며 정상 대기·완료 건을 적체에서 제외합니다. Kafka lag는 메시지 수, 대기 나이는 초 단위입니다.

Alertmanager는 환경·서비스·알람 이름으로 묶고 최초 30초 대기·그룹 갱신 5분·반복 1시간을 기본으로 합니다. 같은 장애의 CRITICAL이 WARNING을 억제하고 복구도 안내합니다. Slack에는 등급·발생/지속 시각·영향·대시보드/조치 문서 링크를 보내고 개인정보·알림 본문·비밀값은 보내지 않습니다. 부하 시험 채널은 운영 채널과 분리합니다. [Alertmanager의 묶음·중복 억제](https://prometheus.io/docs/alerting/latest/alertmanager/)를 사용합니다.

서버·컨테이너 자원은 별도 수집이 필요합니다. Linux 배포 호스트는 node_exporter, 컨테이너는 cAdvisor를 후보로 둡니다. Docker Desktop의 Linux VM·컨테이너 지표로 Mac 전체 상태를 판단하지 않습니다. 같은 호스트의 모니터링도 전체 호스트 중단 때 멈출 수 있으므로 운영 배포 때 외부 생존 확인을 검토합니다.

## 보존과 삭제

계정 종류별 정규화 이메일은 논리삭제 뒤에도 유일성을 보존하며 자동 재가입·기존 계정 연결은 하지 않습니다. 주소록·상품은 논리삭제합니다. 주문 주소 사본은 거래 종료 뒤 90일을 기본 마스킹 시점으로 정하되 진행 중인 반품·분쟁·보존 보류가 있으면 보류합니다. 처리/보류 이력을 남기고 주소를 금융 이벤트로 보내지 않습니다. 금융 금액·정산·마일리지 원장·쿠폰 사용 이력과 주요 행위의 audit_logs는 자동 삭제하지 않습니다. 알림 본문·항목·시도·모의 수신 기록은 거래 종료 후 90일을 기본 보존 기간으로 하며 보존 보류 중에는 삭제하지 않습니다. delivery가 살아 있는 동안 모의 수신 멱등 기록을 먼저 지우지 않고 재처리 기한도 같은 보존 기간으로 제한합니다. 이는 시험 데이터 정책이며 상용 보존 기간의 적법성을 검증했다는 뜻은 아닙니다.

## 경계 검증
