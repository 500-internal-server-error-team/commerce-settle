# 업무 정책

구현할 업무의 설계 기준입니다. 배송완료 후 7일 환불·일일 자동지급·모의 선지급·자동 구매확정·마일리지 반환·선착순 매진은 확정 요구사항이며, 쿠폰 기간·주문 한도·세션·배치 주기는 이를 구현하기 위한 프로젝트 기본값입니다. 실제 운영 약관이나 금융기관 계약을 대신하지 않습니다. API와 저장 구조는 [API](api.md)·[데이터 모델](data-model.md)을 따릅니다. 현재 제공 기능과 정책의 적용 범위는 [API 공통 계약](api.md#공통-계약)에서 확인하며, 명세의 존재를 전체 업무 구현·검증의 완료로 간주하지 않습니다.

## 금액과 주문

| 항목 | 기준 |
| --- | --- |
| 금액 | KRW 정수. 상품 단가 1~10,000,000원, 일반 주문 수량 1~10개, 쿠폰 적용 전 상품대금도 최대 10,000,000원. 선착순 주문 수량은 1개입니다. |
| 계산 | `G=주문 당시 단가×수량`, `S=판매자 쿠폰`, `P=플랫폼 쿠폰`, `B=G−S`, `T=B−P`, `M=우리 마일리지`, `E=T−M`. `T≥1`, `0≤M≤T`, `E≥0`. 쿠폰 사용 시 `M=0`, `S`와 `P` 중 최대 하나만 양수입니다. |
| 수수료 | `F=floor(B×15/100)`, 판매자 순정산액 `N=B−F`. PG·부가세 포함 총수수료이며 별도 PG 차감은 없습니다. `E+M+P=B=N+F`를 각 원장 측에서 보존합니다. P·M을 판매자 몫에서 다시 빼지 않고 주문 당시 원금액·요율을 보존합니다. |
| 결제 구성 | 외부 수단 최대 1개와 마일리지를 함께 사용할 수 있습니다. 쿠폰이 있으면 마일리지 사용은 금지하고 승인한 카드·간편결제만 선택합니다. `E=0`이면 외부 수단/대역/시험 계정을 요구하거나 호출하지 않습니다. `E>0`이면 등록된 외부 수단과 시험 계정이 필요합니다. |
| 원천 | 구매자·판매자·가격·주소·쿠폰 조건은 커머스가 확정합니다. 클라이언트는 가격이나 `buyerId`를 지정하지 않습니다. 마일리지 가용액은 Payment가 검증합니다. |
| 주문 사본 | 결제 요청 뒤 가격·구성·배송지를 덮어쓰지 않습니다. 주소록 수정과 판매가 변경은 새 주문에만 적용합니다. |
| 기본 배송지 | 구매자당 최대 한 개입니다. 첫 주소는 요청과 관계없이 기본이 되고, 다른 주소를 기본으로 지정하면 기존 기본을 같은 트랜잭션에서 해제합니다. 기본 주소에 해제만 요청해도 기본으로 남습니다. 기본 주소를 삭제하면 남은 주소에 기본을 넘기지 않으며 주문서에서 배송지를 고릅니다. 목록은 기본 주소 다음 최신순입니다. |
| 미결제 대기 | 주문 생성 후 10분이 기본 대기 기한입니다. 기한은 취소 요청을 시작할 조건이며 예약을 즉시 해제할 조건이 아닙니다. Payment가 이후 승인을 차단한 취소를 확정해야 재고·쿠폰·마일리지를 해제합니다. 미확정 외부 결과는 기한 이후에도 조회합니다. |
| 재시도 | 확정 거절 후 같은 주문 사본의 재고·이벤트·마일리지 예약을 다시 확보한 경우에만 새 승인 시도를 만듭니다. 쿠폰 예약은 거절 뒤에도 유지하므로 만료 전에 예약한 조건으로 다시 시도합니다. 같은 주문 결제 구성은 유지합니다. 미확정 시도에 새 키/대역을 주지 않습니다. |

설명용 예: `G=23,000, S=0, P=3,000, B=23,000, T=E=20,000, M=0, F=3,450, N=19,550`. 전액 환불은 외부 20,000원 취소와 원장 E·P/N·F의 상쇄입니다. 쿠폰 3,000원을 고객에게 현금으로 더 돌려주지 않습니다. 쿠폰 없는 `G=B=T=10,000, M=2,000, E=8,000` 주문은 수수료 1,500원·판매자 몫 8,500원이며 외부 8,000원 취소와 마일리지 2,000점 복원으로 처리합니다.

플랫폼 쿠폰액 P는 PG 수납액이 아니라 플랫폼의 기존 자금으로 보전합니다. 선지급 재원은 플랫폼 지원분까지 항상 충분하다고 가정하며 시험 전에 모의 현금을 준비합니다. 발급 예산과 현금 기록은 따로 관리하고 원장에 P를 적은 것만으로 현금이 생겼다고 보지 않습니다.

상품권은 약 9%의 PG 수수료를 사업 가정으로 두면 기존 쿠폰·구독 할인과 함께 손익 목표를 유지하기 어려워 초기 결제 범위에서 제외합니다. 쿠폰 유무와 관계없이 상품권 결제 자체를 지원하지 않습니다. 9%는 이번 범위 결정에 사용한 가정이며 모든 PG·상품권의 공통 계약 요율을 뜻하지 않습니다.

## 재고 예약과 복원

주문 생성은 상품 수량을 예약하고, 결제 결과와 환불·반품 입고에 따라 같은 예약을 확정·해제·복원합니다. 예약·확정·해제·복원은 주문 상태·Outbox와 같은 커머스 DB 트랜잭션으로 저장합니다. 상태와 저장 구조는 [inventory_reservations](data-model.md#inventory_reservations)를 따릅니다.

| 작업 | 일반 주문 (수량 q) | 선착순 주문 (수량 1) |
| --- | --- | --- |
| 예약 | 가용 −q, 예약 +q | 이벤트 `R+1`. `S+R<Q`이고 신청 가능 상태일 때만 |
| 결제 확정 | 예약 −q, 판매 +q | `R−1`, `S+1`, 배정 재고 −1, 판매 +1 |
| 확정 거절·승인 차단된 취소 | 예약 −q, 가용 +q | `R−1`. 이벤트가 종료됐으면 풀린 배정분 1개를 가용 재고로 반환 |
| 환불 복구·반품 입고 | 판매 −q, 가용 +q | 판매 −1, 가용 +1. `S`와 게이지는 되돌리지 않음 |

- **판매 수량은 순판매량입니다.** `sold_qty`는 확정 판매에서 환불·반품으로 복원한 수량을 뺀 값입니다. 누적 판매량은 `inventory_movements`에서 `operation='ORDER_CONSUME'`이고 `sold_delta>0`인 수량을 합산해 계산합니다. `REFUND_RESTORE`·`RETURN_RESTORE` 행은 이 누적 판매량에서 제외하며, 선착순 게이지의 `S`와도 구분합니다.
- **예약은 수량만 검사합니다.** 예약 처리는 가용 재고, 또는 이벤트의 남은 수량과 참여 한도만 판단합니다. 상품 조건은 [주문 생성의 상품 확인](#주문-생성의-상품-확인)에서 검사합니다.
- **결제 회차가 일치할 때만 반영합니다.** 예약은 현재 결제 회차를 기록합니다. 확정·해제는 수신한 결과의 회차가 같을 때만 적용하고, 이전 회차의 늦은 결과는 상태를 바꾸지 않습니다. 확정 거절 뒤 재시도는 같은 예약을 새 회차로 다시 확보하며, 확보하지 못하면 `409`로 거절하고 주문은 거절 상태를 유지합니다.
- **기한만으로 해제하지 않습니다.** 예약의 `expires_at`은 주문의 미결제 대기 기한과 같은 값입니다. 취소 작업은 `payment_wait_until`이 지난 `PAYMENT_PENDING` 또는 재시도 대기 중인 `DECLINED` 주문을 찾는 데만 사용하고, 주문 상태를 조건부로 `CANCEL_PENDING`으로 바꿔 취소 요청을 시작합니다. 이미 결제됐거나 취소·환불 등 다른 상태로 진행한 주문은 대상에서 제외합니다. `CANCEL_PENDING`은 예약 해제를 뜻하지 않습니다. Payment가 해당 결제 회차의 승인을 차단했음을 확정한 뒤에만 재고·쿠폰·마일리지 예약을 해제합니다. 기한 경과나 취소 요청 응답 유실만으로 해제하지 않습니다.
- **미발송 주문은 환불 복구에서 복원합니다.** 원장 상쇄 뒤 전달되는 주문 복구 요청을 처리할 때 주문·쿠폰 복구와 함께 재고를 복원합니다.
- **발송 주문은 재판매 가능 상태로 검수한 반품을 입고 즉시 복원합니다.** 판매자가 반품을 승인한 요청에 상품이 실제로 도착하고 재판매 가능한 상태임을 검수해 입고를 확정하면, 금융 환불의 진행·결과와 관계없이 그 트랜잭션에서 재고를 복원합니다. 검수에서 재판매 불가로 판정한 상품은 가용 재고에 더하지 않습니다. 금융 환불이 거절·보류돼도 이미 복원한 재고를 다시 줄이지 않으며, 금융 환불 완료만으로 발송 상품을 재입고하지 않습니다.
- 예약당 복원은 한 번입니다. 같은 이벤트의 재전달이나 같은 요청의 재처리는 기존 결과를 확인하고 수량을 다시 바꾸지 않습니다.

### 주문 생성의 상품 확인

판매 상태·삭제 여부·가격·`expectedProductVersion`은 주문 생성 응용 서비스가 상품 도메인 규칙으로 검사합니다. 검증과 재고·쿠폰·이벤트 예약, 주문·Outbox·멱등 기록 저장은 같은 트랜잭션에 둡니다. 잠금 대기는 설정된 상한 안에서 끝내며 시간 초과 시 전체 트랜잭션을 롤백합니다.

- **일반 주문은 재고 행 잠금으로 판매자 변경과 직렬화합니다.** 주문 생성 트랜잭션은 `product_inventory` 행을 배타 잠금(`FOR UPDATE`)으로 먼저 확보한 뒤 상품 행을 읽어 판매 가능 여부와 요청 버전을 확인하고 가격 사본을 고정합니다. 상품 행에는 공유 잠금을 걸지 않습니다. 상품 조회는 잠금 확보 뒤에 하며, 같은 트랜잭션에서 그 전에 읽은 상품 값을 재사용하지 않습니다. 재고 쪽은 재고 행 잠금과 상품 조회를 하나의 메서드로 제공합니다. 이 메서드는 호출한 주문 생성 트랜잭션에 참여하고(`Propagation.MANDATORY`) 트랜잭션 밖 호출은 거절하며, 따로 커밋하지 않습니다. 따라서 잠금은 주문·예약·Outbox·멱등 기록 저장이 커밋되거나 롤백될 때까지 유지됩니다.
- **판매자의 상품 변경도 같은 재고 행을 먼저 잠급니다.** 상품 이름·가격·상태 변경과 논리삭제는 `product_inventory` 행을 배타 잠금으로 확보한 뒤 상품 버전을 검사하고 갱신합니다. 판매자 변경이 먼저 커밋되면 주문은 새 상태·버전을 기준으로 거절하고, 주문이 먼저 잠그면 판매자 변경은 주문 트랜잭션이 끝난 뒤 적용됩니다.
- **선착순 주문은 상품·재고 행을 잠그지 않습니다.** 이벤트 가격·수량은 공개 때 고정한 사본을 쓰고, 이벤트 기간에는 [상품 변경을 막으므로](#선착순-상품-이벤트) 상품 행을 잠금 없이 읽어 확인합니다. 수량은 `sale_events`의 조건부 갱신 한 번으로 예약합니다.

## 쿠폰

### 종류와 책임

쿠폰은 발급 목적과 비용 부담에 따라 아래 세 종류로 구분합니다. `GRADE`의 등급은 선정자의 할인액을 정하며, 세 종류는 발급·예약·환불 처리를 공유합니다.

| 종류 | 목적·발급 조건 | 비용 부담 | 적용 범위·초기 조건 |
| --- | --- | --- | --- |
| `WELCOME` 웰컴 | 신규 가입 혜택. 가입 때 한 장 발급하고 계정당 한 번의 유효 사용만 허용 | 플랫폼 | 가입 후 14일 이내, 상품대금 20,000원 이상에 3,000원 할인 |
| `GRADE` 월간 우수고객 | 플랫폼 전체의 전월 구매 실적 상위 100위와 동점자에게 월 한 장 발급 | 플랫폼 | 브론즈 3,000원/50,000원 이상, 실버 5,000원/70,000원 이상, 골드 7,000원/90,000원 이상 |
| `SELLER` 판매자 | 판매자가 대상 구매자·기간·발급 수·할인 예산을 정해 발급 | 해당 판매자 | 해당 판매자의 전체 상품 또는 지정 상품 하나. 할인 후 상품대금이 20,000원 이상인 조건으로 설정 |

웰컴은 **가입 후 14일 안에 예약할 수 있는 한 번의 가입 혜택**으로 정의합니다. 쿠폰 없이 먼저 결제했어도 남은 기간 안에 사용할 수 있으므로 `첫 결제 한정`으로 안내하지 않습니다. 엄격한 첫 결제 제한은 동시 주문의 PG 승인 순서까지 묶어야 하고 실수로 쿠폰을 놓친 고객을 배제하므로 채택하지 않습니다. 미결제 취소·전액 환불의 원쿠폰 복구는 새 발급이나 두 번째 혜택 생성이 아닙니다.

커머스가 발급·대상·예약·할인 비용 이력을 소유하고, Payment가 실제 결제 결과를, Settlement가 정산·환불 상쇄를 소유합니다. 플랫폼 쿠폰은 서버의 정해진 혜택 규칙으로 자동 발급하며 운영자 승인·재승인 절차를 두지 않습니다. 판매자는 자기 캠페인만 생성하고 구매자·판매자 API로 플랫폼 할인액·등급·부담자를 지정할 수 없습니다.

판매자 쿠폰은 월 배치나 구매 순위와 무관합니다. 판매자가 자기 템플릿으로 등록된 구매자에게 발급하며, 캠페인별로 같은 구매자에게 한 장만 발급합니다. 공통 100장 상한·판매자별 월 1캠페인·구매자별 월 1장 제한은 두지 않습니다. 판매자가 정한 발급 수와 할인 예산은 원자적으로 차감하고, 신규 발급·사용은 템플릿의 시작 이상·종료 미만 시각에만 허용합니다. 발급된 쿠폰의 만료는 해당 종료 시각으로 고정합니다. 같은 캠페인의 중복 발급, 발급 종료·발급 기간 밖의 요청, 발급 수·예산 소진은 다시 시도해도 성공하지 않는 거절로 서로 구분해 각각 `COUPON_ALREADY_ISSUED`·`COUPON_CAMPAIGN_NOT_ISSUABLE`·`COUPON_BUDGET_EXHAUSTED`로 응답하며, 응답 계약은 [API 오류 코드](api.md#오류와-완료-기준)를 따릅니다.

### 사용 조건

단일 판매자·단일 상품 주문을 유지합니다. 여러 쿠폰을 보유해도 주문에는 한 장만 사용하고 웰컴·월간 우수고객·판매자 쿠폰을 겹치지 않습니다. 선착순 이벤트 주문에도 쿠폰 한 장을 쓸 수 있으며, 아래처럼 최소 주문금액은 이벤트 가격으로 판단합니다. 쿠폰과 우리 마일리지의 동시 사용은 금지하며, 쿠폰 없는 마일리지 결제는 별도 재원 정책을 따릅니다. 구매 적립 3%는 도입하지 않습니다.

배송비 0원인 현재 시험 범위를 유지합니다. `G`는 상품/이벤트 가격을 반영한 단가×수량이며, 최소 주문금액은 해당 쿠폰 적용 전 `G`로 판단합니다. 배송비를 합쳐 조건을 채우지 않습니다. SELLER의 최소 주문금액은 `G−할인액≥20,000`도 충족하도록 설정합니다. 할인액은 양의 정수이고 할인 후 구매자 부담액은 1원 이상입니다.

### 비용과 손익 기준

15%는 판매자에게 부과하는 **PG·부가세 포함 총액**입니다. 부가세나 PG 3.4%를 판매자에게 다시 더하지 않습니다. 실제 판매자 원가·배송비·수용 가능 수수료는 미확인입니다. `N−매입원가−판매자 배송비−기타 비용`이 판매자 이익이므로 N을 이익이라고 안내하지 않습니다. 판매자 할인 예산과 최소 허용 정산액을 승인받고, 완료된 거래를 현재 요율로 다시 계산하지 않습니다.

2026-10-26 확인한 [토스페이먼츠 공개 요금](https://www.tosspayments.com/about/fee)은 일반 카드·간편결제 3.4%·VAT 별도이며 일부 간편결제는 추가 비용이 있습니다. API 조회 횟수당 3.4%가 아니라 실제 결제금액에 대한 요율입니다. 상품권은 위의 초기 지원 범위에서 제외합니다.

비교 모델은 다음처럼 비용을 보수적으로 잡습니다. 이것은 금융기관 청구·세금 신고 계산식이 아닙니다.

- 수수료 순수입 추정 `R=floor(F×10/11)`: 총수수료에서 부가세 상당액을 제외한 비교값.
- PG 비용 상한 `C=ceil(E×400/10,000)`: VAT·부가 비용을 포함해 4% 이하인 계약·수단에만 적용하는 시험 가정. 4%를 실제 계약 요율이라고 안내하지 않습니다. PG 매입세액 공제 효과는 계산하지 않습니다.
- 기타 변동비 충당액 `O=1,000원/주문`: 지원·지급·환불 기대비용을 위한 미검증 가정. 실제 원가·광고비·고정비·차지백 손실을 전부 포함한 값은 아닙니다.
- 쿠폰 주문의 보수적 잔여액 `H=R−P−C−O`. 쿠폰과 마일리지를 함께 쓸 수 없으므로 여기서는 M=0입니다. SELLER 할인은 이미 B에 반영되므로 P처럼 다시 빼지 않습니다.

| 조건·최소 상품대금 G | 고객 결제 E | 수수료 순수입 추정 R | 플랫폼 쿠폰 P | PG 상한 C | 충당액 O | 잔여액 H |
| --- | --- | --- | --- | --- | --- | --- |
| 웰컴 3,000원 / 20,000원 | 17,000 | 2,727 | 3,000 | 680 | 1,000 | **−1,953** |
| 웰컴 5,000원 / 20,000원: 보류 후보 | 15,000 | 2,727 | 5,000 | 600 | 1,000 | **−3,873** |
| 웰컴 5,000원 / 40,000원: 비교 후보 | 35,000 | 5,454 | 5,000 | 1,400 | 1,000 | **−1,946** |
| 등급 3,000원 / 50,000원 | 47,000 | 6,818 | 3,000 | 1,880 | 1,000 | **938** |
| 등급 5,000원 / 70,000원 | 65,000 | 9,545 | 5,000 | 2,600 | 1,000 | **945** |
| 등급 7,000원 / 90,000원 | 83,000 | 12,272 | 7,000 | 3,320 | 1,000 | **952** |
| 판매자 3,000원 / 23,000원 | 20,000 | 2,727 | 0 | 800 | 1,000 | **927** |

웰컴은 위 가정에서 주문당 모델 손실 2,000원 이내를 목표로 하는 고객 확보 실험으로 택합니다. 같은 20,000원 조건의 5,000원 할인은 이 기준을 넘으므로 기본값에서 제외합니다. 40,000원에 5,000원 할인도 기준을 만족하지만 구매 문턱이 높아집니다. 낮은 최소 주문금액으로 시작하는 기본 할인은 3,000원이며, 실제 객단가·전환율을 확보하면 40,000원 이상 5,000원 할인과 비교합니다.

등급·판매자 쿠폰은 최소 주문금액에서도 `H≥500원`을 남기는 조건을 사용합니다. 등급 3,000원을 40,000원부터 주면 H=−26원이고, 5,000원을 50,000원부터 주면 H=−982원이므로 이 조건은 제외합니다. 500원은 고정비·광고비 차감 후 순이익 보장이 아니며 웰컴 모델 손실도 취소 반복·차지백을 포함한 실제 최대 손실을 보장하지 않습니다.

이 기준은 서버 혜택 규칙과 판매자 캠페인 등록 시 검증합니다. 이미 발급한 쿠폰을 사용하는 시점에 바뀐 손익 목표로 거절하거나 할인액을 줄이지 않습니다. 쿠폰 세 종류 모두 총 PG 비용이 4% 이하인 카드·간편결제 수단에 한정하고, 사용 가능 수단을 발급 때 고정·안내합니다. 현재 지원하는 신용카드·체크카드와 `EASY_PAY` 대역은 위 공개 요금 기준 3.4%에 부가세를 더해도 이 상한 안에 있다고 보고 웰컴·월간 우수고객 쿠폰에 모두 허용하며, 판매자 쿠폰은 판매자가 이 중에서 고릅니다. 4%를 넘는 수단을 지원하려면 쿠폰 사용과 주문 지원 여부를 먼저 정하며, 쿠폰 템플릿과 발급 쿠폰의 허용 수단은 DB 제약으로 이 세 값으로 막습니다. 판매자 부담 쿠폰도 PG 비용은 플랫폼이 부담하므로 예외가 아닙니다. 지원하지 않는 수단은 쿠폰 없는 주문에서도 거절합니다. 재시도·대역 전환으로 더 비싼 수단을 임의 선택하지 않습니다.

### 발급 대상·주기·예산

다음 월별 기준은 플랫폼의 `GRADE` 발급에만 적용합니다. 업무 월은 Asia/Seoul 달력월입니다. 시각의 저장·표현은 [공통 시간 규약](../CONTRIBUTING.md#요청과-응답)을 따릅니다. 매월 1일 00:00의 커머스 DB 일관된 스냅샷을 회차로 고정하고, 00:10부터 자동 발급합니다. 중단됐으면 불변 확정·취소 반영 이력과 최초 반영 시각으로 마감 상태를 재구성합니다. 근거가 없으면 현재 상태로 대체하지 않고 발급을 멈춥니다. 미완료 회차는 10분마다 같은 대상·업무 키로 자동 재시도하며 사람의 승인이나 수동 재개를 기다리지 않습니다. 발급 월의 다음 달 1일 00:00에 만료하고 지연으로 연장하지 않습니다. 만료 후 재개한 회차는 새 발급 없이 미처리 이유를 남깁니다.

전월에 커머스에 반영된 구매확정 주문 중 환불되지 않은 거래의 **외부 결제액 E 합계**를 사용합니다. 수량·구매 횟수를 다시 곱하지 않고 배송비·사용 마일리지·플랫폼/판매자 쿠폰액을 더하지 않습니다. 확정 반영 시각은 최초 저장 뒤 바꾸지 않으며, 늦게 반영된 확정은 반영 월에 한 번만 산입합니다. 결제 승인일·PG 응답 시각으로 닫힌 회차를 다시 계산하지 않습니다.

| 대상 | 초기 규칙·유일성 |
| --- | --- |
| 웰컴 | 가입과 함께 자동 발급. 가입 회차와 무관하게 `buyerId+WELCOME` 한 이력. 발급·혜택 이용 이력은 탈퇴로 삭제하지 않음 |
| 월간 우수고객 | 플랫폼 전체의 전월 E 합계>0인 구매자를 금액 내림차순으로 정렬해 상위 100위와 동점자 전원. 100명 미만이면 실제 인원만. `buyerId+GRADE+대상월` 한 장 |
| 판매자 | 판매자가 정한 구매자. `templateId+buyerId` 한 장이며 다른 캠페인의 쿠폰도 보유 가능 |

월 순위는 `RANK() OVER (ORDER BY E합계 DESC)≤100`에 해당합니다. 구매자 ID는 동점자를 제외하는 기준으로 쓰지 않고 처리 순서에만 사용합니다. 예를 들어 99명보다 구매액이 적은 다음 5명이 동점이면 104명에게 지급합니다. 서로 다른 구매액 100개를 고르는 `DENSE_RANK`는 사용하지 않습니다.

선정된 고객의 전월 E 합계가 300,000원 미만이면 브론즈, 300,000~499,999원이면 실버, 500,000원 이상이면 골드 혜택을 줍니다. 100,000원 미만이어도 선정되면 브론즈를 적용하며, 순위 밖의 고객은 등급 금액을 충족해도 발급하지 않습니다. 등급 점수와 사용 가능한 마일리지 잔액은 분리하고 혜택 사용으로 당월 등급을 낮추지 않습니다. 월 회차의 대상·인원·경계 구매액·등급·처리 순서를 저장해 재실행 시 바꾸지 않습니다.

플랫폼 쿠폰에는 미리 정한 발급 수·할인 예산 상한을 두지 않습니다. 월 배치가 대상·등급·인원을 고정하고 할인 총액을 자동 산정해 발급합니다. 브론즈 대상자가 동점자 포함 104명이면 `104×3,000=312,000원`이 지급 예정 할인액입니다. 별도의 한도 증액이나 재승인은 없으며, 비용 계산 자체가 현금 확보를 뜻하지는 않습니다.

판매자 캠페인만 판매자가 정한 발급 수·명목 할인 예산 안에서 처리합니다. `총예산=미사용 가용액+발급 약속액+사용 누계액`을 유지하고, 발급 수 증가·쿠폰 저장·할인액 전액의 약속액 반영을 같은 DB 트랜잭션에서 처리합니다. 한도 소진은 해당 캠페인의 신규 발급만 막습니다.

모든 쿠폰은 발급 시 할인 약속액, 사용 시 사용 누계액, 미사용 만료·전액 환불 시 상쇄액을 기록합니다. 만료됐어도 예약 중·PG 결과 미확정이면 약속액을 유지합니다. 환불 후 유효한 원쿠폰은 약속액으로 되돌리고, 이미 만료됐으면 사용액만 상쇄하며 새 쿠폰을 만들지 않습니다. 회차·쿠폰·원결제 업무 키로 중복 반영을 막고 기존 쿠폰의 할인·기한·부담자를 보존합니다. 실제 PG·환불 비용도 따로 기록하며 플랫폼 비용을 판매자 정산에 전가하지 않습니다.

현재 식별자는 구매자 계정입니다. 동일 이메일 재가입 차단은 가능하지만 다른 이메일을 가진 동일인을 식별한 것은 아닙니다. 실명 1인 1회·자전거래 완전 차단을 구현했다고 안내하지 않으며, 상용 발급 전 중복 계정·자전거래 대응과 예산 악용 방지를 별도 검증합니다.

월간 혜택의 대상 확정·발급 단계와 실행 앱·재시작 경계는 [월간 혜택 Job](architecture.md#월간-혜택-job)을 따릅니다. 이 등급은 선정자의 쿠폰 혜택을 정하며 전체 회원의 상시 등급 갱신을 뜻하지 않습니다.

### 월간 회차 검증과 오류 교정

월간 Job은 대상 확정·자동 검증과 발급의 두 Step으로 실행합니다. 대상 수는 마감 원자료의 `RANK() <= 100` 결과와 같아야 하며 동점자를 임의로 자르지 않습니다. 대상·템플릿·등급·할인 합계·중복을 확인한 뒤에만 ISSUING으로 전이합니다. 검증 실패 시 발급을 시작하지 않고 오류·진행 상태를 보존합니다. 플랫폼 할인 총액의 산술 검증은 예산 한도 검사가 아니며 별도 승인·재승인을 요구하지 않습니다.

집계 오류의 운영 교정은 **원회차가 PREPARING/ISSUING/COMPLETED이며 발급이 0건이고, 실행이 안전하게 멈춘 경우**에만 허용합니다. 실행 이력·실행자 부재·미커밋 작업의 종료를 확인하고, STARTING/STARTED/STOPPING 잔류가 있으면 교정 전에 정상 중단·복구합니다. 확인할 수 없으면 판정을 미루며 실행 중인 작업을 새 회차로 우회하지 않습니다. 취소·대상 저장·발급·Job 실행 등록은 같은 회차 행 잠금과 상태 확인으로 직렬화합니다. ISSUED 대상·연결 쿠폰·해당 대상의 ISSUE 이력이 하나라도 있으면 취소하지 않습니다.

교정은 [운영 내부 계약](api.md#월간-혜택-운영-조회와-오류-교정)으로 원회차 CANCELLED 전이·대체 PREPARING 회차·감사·멱등 결과를 한 트랜잭션에 저장합니다. 취소 사유 코드·검증한 운영자·시각·이전 회차를 보존합니다. 대체 회차는 **같은 대상월·마감 자료·정책 버전·원래 만료**를 사용하며 구매자 목록·등급·금액을 운영자가 지정하지 않습니다. 기존 회차·대상은 삭제하거나 덮어쓰지 않습니다. 취소되지 않은 회차는 월당 하나이고 구매자별 GRADE 월 한 장 제약도 유지합니다.

발급을 한 건이라도 커밋했거나 원회차가 EXPIRED이면 교정하지 않습니다. 집계 오류로 대상0명을 확정해 COMPLETED가 된 빈 회차도 발급 기한 안에서는 같은 0건 교정 조건을 적용합니다. 취소된 회차는 Scheduler·재시작·발급에서 제외합니다. 정상 오류 복구는 기존 대상·같은 runId의 미발급 대상부터 재개합니다. 원래 발급 기한이 지나면 교정·발급 없이 EXPIRED로 종결합니다. 이 절차는 정상 회차의 운영자 승인이나 쿠폰 회수 기능이 아닙니다.

### 쿠폰 만료 처리

커머스는 `expiresAt≤현재 시각`인 미사용 ISSUED 쿠폰을 주기적으로 찾아 EXPIRED로 전이하고 미사용 할인 약속액을 한 번만 상쇄합니다. 쿠폰 상태·템플릿 비용 집계·만료 이력은 같은 DB 트랜잭션으로 반영하며, 쿠폰별 만료 업무 키와 예상 상태·버전으로 사용·예약과의 경합 및 재실행 중복을 막습니다. 이력과 누적 발급 수는 지우거나 되돌리지 않습니다.

RESERVED이거나 금융 결과 미확정인 쿠폰은 만료 시각이 지났어도 예약·약속액을 유지합니다. 이후 안전한 예약 해제나 전액 환불이 확인됐을 때 원래 만료 시각에 따라 비용·상태를 반영합니다. 만료 스케줄러의 실행 지연은 사용 기한을 연장하지 않으며 요청 경계에서도 기한을 검사합니다. 실행 위치·주기는 [정기 작업](architecture.md#정기-작업과-비동기-실행), 저장 구조는 [쿠폰 이력](data-model.md#coupon_history)을 따릅니다.

### 예약·취소·환불

시간 판단은 서버 예약 시각의 `validFrom≤시각<expiresAt`을 사용합니다. 웰컴 `expiresAt=가입시각+14일`, GRADE는 다음 달 1일 00:00 KST, SELLER는 템플릿의 종료 시각이며 발급 때 사본으로 고정합니다. 발급 자체도 expiresAt 전에만 가능하며 늦은 재시도로 만료 쿠폰을 새로 발급하지 않습니다. 만료 전 예약한 주문은 원금액·조건을 보존합니다.

`ISSUED→RESERVED→USED` 상태와 원사용 이력을 유지합니다. 확정 거절은 재시도 기한까지 예약을 유지해 만료 전에 예약한 주문이 같은 금액·조건으로 다시 시도하게 합니다. 승인 차단된 미결제 취소가 확정될 때만 예약을 해제하고 아직 유효하면 ISSUED, 아니면 EXPIRED로 처리합니다. 거절된 주문도 미결제 대기 기한이 지나면 자동 취소 요청을 거쳐 이 해제에 이릅니다. 타임아웃·응답 유실·월 배치 재실행·단순 예약 TTL은 해제 근거가 아닙니다. 이전 결제 회차의 늦은 실패 이벤트가 새 예약을 해제하지 못하게 합니다.

전액 환불은 최초 `E`만 외부 취소하고 사용 `M`을 복원하며 원장 SOURCE의 E·M·P와 ALLOCATION의 N·F를 최초 금액으로 한 번씩 상쇄합니다. 플랫폼 지원액 P를 고객에게 현금으로 더 돌려주지 않습니다. 내부 원장·주문 복구까지 확인한 뒤 원쿠폰 한 장만 복구하고 원래 만료 시각을 유지합니다. 만료 후 환불은 이력·예산만 상쇄하며 재사용·기간 연장·대체 발급을 하지 않습니다. PG가 반환하지 않는 취소 비용은 별도 비용이며 쿠폰 예산이 복구됐다는 이유로 지우지 않습니다.

부분 환불·교환·지급 후 환불은 현재 설계 범위에 추가하지 않습니다. 수량 여러 개 주문도 전액 환불만 처리합니다. 모의 배송완료 기준 7일을 실물상품 상용 약관으로 사용하지 않습니다. 하자 등 법정 예외·지급 후 회수 재원은 [전자상거래법 제17조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1031805939)·[제18조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1027063339)를 반영해 별도로 갖출 상용 전환 조건입니다.

## 선착순 상품 이벤트

판매자는 이벤트 이름(`name`, 1~80자)을 직접 정합니다. 예: ‘주말 특가’, ‘오픈 기념 한정 판매’. 특정 행사명이나 방송에 종속되지 않습니다. 상품 1개·가격·수량·시작/종료 시각을 정하고 공개할 때 재고를 배정합니다. 같은 상품의 겹치는 공개 기간은 상품 재고 행 잠금 아래 검사합니다. 공개 후 이름·가격·수량·기간은 고정하고 조기 종료만 허용합니다.

이벤트 기간에는 상품을 바꾸지 않습니다. 공개(`SCHEDULED`)부터 종료(`CLOSED`·`SOLD_OUT`) 전까지 해당 상품의 이름·가격·상태 변경과 논리삭제는 `409 PRODUCT_EVENT_IN_PROGRESS`로 거절합니다. 이 확인은 이벤트 공개와 같은 상품 재고 행 잠금 아래에서 하므로 공개와 상품 변경이 엇갈리지 않습니다. 상품을 바꾸려면 이벤트를 먼저 조기 종료합니다. 판매자의 일반 가용 재고 조정은 이벤트 배정 수량을 바꾸지 않으므로 막지 않습니다.

`Q=한정 수량`, `S=누적 결제 확정 수량`, `R=대기 예약 수량`, `0≤S+R≤Q`. 선착순은 DB 예약 커밋 순서이고, 구매자당 진행 중/확정 참여는 1건입니다. 게이지는 `floor(100×S/Q)%`; 예약 마감과 100% 매진은 다른 상태입니다. `S=Q`면 종료하고 환불로 재개하지 않습니다. 기한 종료·조기 종료 후에도 기존 예약의 결과는 끝까지 확인합니다. [수량 복구 흐름](design.md#선착순-상품-이벤트)을 따릅니다.

게이지 조회 캐시 TTL과 화면 기본 조회 간격은 1초입니다. 응답에 `asOf`(계산 시각)를 포함합니다. 캐시는 외부 저장소가 아닌 인스턴스 메모리에 두어, 이벤트별로 1초 안의 조회는 처음 계산한 값을 돌려주고 동시 미스는 DB를 한 번만 읽습니다. 별도 캐시 장애 경로는 없고 DB 조회 실패는 저장하지 않고 일반 오류로 응답합니다. 인스턴스마다 최대 1초 다른 값을 보일 수 있으며 구매 허용 판단은 캐시로 대체하지 않습니다. 이 값은 시험할 시작 설정이며 성능·최신성 달성 결과는 아닙니다.

## 마일리지와 외부 대역

우리 마일리지는 Payment 소유의 1점=1원 플랫폼 부담 잔액입니다. 시험용 사전 지급·예약·차감·전액 복원만 포함하고 충전·현금 인출·구매 적립·만료는 제외합니다. `잔액−예약 합계≥0`을 DB에서 보호합니다. 원결제별 사용/복원은 한 번뿐이며, 계정 이용 제한 중에도 반환 잔액·이력은 보존합니다.

신용/체크카드는 선택한 PG A/B/C, 간편결제는 `EASY_PAY`만 호출합니다. 간편결제의 모의 잔액은 우리 마일리지와 다릅니다. 원대역·업무 키·결과·금액을 영속 저장하고 원거래로 조회·취소합니다. 수단·PG별 처리 중/미확정/성공/거절을 구분하며 타임아웃만으로 잔액·예약을 반환하지 않습니다.

### 시험 데이터 준비

운영자 자격으로 `/mock/accounts`·`/mock/scenarios`를 생성하고 `/mock/accounts/{accountId}`에서 현재 잔액을 조회합니다. Payment·Settlement·Gateway 자격은 준비 API에 사용할 수 없으며, 운영자 자격에 사용자 신원 헤더를 붙인 요청도 거절합니다. 검증한 발신자 식별자로만 멱등 범위를 정합니다.

계정은 `providerId+accountRef+purpose`, 시나리오는 `providerId+scenarioVersion`마다 하나이며 새 키로 기존 자원을 덮어쓸 수 없습니다. 리소스 생성과 `actor_kind=OPERATOR`·`operation=MOCK:ACCOUNT:CREATE` 또는 `MOCK:SCENARIO:CREATE`의 완료 키를 한 트랜잭션으로 보존합니다. `actor_id`는 검증한 전체 발신자 ID가 100자 이하면 원문을 유지하고, 더 길면 `sha256:` 뒤에 전체 ID의 SHA-256 64자리 16진수를 저장합니다. 기존 짧은 ID의 키 범위를 유지하며, 긴 ID도 운영자별로 구분해 DB의 100자 한도 안에 저장합니다. 준비 키는 `Idempotency-Key`의 SHA-256이며 만료시키지 않습니다. 같은 키·정규화한 본문은 최초 생성 결과, 다른 본문은 409입니다. 같은 수치의 확률 표기 차이는 충돌로 보지 않습니다. 경합 중 잠금 상한을 넘긴 요청은 409로 끝나며, 같은 키·본문 재시도로 원결과를 확인합니다. 저장 중단은 미커밋 자원·키를 함께 롤백하고 커밋 뒤 응답 유실은 원키 재시도로 복구합니다.

계정 생성의 `balance`는 불변 기초잔액입니다. POST 재요청은 불변 계정 정보와 기초잔액으로 최초 응답을 복원하고, 실제 잔액·예약·버전은 GET에서 읽습니다. 시나리오는 기존 승인/PAYOUT·환불·조회 프로필과 seed를 보존하며 생성 이후 바꾸지 않습니다. 확률은 0~1·소수점 7자리까지 검증해 DB 저장 시 반올림으로 실행 값이 달라지지 않게 합니다. PG/EASY_PAY에는 입금 지연·환불 설정이 필수이고 PAYOUT에는 모두 null입니다. 새 버전을 등록해도 원승인·환불의 금융 버전과 지급 당시 계정 사본은 바뀌지 않습니다.

## 배송·환불 기한과 자동 구매확정

정책 버전은 `delivery-daily-v1`입니다. 업무 시간대는 Asia/Seoul이며 시각은 마이크로초 정밀도를 유지합니다. 저장·표현은 [공통 시간 규약](../CONTRIBUTING.md#요청과-응답)을 따릅니다. 영업일은 월~금 중 주입한 공휴일 목록을 제외한 날입니다. 기본 시험 달력은 공휴일 없는 `weekdays-v1`이며, 시험 시작 시 seed·달력 버전과 날짜 목록을 고정합니다. 기존 주문·PG 거래의 달력을 설정 변경으로 바꾸지 않습니다.

- 주문 생성 시 `SHA-256(seed + ":" + orderId)`의 마지막 바이트가 짝수이면 2, 홀수이면 3영업일을 배송 소요일로 저장합니다. 멱등 재요청·결제 재시도·재시작에서 다시 추첨하지 않습니다.
- 발송은 유효한 결제 완료·미발송·진행 중 취소/반품/환불 없음일 때만 허용합니다. 서버가 `shippedAt`을 기록하고, 발송 당일을 제외한 다음 영업일부터 소요일을 세어 같은 현지 시각을 `deliveryDueAt`으로 고정합니다. 같은 발송의 재요청은 최초 값을 반환합니다.
- 매분 모의 배송 작업이 `현재 시각≥deliveryDueAt`인 발송 주문을 찾습니다. 유효한 주문만 DELIVERED로 전이하며 `deliveredAt=deliveryDueAt`, `refundDeadlineAt=deliveredAt+168시간`을 함께 저장합니다. 작업 지연으로 기한을 늘리지 않습니다. 미결제·미발송·취소/환불 완료 주문을 배송완료로 만들지 않습니다.
- 배송 전에는 환불 마감이 없으며 결제 완료 주문의 취소·반품을 접수합니다. 미발송 취소는 자동 승인하고 발송 후에는 판매자 승인이 필요합니다. 배송완료 후에는 커머스가 주문 행을 확보해 기록한 서버 접수 시각이 `refundDeadlineAt` 이하인 요청만 허용합니다. 마감 정각은 허용하고 그 뒤 신규 요청은 거절합니다. 배송 작업이 늦었으면 같은 주문 잠금 아래 도래한 배송완료·기한을 먼저 반영해 마감 이후 접수를 허용하지 않습니다.
- 기한 내 접수한 환불은 마감 뒤에도 끝까지 처리합니다. 외부 환불·마일리지 복원·원장 상쇄·주문 복구가 끝나야 전체 완료입니다. 부분 환불·교환·지급 예약 후/지급 후 환불은 제외합니다.

자동 구매확정은 매분 배송완료된 유효 결제 주문 중 `현재 시각>refundDeadlineAt`이고 진행 중인 취소·반품·환불이 없는 주문을 찾습니다. 환불 접수와 같은 주문의 조건부 전이·버전을 사용해 경합하고 확정 상태와 Outbox를 한 번만 저장합니다. 수동 조기 확정은 제공하지 않습니다. 미처리 대상 전체를 재조회하며 배송·환불·확정 작업은 주입한 Clock으로 검증합니다.

금융 환불의 거절이 취소·반품 의사의 철회를 뜻하지는 않습니다. 주문이 계속 유효한 것으로 해당 절차가 안전하게 종결된 경우만 자동 확정을 재판정합니다. 발송 상품의 재고는 금융 환불과 별도로 판매자 반품 입고 확인 뒤 복원합니다.

## 정산·재처리

Asia/Seoul **매일 10:00**을 마감으로 판매자별 배치를 만듭니다. `sellerId+batchDate+policyVersion`이 같은 실행은 기존 배치를 재개합니다. 상품 등록 시각·상품별 회차는 지급 기준으로 사용하지 않습니다. 10:00 정각에 준비된 거래는 다음 날 대상입니다.

`readyAt=max(purchaseConfirmedAt, eligibleReceivedAt)`이며 `eligibleReceivedAt`은 자동 구매확정과 선행 결제 원장이 Settlement에 모두 준비된 시각입니다. `readyAt<cutoffAt`인 미환불·미예약·미지급 항목 전체를 찾습니다. 오늘 발생한 거래로 제한하지 않고, 늦은 이벤트·중단 뒤 미처리 항목도 다음 실행에서 선택합니다. 같은 판매자 배치의 대상·합계·지급·작업을 한 트랜잭션으로 고정하고 닫힌 배치에 항목을 추가하지 않습니다.

대상이 없으면 새 배치·지급을 만들지 않습니다. 운영 생성 API는 `409 SETTLEMENT_NO_ELIGIBLE_ITEMS`를 반환하고 자동 작업은 다음 마감을 기다립니다. 같은 키의 배치가 이미 있으면 대상 재조회보다 기존 배치 반환이 우선입니다.

환불/지급 예약은 같은 항목에서 배타적입니다. 환불 예약은 WAITING_CONFIRMATION/PAYABLE에서, 지급 예약은 PAYABLE에서만 가능합니다. 지급 예약과 `payoutId` 연결 뒤에는 보류·중단돼도 새 배치에 다시 배정하지 않습니다. 보상은 원상태와 최신 구매확정/환불 정보를 대조합니다.

지급 생성 전 커머스의 서비스 인증 컨텍스트로 각 상품/판매자 일치와 판매자 상태·수취 시험계정·버전을 검증합니다. 판매자별 합산 항목의 수취 계정 사본이 하나로 일치해야 하며, 검증 실패 시 선점·합계를 전부 롤백합니다. 컨텍스트는 DB 트랜잭션 밖에서 조회하고, 선점할 때 항목 상태와 검증한 상품 집합을 다시 확인합니다. 조회 실패(무응답·자격 거절·응답 불일치)는 모든 판매자에게 같이 일어나므로 일배치를 실패시켜 원인 해결 뒤 재시작하고, 검증 거절은 그 판매자만 건너뜁니다. 지급 레코드의 수취/출금 계정은 재시도에 그대로 사용합니다.

정산 일배치와 모의 지급은 주말·공휴일 구분 없이 매일 처리합니다. 지급 대역은 영업일을 검사하지 않으며 비영업일 보류·다음 영업일 재개·달력 조회 계약을 두지 않습니다. 기존 업무 키가 있으면 원거래 조회·원결과 반환이 우선이며 요청 해시로 같은 키의 다른 금액·계정을 거절합니다. 이는 모의 지급 대역의 범위이며 배송·PG 입금 예정일의 영업일 달력은 유지합니다.

외부 접수 뒤 미확정이면 예약을 유지하고 5분마다 원거래를 조회합니다. 확정 성공은 최초 `succeededAt`을 보존하고 항목·지급·작업을 원자 완료합니다. 확정 거절은 지급을 DECLINED, 배치·작업을 REVIEW_REQUIRED로 남기며 자동으로 새 업무 키를 만들거나 항목을 해제하지 않습니다. 완료·확정 거절의 nextAttemptAt은 null입니다. 판매자 조회는 예정 마감·보류 사유·다음 시도·실제 성공 시각을 구분합니다.

### 정산 대조

자동 정산 대조 Job·정기 스케줄은 지원하지 않습니다. 아래는 수동 정합성 검사의 기준이며 업무 상태 보정이나 새 금융 거래를 만들지 않습니다. 현재 [부하 도구](../tests/load/README.md)는 Payment·금융 대역을 대조하며 Settlement까지의 전체 검사를 대신하지 않습니다.

기준 시각 T는 일배치의 `cutoff_at`입니다. Payment의 불변 결제·환불 이벤트와 Settlement 원장을 원천 `occurred_at≤T`로 자르고 이후 환불·현재 상태를 섞지 않습니다. 검증한 최대 업무 트랜잭션 시간보다 긴 안전 여유가 지난 뒤에만 원천을 조회하며, 보장할 수 없으면 503으로 중단합니다. 최초 snapshot·cursor로 전체 페이지를 읽고 기준선·진행 위치·미완료 키를 검사 회차의 기록에 보존합니다.

| 관측 | 판정 |
| --- | --- |
| Inbox APPLIED | 발행 위치 미확정·재발행 여부와 관계없이 금액·참조 대조 |
| Inbox RECEIVED·WAITING | 반영 대기 |
| REVIEW_REQUIRED·격리 기록 | 격리·수동 확인 |
| 수신 기록 없음 + 발행 위치 미확정 | 발행 대기. 이 이벤트도 기준선에 포함 |
| 수신 기록 없음 + 자기 Consumer 그룹의 커밋 offset 부재 또는 이벤트 offset 이하 | 전달 대기 |
| 커밋 offset이 이벤트 위치를 지났지만 수신·격리 기록 없음, 또는 APPLIED의 금액·참조 불일치 | 결함 |

offset은 같은 topic·partition으로 비교하며 커밋 offset은 다음 읽을 위치이므로 이벤트 offset보다 커야 합니다. 조회 실패를 0으로 대체하지 않습니다. 발행·전달·반영 대기가 15분을 넘으면 지연으로 기록하며 시간만으로 금액 결함에 넣지 않습니다. 위치·Inbox가 바뀌면 같은 기준선의 미완료 키를 재대조합니다. UNKNOWN·환불/지급 예약·PROCESSING·보류는 진행 중으로 따로 집계하며 오래 남은 건은 [운영 알람](#운영-알람)으로 다룹니다.

서비스별 검사에서는 자기 DB만 직접 읽고 Payment는 [대조 API](api.md#정산-대조-조회), 지급은 원대역 GET, offset은 자기 Kafka 그룹의 관리 조회로 확인합니다. T까지 생성된 지급 중 최초 `succeededAt≤T`인 성공액만 대조하며 이후 성공은 다음 회차 대상입니다. Settlement의 검사 범위는 Settlement 원장·정산↔지급·내부 참조·Payment↔Settlement·지급 성공액↔대역 차감액이며, 전체 [금액 대조](design.md#금액-대조)는 부하·장애 시험 후 수행합니다.

### 선지급 재원과 PG 회수

선지급 재원은 PG 입금 여부와 관계없이 항상 충분하다고 가정합니다. 시험 시작 전에 최대 누적 지급액과 입금 후 환불액을 모두 감당할 PAYOUT 자금을 초기 계정에 준비합니다. 기본 단일 흐름 fixture는 100,000,000원이며 대규모 시험은 필요한 상한에 맞춥니다. 재원 부족 보류·재시도·알림·보충 API는 제공하지 않습니다. 준비액이 전제를 충족하지 못하면 시험 준비 오류로 처리하고 판매자 지급 상태로 노출하지 않습니다. 플랫폼 쿠폰 P·마일리지 M은 플랫폼 자금으로 부담합니다.

외부 승인 E>0이면 대역이 원승인·재원 계정·달력 버전·입금 예정일을 저장합니다. Payment와 Settlement는 시험 시작 때 선택한 같은 PAYOUT 재원을 사용합니다. 입금 지연은 PG_A/EASY_PAY 5영업일, PG_B 6영업일, PG_C 7영업일이며 승인 당일을 제외하고 배송과 같은 영업일 계산을 적용합니다. 장애 설정의 `settlementDelayBusinessDays`는 0~365로 검증하고 승인 당시 값으로 예정일을 고정합니다. 0이면 승인과 같은 시각부터 입금 처리할 수 있으며, 15영업일 지연 fixture로 PG 입금 전 지급을 재현합니다. PAYOUT 시나리오의 해당 값은 null입니다. 실제 금융기관 계약이 아닌 시험 입력입니다.

마일리지 전액 결제에는 PG 입금을 만들지 않습니다. 매분 도래한 미처리 입금을 재조회하고 원승인당 한 번만 E를 입금합니다. P·M을 PG 입금액에 더하지 않습니다.

전액 환불이 입금보다 먼저 확정되면 예정 입금을 0으로 종결합니다. 입금 뒤 환불은 같은 재원에서 E를 차감합니다. 환불 결과·간편결제 잔액 복원·입금 상쇄·현금 기록은 대역 DB의 같은 트랜잭션으로 처리하고 원승인 잠금으로 입금/환불 경합을 막습니다. 이 차감액도 사전 준비한 모의 자금에 포함합니다. 미확정 환불은 성공으로 상쇄하지 않습니다.

실행 시 `balance−reservedAmount` 안에서 지급액을 원자 선점합니다. 성공 시 한 번만 차감하고 확정 실패 시 대역 자금 선점을 해제하며, 응답 유실만으로 해제하지 않습니다. `기초잔액+PG입금−입금후환불−성공지급=현재잔액`과 `0≤예약액≤잔액`을 유지합니다. PG 입금 전 지급액과 회수 대기기간은 원승인·입금·지급 시각으로 구분하며 마일리지/쿠폰 부담을 PG 미수로 집계하지 않습니다. PG 비용의 실청구는 이번 대역 현금 모델에 포함하지 않습니다.

### 공통 복구

일시적 오류는 최대 10회, 1초부터 지수 증가해 최대 60초 간격으로 재시도하고 소진 시 REVIEW_REQUIRED로 보존합니다. 미확정 금융 작업은 실패/예약 해제로 바꾸지 않고 같은 원거래를 조회합니다. 메시지 자동 재시도 초과는 DLT로 넘기되 영속 작업을 잃지 않습니다. 운영 재처리는 원래 업무 키와 실행 주체·사유를 보존합니다.

승인 작업은 외부 호출 전에 Payment 상태를 PROCESSING으로 원자 전이합니다. 미결제 취소는 외부 호출 전 결제만 CANCELLED로 전이하고 승인을 차단합니다. 처리 중/미확정이면 예약을 유지하고 조회합니다. 취소가 먼저 도착하면 불변 주문 컨텍스트로 취소를 먼저 저장하며 늦은 결제 요청으로 재활성화하지 않습니다. 오래된 `paymentCycleId`의 결과로 새 예약을 해제하지 않습니다.

#### 금융 결과 조회와 원키 재요청

Payment·Settlement의 외부 승인·환불·지급 작업에 적용합니다. 최초 호출 전에 원대역·작업 종류·업무 키·금액·계정·시나리오 버전을 영속 확정하고 재개할 요청을 같은 값으로 구성합니다. 환불은 원승인의 시나리오 버전을 계승하고 지급은 생성 때 선택한 버전을 고정합니다. 마일리지 전액 거래에는 외부 작업을 만들지 않습니다.

| 원대역 조회 결과 | 후속 처리 |
| --- | --- |
| `200 SUCCEEDED` | 반환된 대역·작업·업무 키·금액·원거래 대응을 검증하고 내부 반영을 재개. 외부 실행을 반복하지 않음 |
| `200 DECLINED` | 확정 거절에 맞는 실패·보상을 진행. 같은 거래를 성공으로 다시 추첨하지 않음 |
| `200 PROCESSING` | 예약을 유지하고 같은 거래를 재조회. 실행 요청을 추가하지 않음 |
| `404 MOCK_TRANSACTION_NOT_FOUND` | 신뢰한 대역의 해당 provider·operation·businessKey 조회에서만 인정. 현재 작업 권한·금융 상태를 재검사한 뒤 원키·원본문으로 실행 요청을 재전송 |
| 통신 실패·타임아웃·`503`·그 밖의 불명확한 응답 | 미확정·예약을 유지하고 조회 재시도. 거래 없음이나 확정 거절로 해석하지 않음 |

예를 들어 PROCESSING 저장 직후 PG 호출 전에 Worker가 죽으면 조회에 거래가 없을 수 있습니다. 404는 조회 시점의 부재이며 이전 요청이 나중에 도착하지 않는다는 증명이 아닙니다. 원키 재전송과 늦은 최초 요청이 겹쳐도 대역은 하나의 금융 거래만 만들고 같은 본문이면 기존 결과를 반환해야 합니다. 조회 404만으로 취소를 확정하거나 재고·쿠폰·마일리지·정산 예약을 해제하지 않습니다. PROCESSING 이후에는 미결제 취소나 새 결제 회차로 전환하지 않고 원거래 결과를 끝까지 확인합니다.

대역은 기존 `idempotency_records`를 사용해 발신 서비스와 provider·operation·businessKey 범위의 요청 해시를 보존합니다. 원거래 생성·멱등 기록·잔액/자금 선점은 같은 대역 DB 트랜잭션으로 확정합니다. 같은 키의 다른 금액·계정·원거래·금융 시나리오 버전은 `409`이며 금융 효과를 만들지 않습니다. 중복 요청은 장애 확률을 다시 적용하기 전에 기존 결과를 확인합니다. 일시 오류의 자동 재시도 소진은 REVIEW_REQUIRED이며 금융 실패나 예약 해제가 아닙니다. 지급 미확정은 주말·공휴일에도 5분마다 원거래를 조회합니다.

대역 금융 기록은 `actor_kind=SERVICE`, `actor_id=검증한 발신 서비스`, `operation=MOCK:<providerId>:<operation>`으로 구분하고 본문의 정규화한 UUID `businessKey`를 해시해 `key_hash`에 저장합니다. `request_hash`는 금액·계정·원거래·금융 시나리오 버전을 포함한 정규화한 요청에서 계산합니다. HTTP 멱등 헤더를 바꿔도 같은 금융 업무 키의 중복/충돌 검사를 우회하지 못합니다.

#### 금융 Worker 임대와 결과 반영

기본 작업 조회 간격은 1초, 임대는 30초, 외부 HTTP 호출의 전체 제한 시간은 5초입니다. 시험에서 제한 시간을 바꾸면 실제 설정을 기록하고 `0<호출 제한 시간<임대 시간`을 검증합니다. 동시 실행·복구 전용 슬롯과 풀의 초기값은 [실행 설정](development.md#kafka-전달-기반)을 따릅니다. 실행 동시성은 실행별 양의 정수 서버 설정으로 제한하며 누락·잘못된 값이면 Worker를 열지 않습니다. 이 값은 구현·시험의 시작 기준이며 처리량 보장이 아닙니다. 한 임대에서 실행할 호출에 필요한 시간이 남아 있지 않으면 새 호출을 시작하지 않습니다. 임대는 자동 연장하지 않고 만료 뒤 다시 선점합니다.

- Payment API는 접수·조회, Payment Worker는 영속 금융 Job 실행을 맡습니다. Settlement의 지급 Worker도 같은 임대 규칙을 사용합니다. 여러 인스턴스는 같은 소유 DB의 작업을 제한된 묶음으로 선점하고, 상태·도래 시각·임대 조건을 검사해 `RUNNING`, 실행자, 새 UUID `leaseToken`, `leaseUntil`, 버전을 원자 저장합니다. DB 시각으로 만료를 판정하며 외부 호출 중 DB 잠금을 유지하지 않습니다.
- 임대가 만료된 RUNNING도 다시 찾습니다. 금융 결과를 모르는 작업은 조회부터 재개하며, 회수도 자동 시도 횟수에 포함해 반복 중단이 상한을 우회하지 못하게 합니다. 금융 상태·원업무 키·예약은 유지합니다. 다른 실행자가 인계할 때마다 token을 바꾸며, 유효 임대 중의 운영 재처리는 거절합니다.
- 각 외부 호출 직전 현재 token·실행자·유효 임대·Job 상태·결제 회차/금융 상태를 검사합니다. 결과 반영 때도 같은 조건과 예상 버전을 조건부 갱신으로 확인하고, 금융 상태·마일리지/원장·Job·Outbox의 해당 변경을 같은 로컬 트랜잭션에 저장합니다. 조건이 다르거나 임대가 끝났으면 전부 롤백하고 늦은 실행 결과로 상태를 덮어쓰지 않습니다. 새 실행자가 원대역 조회로 확인합니다.
- 호출 직전 검사 뒤 프로세스가 멈췄다가 재개할 수 있으므로 임대 token이 외부 호출 자체의 중복까지 막는다고 보지 않습니다. 겹친 호출은 위의 대역 원키·본문 일치 계약이 보호하고 token은 오래된 내부 반영을 차단합니다. 승인 성공 뒤 내부 저장만 실패했어도 외부 결제를 실패로 바꾸거나 마일리지 예약을 해제하지 않습니다.

구현 검증은 호출 전 중단→404→원키 재전송, 외부 성공 후 내부 커밋 전 중단, PROCESSING 재조회, A 임대 만료→B 인계→A의 늦은 응답, 같은 키 다른 본문, 반복 임대 회수의 재시도 소진을 각각 재현합니다. 최종 외부 거래·마일리지 차감/복원·원장 반영은 업무별 한 번이어야 합니다. 시험별 실제 DB·대역 사용 범위와 결과를 PR에 남깁니다.

### 적체 시 신규 접수

신규 주문·새 결제 회차의 접수 제한값·재개 조건·503 응답은 [신규 접수 제한과 재개](#신규-접수-제한과-재개)를 따릅니다. 기존 동일 키 재요청·취소·환불·지급·원업무 복구는 이 제한의 대상이 아닙니다. 전달 기록·금융 멱등 기록의 [보존과 삭제](policies.md#보존과-삭제)를 금융 원장의 삭제 기한으로 사용하지 않습니다.

## 인증·공통 API 기준

API 경로·HTTP 메서드·이름·버전과 명세 작성은 [API 경로와 명세 규칙](../CONTRIBUTING.md#api-경로와-명세)을 따릅니다. 아래는 인증과 업무 요청에 적용하는 정책입니다.

인증은 **Redis를 원본 저장소로 쓰는 불투명 Bearer 세션**입니다. 커머스가 구매자·판매자 계정과 비밀번호를 PostgreSQL에서 확인하고, 256비트 이상 임의 토큰의 SHA-256 해시와 계정 종류·ID·인증 버전·발급/만료 시각을 Redis에 저장한 뒤 원문 토큰을 반환합니다. 로그인 세션을 PostgreSQL에 중복 저장하거나 장애 때 DB에서 복원하지 않습니다. 비밀번호 복구 토큰은 별도 PostgreSQL 테이블에서 10분·일회용으로 관리합니다. [저장 구조](data-model.md#redis-인증-데이터)를 따릅니다.

### 세션 발급과 검증

- 세션은 발급부터 **고정 30분**이며 `expiresAt`에 맞춰 Redis TTL을 설정합니다. 요청·조회·서버 재시작으로 연장하지 않고 `현재 시각≥expiresAt`이면 거절합니다. TTL은 정리 수단이고 서버의 만료 검사를 대신하지 않습니다.
- Gateway는 OpenAPI의 PUBLIC 작업을 HTTP 메서드·정규화한 경로로 구분하고, 보호 요청마다 Redis의 세션과 계정별 인증 가드를 원자적으로 확인합니다. 같은 경로의 다른 메서드를 공개로 간주하지 않습니다. 세션의 계정 종류·ID·인증 버전이 ACTIVE 가드와 일치해야 합니다. 로그인 발급도 DB의 활성 계정·인증 버전을 확인한 뒤 같은 가드와 버전이 일치할 때만 세션을 저장합니다. 자격 검증 뒤 버전이 바뀌면 발급을 중단하며 새 버전에 맞춰 토큰을 임의 발급하지 않습니다. 세션 저장 실패·쓰기 거절이면 토큰을 반환하지 않습니다.
- Gateway는 매 요청 Redis를 확인하며 로컬의 이전 인증 성공 결과를 재사용하지 않습니다. 세션 없음·폐기·만료·버전 불일치, 변경 중이 아닌 정지/삭제 계정은 `401`입니다. 로그인 자격 오류·발급 중 버전 변경도 계정 존재 여부를 구분하지 않는 `401`입니다. Redis 연결 실패·시간 초과, 유효 세션의 가드 누락, pendingChangeId가 있는 변경 중 가드·복구 차단은 `503`입니다. 저장소 오류를 로그인 만료로 바꾸거나 보호 요청을 통과시키지 않습니다.
- Gateway가 확인한 신원을 백엔드에 전달하는 방식과 서비스별 호출 자격은 [인증 경계](architecture.md#사용자-인증과-내부-신원-전달)를 따릅니다. 서비스는 호출자 신원과 계정 역할·거래 소유권을 검사합니다. `/internal`·`/mock`는 Gateway에 공개하지 않고 서비스·운영자 전용 자격으로 검증합니다.

### 폐기와 저장소 복구

로그아웃은 현재 세션의 Redis 삭제가 확인된 뒤 완료합니다. 응답 유실 뒤 삭제된 세션으로 재요청하면 인증 실패로 처리하며 세션을 복원하지 않습니다. 계정 정지·삭제·비밀번호 재설정은 해당 계정 종류·ID의 전체 세션을 폐기합니다. 구매자와 판매자의 폐기 범위를 합치지 않습니다.

폐기·가드 차단 이후의 Gateway 세션 검증은 해당 세션을 허용하지 않습니다. 차단 전에 인증을 마친 진행 중 HTTP 요청을 소급 취소하지 않으며, 이미 접수한 금융 작업도 원업무 키로 처리합니다. 업무 상태·금액·소유권 검사는 해당 서비스의 트랜잭션 경계에서 계속 적용합니다.

전체 폐기는 **Redis 가드 차단 → DB의 계정 상태/비밀번호·`auth_version` 증가와 감사 커밋 → Redis 가드에 확정 상태/버전 반영** 순서입니다. 계정별 가드의 `pendingChangeId`를 조건부 설정해 변경을 직렬화하고, 차단 뒤 시작된 로그인과 이전 버전 세션을 거절합니다. Redis 차단 실패 시 DB 변경을 시작하지 않습니다. DB 변경은 가드 획득 당시의 인증 버전을 조건으로 갱신하고 감사 correlation_id에 같은 변경 ID를 남깁니다. DB 커밋 또는 Redis 반영이 미확정이면 차단을 유지하고 성공을 반환하지 않습니다. 커머스의 인증 재조정 작업은 같은 변경의 DB 확정 결과를 확인하며, 롤백 뒤 가드를 다시 열 때도 DB 인증 버전을 조건부 증가시켜 이전 요청의 늦은 커밋을 막습니다. 진행 중 변경·지연된 이전 버전 반영·단순 시간 경과·일반 로그인으로 가드를 다시 열지 않습니다. 비밀번호 교체·복구 토큰 소비·인증 버전 증가는 같은 DB 트랜잭션입니다. Redis와 DB가 하나의 트랜잭션이라고 가정하지 않습니다.

비밀번호 재설정의 `503`·응답 유실은 비밀번호가 바뀌지 않았다는 뜻이 아닙니다. DB 커밋 뒤 Redis 반영이 실패했을 수 있으므로 클라이언트는 결과 확인이 필요하다고 안내하고 자동 재전송하지 않습니다. 복구 후 새 비밀번호로 로그인하고, 실패하면 새 복구 토큰을 요청합니다. 소비한 복구 토큰의 재사용은 `401`이며 같은 요청으로 비밀번호를 다시 바꾸지 않습니다. 계정 정지·삭제·재활성화 API는 현재 범위에 없으며, 해당 상태를 변경하는 시험용 응용 유즈케이스도 위 폐기 절차를 거쳐야 합니다. DB 상태만 직접 바꾸고 폐기가 끝났다고 간주하지 않습니다.

Redis 단절·재접속·실행 식별자 변경을 감지하면 Gateway와 커머스의 사용자 인증을 차단합니다. 복구 시에는 [운영 절차](development.md#redis-세션-검증과-복구)에 따라 새 세션 세대를 적용하고 기존 세션을 모두 무효화합니다. AOF에 남은 이전 세션이나 계정 가드를 그대로 신뢰해 인증을 재개하지 않습니다. 이미 접수한 금융 작업은 원업무 키로 계속 처리하며 사용자 세션을 Kafka 이벤트에 싣지 않습니다.

### 로그인·복구 요청 제한

커머스(`commerce`)가 `POST /api/buyer-sessions`, `POST /api/seller-sessions`, `POST /api/password-reset-requests`의 요청 제한을 소유합니다. 입력 형식을 확인한 뒤 계정 조회·비밀번호 해시 검사·복구 토큰 발급/이전 토큰 폐기·전달보다 먼저 제한을 검사합니다. 제한에 걸린 복구 요청은 기존 복구 토큰을 폐기하거나 새 알림을 만들지 않습니다. 여러 인스턴스가 같은 제한을 적용하며 Gateway의 세션·가드 읽기 권한을 늘리지 않습니다.

- 키는 `commerce-settle:auth:rate-limit:<operation>:<actorKind>:<identifierHash>`입니다. `operation`은 `LOGIN`/`PASSWORD_RESET_REQUEST`, `actorKind`는 BUYER/SELLER이며 구매자·판매자 로그인을 분리합니다. `identifierHash`는 로그인과 같은 규칙으로 정규화한 이메일의 서버 키 기반 HMAC-SHA256입니다. 서버 키는 커머스 인스턴스에 동일하게 설정하고 원문 이메일·키·카운터 키는 로그에 남기지 않습니다. 로그인과 복구의 예산은 공유하지 않습니다.
- 계정 존재 여부·비밀번호 정답과 관계없이 형식이 유효한 모든 시도를 셉니다. 첫 허용 요청에서 시작한 고정 시간창 안의 요청 수를 Redis에서 원자적으로 검사·증가시키고, 키 생성과 만료도 함께 설정합니다. 동시 요청이 상한을 넘지 않아야 하며 재요청으로 만료를 연장하거나 로그인 성공으로 카운터를 초기화하지 않습니다. 시간창이 끝나면 제한이 풀립니다. 이 제한으로 계정 상태·`auth_version`을 바꾸거나 세션을 폐기하지 않습니다.
- 초기 기본값은 구매자·판매자 로그인을 각각 15분에 5회(`loginMaxRequests=5`, `loginWindowSeconds=900`), 비밀번호 복구 요청을 계정 종류별 1시간에 3회(`passwordResetMaxRequests=3`, `passwordResetWindowSeconds=3600`)로 합니다. 허용 횟수를 모두 사용한 뒤의 요청부터 제한합니다. 이 값은 구현·시험을 시작하기 위한 프로젝트 기본값이며 운영 환경에서 검증된 보안 수치라는 뜻은 아닙니다.
- 네 설정은 필수 서버 설정으로 받고 횟수와 초 단위 시간창은 양의 정수로 검증합니다. 설정 누락·잘못된 값·HMAC 키 누락 시 해당 인증 진입점을 열지 않습니다. 인증 구현 시 동시 요청에서도 상한을 넘지 않는지, 제한 후 `Retry-After`가 남은 시간창과 일치하는지, 복구 제한이 토큰 폐기·발급·전달 전에 적용되는지 검증합니다. 부하와 복구 안내 전달량을 확인한 뒤 기본값의 적정성을 재검토합니다.
- 상한을 이미 사용한 요청은 `429`, `COMMON_RATE_LIMITED`, 남은 시간창을 초 단위로 올림한 양의 정수 `Retry-After`를 반환합니다. 존재하지 않는 계정에도 같은 카운터·상태·응답 본문 기준을 적용하고 계정 조회 결과를 응답에 넣지 않습니다. 제한 확인·증가·만료 설정을 확정할 수 없으면 `503`으로 거절하며 비밀번호 검사·토큰 발급/폐기·전달을 진행하거나 로컬 카운터로 우회하지 않습니다. Redis 장애 복구는 [인증 복구 절차](development.md#redis-세션-검증과-복구)를 따릅니다.

계정 식별자별 예산을 공유해 출발지가 달라져도 같은 계정의 반복 추측과 복구 재발급을 제한합니다. [OWASP 로그인 제한](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#login-throttling)과 [복구 요청 제한](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html#forgot-password-request)을 참고합니다.

### 비밀번호와 공통 요청

비밀번호는 12~128자로 받고 Argon2id와 사용자별 salt를 사용합니다. 시작 설정은 메모리 19MiB·반복 2·병렬 1이며 대상 환경에서 로그인 부하를 검증합니다. [OWASP 비밀번호 저장 기준](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)을 참고합니다. 비밀번호 재설정 토큰은 별도 목적·10분·일회용이며 세션 토큰으로 쓸 수 없습니다. 계정 존재 여부와 무관하게 요청 응답은 같고, 등록된 수신 경로에만 전달합니다.

역할 불일치는 `403`, 같은 역할의 타인 소유 리소스는 `404`로 처리합니다. 목록은 `page≥0`, `1≤size≤100`·기본 20, 정렬은 `createdAt DESC, id DESC`입니다. 목록 응답은 `items/page/size/totalElements/totalPages`를 사용합니다. 버전이 있는 업무 리소스의 변경에는 명세의 `expectedVersion`을 검증하고 충돌은 `409`입니다. 로그인·현재 세션 로그아웃·비밀번호 재설정에는 클라이언트의 expectedVersion을 요구하지 않습니다.

멱등키는 8~128자이며 계정 종류·ID·작업에 묶습니다. 같은 키와 정규화한 같은 요청은 기존 리소스로 연결하고 본문이 다르면 `409`입니다. 금융·주문 키는 해당 거래 이력과 함께 보존하며 일반 관리 작업의 키는 24시간 보존합니다. 키 만료로 도메인 중복 제약을 없애지 않습니다. 비밀번호·토큰·멱등키 원문·실결제 비밀값은 로그에 남기지 않습니다.

### 구매자 가입 재시도

`POST /api/buyers`는 `Idempotency-Key` 헤더(8~128자)가 필수이며 누락·길이 위반은 `400`입니다. 클라이언트는 UUID v4 등 추측하기 어려운 값을 가입 시도마다 만들고 응답 유실 뒤에는 같은 키·본문을 재전송합니다. 아직 계정 ID가 없으므로 [멱등 기록](data-model.md#idempotency_records)의 서버가 고정한 가입 범위를 사용합니다. 클라이언트가 계정 ID나 키 범위를 지정하지 않습니다.

요청 비교에는 정규화한 이메일·원문 그대로의 비밀번호·표시명을 포함한 전체 본문의 서버 키 기반 HMAC-SHA256을 사용합니다. 원문 비밀번호·본문·멱등키를 멱등 기록이나 로그에 저장하지 않습니다. 같은 키의 다른 본문은 `409 COMMON_IDEMPOTENCY_CONFLICT`로 거절하며 비밀번호 변경이나 기존 계정 연결로 처리하지 않습니다.

계정·웰컴 쿠폰·할인 약속액·멱등 완료 기록을 같은 커머스 DB 트랜잭션에 저장하고 커밋 후 응답합니다. 기록은 완료부터 24시간 보존합니다. 그 안의 같은 키·본문 재요청은 같은 계정의 `Account`와 `Location`을 `201`로 반환하고 쿠폰을 추가 발급하지 않습니다. 단, 요청 비교에 쓰는 HMAC 키(`AUTH_RATE_LIMIT_HMAC_KEY`)를 교체한 뒤에는 교체 전에 완료된 가입 요청의 재요청도 `409`가 될 수 있습니다. 처리 중인 동일 키는 `409 COMMON_IDEMPOTENCY_CONFLICT`로 재시도를 안내합니다. 저장 실패는 모두 롤백하고 같은 키로 재시도할 수 있습니다.

다른 키 또는 기록 만료 뒤의 동일 이메일 가입은 계정의 이메일 유일성으로 `409`를 반환합니다. 기존 계정 결과를 재사용하거나 웰컴을 다시 발급하지 않습니다. 이 가입 계약은 판매자 가입·로그인·비밀번호 재설정에 확대 적용하지 않습니다.

## 거래 알림

구매자·판매자에게 필요한 거래 결과는 카카오 알림톡 형식으로 안내합니다. 기본 `MOCK_KAKAO` 채널은 **모의 발송 기록만 저장**하며 실제 카카오·문자·전화번호를 사용하지 않습니다. 수신처는 계정 종류와 ID에서 만든 `mock:<BUYER|SELLER>:<UUID>`입니다. 구매자·판매자 알림을 합치지 않으며, 거래 내역은 원래 주문·결제·정산 API에서도 확인합니다.

### 대상과 발송 시점

| 종류 | 수신자 | 발송 조건·내용 |
| --- | --- | --- |
| `PAYMENT_COMPLETED` | 구매자 | 외부 승인과 마일리지 차감 확정 뒤 주문 반영 확인. 외부 결제액·사용 마일리지·차감 직후 잔액 |
| `SHIPMENT_STARTED` | 구매자 | 판매자의 발송 처리 저장. 택배사 배송 완료를 추정하지 않음 |
| `SHIPMENT_DELIVERED` | 구매자 | 모의 배송 완료 전이 저장. 실제 택배사 완료 확인과 구분 |
| `PURCHASE_CONFIRMED` | 구매자 | 환불 기한 후 자동 구매확정 저장 |
| `CANCELLATION_COMPLETED` | 구매자·판매자 | 미결제 주문 취소 확정. 결제한 주문의 취소는 환불 결과로 안내 |
| `RETURN_REQUESTED` | 구매자·판매자 | 기한 내 취소·반품 요청 접수. 구매자는 접수 확인, 판매자는 승인 필요 여부 확인 |
| `RETURN_DECIDED` | 구매자 | 판매자의 반품 승인·거절 저장. 승인을 환불 완료로 안내하지 않음 |
| `RETURN_RECEIVED` | 구매자 | 판매자의 반품 입고 확인 저장. 금융 환불 완료로 안내하지 않음 |
| `REFUND_COMPLETED` | 구매자·판매자 | 원외부 결제액 환불·마일리지 복원·원장 상쇄·주문 복구 완료. 구매자에게 복원액·복원 직후 잔액 안내 |
| `REFUND_ACTION_REQUIRED` | 구매자·판매자 | 금융 환불 확정 실패가 주문에 반영됨. 미환불 상태와 문의 경로 안내; 미확정을 확정 실패로 바꾸지 않음 |
| `SALE_COMPLETED` | 판매자 | 주문의 결제 확정 반영. 판매자별 1분 동안 받은 판매를 묶어 건수·주문 결제액 합계 안내 |
| `SETTLEMENT_READY` | 판매자 | 판매자별 일배치 대상·금액 확정. batchDate·마감·합계와 지급 처리 중임을 안내 |
| `PAYOUT_COMPLETED` | 판매자 | 원지급 `SUCCEEDED` 확인. 실제 지급액·원대역의 최초 성공 시각 안내 |
| `PAYOUT_ACTION_REQUIRED` | 판매자 | 지급 확정 거절. 확인 경로 안내 |

마일리지 잔액은 Payment가 원장 변경과 같은 트랜잭션에서 저장한 **해당 처리 직후 값과 walletVersion**입니다. 늦은 알림의 잔액을 현재 잔액으로 표시하지 않습니다. 마일리지 미사용 결제에는 잔액 안내를 생략할 수 있고 구매 적립 알림은 만들지 않습니다. 요청 철회·운영 종결 결과는 기존 요청 조회에 남기며 완료되지 않은 환불을 성공으로 알리지 않습니다.

### 소유권과 복구

- 커머스 `commerce`가 알림 이력·묶음·발송을 소유합니다. 로컬 주문 전이는 상태와 알림 항목을 같은 DB 트랜잭션으로 저장합니다. Payment·Settlement는 자기 상태와 알림 요청 Outbox를 함께 저장합니다. 커머스의 `commerce-notifications.v1` 소비자는 Inbox와 알림 항목을 저장한 뒤 ack합니다. 금융 거래를 발송과 묶어 롤백하지 않습니다.
- Payment는 DEBIT/RESTORE와 같은 트랜잭션에서 알림 요청 Outbox에 원거래 ID·결제 회차·금액·처리 직후 잔액/지갑 버전 사본을 저장합니다. 마일리지 미사용이면 결제/외부 환불 확정 트랜잭션에서 잔액·지갑 버전을 함께 null로 저장합니다. `REFUND_COMPLETED`는 복원 때 발송을 준비하는 종류 이름이며 실제 안내는 아래 주문 복구 확인까지 대기합니다. 주문/회차가 아직 연결되지 않았으면 Inbox의 원본 payload·다음 실행 시각을 보존해 기다립니다. 결제 알림은 해당 회차의 확정 반영, 환불 알림은 해당 환불의 주문 복구를 확인한 뒤 생성합니다. 뒤에 반품·구매확정이 진행됐다는 이유만으로 앞선 확정 사실을 누락하지 않습니다.
- 같은 `sourceService + kind + businessRef + recipientKind + recipientId`는 한 알림 항목입니다. 판매 묶음은 **접수 시각**의 KST 1분 구간으로 모으고 종료 때 건수·합계·본문을 고정합니다. 늦은 이벤트는 새 열린 구간에 넣고 닫힌 묶음을 수정하지 않습니다. 다른 종류는 항목 하나당 발송 하나입니다. 판매 합계는 순매출·정산액이 아니며 환불은 따로 안내합니다.
- 발송 작업은 1초마다 도래 건을 임대합니다. 임대 30초·호출 제한 5초가 기본값이며 leaseToken·버전으로 결과 반영 주체를 검사합니다. 응답 유실·임대 만료는 `UNKNOWN`으로 두고 원래 deliveryId로 모의 수신 기록을 조회합니다. 기록이 없을 때만 같은 키·본문으로 재요청합니다. 수신부의 `UNIQUE(delivery_id)`와 본문 해시로 중복·같은 키 다른 본문을 차단합니다.
- 일시적 오류는 1초부터 최대 60초 간격으로 지수 재시도하고 조회·발송을 합쳐 한 라운드 최대 10회입니다. 확정 거절·본문 충돌·상한 초과는 `REVIEW_REQUIRED`로 보존합니다. 운영 재처리는 원키·수신자·본문을 유지해 새 라운드만 열고 실행자·사유를 남깁니다. `SENT`와 유효 임대 중인 작업의 재처리는 409입니다.
- `MOCK_KAKAO`의 `SENT`는 모의 수신 기록 확인이며 실제 카카오 전달·읽음을 뜻하지 않습니다. 실패해도 주문·환불·마일리지·지급 상태를 바꾸지 않습니다. 발송 순서 역전을 허용하되 거래 발생 시각을 표시합니다. 주소·전화번호·토큰을 이벤트·Slack에 싣지 않습니다.

### 본인 카카오톡 시연

[본인 카카오톡 시연](development.md#본인-카카오톡-시연)의 `KAKAO_SELF`는 실제 알림톡과 별개인 본인 수신 시연 채널입니다. 명시적으로 켠 설정과 시험 구매자·판매자 UUID 목록이 일치할 때만 본인 카카오 계정의 나와의 채팅으로 실제 HTTP 전송합니다. 그 외 계정은 `MOCK_KAKAO`를 유지합니다. 채널·앱 ID와 본인 사용자 ID 조합의 SHA-256 참조·내부 수신자 종류·ID·본문은 발송 준비 때 고정하며, 설정 변경으로 기존 발송을 다른 채널·계정에 돌리지 않습니다. 구매자·판매자 표시와 실제 거래의 주문·상품·금액·상태를 포함하되 판매자에게 구매자의 지갑 잔액을 보내지 않습니다. 판매 알림의 1분 집계는 같은 물리 계정·판매자별로 유지합니다. self-send는 `transaction-self-v2` 본문을 저장하며 상품 표시명만 제어문자 제거 후 최대 24 UTF-16 단위로 줄입니다. 본문에는 내부 주문·환불·지급·배치 UUID를 표시하지 않고, 상품·쉼표로 구분한 원 단위 금액·처리 결과·발생 시각과 역할을 200자 이내로 안내합니다. 판매 묶음은 결제 완료 주문 건수·금액 합계와 첫 주문 상품을 구분해 표시하며, 접수 구간을 거래 발생 구간으로 표현하지 않습니다. 실제 주문 연결과 권한·멱등 판정은 내부 항목의 원업무 ID로 유지하고 전송 때 다시 렌더하지 않습니다. 기존에 고정한 본문은 재처리해도 바꾸지 않습니다.

공식 텍스트 템플릿은 200자 이내로 구성합니다. 의미 있는 거래 값이 빠지도록 본문 전체를 잘라 보내거나 여러 HTTP 발송으로 쪼개지 않습니다. 한 건을 표현할 수 없는 본문은 전송 전에 거절해 수동 확인 대상으로 둡니다. 메시지 링크는 앱에 등록한 제품 도메인만 지정하며 사용자 토큰이나 개인정보를 URL에 넣지 않습니다.

`KAKAO_SELF`에는 deliveryId 멱등·원수신 조회가 없습니다. `SENT`는 카카오 API의 `result_code=0` 응답 확인이며 읽음·단말 팝업 확인이 아닙니다. 응답 유실·시간 초과·5xx·해석 불가 응답과 실제 발송 임대 만료는 UNKNOWN 시도와 `REVIEW_REQUIRED`로 보존하고 자동 조회·재발송하지 않습니다. 재인증이 필요한 거절·확정 거절도 수동 확인 대상으로 둡니다. 401 응답은 다음 시도에서 access token을 갱신하고, 429와 문서상 일시 거절 코드(-1·-7·-10)는 기존 유한 재시도 경계로 재개합니다. HTTP 400의 내부 처리 타임아웃(-603)은 미확정으로, 동의 부족(-402)은 재인증 대상으로 구분합니다. 원거래 결과는 이 실패로 되돌리지 않습니다.

운영자는 본인 채팅·발송 이력과 마지막 오류를 대조한 뒤 원키·원수신자·고정 본문·버전을 유지한 재처리 여부를 결정합니다. 실제 수신 조회가 없으므로 미확정 건의 재발송에는 중복 가능성이 남습니다. 이 위험과 재처리 사유를 기록하고 실제 채널 재처리는 원발송을 PENDING으로 열어 다시 전송합니다. 수신을 확인할 수 없다는 이유로 원거래나 고객에게 금융 실패를 확정하지 않습니다. 토큰 갱신·재인증·실행 절차와 실제 검증 상태는 [개발 환경](development.md#본인-카카오톡-시연)을 따릅니다.

실제 알림톡 전환은 비즈니스 채널·공식 딜러 연동, 사용 가능한 공용/승인 템플릿, 수신처 검증과 개인정보 처리를 갖춘 별도 구현입니다. [카카오 공식 안내](https://kakaobusiness.gitbook.io/main/ad/infotalk)를 따릅니다.

## 신규 접수 제한과 재개

제한 대상은 새 금융 부하를 만드는 `POST /api/orders`와 확정 거절 뒤 새 결제 회차를 만드는 `POST /api/orders/{orderId}/payment-retries`입니다. 동일 멱등키·본문의 이미 접수된 요청은 기존 결과로 연결하고, 다른 본문은 기존 `409`를 유지합니다. 취소·환불·기존 지급·원업무 재처리·상태 조회에는 이 신규 접수 gate를 적용하지 않습니다. 각 작업의 권한·상태·저장소 가용성 검사는 계속 필요합니다.

| 관측 항목 | 신규 접수 중단 | 재개 기준 |
| --- | --- | --- |
| 필수 그룹 `commerce.v1`·`payment.v1`·`settlement.v1`의 Kafka lag | 그룹별 구독 파티션 lag 합계가 하나라도 100,000건 이상 | 각 그룹 50,000건 미만 |
| 소유 서비스별 미완료 Outbox·금융 Inbox·금융 Job | 논리 대기열별 100,000건 이상 또는 실행이 도래한 미처리 건의 최장 지연 60초 이상 | 모든 대상 대기열 50,000건 미만·도래 지연 30초 미만 |
| Kafka·PostgreSQL 데이터 저장소 | 파일시스템 사용률 하나라도 80% 이상 | 모든 대상 70% 미만 |
| 필수 관측·운영 중단 | 필수 관측 누락·수집 실패·관측 시각이 45초보다 오래됨 또는 운영자가 접수 중단 | 모든 관측 유효·최신, 운영 중단 해제 |

하나라도 중단 조건이면 새 접수를 닫고, **모든 재개 조건이 연속 60초** 유지된 뒤 다시 엽니다. 기동 때는 닫힌 상태로 같은 검사를 시작합니다. 알림 전용 그룹·Job의 적체는 금융 gate의 건수·지연 조건에서 제외하고 별도 경보로 다룹니다. 공유 디스크 압박은 전체 저장 능력에 영향을 주므로 제외하지 않습니다.

건수는 아직 종결되지 않은 로컬 행을 각각 세며 같은 업무가 서로 다른 단계에 있다는 이유로 합산한 총량과 비교하지 않습니다. 미발행 Outbox와 RECEIVED/WAITING/REVIEW_REQUIRED Inbox, 실행·재시도·수동 확인이 남은 금융 Job을 포함합니다. 예약된 미래 지급·재시도의 도래 전 시간은 지연으로 세지 않고, REVIEW_REQUIRED는 자동 실행 지연에서 제외하되 미완료 건수와 별도 알람에는 포함합니다. 이로써 정상적인 다음 실행 시각 대기나 5분 조회 주기를 적체로 오인하지 않습니다.

Commerce의 각 인스턴스가 기존 내부 Prometheus에서 필요한 관측을 15초마다 묶어서 읽어 접수 상태를 판정합니다. 요청마다 원격 지표·다른 서비스 DB를 조회하지 않습니다. 각 소유 앱은 자기 DB의 논리 대기열·수집 시각을 내보내며 같은 대기열을 여러 인스턴스가 관측해도 중복 합산하지 않습니다. Kafka lag와 실제 데이터 파일시스템 사용률도 담당 수집기의 원본 관측 시각을 확인합니다. 누락된 지표를 0으로 대체하거나 Prometheus 조회 성공만으로 오래된 표본을 최신으로 취급하지 않습니다. 최초 그룹 offset·소유 스키마·필수 수집기가 준비되지 않으면 접수는 계속 닫힙니다. [활성화·복구 절차](development.md#금융-관측과-접수-복구)를 따릅니다.

관측 연동은 다음 metric 이름과 label을 사용합니다. 값 metric과 원본 시각 metric의 수집기 label(`job`·`instance` 등)은 같아야 합니다. `signal`은 아래 표의 대문자 값이며 `resource`는 값 metric의 `queue`·`group`·`store` 값과 같습니다. 각 수집기는 값과 원본 시각을 같은 관측 묶음에서 캡처해 한 scrape에 내보냅니다. 원본 시각은 epoch 초이며 0은 미수집/실패입니다. Prometheus가 제공하는 표본 timestamp를 원본 수집 시각으로 대신하지 않습니다.

| 신호 | 값 metric · 필수 resource |
| --- | --- |
| `QUEUE_SIZE` | `commerce_settle_financial_queue_records{queue="…"}` |
| `DUE_AGE` | `commerce_settle_financial_queue_due_delay_seconds{queue="…"}` |
| `LAG` | `commerce_settle_kafka_group_lag_records{group="commerce.v1\|payment.v1\|settlement.v1"}` |
| `STORAGE` | `commerce_settle_data_filesystem_usage_ratio{store="kafka\|postgres"}` |
| 원본 시각 | `commerce_settle_admission_observed_timestamp_seconds{signal="…",resource="…"}` |

표의 `\|`는 필수 값의 나열이며 실제 label 값에 포함하지 않습니다. 필수 대기열은 `commerce.outbox`, `commerce.inbox`, `payment.outbox`, `payment.inbox`, `payment.payment_jobs`, `settlement.outbox`, `settlement.inbox`, `settlement.payout_jobs`입니다. 새 금융 논리 대기열을 추가하면 필수 대상과 소유 수집기를 함께 갱신합니다. lag 수집기는 그룹의 모든 구독 파티션을 합산하고 일부 관측 실패도 전체 실패로 처리합니다. 저장소 수집기는 서비스 이름의 디스크 대신 각 종류의 실제 데이터 파일시스템을 모두 확인해 최대 사용률과 가장 오래된 원본 시각을 내보냅니다. 같은 resource의 복제 관측은 가장 최신 원본 시각을 선택하며 동시각이면 최대값을 사용합니다. 알림 전용 대기열은 포함하지 않습니다.

거절은 `503 COMMON_CAPACITY_EXCEEDED`, `Retry-After: 30`으로 응답합니다. 일시적 서비스 용량 부족을 계정별 `429`와 구분합니다. gate 확인은 기존 멱등 결과/본문 충돌 판정 뒤, 새 주문·결제 회차와 재고·쿠폰·마일리지 예약·Outbox 저장 전에 하며, 거절을 완료된 멱등 결과로 캐시하지 않습니다. 클라이언트는 같은 키·본문으로 재시도합니다. 이미 접수한 작업의 상태·예약·원키는 바꾸지 않고 Consumer·Worker·Outbox 배출을 계속합니다. 저장소 오류로 트랜잭션을 완료할 수 없다면 접수 성공을 반환하지 않습니다.

이는 표본 간격·진행 중 요청만큼 초과할 수 있는 조기 제한이며 정확한 최대 행 수나 저장 공간 확보의 보장은 아닙니다. 관측 시스템 장애에도 신규 접수가 닫히는 가용성 비용을 감수합니다. 디스크 80% 이전 경보와 남은 20%를 기존 작업의 배출·복구에 사용하며, 새 접수를 닫아도 공간이 부족하면 저장소 확보와 장애 복구가 필요합니다. 기록 삭제·보존 기간 단축·이미 접수한 금융 작업 폐기로 공간을 만들지 않습니다.

## 운영 알람

조치가 필요한 장애는 `Prometheus → Alertmanager`로 전달하고 Grafana에서 원인을 확인합니다. 기본은 화면 확인이며 Slack은 [비밀 파일 overlay](development.md#dlt-관측과-조치)를 명시적으로 적용합니다.

| 조건 | 초기 기준 | 등급·조치 |
| --- | --- | --- |
| 금융 미확정 | 결제·환불·지급 `UNKNOWN` 최장 나이 5분/15분 초과 | WARNING/CRITICAL. 원거래 조회·대조; 새 금융 거래 금지 |
| 환불 지연 | 미완료 환불 최장 나이 10분/30분 초과 | WARNING/CRITICAL. 외부 환불·복원·원장·주문 단계 확인 |
| 지급 지연 | 확정 배치가 회차 마감 후 30분/60분 동안 미지급 | WARNING/CRITICAL. 정상적인 다음 회차 이월 제외 |
| 수동 확인 | 새 `REVIEW_REQUIRED`, 신규 격리·DLT | CRITICAL. 원업무·재처리 사유 확인 |
| 작업 적체 | 미발행 Outbox·미처리 Inbox·실행 작업 최장 나이 5분/15분 초과 | WARNING/CRITICAL. Kafka lag·소비율·작업자 확인 |
| 알림 지연 | 준비된 발송 최장 대기 5분/15분 초과, 새 발송 수동 확인·재시도 소진·카카오 재인증 필요 | WARNING/CRITICAL. 채널별 수신 확인·재인증·재처리 |
| 서비스 장애 | 수집 대상 `up=0` 1분, OOM/컨테이너 비정상 종료 | CRITICAL. 기동·메모리·의존 서비스 확인 |
| HTTP 장애 | 5분간 요청 100건 이상에서 5xx 비율 5% 초과가 5분 지속 | WARNING. 서비스·경로 템플릿별 오류·trace 확인 |
| 자원 부족 | 메모리 제한 90% 초과 5분, 디스크 가용 10% 미만 5분, CPU 할당량 90% 초과 10분 | WARNING. 부하 중단·자원 조정 판단; 여유 메모리 5% 미만/OOM은 CRITICAL |

Payment 격리는 소유 DB에서 상태별 건수·도래 후 최장 나이를 계산해 `/actuator/prometheus`로 노출합니다. 최근 5분 신규 원문과 소진 작업을 경보하며 발행 완료를 금융 업무 성공으로 간주하지 않습니다. 금융 작업의 수동 확인은 논리 대기열별로 세고, 결제 미확정은 현재 UNKNOWN 전이 시각, 지급 미확정은 반복 조회에도 유지하는 `unknown_since`, 미완료 환불은 `accepted_at`, 확정 배치 미지급은 `cutoff_at`부터 나이를 셉니다. 다음 회차에 아직 확정하지 않은 항목은 미지급 배치에 포함하지 않습니다. 금융 경보는 가장 최신 원본 시각의 복제 관측만 사용하고 동시각이면 최대값을 선택합니다. 데이터 파일시스템 70% 이상이 5분 지속되면 WARNING, 80% 이상이면 CRITICAL이며 금융 lag 50,000건 이상은 WARNING입니다. 계정/주문 ID를 메트릭 label로 사용하지 않습니다. 무작업이면 나이·건수는 0이며 정상 대기·완료 건을 적체에서 제외합니다. Kafka lag는 메시지 수, 대기 나이는 초 단위입니다.

Alertmanager는 환경·서비스·알람 이름으로 묶고 최초 30초 대기·그룹 갱신 5분·반복 1시간을 기본으로 합니다. 같은 장애의 CRITICAL이 WARNING을 억제하고 복구도 안내합니다. Slack에는 등급·발생/지속 시각·영향·대시보드/조치 문서 링크를 보내고 개인정보·알림 본문·비밀값은 보내지 않습니다. 부하 시험 채널은 운영 채널과 분리합니다. [Alertmanager의 묶음·중복 억제](https://prometheus.io/docs/alerting/latest/alertmanager/)를 사용합니다.

서버·컨테이너 자원은 별도 수집이 필요합니다. Linux 배포 호스트는 node_exporter, 컨테이너는 cAdvisor를 후보로 둡니다. Docker Desktop의 Linux VM·컨테이너 지표로 Mac 전체 상태를 판단하지 않습니다. 같은 호스트의 모니터링도 전체 호스트 중단 때 멈출 수 있으므로 운영 배포 때 외부 생존 확인을 검토합니다.

## 보존과 삭제

Outbox·Inbox·금융 Job·격리 기록은 완료 여부와 관계없이 DB에 보존하며 자동 삭제하지 않습니다. 금융·주문 멱등 기록은 `expires_at=null`이고, 일반 관리·가입의 24시간 만료와 구분합니다. Kafka·DLT의 보존 기간을 이 DB 이력의 TTL로 사용하지 않습니다. 보존 기간 변경·정리기 도입에는 미완료·격리·재전달·원업무 유일성·복구 검증이 필요합니다.

계정 종류별 정규화 이메일은 논리삭제 뒤에도 유일성을 보존하며 자동 재가입·기존 계정 연결은 하지 않습니다. 주소록·상품은 논리삭제합니다. 주문 주소 사본은 거래 종료 뒤 90일을 기본 마스킹 시점으로 정하되 진행 중인 반품·분쟁·보존 보류가 있으면 보류합니다. 처리/보류 이력을 남기고 주소를 금융 이벤트로 보내지 않습니다. 금융 금액·정산·마일리지 원장·쿠폰 사용 이력과 주요 행위의 audit_logs는 자동 삭제하지 않습니다. 알림 본문·항목·시도·모의 수신 기록은 거래 종료 후 90일을 기본 보존 기간으로 하며 보존 보류 중에는 삭제하지 않습니다. delivery가 살아 있는 동안 모의 수신 멱등 기록을 먼저 지우지 않고 재처리 기한도 같은 보존 기간으로 제한합니다. 이는 시험 데이터 정책이며 상용 보존 기간의 적법성을 검증했다는 뜻은 아닙니다.

커머스의 보존 작업이 기한이 지난 종결 거래를 제한된 묶음으로 조회해 주문 주소를 마스킹하고 알림 기록을 정리합니다. 각 변경 직전에 거래 종결·진행 중 반품/분쟁·보존 보류를 다시 검사합니다. 미완료 발송이나 재처리 가능한 delivery의 모의 수신 멱등 기록은 유지하고, 제거할 발송과 연결된 항목·시도·수신 기록은 같은 DB 트랜잭션으로 정리합니다. 마스킹·보류·정리 결과를 남겨 중단 후 재조회·재실행할 수 있게 하며 금융·쿠폰 사용·행위 감사 이력으로 삭제 범위를 넓히지 않습니다. 실행 위치·주기는 [정기 작업](architecture.md#정기-작업과-비동기-실행)을 따릅니다.

종결 기준은 `CANCELLED`·`REFUNDED`·`PURCHASE_CONFIRMED` 전이 때 고정한 `closed_at`입니다. 정확히 90×24시간이 지난 시각부터 대상이며 일반 수정 시각으로 기한을 연장하지 않습니다. 주소의 기존 암호문 세 값은 모두 복호화 불가능한 1바이트 마커로 대체하고 `masked_at`을 남깁니다. 나중에 보류를 설정해도 이미 마스킹한 주소나 삭제한 본문은 복원하지 않습니다.

판매 알림 묶음은 모든 항목의 연결 주문이 종결·기한·보류 검사를 통과해야 함께 제거합니다. 정산·지급 알림은 연결 배치가 실제 `COMPLETED`로 전이한 Settlement 소유 `closed_at`부터 같은 90일 정책을 적용합니다. 지급 성공에도 항목 대조가 끝나지 않으면 배치가 미종결이므로 보존합니다. 이 종결은 되돌리지 않으며 Commerce는 인증된 내부 조회로 확인한 종결 사실만 캐시합니다. 조회 불가·부재·판매자 불일치는 보존합니다. 배치별 알림 보존 보류는 Commerce 소유이며 삭제와 같은 배치 행 잠금으로 설정·해제합니다. 이는 지급의 금융 보류를 변경하지 않습니다. `SENT`·`REVIEW_REQUIRED`이고 임대·실행 중 시도가 없는 발송만 제거하며, 미완료 발송과 수신 멱등 기록은 함께 유지합니다. 삭제한 본문 대신 최소 업무 키와 payload 해시를 보존해 늦은 동일 요청은 무변경, 다른 본문은 충돌로 처리합니다. 운영 재처리도 연결 거래의 보존 기한을 넘긴 경우 거절합니다.

## 경계 검증

금액·기한·동시성·중단 복구의 입력과 기대 결과는 [업무 검증 시나리오](design.md#9-실패공격범위-이탈에-대한-검증)에 모읍니다. 실제 DB·대역 검증과 문서 산술 검사를 구분합니다.

실제 서비스에서는 종류별 발급·유효 사용·취소·총지원액, 신규 고객의 30/90일 재구매와 추가 주문 잔여액, PG/환불 실제 비용, 판매자 최종 마진·입점 이탈을 관측합니다. 고객당 누적 주문 잔여액에서 유입 광고비를 뺀 값과 전체 고객군 합계로 비교하며, 재구매한 고객만 골라 회수됐다고 판단하지 않습니다. 혜택 금액 변경은 이 관측에 근거하고 초기 쿠폰 이용 증가를 전체 사업 이익으로 승격하지 않습니다.
